Releasing html-spec

What this project's release procedure is for, and the hazards its history taught. The first two were learned twice, at 0.10.0 and again at 0.12.0, because the only record of the first was an archived tasks document that binds nothing and is read by nobody. They are requirements here so that the sixth release is not positioned to rediscover what the fourth and fifth both wrote down. The second turned over when this repository became its own project at 0.29.0: what a run once had to remove is now the project, and a run must leave it in place. A third arrived with 0.33.0, when the crates began pinning one another to the workspace's version: the version moves only with its pins.

What this runbook is for

Shipping a version of html-spec is four steps, and this project has run them five times. Each of those five runs retyped the steps into a new tasks.md, under a section number that was different every time — 6, 8, 6, 9, 7 — because nothing was shared.

The procedure has been got wrong, and the same lesson was learned twice. That is what makes this a runbook rather than a note. A procedure whose steps are exact belongs in a script, and this project keeps those in scripts/; what a script cannot hold is the step whose content is judgment, and the release contains one that this project has already decided is judgment. archive.md says so: deciding whether the change earned a patch, a minor, or a major increment is judgment, so it is the contributor's, and whether one version follows another is exact, so it is the program's.

The requirements below are what this runbook requires of a run. They are not obligations of the project — the project's contract is what its accepted specifications state, and a runbook is a procedure the project keeps.

Requirements

The version is advanced before the instruction files are regenerated req-version-before-regenerate

A run of this procedure MUST advance the workspace version before it regenerates the installed instruction files, and MUST NOT treat the regeneration as conditional on whether any workflow body changed.

Each installed file carries generatedBy: htmlspec <version> in its frontmatter, written from CARGO_PKG_VERSION at run time. Advancing the version therefore makes every installed file disagree with the binary, whatever the change did to the workflow prose. Regenerating first means regenerating twice.

This check is coupled to the version rather than only to workflow prose, so every release regenerates. A change that bumps the version and touches no workflow still has this step to do.

A release that changed no workflow body

Given
A change that edits no file under the instructions source directory.
When
The run advances the version and then checks the installed files.
Then
Every installed file is stale, and regeneration rewrites exactly one line in each — the version stamp — and nothing else.

A run that regenerates before advancing the version

When
A run regenerates the installed files and then advances the version.
Then
The installed stage of the suite turns red, and the run has to regenerate a second time — which is the outcome this ordering exists to prevent.

The stamp edited rather than regenerated

When
A run updates the version stamp by editing the installed files.
Then
The result is a file claiming a run that never happened, which is the specific defect the installed-files check was written to make impossible to repeat quietly.

The version moves only through the script that moves its pins req-the-version-moves-with-its-pins

A run of this procedure MUST advance the workspace version only by running scripts/set-version with the new version, and MUST NOT edit version under [workspace.package], or any htmlspec-* entry in [workspace.dependencies], by hand.

Since 0.33.0 the six crates release together, so each internal dependency names the workspace's exact version, version = "=X.Y.Z", beside its path. Cargo cannot read the workspace version into those entries, so they are strings, and a version raised without them leaves every one naming the old version. The offline relock then fails, and so does every stage of the suite that builds, before the release check could name the stale pin. The script writes the version and every pin in one edit, relocks offline, and puts the manifest back when the relock fails.

The version raised by hand, its pins left behind

Given
The workspace at 0.32.0, with each internal dependency pinned at =0.32.0.
When
A run raises version under [workspace.package] to 0.32.1 by hand and runs cargo update --workspace --offline.
Then
cargo exits 101 with "failed to select a version for the requirement htmlspec-parse = "=0.32.0"". scripts/set-version 0.32.1 on the same tree writes the five pins and relocks, changing only the workspace's own entries in Cargo.lock.

A pin that names another version

Given
A workspace declaring 0.32.0 in which one internal dependency is pinned at =0.31.0.
When
A run reaches the release check.
Then
scripts/check-release fails, naming the entry, the version it pins, the version the workspace declares, and scripts/set-version as the repair.

Regenerating inside this repository leaves its project in place req-regenerating-leaves-the-project-in-place

A run of this procedure MUST regenerate the instruction files from the repository root, MUST NOT remove htmlspec/ or spec.nix, and MUST stop rather than continue when the regeneration changed anything other than the installed instruction files and the assets it reports establishing in the project's store.

This repository is an html-spec project. htmlspec/ holds its accepted specifications, its archive, its asset store, this runbook, and any change under way, and spec.nix declares its version. The command that regenerates the instruction files is the command that establishes a project, and where it finds one it extends it: run from the root, it reports extending the project in the root and spec.nix already exists, so it was left as it is, and writes nothing but the installed files.

Where it finds no project it makes one, and it looks only where it is run. From any other directory, or with htmlspec/ missing, it reports created the project structure and declared the project at version 0.0.0, and writes a second project and a second set of instruction files there. That report, or a path that git status lists after the regeneration and did not list before it, outside the root's .claude/, .codex/, and .pi/ and the assets init reports establishing, is the signal to stop. The listing before is the baseline because the working tree is not clean when the regeneration runs: the version the step before it advanced is not committed yet, and the change being released may not be either. The run removes nothing, then or later. What a misdirected regeneration writes is untracked, so git status lists every path of it, and none of them is the project. By name, though, they are the project's names, and telling the two apart is a person's work rather than a step's.

Before 0.29.0 the obligation was the opposite. The repository kept its specifications in OpenSpec's markdown and was not a project, so what the bootstrap wrote was stray and a run had to remove it, and this runbook's 0.1.0 required that. Followed now, that removal deletes the project, and the asset-topology stage, which 0.1.0 named as the check that catches a mistake here, passes after it.

The removal 0.1.0 required, followed

Given
The repository with its project in htmlspec/ and its declaration in spec.nix.
When
A run regenerates the instruction files and then removes both.
Then
The project's accepted specifications, its archive, its asset store, this runbook, and the change being released are gone. The release stage and the runbook stages of the suite exit 2, the asset-topology stage passes, and a change under way that no commit holds cannot be recovered.

Regenerating in the project

Given
A working tree in which the advanced version in Cargo.toml and Cargo.lock, and the change being released, are not yet committed.
When
A run regenerates the instruction files from the repository root.
Then
The bootstrap reports that it is extending the project there and left spec.nix as it is, and the only paths git status lists that it did not list before are the installed files under .claude/, .codex/, and .pi/. The uncommitted version and change are listed before and after, so they do not stop the run.

Regenerating from another directory

Given
A run whose working directory is beneath the repository root rather than the root.
When
It regenerates the instruction files.
Then
The bootstrap does not find the repository's project, reports that it created the project structure and declared a project at version 0.0.0, and writes them with a set of instruction files where it ran. The run stops, and removes nothing.

The size of the increment is the contributor's decision req-the-increment-is-judgment

A run of this procedure MUST NOT derive the version increment from anything the program can compute, and the run MUST state the reasoning for the increment it chose.

This is a reservation the project already took and wrote down, and it is why the release cannot be a script end to end. The release-hygiene check's own docstring explains why the automated version is impossible rather than merely unbuilt: a change under way legitimately has not advanced the version, because the patch-versus-minor decision is best made once the work's shape is known, so a stage asking about it would be red from a change's first commit to its last — and a suite that is always red is one a contributor learns to skip.

What remains automatable is checked automatically. Whether one version is ordered after another is exact, so archival compares them and refuses on the comparison alone.

An increment chosen and reasoned

When
A run advances the version.
Then
It states whether the change earned a patch, a minor, or a major increment and why, so a reader can disagree with the reasoning rather than only with the number.

The changelog heading names the version req-the-changelog-heading-names-the-version

A run of this procedure MUST write a changelog entry whose heading contains the version as a dotted numeric string.

The release-hygiene check finds an entry by reading headings for that pattern and reads nothing else. An entry whose version appears only in its prose is an entry the check cannot see, so the release fails on a changelog that a person would say is present.

A version named only in the entry's body

Given
A changelog entry whose heading is a title and whose body names the version.
When
The release-hygiene check runs.
Then
It reports that no heading names the version, because it reads headings and not prose.

The change's recorded version is written at archival req-the-recorded-version-waits-for-archival

A run of this procedure MUST NOT write the VERSION file beside the change's documents itself, MUST raise the version spec.nix declares, at archival, to the version it set in Cargo.toml, and MUST leave the release check's question about the archived version open until archival has run.

The file lives in the archived change's directory, which does not exist until archival creates it. htmlspec archive creates the directory and writes the file, recording the version spec.nix declares, after refusing any version not ordered after the last one archived. So a run does not write the file at all. Under the OpenSpec workflow a run did, by hand, at archival, and every archived change that ran this procedure then recorded the same thing: this was the last task open, and it was the last one open because it could not be done earlier rather than because it was forgotten.

What a run owes is the value. The version is declared twice: Cargo.toml's is what the binary reports and what the release-hygiene check reads as declared, and spec.nix's is what archival compares and records. Nothing compares the two. The archive workflow raises spec.nix at archival, and this runbook requires it raised to the version the first step set, as each release since this repository became its own project raised it.

The half that can be done during implementation is the declared version's changelog entry, which the release-hygiene check asks about separately.

The recorded version attempted early

When
A run tries to write the recorded version before archival.
Then
There is no archived directory to write it into, so the step stays open and the run says so rather than reporting it done.

The declaration raised to a version the workspace does not declare

Given
A run that advanced Cargo.toml to one version and, at archival, raised spec.nix to another.
When
Archival runs, and then the release-hygiene check.
Then
The archive records the version spec.nix declared, which no binary of the release reports, and the check fails unless a changelog heading names that version as well as the declared one.

The toolchain the flake pins is the one the run uses req-the-pinned-toolchain-is-what-runs

A run MUST start with cargo, rustc, and python3 resolving to the development shell flake.nix pins, and MUST NOT start from a toolchain or an interpreter installed beside it.

preflight/v1 {"kind":"toolchain","manifest":"flake.nix","shell":"default","tools":["cargo","rustc","python3"]}

The declaration names the manifest rather than a version, and that is the point of it: rust-toolchain.toml already pins the compiler, and a version restated here would be a second pin that drifts from the first. What the check establishes is provenance — that the executables this run invokes are the ones the pin selects.

This is stricter than the procedure strictly needs, and the cost is named rather than discovered at step three. A contributor whose cargo comes from rustup reading the same rust-toolchain.toml has a working toolchain and will be refused, because nothing observable from outside distinguishes it from an unpinned one. The remedy the refusal names is to enter the shell; the alternative was a check that accepts any cargo and therefore establishes nothing about the pin. The ~/.cargo/bin/cargo broken symlink this procedure has met is the case that makes the distinction worth paying for: it resolves, and it does not run.

python3 is declared beside the compiler because the shell supplies it and a step cannot run without it. On macOS the python3 outside the shell is /usr/bin/python3, a stub that runs the interpreter the developer tools at DEVELOPER_DIR hold, and the shell points DEVELOPER_DIR at the Nix SDK, which holds none. The stub resolves and then exits with "error: tool 'python3' not found". This runbook's 0.2.0 changelog records the release check failing that way, and the publish runbook's first run met it at its second step. The toolchain form states no version, so declaring python3 in it pins nothing the flake does not already pin.

git is deliberately not declared. A tool check states an exact version, and this procedure needs any git that stages a file, and the shell does not supply one, so the toolchain form would refuse every run. It stays an obligation of the run, stated in the procedure's own prose and recorded by whoever runs it.

An interpreter that resolves outside the shell

Given
A macOS machine whose search path resolves python3 to /usr/bin/python3, the developer-tools stub, because the run was started outside nix develop.
When
The prerequisites are checked before the run starts.
Then
The check reports that python3 resolves to /usr/bin/python3, which is not inside the declared environment, and the run does not start.

A toolchain installed beside the pinned one

Given
A machine whose search path resolves cargo to an installation of its own.
When
The run's prerequisites are checked before it starts.
Then
The check reports where cargo resolved and that it is not the pinned environment's, and the run does not start — which is the difference between learning this now and learning it from a build that used the wrong compiler.

An environment this machine has never entered

Given
A checkout whose pinned inputs are not in the local store.
When
The prerequisites are checked.
Then
The check reports readiness as unavailable rather than fetching or building anything, because an inspection that provisioned its way to an answer would have changed the machine it was asked about.

Decisions

The step order corrects the archive rather than transcribing it decision-order-corrects-the-archive

This runbook states the version bump first, although all five archived release sections state regeneration first.

The five sections agree with each other and disagree with what three of them then measured. The 0.10.0 run recorded that the version bump restaled every installed file and turned the check red; the 0.12.0 run predicted a no-op, found the same thing, and wrote down the general form. Transcribing the stated order would ship a procedure whose own history contradicts it, and the alternative — stating the order and adding a note that it is wrong — is what the archive already has.

The hazards are requirements rather than notes beside the steps decision-hazards-are-requirements

Each hazard is a requirement in this document with scenarios, rather than a sentence in the corresponding task's note.

A hazard written beside a step is exactly what the archive already held, five times, and what nothing read. A requirement is addressable, carries scenarios that state the failure concretely, and is what a run's record can attest to once run records exist. The cost is that the procedure and the reasons for its shape are two documents, which the split between a specification and a tasks document forces anyway.

Risks

A step changes and this runbook does not risk-this-runbook-goes-stale

Nothing compares this runbook against the scripts and commands it names. A stage renamed in the check suite, or a flag the bootstrap command stops accepting, leaves this document confidently wrong.

Partly held down and honestly not fully. The steps name commands rather than restating what those commands do, so a renamed stage produces a command that fails loudly at the moment it is run rather than a silently wrong instruction. What is not held down is a step that becomes unnecessary: nothing would report that. The check this project already runs over its installed instruction files is the shape that would close it, and building it is not this runbook's work. It happened, and worse than this predicted. When this repository became its own project at 0.29.0, the step that removed a stray project became a step that removes the project, and nothing reported it. The change that moved this runbook into the project found it by reading, and 0.2.0 is the correction.

The inputs are prose that nothing checks risk-the-inputs-are-prose

This procedure requires a toolchain, an interpreter, a clean working tree, and a repository whose project is in place. The first two are checked before a run starts. The other two are prose in the tasks document, so a run on a machine missing one discovers it partway through — at the step that needs it, with the version already advanced.

Partly held down. The toolchain and the interpreter are a machine requirement, req-the-pinned-toolchain-is-what-runs, which preflight checks and which gates starting a run. The pinned development shell supplies both, and preflight refuses a python3 from outside it, because on macOS the system's cannot run inside that shell. A runbook has no notion of an input, which is an open finding of the change that established runbooks, so the other two stay prose.

Evidence

The same lesson recorded at two releases evidence-the-lesson-learned-twice

At 0.10.0 the release record states that the version bump restales every installed file, and that the stage which reports it found, on its first release, the class of drift it was written for. Three weeks later, at 0.12.0, the release task predicted regeneration would be a no-op and recorded that it was not — advancing the version in 7.2 made all 45 files stale — and then wrote down the general form: the check is coupled to the version, not only to workflow prose, so every release regenerates.

Two records of one fact, three weeks apart, in two archived documents that bind nothing. That is the measurement behind this runbook existing at all.

Nine duplicate assets, when this repository was not a project evidence-nine-duplicate-assets

Before 0.29.0, running the bootstrap command in this repository and then the asset-topology check reported exactly nine duplicated assets and exited non-zero. Eight were the assets the bootstrap copied into the stray store, each already present byte-identically in the repository's own. The ninth was the one an empty directory alone produced: the stray directory made the repository resolve as a project, and the check then compared across the conformance fixtures' deliberate stores.

Reproduced for this runbook's 0.1.0 rather than quoted from the archive, which is what distinguished the ninth error from the eight. The archived record gave the number and not the split. It is why 0.1.0 required the removal, and it no longer occurs: the repository resolves as a project, and the check compares only the stores inside it with one another.

The removal, measured against the project evidence-the-removal-measured-against-the-project

Measured at 0.30.1 in a scratch copy of the repository, beside an untouched copy. Run from the root, the bootstrap reported extending the project and spec.nix already exists, so it was left as it is, and a recursive diff against the untouched copy found nothing. Removing htmlspec/ and spec.nix then deleted 504 files: 13 accepted specifications, 38 archived changes, this runbook, the asset store, and the change under way. Afterwards the release-hygiene check and the runbook validation stage exited 2, and the asset-topology check exited 0.

Run from crates/, the bootstrap reported created the project structure and declared the project at version 0.0.0, and wrote crates/htmlspec/, crates/spec.nix, and three instruction directories beside them, leaving the root's project as it was. Run from the root with the project removed, it reported the same and established an empty project there.

Verification

The ordering hazard, checked at both points verify-the-ordering-hazard

Run the installed-files check before advancing the version and again after, with nothing else changed between the two runs. The first passes and the second fails, which establishes that the version alone is the trigger. The 0.12.0 release performed exactly this and recorded both outcomes; the diff after regeneration was one line in each of 45 files, and inspecting the whole diff found nothing but the version stamp.

The version raised alone, and then through the script verify-the-version-moves-with-its-pins

On the tree that pinned each internal dependency at =0.32.0, raise version under [workspace.package] to 0.32.1 by hand and run cargo update --workspace --offline with the pinned cargo 1.90: it exited 101 with "failed to select a version for the requirement htmlspec-parse = "=0.32.0"". Then run scripts/set-version 0.32.1 on the same tree: it wrote the five pins and relocked, changing only the seven workspace entries in Cargo.lock, and with the instruction files regenerated and a trial changelog heading all 13 stages of scripts/check passed. With one pin set to =0.31.0, scripts/check-release exited 1 naming the entry and the script. Recorded on 2026-10-19 by ship-through-four-channels, and the trial was reverted.

Nothing is left to remove, and removing is what destroys verify-the-project-is-left-in-place

In a scratch copy of the repository, run the bootstrap from the root and diff the copy against an untouched one: nothing differs, and the report says it extended the project. Remove the copy's htmlspec/ and spec.nix and run the release-hygiene check, the runbook validation stage, and the asset-topology check: the first two exit 2 and the third exits 0, so the asset stage cannot be what catches the removal. Run the bootstrap from a subdirectory: it reports a project created where it ran. The three readings establish that nothing is left to remove, that removing deletes the project and passes the stage 0.1.0 relied on, and that the report tells a misdirected run apart. At a release the version has advanced, and each of the three runs since 0.29.0 recorded one line changed in each of 45 installed files and nothing else. Rehearsed for 0.2.0's code review with the advanced version and the change being released left uncommitted, as a run leaves them: from the root, the same 9 paths outside the three directories were listed before the regeneration and after it, and the 45 paths it added were all installed files, so comparing with the listing from before passes where a check for any change outside them stops. From crates/, all 54 paths it added were outside the root's three directories. With a commit removing one asset from the store, it reported establishing 1 shared asset, and the one path it added outside the three directories was that asset under htmlspec/assets/.

Nothing in the suite derives the increment verify-the-increment-is-not-derived

Read the release-hygiene check and confirm which questions it asks. It asks four of the archive — that every archived change records a version, that every recorded version above the baseline is distinct, that every recorded version has a changelog entry, and that every runbook release the archive publishes is accounted for — plus three of the workspace: that the declared version has a changelog entry, that every internal dependency pins it, and that every published crate carries the root LICENSE. Given a tag, it also asks whether the tag names the declared version. None of them computes what the next version should be, and the file's own docstring states that a check which did would be red from a change's first commit to its last. So the reservation holds by the absence of a gate rather than by a gate enforcing it, which is what this verification records.

The archived directory does not exist before archival verify-the-recorded-version-cannot-be-early

Read the archived release sections of the five changes that ran this procedure and confirm what each recorded about this step. All five state it as the last task, and two state explicitly that it could only be done at archival — the 0.11.0 run says this is why it was the last one open, and the 0.12.0 run records it as left open deliberately, following its predecessor. Five independent runs reaching the same conclusion is the measurement; the mechanism is that archival is what creates the directory the file goes in. Since 0.29.0 archival is htmlspec archive. Rehearsed for this runbook's 0.2.0 in a scratch copy, it wrote the archived change's VERSION from the version spec.nix declared. With spec.nix raised to a version Cargo.toml did not declare, it recorded that version, and the release-hygiene check then failed for want of a changelog heading naming it.

Both of this runbook's documents are accepted verify-this-runbook-validates

Validate this document and the tasks document beside it with the project's own validator, under default and strict strictness, and check both against the canonical format. All four commands accept them, which is the claim that a runbook's documents need no validation of their own: they are ordinary documents of two existing kinds.

The declaration checks the shell this repository pins verify-the-pinned-toolchain

Ask the pinned environment what it supplies and ask the search path where each tool resolves, then compare. Inside the shell the flake declares, cargo and rustc both resolve inside the Rust input's store path, so the check passes; jq resolves to the -bin output of an input declared as -dev, which is why the comparison reads the inputs' closures rather than the inputs alone. Outside the shell, both resolve to an installation of their own and the check reports the differing provenance. Neither reading builds, downloads, or changes a lock: the evaluation is offline with import-from-derivation disabled, and the working tree is unchanged afterwards.
