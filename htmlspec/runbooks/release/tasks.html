Releasing html-spec

The four steps that ship a version of this project, in the order its known hazards force rather than in the order five archived change documents each wrote them. Read the specification beside this document first: it states why the version is advanced before the instruction files are regenerated, and every release that got the order wrong discovered the reason at run time, and why the version moves only through the script that moves its pins.

What this procedure consumes

This section is here because there is nowhere else to put it, and that is a recorded finding rather than a design. None of the following is a step somebody performs, so none of them is a task unit — but a runbook has no notion of an input, so they are prose.

  • cargo, at the version rust-toolchain.toml pins. Note that ~/.cargo/bin/cargo may be a broken symlink; the rustup toolchain's own bin directory works, and so does running inside nix develop.
  • python3, standard library only. scripts/set-version, scripts/check-release, and scripts/check-installed are all Python. nix develop supplies it, and the specification beside this document declares it, because on macOS the system python3 cannot run inside that shell.
  • git, for staging. A file no commit has staged is invisible to the build sandbox, which receives a filtered snapshot of git-tracked files rather than the working tree.
  • A working tree whose change is finished. This procedure ships work; it does not decide whether the work is done.
  • A repository whose project is in place. htmlspec/ holds this repository's project and spec.nix declares its version, and this procedure regenerates inside it. Until 0.29.0 the procedure assumed the opposite, and the second hazard in the specification beside this document is what changed.

The order of the steps

The order the change that established this runbook drew in its design, with the hazard that puts the version ahead of regeneration on the edge between them. The project's VERSION is written later, at archival, which is outside this procedure.

Tasks

Each step is one unit of work, individually addressable, so a state change is a change to one unit rather than to a list. These four stay todo in this document forever, because this is the canonical procedure and nobody works it — a run copies the document and advances the states in the copy.

The order is the correction, not the transcription. All five archived ## N. Release sections state regeneration before the version bump, and the last three of them each discovered at run time that they then had to regenerate again. The order below is what those three learned.

  • Advance the workspace version and relock offline task-advance-the-version

    Run scripts/set-version X.Y.Z with the new version. It writes version under [workspace.package] in Cargo.toml and every htmlspec-* pin in [workspace.dependencies] in one edit, then runs cargo update --workspace --offline. Offline because the relock must move the workspace members and nothing else; the suite's stages pass --locked and fail on a lockfile the manifest does not agree with. Edit neither the version nor a pin by hand: a version raised alone leaves every pin naming the old one, and the relock fails before anything can say why, which the specification beside this document states as a requirement. Deciding whether the change earned a patch, a minor, or a major increment is judgment and it is yours — archive.md reserves it, and scripts/check-release's own docstring explains why the automated version is impossible rather than merely unbuilt: a change under way legitimately has not advanced the version, so a stage asking about it would be red from a change's first commit to its last. This is first, and the reason is the first hazard the specification beside this document states as a requirement.

  • Regenerate the installed instruction files task-regenerate-the-instructions

    Run htmlspec init --tools claude,codex,pi — this repository's set, and not all, which appends the workflow bodies to the hand-authored AGENTS.md. This is never a no-op after the step above, whatever the change did to the workflow bodies: each installed file carries generatedBy: htmlspec <version> written from CARGO_PKG_VERSION at run time, so advancing the version restales every one of them. Regenerate through the command rather than editing the stamp — a hand-edited stamp is a file claiming a run that never happened, which is the defect scripts/check-installed exists to make impossible to repeat quietly. Run it from the repository root, with the binary built at the new version. Save what git status --short --untracked-files=all lists at the root first. The working tree is not clean here: the step above left Cargo.toml and Cargo.lock changed, and the change being released can be uncommitted too, so what matters is what init adds to that listing. Remove nothing afterwards. htmlspec/ and spec.nix are this repository's project and its declaration, and init extends the project and leaves both as they are: it reports extending the project in the root and spec.nix already exists, so it was left as it is, and the paths git status lists afterwards that it did not list before are the installed files under the root's .claude/, .codex/, and .pi/, each changed by its generatedBy line. Where the new binary pins an asset the project's store lacks, init also writes it, reports established so many shared asset(s) in the store, and the new files under htmlspec/assets/ are new paths too. If it reports instead that it created the project structure, or git status lists any other path it did not list before, stop the run: init did not find this repository's project, and what it wrote is for a person to settle, not for this step. Then run scripts/check. Its release and self-runbooks stages are the ones that read the project.

  • Write the changelog entry task-write-the-changelog

    Add an entry to CHANGELOG.md, newest first. The heading must name the version, because scripts/check-release finds an entry by reading headings for a dotted numeric version and nothing else. Open with what a contributor gets rather than with what was implemented, and state what the release does not do — an entry that names only the win is one a reader cannot check. Prose inside an entry is not parsed: a changelog exists to be read by a person.

  • Confirm scripts/check-release passes task-confirm-the-release-check

    Run scripts/check-release. It asks four questions of the archive in htmlspec/changes/archive/ — every archived change records a version, every recorded version above the baseline is distinct, every recorded version has a changelog entry, and every runbook release the archive publishes is accounted for — plus three about the workspace: the version Cargo.toml declares has a changelog entry, every internal dependency pins exactly that version, and every published crate carries a copy of the root LICENSE. The VERSION file beside the change's documents is written at archival rather than here, because the archived directory does not exist until archival runs, and htmlspec archive writes it, from the version spec.nix declares. Do not write it. Raise spec.nix at archival, as the archive workflow does, to the version the first step set in Cargo.toml. So this step passes on the declared version now and the archived one later, which is why it is the last task open in every change that has run this procedure.
