Publishing html-spec

The nine steps that publish a release after its change is archived and merged: from this repository's main, through a reviewed export, to the public repository, its tag, and the four channels the tag publishes to. Read the specification beside this document first. It states why no step pushes a ref from this repository, why the first run switches the public repository's protection off for one push and must see it on again, and why each channel is installed rather than assumed.

What this procedure consumes

None of these is a step somebody performs, so none is a task unit. A runbook has no notion of an input, so they are prose, as the release runbook's are.

  • A release whose change is archived and merged into this repository's main, with X.Y.Z its version. The release runbook prepared it inside the change.
  • cargo and rustc from the development shell flake.nix pins, which the specification declares for preflight. The export runs scripts/check inside the exported tree.
  • git, with this clone's hooks installed by scripts/install-hooks, so git config core.hooksPath prints .githooks, and python3, standard library only, for publish/export.
  • gh, signed in as an account that may change the public repository's rulesets and create its refs, and that may merge its pull requests.
  • nix and brew, for step 8, and a crates.io login as smurphy8, the crates' owner, for step 7 on the first release.
  • HOMEBREW_TAP_TOKEN expires around 2027-01-16. A release after that date fails at the tap job, after the crates are published. Renew the token first, or renew it when the tap job fails and run the job again.

A run starts with htmlspec preflight publish, inside nix develop, and then htmlspec run publish --as vX.Y.Z, which writes the run's record beneath htmlspec/runbooks/publish/runs/. The record is untracked until step 9 commits it, and the export counts only tracked changes as a dirty tree, so the record never stops the export.

Tasks

Each step is one unit of work, so a state change is a change to one unit rather than to a list. These nine stay todo in this document, because this is the canonical procedure and nobody works it: a run copies the document and advances the states in the copy. SOURCE is the private commit being published, TREE the exported tree a person reviewed, MERGE the public commit that merged it, and vX.Y.Z the release's tag.

  • Start from the archived release task-start-from-the-archived-release

    Run git fetch origin, and record SOURCE as what git rev-parse origin/main prints. Confirm that the archive records the version: git grep -l -E '^X\.Y\.Z$' SOURCE -- 'htmlspec/changes/archive/*/VERSION' prints the release's archived change, and git show SOURCE:Cargo.toml declares version = "X.Y.Z". Stop if either does not. git status --porcelain --untracked-files=no prints nothing, because the export refuses a tracked change.

  • Review the exact export privately task-review-the-export

    Run publish/export --ref SOURCE, the export's local review. It builds the export commit in a scratch repository and keeps it, runs the suite inside the exported tree, changes nothing public, and prints tree: followed by TREE, with the command that shows what would be published. Read the whole diff that command shows, not only its --stat. Record TREE. Where the export refuses files added or changed since their read, read each file it names against publish/READINESS.md's list, and record each path's read at the content the refusal names, with the reader and the date. Where READINESS.md at SOURCE carries no sign-off, the contributor signs it after reading it and the diff. Either lands through a pull request into main, with the skip-changelog label, and then the run takes step 1 again, because the export reads the readiness record at SOURCE. publish/ never crosses, so the new SOURCE exports the same TREE. On the first run the public repository is empty, and this review shows the bootstrap commit alone: README.md and LICENSE.

  • First run only: bootstrap the public repository task-bootstrap-the-public-repository

    Only while gh repo view Firefly-Projects/htmlspec --json isEmpty --jq .isEmpty prints true. Otherwise mark this step dropped, with the reason that the public repository already has its main. In order: gh api -X PUT repos/Firefly-Projects/htmlspec/rulesets/25362895 -f enforcement=disabled; publish/export --ref SOURCE --bootstrap --reviewed TREE, with step 2's tree; gh api -X PUT repos/Firefly-Projects/htmlspec/rulesets/25362895 -f enforcement=active, at once, whatever the bootstrap reported. Then gh api repos/Firefly-Projects/htmlspec/rulesets/25362895 --jq .enforcement must print active. Stop the run if it prints anything else. The ruleset is off for the one push and no longer.

  • Push the export and merge it task-push-the-export-and-merge-it

    On the first run, review again first. publish/export --ref SOURCE now builds the whole export on the bootstrapped main, so read its diff and take its TREE. On a later run, step 2's tree is this one. Run publish/export --ref SOURCE --push --reviewed TREE, which opens a pull request on Firefly-Projects/htmlspec and prints its address. Wait for its checks to pass, which in the public repository include all four builds and the formula whenever the export changes what the builds read, and merge it as a squash. Record MERGE, the output of gh pr view NUMBER --repo Firefly-Projects/htmlspec --json mergeCommit --jq .mergeCommit.oid. gh api repos/Firefly-Projects/htmlspec/commits/MERGE --jq .commit.tree.sha must print TREE, because what was merged is exactly what was reviewed.

  • Tag the public merge commit through the API task-tag-the-merge-commit

    Run gh api repos/Firefly-Projects/htmlspec/git/refs -f ref=refs/tags/vX.Y.Z -f sha=MERGE. Within a few minutes, gh run list --repo Firefly-Projects/htmlspec --workflow release.yml must show a run for vX.Y.Z. Stop the run if none appears, and decide between deleting and recreating the tag and starting the workflow by hand. Never push a tag from this repository, whatever happens here. A private tag, where a contributor wants one, is named private/vX.Y.Z.

  • Watch the release workflow to its end task-watch-the-release-workflow

    Run gh run watch RUN --repo Firefly-Projects/htmlspec --exit-status. If the crates job stops partway, run it again with gh run rerun RUN --repo Firefly-Projects/htmlspec --failed: scripts/publish-crates skips each crate already published and waits out the rate limit. If the tap job fails because HOMEBREW_TAP_TOKEN expired, renew it with gh secret set HOMEBREW_TAP_TOKEN --repo Firefly-Projects/htmlspec and run the job again. Record the run's address and each job's result.

  • First release only: add the co-owner task-add-the-co-owner

    Only on the release that first published the crates. Otherwise mark this step dropped, with the reason that the team already owns them. Signed in to crates.io as smurphy8, a member of the team, and with CARGO_HTTP_USER_AGENT set to what python3 scripts/release_facts.py user-agent prints, so no request names a person or a machine, run cargo owner --add github:Firefly-Projects:firefly-developers CRATE for each of htmlspec-schema, htmlspec-parse, htmlspec-assets, htmlspec-format, htmlspec-validate, and htmlspec-cli. Then cargo owner --list CRATE names the team for each of the six.

  • Check each channel task-check-each-channel

    Each must print htmlspec X.Y.Z and its revision, and the record holds what each printed. Run each binary by its full path, so a copy installed another way earlier on the path cannot answer instead. The flake: nix run github:Firefly-Projects/htmlspec/vX.Y.Z -- --version. Homebrew: brew install Firefly-Projects/tap/htmlspec, then "$(brew --prefix)/bin/htmlspec" --version. crates.io: cargo install --locked htmlspec-cli --root SCRATCH, then SCRATCH/bin/htmlspec --version. The release: gh release download vX.Y.Z --repo Firefly-Projects/htmlspec --pattern 'htmlspec-X.Y.Z-TARGET.tar.gz' --pattern SHA256SUMS --dir SCRATCH, for this machine's target; check the tarball against SHA256SUMS with shasum -a 256 --check --ignore-missing SHA256SUMS, from SCRATCH, then unpack it and run its binary. SCRATCH is an empty directory made for the step.

  • Land the record task-land-the-record

    Commit the run's record beneath htmlspec/runbooks/publish/runs/ on a branch of this repository, and merge it through a pull request with the skip-changelog label, its title checked with scripts/check-pull-request. It crosses to the public repository with the next export, once a person has read it, because every file it adds under htmlspec/ is a file changed since that path's read.
