What this procedure consumes

None of these is a step somebody performs, so none is a task unit. A runbook has no notion of an input, so they are prose, as the release runbook's are.

  • A release whose change is archived and merged into this repository's main, with X.Y.Z its version. The release runbook prepared it inside the change.
  • cargo, rustc, and python3, standard library only, from the development shell flake.nix pins, which the specification declares for preflight. The export is Python, and runs scripts/check inside the exported tree. nix develop supplies all three, and preflight refuses a python3 from outside it, because on macOS the system's cannot run inside that shell.
  • git, with this clone's hooks installed by scripts/install-hooks, so git config core.hooksPath prints .githooks.
  • gh, signed in as an account that may change the public repository's rulesets and create its refs, and that may merge its pull requests. The export pushes as that account, with gh's credentials, so git needs none of its own for GitHub.
  • nix and brew, for step 8, and a crates.io login as smurphy8, the crates' owner, for step 7 on the first release.
  • HOMEBREW_TAP_TOKEN expires around 2027-01-16. A release after that date fails at the tap job, after the crates are published. Renew the token first, or renew it when the tap job fails and run the job again.

A run starts with htmlspec preflight publish, inside nix develop, and then htmlspec run publish --as vX.Y.Z, which writes the run's record beneath htmlspec/runbooks/publish/runs/. The record is untracked until step 9 commits it, and the export counts only tracked changes as a dirty tree, so the record never stops the export.

What this run must record

Copied from the runbook's specification, which is forced rather than chosen: a reference from a runbook's documents resolves within the document that makes it, so a record naming a requirement that lives elsewhere resolves to nothing. These state what this runbook requires of a run, not what the project requires of itself.

The public repository is reached only through the export and the API calls the steps name req-the-public-repository-is-reached-only-through-the-export-and-the-api

A run MUST deliver to Firefly-Projects/htmlspec only through publish/export with --bootstrap or --push, and through the gh api calls its steps name, and MUST NOT run git push to the public repository from this repository, for any ref.

A push from this repository carries its history, whatever the push names: a tag pushes every commit behind it. The export pushes from a scratch repository holding one commit on the public main, so nothing of this repository's history goes with it. The release tag is created on GitHub, on a commit the public repository already holds, so making it moves no object at all. .githooks/pre-push refuses every push to the public repository from a checkout holding publish/export, under any spelling of its address, with no override. It compares the owner and name an address names, not the address as written, so a user, a port, a trailing .git, a slash after the scp form's colon, or an ssh Host alias does not get past it. It is a guard rail and not a lock: it protects only a clone that installed it with scripts/install-hooks, and --no-verify skips it.

A clone of this repository with the hooks installed, holding a tag vX.Y.Z on a private commit.
When
A contributor runs git push https://github.com/Firefly-Projects/htmlspec.git vX.Y.Z, the natural next command after a tag command that failed because the name was taken.
Then
The pre-push hook refuses it, saying it refuses every push from the private working repository to the public one, and nothing leaves the machine. Without the hook, the push would deliver the tag, every private commit behind it, and a release workflow run on the private tree.

The public tag names the public merge commit and the version the archive records req-the-tag-names-the-public-merge-commit-and-the-archived-version

A run MUST create the tag vX.Y.Z on MERGE, the commit that merged the export's pull request into the public repository's main, where X.Y.Z is the version the release's archived change records in its VERSION file.

The release workflow checks both before it builds: its verify job refuses a tag whose commit the public main does not hold, and scripts/check-release --tag refuses a tag naming another version than Cargo.toml's. So a wrong tag publishes nothing, and it stays on the public repository until a person deletes it.

The first run leaves the public repository's ruleset active req-the-first-run-leaves-the-ruleset-active

The run that bootstraps the empty public repository MUST set ruleset 25362895 to active again as soon as the bootstrap's push is done, and MUST stop unless gh api repos/Firefly-Projects/htmlspec/rulesets/25362895 --jq .enforcement then prints active.

The ruleset requires a pull request into main, refuses deletion, and refuses a push that is not a fast-forward, with no one allowed to bypass it. The empty repository has no main for a pull request to target, so its first commit is a direct push, which the active ruleset refuses. The export never changes a ruleset: it refuses to bootstrap while a ruleset on main is enabled, and refuses to push while one is not. Switching it off is a person's act, so switching it on again is a step with a check, and a ruleset left off stops the run where it happened.

A run publishes only an archived and merged release req-only-an-archived-and-merged-release-is-published

A run MUST take SOURCE from this repository's main at or after the merge of the release's archived change, and MUST NOT continue past step 1 unless the archive records, in an archived change's VERSION, the version being published.

A release's version, changelog, and instruction files are made inside its change, and archival records its version. A commit before that holds a release nobody finished, and a commit on a branch holds one nobody merged. The export holds the delivering steps to main as well: --push and --bootstrap refuse a commit that refs/remotes/origin/main does not hold, so the readiness record and the sign-off they read are ones a reviewed pull request landed.

The toolchain the flake pins is the one the run uses req-the-pinned-toolchain-is-what-runs

A run MUST start with cargo, rustc, and python3 resolving to the development shell flake.nix pins, and MUST NOT start from a toolchain or an interpreter installed beside it.

preflight/v1 {"kind":"toolchain","manifest":"flake.nix","shell":"default","tools":["cargo","rustc","python3"]}

The export runs the whole suite, scripts/check, inside the exported tree before it commits anything, and the suite builds with cargo. A suite that passes with another compiler proves less about the public tree than it says. The declaration names the manifest rather than a version, as the release runbook's does, because rust-toolchain.toml already pins the compiler.

python3 is declared beside the compiler because the shell supplies it and a step cannot run without it. On macOS the python3 outside the shell is /usr/bin/python3, a stub that runs the interpreter the developer tools at DEVELOPER_DIR hold, and the shell points DEVELOPER_DIR at the Nix SDK, which holds none. The stub resolves and then exits with "error: tool 'python3' not found". The first run of this runbook met that at its second step, after its preflight had reported it ready. The toolchain form states no version, so declaring python3 in it pins nothing the flake does not already pin.

gh, git, nix, and brew are inputs the tasks state in prose rather than declared here. A tool check states an exact version, and this procedure needs any working version of each.
