Publishing html-spec

What a run of this project's publishing procedure requires. A release is prepared inside its change by the release runbook, and this runbook publishes it after the change is archived and merged: to the public repository, as a reviewed export, and from there to the GitHub release, crates.io, Homebrew, and the Nix flake. The first three requirements are hazards the code review of the plan for 1.0, #63, found before any release was published: a tag pushed from this repository carries every private commit behind it, the tag must name a commit the public repository holds, and the empty public repository takes its first commit only with its protection off for that one push.

What this runbook is for

This repository is private, and it is the working record. The project is published from it to Firefly-Projects/htmlspec, a public repository that shares none of its history and receives only exports: the allowlisted paths, rewritten, scanned, and passed by the suite, built by publish/export in a scratch repository. A version tag in the public repository then runs the release workflow, which publishes the binaries, the six crates, and the Homebrew formula, and the flake builds from the tag.

The steps run after the release's change is archived, against another repository. That is why they are a runbook of their own. The release runbook's four steps run inside the change, before archival, and a run of one runbook copies its whole procedure into its record. One runbook holding both kinds of step would open every publishing record with four steps already done.

The requirements below are what this runbook requires of a run. They are not obligations of the project. The project's contract is what its accepted specifications state, and the contract is silent on how a release is published.

Requirements

The public repository is reached only through the export and the API calls the steps name req-the-public-repository-is-reached-only-through-the-export-and-the-api

A run MUST deliver to Firefly-Projects/htmlspec only through publish/export with --bootstrap or --push, and through the gh api calls its steps name, and MUST NOT run git push to the public repository from this repository, for any ref.

A push from this repository carries its history, whatever the push names: a tag pushes every commit behind it. The export pushes from a scratch repository holding one commit on the public main, so nothing of this repository's history goes with it. The release tag is created on GitHub, on a commit the public repository already holds, so making it moves no object at all. .githooks/pre-push refuses every push to the public repository from a checkout holding publish/export, under any spelling of its address, with no override. It compares the owner and name an address names, not the address as written, so a user, a port, a trailing .git, a slash after the scp form's colon, or an ssh Host alias does not get past it. It is a guard rail and not a lock: it protects only a clone that installed it with scripts/install-hooks, and --no-verify skips it.

The private tag pushed by habit

Given
A clone of this repository with the hooks installed, holding a tag vX.Y.Z on a private commit.
When
A contributor runs git push https://github.com/Firefly-Projects/htmlspec.git vX.Y.Z, the natural next command after a tag command that failed because the name was taken.
Then
The pre-push hook refuses it, saying it refuses every push from the private working repository to the public one, and nothing leaves the machine. Without the hook, the push would deliver the tag, every private commit behind it, and a release workflow run on the private tree.

The tag made on GitHub

When
Step 5 runs gh api repos/Firefly-Projects/htmlspec/git/refs -f ref=refs/tags/vX.Y.Z -f sha=MERGE.
Then
GitHub creates the tag on MERGE, a commit only the public repository holds, and no object of this repository is sent anywhere.

The public tag names the public merge commit and the version the archive records req-the-tag-names-the-public-merge-commit-and-the-archived-version

A run MUST create the tag vX.Y.Z on MERGE, the commit that merged the export's pull request into the public repository's main, where X.Y.Z is the version the release's archived change records in its VERSION file.

The release workflow checks both before it builds: its verify job refuses a tag whose commit the public main does not hold, and scripts/check-release --tag refuses a tag naming another version than Cargo.toml's. So a wrong tag publishes nothing, and it stays on the public repository until a person deletes it.

The tag on the export branch's commit

Given
The export's pull request, not yet merged, or merged by a squash that made another commit.
When
The tag is created on the export branch's own commit rather than on MERGE.
Then
The release workflow's verify job fails with "tag vX.Y.Z is on SHA, which main does not hold", and nothing builds or publishes.

A tag naming another version

When
The tag names a version other than the one Cargo.toml declares at MERGE.
Then
scripts/check-release --tag fails in the verify job, before anything is built.

The first run leaves the public repository's ruleset active req-the-first-run-leaves-the-ruleset-active

The run that bootstraps the empty public repository MUST set ruleset 25362895 to active again as soon as the bootstrap's push is done, and MUST stop unless gh api repos/Firefly-Projects/htmlspec/rulesets/25362895 --jq .enforcement then prints active.

The ruleset requires a pull request into main, refuses deletion, and refuses a push that is not a fast-forward, with no one allowed to bypass it. The empty repository has no main for a pull request to target, so its first commit is a direct push, which the active ruleset refuses. The export never changes a ruleset: it refuses to bootstrap while a ruleset on main is enabled, and refuses to push while one is not. Switching it off is a person's act, so switching it on again is a step with a check, and a ruleset left off stops the run where it happened.

The bootstrap against the active ruleset

When
A run gives --bootstrap before disabling the ruleset.
Then
The export refuses, naming the ruleset and the command that disables it, and nothing is pushed.

The ruleset left off

Given
A bootstrap that succeeded, and an enforcement=active call that was never made or that failed.
When
The run reads the ruleset's enforcement.
Then
It prints disabled, and the run stops at step 3. Step 4's --push would refuse too, saying the ruleset on main is not active.

A run publishes only an archived and merged release req-only-an-archived-and-merged-release-is-published

A run MUST take SOURCE from this repository's main at or after the merge of the release's archived change, and MUST NOT continue past step 1 unless the archive records, in an archived change's VERSION, the version being published.

A release's version, changelog, and instruction files are made inside its change, and archival records its version. A commit before that holds a release nobody finished, and a commit on a branch holds one nobody merged. The export holds the delivering steps to main as well: --push and --bootstrap refuse a commit that refs/remotes/origin/main does not hold, so the readiness record and the sign-off they read are ones a reviewed pull request landed.

A run before archival

Given
A release whose change is implemented and not archived.
When
Step 1 looks for the version in htmlspec/changes/archive/ at SOURCE.
Then
No archived change records it, and the run stops at step 1.

The readiness record lands after archival

Given
A step 2 whose export refused files changed since their read, or which lacked the contributor's sign-off.
When
The reads or the sign-off land through a pull request, and the run takes step 1 again.
Then
SOURCE is main's new commit, the archive still records the version, and the export's tree is the one step 2 built, because publish/ never crosses.

Each channel's version is recorded req-each-channels-version-is-recorded

A run MUST record, for each of the four channels, what htmlspec --version prints after installing from it, and MUST NOT settle step 8 as done while any channel fails to install or prints another version than X.Y.Z.

The release workflow passing says that each job ran. It does not say that a person can install the release, which is what publishing is for. The four channels are installed and run the way a reader of the README would, so a channel that broke is found by the run rather than by the first person to try it.

The tap not updated

Given
A release whose tap job failed, because HOMEBREW_TAP_TOKEN had expired.
When
Step 8 installs through Homebrew.
Then
The formula is absent or names the previous version. The step stays open, and the record names the channel and what it printed, until the token is renewed and the tap job is run again.

The toolchain the flake pins is the one the run uses req-the-pinned-toolchain-is-what-runs

A run MUST start with cargo and rustc resolving to the development shell flake.nix pins, and MUST NOT start from a toolchain installed beside it.

preflight/v1 {"kind":"toolchain","manifest":"flake.nix","shell":"default","tools":["cargo","rustc"]}

The export runs the whole suite, scripts/check, inside the exported tree before it commits anything, and the suite builds with cargo. A suite that passes with another compiler proves less about the public tree than it says. The declaration names the manifest rather than a version, as the release runbook's does, because rust-toolchain.toml already pins the compiler.

gh, git, nix, and brew are inputs the tasks state in prose rather than declared here. A tool check states an exact version, and this procedure needs any working version of each.

A toolchain installed beside the pinned one

Given
A machine whose search path resolves cargo to an installation of its own.
When
The run's prerequisites are checked with htmlspec preflight publish.
Then
The check reports where cargo resolved and that it is not the pinned environment's, and the run does not start.

Decisions

The tag is made on GitHub, and this repository needs no release tag decision-no-ref-leaves-this-repository

Step 5 makes the public tag through GitHub's API on the public merge commit, and no step pushes a ref from this repository. The archive's VERSION records which release this repository made, so it needs no tag of its own. A contributor who wants one names it private/vX.Y.Z, so no name is shared with the public repository.

A shared name makes the natural recovery from "tag already exists" a push of the private tag. Pushing the public tag from the export's fetched copy of the public main works when typed exactly, and one wrong word sends the private one. With no push in any step, the pre-push hook can refuse every push to the public repository without an exception. The tag is expected to start the release workflow as a pushed tag does, but GitHub's documentation does not say that a ref created through the API starts a push workflow, so that is unconfirmed until the first run. Step 5 checks that a run started, and the risk that the tag starts no workflow says what the run does if none did.

The exact export is reviewed before it is public decision-the-export-is-reviewed-before-it-is-public

Step 2 builds the export locally and a person reads its diff, and steps 3 and 4 deliver that tree and no other, by passing its id as --reviewed. On the first run the whole export is read again after the bootstrap, because against an empty target the local review builds the bootstrap commit alone.

A branch pushed to the public repository is public from that moment, and GitHub keeps a pull request's commits after its branch is deleted. A review after the push is too late.

The first run's own steps say so decision-first-run-steps-say-so

Steps 3 and 7 run on the first publication only, and each says so in its own text. A later run marks them dropped, with that as the reason.

The bootstrap can happen once, because afterwards the public repository has a main, and the crates' co-owner is added once, after the first publish creates the crates. Keeping both in the procedure keeps the first run's record whole, and the procedure the same for every run.

Risks

A tag made through the API does not start the release workflow risk-the-api-tag-starts-no-workflow

If GitHub does not treat the created ref as a push, no release runs, and the tag sits on the public repository with nothing published.

Held down by step 5, which requires a run for the tag to appear and stops the run otherwise. The stopped run is recorded, and a person decides between deleting and recreating the tag and starting the workflow by hand.

The tap token expires risk-the-tap-token-expires

Accepted, because a failed tap job is rerun once the token is renewed: the formula is rendered from the release that already exists. HOMEBREW_TAP_TOKEN expires around 2027-01-16, and a release after that date fails at the tap job after the crates are published. The tasks name the expiry before the steps.

The first run is the first time the public steps run risk-the-first-run-is-the-first-use

Steps 3 to 8 touch live services, and none of them can run before the first release.

Partly held down. Steps 1, 2, and 4 were rehearsed against a local target with the export as built, and the commands of steps 3, 5, and 7 were read against GitHub's and cargo's documentation before this runbook was published. What stays unproven is the live calls themselves, and the first run watches each one.

Evidence

The private tag's push, reproduced by the review evidence-the-private-tag-push

The code review of #63 found that the plan's tag step made the private and public tags share the name vX.Y.Z, and reproduced, with the hook as it then was, that git push of the private tag to the public repository passed: the hook and the ruleset guarded only main. publish-a-public-tree then made the hook refuse every push to the public repository from a checkout holding publish/export, matching seven spellings of its address. The code review of publish-releases-through-their-own-runbook ran the hook on three more, a user in the address, the port of ssh.github.com, and a slash after the scp colon, and saw each pass. The hook now compares the owner and name an address names, and its tests give it seventeen spellings and see each refused.

Steps 1, 2, and 4, rehearsed against a local target evidence-the-rehearsal

Before this runbook's first publication, publish-releases-through-their-own-runbook ran steps 1, 2, and 4, with the first run's bootstrap, against a bare repository on the contributor's machine, with the export as built and the real suite inside the exported tree. Its record is that change's evidence, the-rehearsal-2026-10-20.md, in the archive.
