Deterministic formatting

Defines the canonical serialization of a specification document, so that rich HTML still produces small, meaningful Git diffs and two agents editing the same document independently do not fight over formatting.

This is the deterministic-formatting capability specification, converted from Markdown into a conforming HTMLSpec document by the toolchain it specifies. Task 9.1.

Requirements

Formatting is idempotent req-idempotent

Formatting a document SHALL be a fixed point: formatting an already-formatted document SHALL produce byte-identical output.

Applying formatting repeatedly SHALL never continue to change the file.

Second pass changes nothing

When
A document is formatted twice in succession.
Then
The output of the second pass is byte-identical to the output of the first.

A formatted file in version control

Given
A formatted document committed to Git.
When
Formatting is run again with no content edits.
Then
Git reports no changes.

Formatting preserves meaning req-preserves-meaning

Formatting SHALL NOT change a document's semantic content. It SHALL preserve every semantic unit, every identifier, every attribute value, every cross-reference, and the document order of content.

Formatting SHALL NOT add, remove, or reorder semantic units.

Identifiers survive formatting

When
A document is formatted.
Then
Every semantic unit retains the identifier it had before.

Content order is preserved

When
A document with requirements in a deliberate order is formatted.
Then
The requirements appear in the same order.

Whitespace-sensitive content is untouched

When
A document contains a preformatted code excerpt.
Then
Formatting leaves that content's internal whitespace and line breaks exactly as authored.

Formatting an invalid document

When
Formatting is applied to a document that fails validation.
Then
The formatter either produces canonically formatted output without altering meaning, or refuses and reports why. It never silently repairs or discards content.

Serialization is canonical req-canonical

For any given document content, there SHALL be exactly one canonical serialization.

Attribute order, indentation, line breaking, quoting, character escaping, tag closing, and case SHALL be fully determined by the formatting rules rather than by authoring choices or generator behavior.

Two agents converge

Given
Two agents that produce the same semantic document with different attribute order and indentation.
When
Both outputs are formatted.
Then
The two files are byte-identical.

Attribute order is fixed

When
A formatted element carries a class, an identifier, and a change state.
Then
Those attributes appear in the order the formatting rules prescribe, regardless of the order they were written in.

Escaping is consistent

When
Content contains characters that may be written either literally or as entities.
Then
The formatted output uses one prescribed form for each such character.

Formatting introduces no diff churn req-no-churn

Formatting SHALL NOT widen a diff beyond the units a content edit touched. Editing, adding, or removing a unit SHALL NOT cause the formatter to reflow or reindent unrelated parts of the document.

This requirement constrains the formatter only. It does not promise a minimal Git diff for a given edit: preserved author line breaks mean a one-line paragraph produces a whole-line change when one sentence changes, and that cost belongs to the line structure rather than to the formatter. Diff minimality is measured as a separate property, recorded in the diff-locality evidence.

Editing one requirement

When
The prose of one requirement is revised and the document is formatted.
Then
The formatter changes no line outside that requirement.

A whole-line change is not a violation

When
One sentence changes inside a paragraph held on a single long line.
Then
The diff covers that whole line, and the formatter is still conformant.

Inserting a requirement

When
A new requirement is inserted between two existing ones.
Then
The diff shows the added requirement and does not rewrite the surrounding requirements.

Long prose is not reflowed

When
A sentence within a paragraph is edited.
Then
The diff does not rewrap the entire surrounding paragraph or section.

Generated content is ordered deterministically req-generated-order

Where a document contains content whose order is not authored — such as collected references, indexes, or navigation — that order SHALL be determined by a stable rule.

Regenerating such content from unchanged inputs SHALL produce identical output.

Regenerating navigation

When
A document's navigation is regenerated with no content change.
Then
The navigation is byte-identical to before.

No incidental ordering

When
Generated content is produced twice from the same inputs in different runs.
Then
The ordering does not vary with iteration order, timestamps, or filesystem order.

Formatting can be checked without writing req-check-mode

It SHALL be possible to determine whether a document is canonically formatted without modifying it, so that continuous integration can reject unformatted documents.

The check passes

When
A canonically formatted document is checked.
Then
The check reports success and the file is not modified.

The check fails

When
An unformatted document is checked.
Then
The check reports failure, identifies the document, and the file is not modified.

Files use a stable text encoding and line ending req-file-normalization

Formatted documents SHALL use UTF-8 encoding, SHALL use a single prescribed line ending, SHALL end with exactly one final newline, and SHALL NOT contain trailing whitespace on any line.

Line endings are normalized

When
A document authored with mixed line endings is formatted.
Then
The output uses the prescribed line ending throughout.

Cross-platform round trip

Given
Contributors on different operating systems.
When
Each formats the same document.
Then
The results are byte-identical.

Decisions

The formatter never rewraps text decision-never-rewrap

The canonical serializer normalizes the indentation and line breaking of block structure, fixes attribute order and quoting, and prescribes one escaping form per character. It does not reflow prose: author line breaks inside text-bearing content are preserved exactly.

General HTML formatters that rewrap text are notoriously difficult to make idempotent, because inline whitespace is semantic and every wrap decision interacts with the next. Refusing to rewrap makes the fixed-point property nearly structural rather than something to be asserted and hoped for.

The cost is that prose line breaks become the author's problem, and agents may produce very long lines. That is acceptable: no requirement constrains line length, and a long line still diffs as one line.

Only ambiguity is refused decision-refuse-ambiguous

The formatter refuses a document whose markup requires parser error recovery, and formats every other document — including one that fails validation.

A document with a dangling reference or a duplicate identifier has one unambiguous tree, so canonicalizing it alters no meaning. Refusing there would mean a document could not be tidied until it was already correct, which is backwards. Ambiguity is different: the formatter would have to pick one reading, and picking one is a silent repair.

The serializer is written here rather than delegated decision-not-prettier

The canonical serializer is implemented in Rust in this project.

prettier was the obvious alternative and is not available: it is JavaScript, and taking a Node dependency for the core operation of a Rust toolchain would compromise the reproducible single-artifact packaging.

Evidence

Idempotence and preservation hold over generated documents evidence-fixed-point

A proptest generator draws its vocabulary from the published schema and produces documents with sprawling indentation, shuffled attribute order, mixed line endings, and text carrying author line breaks. Over 512 cases per property it asserts that formatting is a fixed point across three passes, and that the projected model is unchanged.

Every conformance fixture is additionally formatted twice and compared byte-for-byte, and the projection mapping fixtures cover the whitespace-sensitive cases directly.

Diff locality belongs to line structure, not to the formatter evidence-diff-locality

The same seven-byte edit to the same four sentences costs 225 changed bytes when the paragraph is held on one line and 85 when it is broken at sentence boundaries — a 2.6× difference in what a reviewer must re-read, with an identical changed-line count of one.

Editing the same one-line paragraph at its start and at its end costs 225 and 227 bytes, within one percent of each other. A rewrapping formatter would show a cascade for the early edit and almost nothing for the late one, so the symmetry confirms nothing is being rewrapped.

An edit leaves every other line untouched evidence-no-churn

Editing a unit, inserting one between two others, and removing one each leave every line outside the affected unit byte-identical. A unit made taller does not reindent the unit after it, which is the churn a formatter that re-derived depth from content would produce.

Risks

Agents may produce unreadably long lines risk-long-lines

Because the formatter has no opinion about line breaks, an agent may emit a whole section as one line, and every subsequent edit to it will diff as that whole line.

Measured rather than assumed: the cost is 2.6× more bytes to re-read, not a correctness failure, and it is fully within an author's control. The guidance is to break prose at sentence boundaries. Enforcing a line length is deliberately out of scope, because a line-length rule is a configuration surface and the number to beat is now recorded.

Verification

Idempotence and canonicality verify-idempotence

Run the property suite in crates/htmlspec-format/tests/properties.rs, which asserts a three-pass fixed point and the convergence of two authoring styles over 512 generated documents each, plus the conformance suite's double-format comparison over every fixture.

Absence of formatter churn verify-no-churn

Run crates/htmlspec-format/tests/no_churn.rs, which splits a formatted document around the edited unit and asserts the lines outside it are unchanged for an edit, an insertion, and a removal.

Check mode and file normalization verify-check-mode

Run the CLI integration tests, which invoke the built binary and assert that check mode names the document, exits nonzero, and leaves the file byte-identical, and that mixed line endings converge on one form.
