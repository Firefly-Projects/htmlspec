html-spec

This was the project's first change, made while openspec/specs/ was empty, so every requirement it states is new. It required a closed vocabulary of semantic units, each carried by a reserved class and a stable identifier (Semantic units are identified by class, Every semantic unit has a stable unique identifier), published as a machine-readable schema, a normative HTML-to-model projection, and conformance fixtures (The element contract is published as a machine-readable schema, The HTML-to-model projection is published as a normative specification, Conformance is pinned by fixtures). It also required a page that renders offline and reads without JavaScript (A document is self-contained and offline, Core content is readable without JavaScript), a formatter whose output is a fixed point (Formatting is idempotent), validation that rejects any parser recovery the project does not permit and any remote dependency (Markup must be deterministically parseable, Remote and hidden network dependencies are rejected), and one program that validates, formats, and initializes documents (A single command exposes validate, format, and init).

document-schema

Defines the normative HTML element contract for the semantic units of a specification — requirements, scenarios, decisions, tasks, evidence, risks, and verification — so that agents can address and revise individual units reliably and humans read a document rather than a data format.

Semantic units are identified by class req-semantic-units-are-identified-by-class

A document SHALL express each semantic unit as an HTML element carrying a reserved class name from a closed vocabulary: requirement, scenario, decision, task, evidence, risk, and verification. A reserved class name SHALL NOT be used on an element that is not that semantic unit.

Recognized unit

When
a document contains <section class="requirement" id="req-theme-selection">
Then
consumers treat that element and its descendants as one requirement unit

Class outside the vocabulary

When
a document uses a class name that is not reserved, such as class="note"
Then
the element carries no semantic-unit meaning and is treated as ordinary content

Reserved class on a decorative element

When
a document applies class="requirement" to an element used only for layout, with no requirement content
Then
the document is invalid

Every semantic unit has a stable unique identifier req-every-semantic-unit-has-a-stable-unique-identifier

Every semantic unit SHALL carry an id attribute. The identifier SHALL be unique within the document, SHALL use a prefix reserved for its unit type, and SHALL consist of lowercase alphanumeric characters and hyphens.

Prefix matches unit type

When
a requirement is identified
Then
its id begins with req-, a scenario with scenario-, a decision with decision-, a task with task-, evidence with evidence-, a risk with risk-, and verification with verify-

Duplicate identifier

When
two elements in the same document share the same id
Then
the document is invalid

Identifier is stable across edits

When
an agent revises the prose of a requirement without changing what it requires
Then
the requirement's id is unchanged, and references to it continue to resolve

Renaming a requirement

When
a requirement's title changes but it describes the same obligation
Then
its id SHALL be preserved rather than regenerated from the new title

Semantic units declare a change state req-semantic-units-declare-a-change-state

Every semantic unit SHALL declare its lifecycle state in a data-change attribute with one of the values added, modified, removed, or unchanged. A unit with no data-change attribute SHALL be interpreted as unchanged.

Newly proposed requirement

When
a change introduces a requirement that does not exist in the accepted specs
Then
the requirement carries data-change="added"

Requirement being withdrawn

When
a change removes an accepted requirement
Then
the requirement carries data-change="removed" and remains present in the document so reviewers can see what is being withdrawn

Unrecognized change state

When
a unit carries data-change="pending"
Then
the document is invalid

A requirement contains a title and normative statement req-a-requirement-contains-a-title-and-normative-statement

A requirement unit SHALL contain exactly one heading giving its name and at least one element of prose stating the obligation. The normative statement SHALL use SHALL or MUST, and SHALL NOT rely on should or may to express an obligation.

Well-formed requirement

When
a requirement contains a heading and a paragraph reading "The application MUST let the user select a light or dark theme"
Then
the requirement is well formed

Requirement with no normative statement

When
a requirement contains only a heading
Then
the document is invalid

Requirement with multiple headings

When
a requirement unit contains two headings at its own level
Then
the document is invalid, because the requirement's name is ambiguous

Every requirement contains at least one scenario req-every-requirement-contains-at-least-one-scenario

A requirement SHALL contain at least one scenario unit nested within it. A scenario SHALL NOT appear outside a requirement.

Requirement without scenarios

When
a requirement declares an obligation but contains no scenario
Then
the document is invalid

Orphaned scenario

When
a scenario appears as a sibling of requirements rather than nested inside one
Then
the document is invalid

A scenario states conditions and expected outcomes req-a-scenario-states-conditions-and-expected-outcomes

A scenario SHALL contain a heading naming it and a structured body pairing each condition with its expected outcome, using the labels Given, When, and Then. A scenario SHALL contain at least one When and at least one Then. Given is optional and MAY repeat.

Minimal scenario

When
a scenario pairs a single When condition with a single Then outcome
Then
the scenario is well formed

Scenario missing an outcome

When
a scenario states a When condition with no Then
Then
the document is invalid

Scenario with preconditions

Given
a scenario that depends on prior state
When
it declares one or more Given labels before its When
Then
the scenario is well formed

Unrecognized label

When
a scenario body uses a label other than Given, When, or Then
Then
the document is invalid

Cross-references address units by identifier req-cross-references-address-units-by-identifier

A task, verification, evidence, or risk unit MAY reference the semantic units it relates to. Such a reference SHALL name the target by its identifier, and SHALL resolve to a unit that exists in the same document or in an accepted spec reachable from it.

Task implements a requirement

When
a task declares that it satisfies req-theme-selection
Then
consumers can report implementation progress per requirement

Verification covers a scenario

When
a verification unit references scenario-theme-persists
Then
consumers can report which scenarios have been verified and which have not

Dangling reference

When
a task references req-does-not-exist
Then
the document is invalid

Reference to a removed requirement

When
a task references a requirement carrying data-change="removed"
Then
the document is invalid, because work cannot target a withdrawn obligation

A decision records its outcome and rationale req-a-decision-records-its-outcome-and-rationale

A decision unit SHALL contain a heading, a statement of the decision reached, and its rationale. It SHALL declare a status of proposed, accepted, or superseded. A superseded decision SHALL reference the decision that replaces it.

Accepted decision

When
a decision states the chosen option and why, with status accepted
Then
the decision is well formed

Superseded decision without a successor

When
a decision declares status superseded but references no replacement
Then
the document is invalid

A task declares completion state req-a-task-declares-completion-state

A task unit SHALL declare whether it is complete in a machine-readable attribute, distinct from any visual checkbox. Completion state SHALL be one of todo, in-progress, done, or dropped. A dropped task SHALL state why.

Reporting progress

When
a consumer reads a document containing ten tasks of which four are done
Then
the consumer can report progress without parsing prose or rendered markup

Dropped task without a reason

When
a task declares state dropped and gives no reason
Then
the document is invalid

The element contract is published as a machine-readable schema req-the-element-contract-is-published-as-a-machine-readable-schema

The element contract SHALL be published as a machine-readable schema that is the single source of truth for the vocabulary, required structure, identifier prefixes, and permitted attribute values of the projected document model. Tools that validate, format, or generate documents SHALL derive their understanding of that model from the schema rather than restating it.

The schema describes the projected model. It does not describe the HTML that produces the model, so the schema alone SHALL NOT be treated as the complete public contract.

Contract and tooling agree

When
the published schema is changed to add a semantic unit
Then
tools reflect the new unit without a separate, independently maintained definition

Third-party consumer reads the model contract

Given
a consumer outside this project
When
it reads the published schema
Then
it can determine the full set of semantic units and their required structure in the projected model without reading this project's source code

The HTML-to-model projection is published as a normative specification req-the-html-to-model-projection-is-published-as-a-normative-specification

The project SHALL publish a normative projection specification stating how a document's HTML becomes the projected model. That specification SHALL be part of the public contract alongside the schema. It SHALL state, at minimum:

  • which elements and attributes create a semantic unit, and which are ignored

  • how a nested element becomes a field of its containing unit

  • which content preserves whitespace exactly, and which content normalizes it

  • how a link, and how an explicit reference attribute, each become a reference in the model

  • how a figure, its caption, and its visualization source project

  • how task completion state and unit change state project

  • how presentational markup that carries no semantic unit is discarded

Independent implementation reproduces the model

Given
an implementation written from the projection specification and the schema, with no access to this project's source code
When
it projects a conformance fixture
Then
it produces the same model as this project's implementation

Presentational markup is ignored predictably

When
a document wraps a requirement's prose in additional presentational elements that carry no reserved class
Then
the projection specification determines whether that markup is discarded, and the resulting model does not vary between implementations

Projection rule without a fixture

When
a rule is added to the projection specification with no corresponding mapping fixture
Then
the conformance suite is incomplete and the contract change is not accepted

Conformance is pinned by fixtures req-conformance-is-pinned-by-fixtures

The contract SHALL be accompanied by a conformance suite of example documents, each labelled valid or invalid. Every invalid fixture SHALL identify the rule it violates. Every rule in the contract SHALL be covered by at least one valid and one invalid fixture.

The suite SHALL also contain mapping fixtures, each pairing an HTML input with its expected projected model, so that the projection specification is pinned as precisely as the schema.

Rule without coverage

When
a rule is added to the contract with no corresponding fixtures
Then
the conformance suite is incomplete and the contract change is not accepted

Verifying an independent implementation

Given
an independent implementation of the contract
When
it is run against the conformance suite
Then
it accepts every valid fixture and rejects every invalid fixture, identifying the expected violated rule

document-template

Defines the canonical page a reviewer opens — its structure, its restrained visual system, its print behavior, and the pinned offline runtime that renders diagrams, charts, and equations — so that a specification is legible in a browser, on paper, and with scripting disabled.

A document is self-contained and offline req-a-document-is-self-contained-and-offline

A document SHALL render completely without network access. It SHALL NOT reference remote scripts, stylesheets, fonts, images, or analytics. All referenced assets SHALL resolve to files within the project.

Opened with no network

Given
a machine with networking disabled
When
a reviewer opens a document in a browser
Then
the document renders fully, including its diagrams and charts

Remote reference present

When
a document references a script or font over http: or https:
Then
the document is invalid

No tracking

When
a reviewer opens a document
Then
no request leaves the machine

Core content is readable without JavaScript req-core-content-is-readable-without-javascript

The semantic content of a document — its requirements, scenarios, decisions, tasks, evidence, risks, and verification — SHALL be present in the served markup and legible with JavaScript disabled. JavaScript SHALL only enhance presentation.

Scripting disabled

Given
a browser with JavaScript disabled
When
a reviewer opens a document
Then
every requirement, scenario, decision, task, and verification result is readable, correctly ordered, and styled

Diagram with scripting disabled

When
a document containing a diagram is opened with JavaScript disabled
Then
the diagram's source or a textual description is visible in place of the rendered figure, rather than an empty region

Content injected by script

When
a document supplies a requirement's text only by running JavaScript
Then
the document is invalid

Documents share one pinned runtime req-documents-share-one-pinned-runtime

Diagram, chart, and equation support SHALL come from a fixed set of approved libraries at versions pinned by the project. The runtime SHALL be shared across documents in a project rather than duplicated into each file. Arbitrary generated scripts SHALL NOT be embedded in a document.

Approved libraries

When
a document renders a diagram or a chart
Then
it does so through the project's pinned diagram or charting library, and equations use native MathML with no library at all

Shared assets

Given
a project containing many documents
When
the runtime is measured
Then
each library appears once in the project rather than once per document

Migration note: this change built otherwise. Its init established the assets in the new document's own directory unless --assets named a project root, so documents in different directories each received their own copy, and at archival (commit 6956324) this change's own converted document had an eight-file copy of the runtime in documents/assets/, a second copy alongside the repository's assets/. Nothing then detected the duplicate. The later change 2026-08-13-content-address-runtime-assets fixed it, storing each asset once under a name derived from its bytes and rejecting a project that holds two copies; see its proposal.

Unapproved script

When
a document embeds an inline script that is not part of the pinned runtime
Then
the document is invalid

Runtime version is recorded

When
a reviewer inspects a project's assets
Then
each vendored library's exact version and content hash are recorded, so a rendered document can be reproduced later

A document declares its identity and provenance req-a-document-declares-its-identity-and-provenance

Every document SHALL declare, in machine-readable form, the schema version it conforms to, the change or spec it represents, and its lifecycle status. A reviewer SHALL be able to see this information on the page without reading source.

Migration note: this change built the lifecycle status as an htmlspec-status declaration in the document's head, shown on the page as its Status, as the template and section 9.3 of crates/htmlspec-schema/doc/projection.md at commit 6956324 show. The later change 2026-08-14-separate-artifact-kinds replaced the status with the document's kind; see its specification.

Schema version present

When
a consumer reads a document
Then
it can determine which version of the element contract the document targets before parsing its content

Status visible to a reviewer

When
a reviewer opens a document representing a proposal under review
Then
the page shows its status, so an unapproved proposal is not mistaken for accepted specification

Missing schema version

When
a document omits its schema version
Then
the document is invalid

A document is navigable req-a-document-is-navigable

A document SHALL present its sections in a stable, predictable order and SHALL provide navigation to its semantic units. Every semantic unit SHALL be addressable by a fragment link that resolves within the document.

Deep link to a requirement

When
a reviewer follows a link ending in #req-theme-selection
Then
the browser scrolls to that requirement

Navigation without scripting

When
a document is opened with JavaScript disabled
Then
its navigation still lists the document's sections and its links still resolve

Broken internal link

When
a document contains a fragment link whose target does not exist
Then
the document is invalid

The visual system favors comprehension over decoration req-the-visual-system-favors-comprehension-over-decoration

A document SHALL use the project's shared visual system: flat editorial layout, serif body text, high information density, and muted color. Color SHALL NOT be the only means of conveying meaning. Styling SHALL NOT hide or reorder semantic content.

Change state conveyed without color alone

When
a reviewer with a color-vision deficiency reads a document containing added, modified, and removed requirements
Then
each unit's change state is distinguishable by text or shape, not only by hue

Styling does not hide content

When
a document is styled
Then
no semantic unit is visually hidden or moved out of its document order

Readable at a narrow width

When
a document is viewed in a narrow window
Then
its text reflows and remains readable without horizontal scrolling of body prose

Documents print cleanly req-documents-print-cleanly

A document SHALL provide print styling that produces a legible paper or PDF rendering. Navigation chrome and interactive controls SHALL be omitted from print output. Content SHALL NOT be truncated at page boundaries.

Printing to PDF

When
a reviewer prints a document to PDF
Then
the result contains the full content with legible type, no clipped diagrams, and no navigation chrome

Link targets in print

When
a document containing external references is printed
Then
those references remain identifiable on paper rather than appearing as unresolvable link text

A project can be initialized with a conforming document req-a-project-can-be-initialized-with-a-conforming-document

The project SHALL provide a way to create a new document that already conforms to the element contract, the visual system, and the runtime conventions, without hand-assembly.

Starting a new change

When
a contributor initializes a new change document
Then
the resulting file passes validation immediately and opens as a readable page

Initializing into a project without assets

When
a document is created in a project whose shared assets are not yet present
Then
the assets are established as part of initialization, so the document renders offline without a further step

deterministic-formatting

Defines the canonical serialization of a specification document so that rich HTML still produces small, meaningful Git diffs, and so two agents editing the same document independently do not fight over formatting.

Formatting is idempotent req-formatting-is-idempotent

Formatting a document SHALL be a fixed point: formatting an already-formatted document SHALL produce byte-identical output. Applying formatting repeatedly SHALL never continue to change the file.

Second pass changes nothing

When
a document is formatted twice in succession
Then
the output of the second pass is byte-identical to the output of the first

Formatted file in version control

Given
a formatted document committed to Git
When
formatting is run again with no content edits
Then
Git reports no changes

Formatting preserves meaning req-formatting-preserves-meaning

Formatting SHALL NOT change a document's semantic content. It SHALL preserve every semantic unit, every identifier, every attribute value, every cross-reference, and the document order of content. It SHALL NOT add, remove, or reorder semantic units.

Identifiers survive formatting

When
a document is formatted
Then
every semantic unit retains the identifier it had before

Content order preserved

When
a document with requirements in a deliberate order is formatted
Then
the requirements appear in the same order

Whitespace-sensitive content untouched

When
a document contains a preformatted code excerpt
Then
formatting leaves that content's internal whitespace and line breaks exactly as authored

Formatting an invalid document

When
formatting is applied to a document that fails validation
Then
the formatter either produces canonically formatted output without altering meaning, or refuses and reports why — it never silently repairs or discards content

Serialization is canonical req-serialization-is-canonical

For any given document content, there SHALL be exactly one canonical serialization. Attribute order, indentation, line breaking, quoting, character escaping, tag closing, and case SHALL be fully determined by the formatting rules rather than by authoring choices or generator behavior.

Two agents converge

Given
two agents that produce the same semantic document with different attribute order and indentation
When
both outputs are formatted
Then
the two files are byte-identical

Attribute order is fixed

When
a formatted element carries a class, an identifier, and a change state
Then
those attributes appear in the order the formatting rules prescribe, regardless of the order they were written in

Escaping is consistent

When
content contains characters that may be written either literally or as entities
Then
the formatted output uses one prescribed form for each such character

Formatting introduces no diff churn req-formatting-introduces-no-diff-churn

Formatting SHALL NOT widen a diff beyond the units a content edit touched. Editing, adding, or removing a unit SHALL NOT cause the formatter to reflow or reindent unrelated parts of the document.

This requirement constrains the formatter only. It does not promise a minimal Git diff for a given edit. Preserved author line breaks mean a one-line paragraph produces a whole-line change when one sentence changes, and that cost belongs to the line structure rather than to the formatter. Diff minimality SHALL be measured as a separate property.

Editing one requirement

When
the prose of one requirement is revised and the document is formatted
Then
the formatter changes no line outside that requirement

Whole-line change is not a violation

When
one sentence changes inside a paragraph held on a single long line
Then
the diff covers that whole line, and the formatter is still conformant

Inserting a requirement

When
a new requirement is inserted between two existing ones
Then
the diff shows the added requirement and does not rewrite the surrounding requirements

Long prose reflow

When
a sentence within a paragraph is edited
Then
the diff does not rewrap the entire surrounding paragraph or section

Generated content is ordered deterministically req-generated-content-is-ordered-deterministically

Where a document contains content whose order is not authored — such as collected references, indexes, or navigation — that order SHALL be determined by a stable rule. Regenerating such content from unchanged inputs SHALL produce identical output.

Regenerating navigation

When
a document's navigation is regenerated with no content change
Then
the navigation is byte-identical to before

No incidental ordering

When
generated content is produced twice from the same inputs in different runs
Then
the ordering does not vary with iteration order, timestamps, or filesystem order

Formatting can be checked without writing req-formatting-can-be-checked-without-writing

It SHALL be possible to determine whether a document is canonically formatted without modifying it, so that continuous integration can reject unformatted documents.

Check passes

When
a canonically formatted document is checked
Then
the check reports success and the file is not modified

Check fails

When
an unformatted document is checked
Then
the check reports failure, identifies the document, and the file is not modified

Files use a stable text encoding and line ending req-files-use-a-stable-text-encoding-and-line-ending

Formatted documents SHALL use UTF-8 encoding, SHALL use a single prescribed line ending, SHALL end with exactly one final newline, and SHALL NOT contain trailing whitespace on any line.

Line endings normalized

When
a document authored with mixed line endings is formatted
Then
the output uses the prescribed line ending throughout

Cross-platform round trip

Given
contributors on different operating systems
When
each formats the same document
Then
the results are byte-identical

document-validation

Defines the structural and safety rules a specification document must satisfy to be accepted, along with the diagnostics a validator reports, so that a document is both reliably machine-editable and safe to open.

Structural conformance is enforced req-structural-conformance-is-enforced

Validation SHALL reject any document that violates the element contract. This includes missing or duplicate identifiers, identifier prefixes that do not match the unit type, requirements without scenarios, scenarios outside requirements, missing normative statements, malformed scenario bodies, and attribute values outside their permitted sets.

Duplicate identifier rejected

When
a document contains two units sharing one identifier
Then
validation fails and reports both locations

Requirement without a scenario rejected

When
a requirement contains no scenario
Then
validation fails and identifies the requirement

Conforming document accepted

When
a document satisfies every structural rule
Then
validation succeeds and reports no structural errors

An upstream edit marks dependents for review rather than gating work req-an-upstream-edit-marks-dependents-for-review-rather-than-gating-work

Validation SHALL report a dependent unit as needing review when the unit it references changes materially. Such a report SHALL NOT block continued work, SHALL NOT impose a phase gate, and SHALL NOT require regeneration of the dependent artifact. Exploration, proposal, design, implementation, and verification SHALL be able to loop.

Migration note: as built, a unit changes materially when it declares data-change added or modified. Every unit referencing it is reported, whether or not it still describes that unit's behaviour, and the report clears when the referenced unit returns to unchanged, rather than when the dependents are reconciled. A second rule, review/stale-verification, reports a verification that records an outcome against such a unit. This was deliberate: the module documentation of crates/htmlspec-validate/src/rules/review.rs at commit 6956324 states it as the rule's design. No document of this change records it, so the delta's words are kept.

Requirement revised during implementation

Given
tasks and verification that reference a requirement
When
that requirement's obligation changes while implementation is underway
Then
validation reports the referencing units as needing review, and work continues

Reconciliation clears the report

When
an agent reconciles the units reported as needing review
Then
validation stops reporting them, and no artifact was regenerated wholesale

Stale reference is reported, not fatal

When
a dependent unit still resolves but describes behavior the referenced requirement no longer states
Then
validation reports the inconsistency as needing review rather than as a structural error

Cross-references must resolve req-cross-references-must-resolve

Validation SHALL verify that every reference to a semantic unit resolves to a unit that exists. This includes fragment links within the document, and references from tasks, verification, evidence, and risks to the requirements and scenarios they address.

Dangling task reference

When
a task references a requirement identifier that does not exist
Then
validation fails and reports the task and the unresolved identifier

Broken fragment link

When
a document links to a fragment with no matching element
Then
validation fails and reports the link

Reference to a removed requirement

When
a task or verification references a requirement marked removed
Then
validation fails

Markup must be deterministically parseable req-markup-must-be-deterministically-parseable

Validation SHALL reject a document whose markup cannot be parsed into a single unambiguous structure. Constructs that different parsers would interpret differently SHALL be rejected rather than accepted with a guess.

A conforming document SHALL produce zero recovered parse errors by default. Any recovered parse error SHALL fail validation unless the project permits that specific recovery.

Improperly nested elements

When
a document contains overlapping or improperly nested elements
Then
validation fails and reports the location

Migration note: as built, a parse diagnostic names the document and the parser's message, and cannot name a line or an offset, because the parser hands the message over with no byte offset. evidence/parse-errors.md names this as a limit and leaves offsets out of scope (“Gaps, stated rather than hidden”, limit 2), so the delta's words are kept.

Ambiguous construct

When
a document contains markup whose interpretation depends on parser error recovery
Then
validation fails rather than silently accepting one interpretation

Permitted parser recoveries are enumerated and pinned req-permitted-parser-recoveries-are-enumerated-and-pinned

The project SHALL pin an exact parser version. Every permitted recovery SHALL be enumerated individually, SHALL carry a stable internal diagnostic code owned by this project, and SHALL be justified by a fixture that demonstrates the recovery is unambiguous across consumers.

Permitted recoveries SHALL NOT be derived by collecting whatever a sample of documents happens to produce. A parser version change SHALL require deliberate review of the enumeration before the new version is adopted.

Diagnostic codes are owned by this project

Given
a parser that reports a recovery as free text rather than as a typed code
When
validation reports that recovery
Then
it reports this project's own stable diagnostic code, so a reworded parser message does not change the reported code

Parser rewords a message

When
a new parser version changes the wording of a recovery message
Then
the project's checks fail rather than silently widening or narrowing what documents are accepted

Ambiguous recovery is not permitted

When
a recovery is proposed for the permitted enumeration and no fixture shows it is unambiguous across consumers
Then
the recovery is not permitted

Coarse parser message covering two faults

Given
a parser that reports two distinct faults with one identical message
When
the enumeration is built
Then
it distinguishes the two faults by parser state, or it permits neither

Remote and hidden network dependencies are rejected req-remote-and-hidden-network-dependencies-are-rejected

Validation SHALL reject any document that depends on a resource outside the project. This includes remote scripts, stylesheets, fonts, images, and iframes, and any construct capable of initiating a network request when the document is opened.

Remote script rejected

When
a document references a script by absolute URL
Then
validation fails and reports the reference

Remote font rejected

When
a document's styling loads a font from a remote origin
Then
validation fails

Concealed request rejected

When
a document contains a construct that would issue a network request without a visible remote reference, such as a prefetch directive or a beacon
Then
validation fails

Local asset accepted

When
a document references the project's shared runtime by relative path
Then
validation succeeds

Code examples cannot execute req-code-examples-cannot-execute

Validation SHALL ensure that example code shown in a document is inert. Code presented as content SHALL NOT be capable of executing as part of the page, and SHALL NOT be able to terminate its container and inject markup into the document.

The security property is the absence of element descendants. A code element's children SHALL contain text and comment nodes only. Validation SHALL NOT require exactly one text node, because a parser splits text around a comment and an empty example has no children at all.

Script shown as an example

When
a document displays a JavaScript snippet as an example
Then
validation succeeds and the snippet does not execute when the document is opened

Empty example accepted

When
a code element has no children
Then
validation succeeds, because an empty example carries no element descendant

Text split by a comment accepted

When
a parser represents a code element's content as two text nodes separated by a comment
Then
validation succeeds, because no child is an element

Presentational element inside an example rejected

When
a code element contains a child element, including a purely presentational one
Then
validation fails, because the example is no longer inert text

Container escape rejected

When
an example's content would close its containing element and introduce live markup
Then
validation fails and reports the example

Executable script accepted only from the pinned runtime

When
a document contains an executable script that is not part of the pinned runtime
Then
validation fails

Visualization specifications are validated req-visualization-specifications-are-validated

Validation SHALL check every embedded diagram or chart specification against its own format. An invalid specification SHALL be reported at authoring time rather than failing silently in the browser.

Invalid chart specification

When
a document embeds a chart specification that its format rejects
Then
validation fails and reports the location and the underlying error

Invalid diagram source

When
a document embeds diagram source that cannot be parsed by the diagram library
Then
validation fails

Migration note: as built, a Mermaid diagram is checked only for being non-empty and opening with a recognized diagram keyword, and its diagnostic carries a note that the validation is shallow, so a diagram the library cannot parse passes when it opens with a recognized keyword. The change names this as a gap and defers full validation: see the design's “Visualization sources are visible content, not inert script tags” and its risk “Mermaid diagrams are only shallowly validated”, and task 4.14, which builds the shallow check.
