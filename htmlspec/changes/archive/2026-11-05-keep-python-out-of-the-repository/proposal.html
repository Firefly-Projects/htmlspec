Keep Python out of the repository

The repository's own tools, tests, and checks are 19 Python files and 7,243 lines, plus seven python3 lines in three workflows. This change rewrites each of them in Rust, or deletes it where the Rust crates already do its job, drops python3 from the development shell, the suite's sandbox, and every workflow, and makes the ban a stage of the suite: a Python file outside an exact-path allow-list of four archived data files fails scripts/check, naming the file. It answers the user's three concerns: tests standing in for types, a catch-all language that slows the suite, and scripts nothing governs. The program does not change, and the change archives as 1.3.1.

Keep Python out of the repository

Why

The user asked for this in their own words: "I am inclined to ban all of them and drop the python 3 from the library. It tends to be the case that when we let any python in it is katy bar the door." They named three things to avoid: relying on Python tests instead of solid type definitions, Python as a catch-all that ends in slow suite runs, and disparate, ungovernable scripts all over the place. An explainer they commissioned swept the repository at a11ff12 and measured its suite. The base of this change, 4d0a6fd, differs from it by one run record, and every count below was checked again at the base. The timings are the explainer's and are not measured again here.

What is there today: 19 live Python files, 15 under scripts/ and 4 under publish/, every one standard library only. They hold 117 unittest cases in 4 suites (65 in publish/test, 28 in scripts/check-crate-notices, 19 in scripts/check-publish-crates, 5 in scripts/check-check-formula). They fill 9 of the 18 stages of scripts/check, and all 10 jobs of release.yml run Python, the suite job included. Each of the three concerns holds.

Tests standing in for types

The Rust crates already type the release record: version.rs has one three-part Version and the wrappers ProjectVersion, RunbookVersion, and ToolVersion, and runbook_release.rs gives a content digest its own type. The Python restates the same facts as tuples, strings, and dictionaries, and then tests and fixtures try to keep the restatement honest:

  • Four grammars for one version. Version::parse refuses anything that is not three parts. scripts/check-release's parse_version takes any number of parts, scripts/set-version refuses a leading zero, and scripts/release-notes takes one. Every pair disagrees on at least one input. Python's inventory reader accepts a runbook version of "0.1", which the Rust reader refuses, and none of the 23 cases the two readers share covers a version of two or four parts, so both pass while they disagree.
  • A second reader kept honest by a stage. The runbook-release format has two readers that share no code, so they share 12 JSON fixtures, a manifest of 23 cases, a Python self-test, a Rust test, and the release-fixtures stage. About 350 lines of check-release restate the Rust reader. One Rust test reads check-release's source text and searches it for (0, 1, 0), so reformatting the Python breaks a Rust test.
  • A predicate, then a partial function. publish/publishing.py checks a commit identity with identity_fault, and split_identity matches it again and assumes the match succeeded. It is safe only because the export calls the first 255 lines before the second. AGENTS.md asks for "parsers or smart constructors that return a trusted domain value over predicates that return only a boolean".
  • Lists kept by hand and guarded by tests. CRATES in scripts/release_facts.py names the six published crates in publishing order, and two tests exist only to check it against the manifests, which Cargo already reads. Six functions read Cargo.toml line by line with regular expressions, one of them because tomllib is standard library only from Python 3.11.

A catch-all that slows the suite

The concern holds, though not for the reason it names. The interpreter is cheap: a Python start costs 9.6 ms here. The nine Python stages cost 69 to 83 seconds per suite run, across nine CI runs and laptop passes, and about 57 of those seconds are tests waiting on a real clock. In scripts/check-publish-crates, five tests spend 50.2 of the stage's 58.2 seconds in real waits of at least 10 seconds after an HTTP 429. In scripts/check-prompt, fixed drains and keystroke pauses take at least 7.3 of 8.4 seconds, because the drain loop has no exit for a finished paint. Python does not force those waits, but the script shape pushes toward them: a script has no module boundary, so its tests drive it as a subprocess, and a subprocess runs on the real clock. Where a suite loads its subject in-process, as check-crate-notices does, its 28 cases take 0.03 seconds.

So removing Python will not by itself make the suite fast. In CI, compilation and cargo test dominate, and the Python stages are 7 to 14 percent of a run. On a warm laptop build they are a third of it. What retires the 57 seconds is injecting the clock, which a Rust port with narrow capabilities does as a matter of course.

Scripts nothing governs

  • The scripts live in two directories and run from four places: scripts/check, the workflow YAML, the two runbooks, and each other. They reach each other four ways: eleven files put a directory on sys.path, two load another script by file path, publish/publishing.py reads scripts/check-pull-request's text at a Git ref and runs it with exec, and the rest start processes.
  • Nothing checks the Python. There is no linter, type checker, or formatter configuration and no stage that runs one, while fourteen # noqa comments silence a linter nobody runs. Every Rust file must pass cargo fmt --check and clippy -D warnings.
  • Three scripts on the release path have no test of their own: release-notes, set-version, and all of pack-release but its --sums mode.
  • One rule lives in human memory. flake.nix keeps a hand-written patchShebangs list, and its comment records that a script missing from it "took CI red for five merges".
  • The one reason the repository gives for Python is false. scripts/check says at line 98 that the prompt check cannot be a cargo test because "openpty is an unsafe FFI call". nix 0.27.1 is already in Cargo.lock, through command-group, and its openpty is a safe function behind the term feature, which adds no crate.

What changes

  • One crate for the repository's tools. An unpublished workspace member, xtask/, holds every tool the suite, the workflows, and the release runbook run, as subcommands of one binary under the names the scripts had: cargo xtask check-release, cargo xtask set-version, and so on. rustfmt and clippy govern it like every other crate.
  • The export stays private. Its Rust lives in a Cargo workspace of its own under publish/, which never crosses to the public repository, and publish/export stays the command the publish runbook runs.
  • One reader for each format. The tools read versions, changelog headings, the archive, and the release inventory through the code archival already uses, so the four version grammars become one and the second reader of the runbook-release format, with its release-fixtures stage, is deleted. The workspace is read through cargo metadata, so the hand-kept crate list goes too.
  • Clocks and outside programs are passed in. The publisher takes a clock, a registry, and a cargo, the formula check takes a brew, and the export takes its git and its GitHub, so each test passes a fake and nothing waits on real time or shadows a program on PATH.
  • The ban is a check. A new stage, no-python, fails the suite on any Python outside an exact-path allow-list, and the flake supplies no interpreter, so a script that slips past the stage still cannot run in the sandbox. The accepted contract gains a requirement stating the ban, which the stage enforces, and loses the one scenario that names an interpreter. The requirement also says where tools live: every program the repository runs is built from a Cargo workspace, except four shell files named by exact path, and the stage fails on any other file that begins with #! or carries the executable bit, so the next catch-all cannot be bash either.
  • The runbooks follow. Both declare cargo and rustc to preflight, and no longer python3, and their steps name the Rust tools. Each takes a new release, the publish runbook 0.4.0 and the release runbook 0.6.0.

What working looks like

  1. The flake names no Python package. The development shell adds no python3 to the path, and inside the suite's build sandbox, which the machine's own path does not reach, python3 is not found.
  2. scripts/check --list prints fourteen stages and none of them runs Python. scripts/ holds two files, check and install-hooks, both bash.

  3. A contributor adds scripts/tidy.py to the repository, or a file whose first line is #!/usr/bin/env python3, or a workflow step that runs python3, and runs scripts/check. Once the file is tracked, staged or committed, the no-python stage fails and names each one:

    Python outside the allow-list, which toolchain-packaging's "The repository holds and runs no Python" forbids:
  scripts/tidy.py: a Python file name
  .github/workflows/check.yml:31: runs python3

    Deleting one of the four allow-listed prove-*.py files fails the stage too, saying the path is allow-listed and absent, so the list cannot outlive what it names. So does a new bash script, or a new Git hook: outside scripts/check, scripts/install-hooks, .githooks/pre-push, and publish/export, a tracked file that begins with #! or carries the executable bit fails the stage, whatever its language.

  4. The publisher's tests run on a fake clock and finish in well under a second, and the prompt test waits for the text it expects rather than for a fixed time. No test in the suite sleeps to let something happen.
  5. cargo xtask check-release refuses a runbook inventory entry at version "0.1" exactly as archival does, because both call the same parser.
  6. The release runbook's steps run cargo xtask set-version X.Y.Z and cargo xtask check-release. The publish runbook still runs publish/export, now a launcher of the export's Rust, and its co-owner step takes the User-Agent from cargo xtask facts user-agent. htmlspec preflight on either runbook checks cargo and rustc.
  7. release.yml holds no python3. Its Linux jobs run one tools binary, built once in its first job.
  8. The suite's time is measured before the first pull request and after the last, by the explainer's method, and the change records both numbers against the two goals the user set: no test sleeps on a fixed timer, and the work the nine former Python stages did takes under 10 seconds on a warm laptop build, from 69 to 83 today.

Alternatives considered

  • Lint and type-check the Python. ruff and mypy as stages would answer part of the third concern. They leave every second reader in place, so the first concern stands, and they add a Python toolchain to pin and keep current.
  • Freeze the Python: no new files, keep the 19. The interpreter stays in the shell and in every workflow, the four grammars stay, and so do the 57 seconds. An interpreter on the path is the open door the user described.
  • Keep publish/ in Python because it is private and the largest port. The shell would then keep python3 for the export alone, and the export's own readings of the version and of the pull-request rules would stay second copies of what the public tools read.
  • Port the small tools to bash. Bash has no types and no linter in this suite, so it would rebuild the third concern in another language.
  • Only take the sleeps out of the Python tests. That recovers the 57 seconds and answers neither of the other two concerns.

Scope

  • The program does not change. No operation, flag, exit code, or payload changes, and each channel ships the binary it ships today. The one change to a published crate is a library target on htmlspec-cli that exports three modules the tools read, hidden from its documentation, and 1.3.1 puts it on crates.io for the first time.
  • Bash stays in four files, named by path. scripts/check, scripts/install-hooks, and .githooks/pre-push stay bash, and publish/export becomes a few lines of bash that start the Rust. No other shell script or hook is permitted.
  • Prose about Python is not Python. The changelog's history, archived changes, run records, and fixtures are left as written. The README's build requirements and its workflow table change, because they describe what the repository needs. Its advice to readers to serve documents with python3 -m http.server names a tool on the reader's machine that the project never runs, so it stays.
  • Four data files stay. Two archived evidence scripts and their two copies in the migration fixture are data that nothing runs, and an allow-list keeps them by exact path.
  • No new published crate, and no speed gate. The suite's time is measured against its two goals and never gated, so a slow machine fails nothing.
  • No publish run. Publishing 1.3.1 is a run of the publish runbook, with the user's go at each public step.
  • No contributor's machine is policed. The ban covers what the repository holds and runs, not what is installed beside it.
