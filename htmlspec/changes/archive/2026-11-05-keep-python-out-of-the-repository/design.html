Keep Python out of the repository: design

How the repository stops running Python. Every public tool becomes a subcommand of one unpublished crate, xtask/, run as cargo xtask, and the export's Rust lives in a private workspace under publish/, which never crosses. The tools read each format through the code archival already runs, by way of a library target on htmlspec-cli hidden from its documentation, so the four version grammars become one. Clocks, registries, and outside programs are passed in as capabilities, so no test waits on real time or shadows a program on PATH. A no-python stage with an exact, typed allow-list enforces the ban, and the flake stops supplying an interpreter. The work lands as six pull requests that each keep main green, and the change archives at 1.3.1.

The shape of it

Today the tools are 19 Python files in two directories, reached from scripts/check, from the workflow YAML, from two runbooks, and from each other. Afterwards there are two Rust homes and one rule:

  • The public tools are one crate, xtask/, beside conformance/ as the workspace's second unpublished member. The suite, the workflows, and the release runbook run cargo xtask TOOL. The release workflow runs the same binary, built once for each platform that needs it.
  • The export is a workspace of its own, rooted at publish/, depending by path on xtask. publish/export stays as the command, now a few lines of bash that start it.
  • The rule is a stage, no-python, and the absence of an interpreter in the flake.

Where each file goes

Every one of the 19 has a Rust home. Two things are deleted outright, because the Rust crates already do their job: the second reader of the runbook-release format inside check-release, with the release-fixtures stage, and the hand-kept crate list in release_facts.py, with the two tests that guard it. The bash scripts/check-formula is ported as well, so that its tests can pass a fake Homebrew rather than shadow the real one.

Decisions

1. One tools crate, xtask/, run as cargo xtask

A new workspace member at xtask/, the package htmlspec-xtask, with publish = false, [lints] workspace = true, and no build script. Each tool is a module with a pure core and a thin edge, and a clap subcommand of one binary, xtask. The root manifest's members gains "xtask", and the manifest gains default-members = ["crates/*"]. .cargo/config.toml holds one alias, xtask = "run --quiet --locked -p htmlspec-xtask --". cargo xtask TOOL builds and runs it from the repository root, or from any directory beneath it that belongs to the root workspace, and every place that runs it runs from the root: scripts/check, the workflows, and the runbooks' steps.

The third concern is governability, and one crate is one place to look. It has one formatter, one linter at -D warnings, one module tree a reader can follow, and an interface in its subcommands where the scripts have sys.path, SourceFileLoader, and exec. It sits beside conformance/, the workspace's existing unpublished member, and outside crates/, where every crate is published.

Rejected: a crate for each tool. That is a dozen manifests, and helpers copied between them, which is the copy problem again. Rejected: a member under crates/. It would read as published, and every list of published crates would have to exclude it by name. Rejected: the tools as hidden subcommands of htmlspec. The surface records every command the parser accepts, and toolchain-packaging's "The command surface is stable within a major version" would make each one permanent in 1.x.

No default build reaches the tools crate. With default-members = ["crates/*"], a plain cargo build, cargo build --release, or cargo test at the root builds the six published crates and nothing else. It builds neither the tools crate's library and binary nor their dependencies, nor conformance, which a default build compiles today though nothing ships it. Every command that must reach every member already says so: scripts/check's cargo fmt --all, clippy --workspace --all-targets, and its two cargo test --workspace stages, verify's cargo publish --workspace --dry-run, and the build job's -p htmlspec-cli. cargo run --bin htmlspec, which the self-* stages run, finds the binary among the default members, and the README's cargo build --release still builds it. The Nix package builds the default members, so it compiles what it compiles today less conformance, and its output tree is compared before and after. The suite's derivation reuses a dependency derivation, which may now cover only the default members. Task 1.4 measures whether the tools crate's own dependencies compile in the suite instead, and gives the dependency derivation --workspace if they do.

Measured while it was built: the dependency derivation never served the suite. crane's buildDepsOnly builds in the release profile, and every stage of scripts/check builds in the dev profile, so the suite's derivation compiled every dependency itself before this change as well as after it. At the base, the log of check.yml's run 41145897950 shows 255 crates compiled by the dependency derivation and 247 by the suite's. After task 1.4, a local nix flake check shows 249 and 240, and the run of check.yml on pull request 99, 41161720770, shows 250 and 241. The suite's crates include clap, sha2, and pretty_assertions, as they did before. Narrowing the dependency derivation to the default members moves no compilation into the suite, so it does not take --workspace: it serves the package, which builds the default members. Making it serve the suite as well would be a change of its own, and this one does not make it.

Rejected: required-features on the binary, as conformance's generate_fixtures has. It keeps the binary out of a default build, but not the library or the dependencies the library pulls in, such as clap and the packer's archive crates. default-members keeps out both, and leaves the binary within reach of --all-targets, so clippy lints it and test builds it, with no feature to name in the alias.

Not inside publish/. publish/ is a workspace of its own (decision 3). Inside it, cargo resolves publish/Cargo.toml, where htmlspec-xtask is not a member, and refuses the alias. A --manifest-path in the alias would be read against the current directory and break everywhere else, because an alias has no path relative to the file that declares it. So the alias stays as written, and the rule is that tools run from the root. The runbooks' steps already run there, and publish/export finds its own workspace by its own path, so it runs from anywhere.

2. scripts/ keeps its shell, and every other tool keeps its name as a subcommand

scripts/check stays the suite's one command, and scripts/install-hooks stays the hook installer. Both are bash. Every Python script becomes cargo xtask followed by its own name, check-release, set-version, release-notes, pack-release, render-formula, crate-notices, publish-crates, check-readme-install, check-installed, or check-pull-request. The bash check-formula becomes cargo xtask check-formula, release_facts.py becomes cargo xtask facts, and the ban adds cargo xtask no-python. Nothing is left at the old paths.

Because the names stay, a reader maps every old command to its new one by the prefix alone, and the runbooks, the README, the workflows, and the Rust comments that name a script all change by the same rewrite. Launchers at the old paths would leave those texts alone, but they would give every tool two names, and a directory of launchers is the scattered shape the user asked to be rid of. publish/export is the one exception, for the reasons in decision 3.

3. The export's Rust is a private workspace rooted at publish/

publish/Cargo.toml declares its own [workspace] and one package, htmlspec-publish, with publish = false, one binary, export, and the scan as a module the export calls. It keeps its own publish/Cargo.lock and depends by path on ../xtask for what the public tools already type: the version, the facts, the workspace reader, and the git plumbing they share. publish/export stays as a bash launcher that runs cargo run --quiet --locked --manifest-path on the workspace beside it. publish.yml installs the pinned toolchain and runs cargo test --locked --manifest-path publish/Cargo.toml.

toolchain-packaging's "The public repository receives only reviewed exports of the private one" requires that "The publishing tooling, its allowlist, rewrites, pattern file, and tests, SHALL stay in the private repository and SHALL be absent from every export". A workspace of its own leaves no trace in the public tree: the root manifest names no member under publish/, and the root lockfile names none of its packages, so the public tree builds as it does today. The launcher keeps three things that read the path. .githooks/pre-push recognises the private repository by whether publish/export exists, at line 87. The publish runbook's steps run it. And the runbook's "The public repository is reached only through the export and the API calls the steps name" names it.

Rejected: a member of the root workspace, removed from the export by a rewrite. The public tree's Cargo.lock would then differ from every lockfile a private run tested, and --locked refuses a lockfile that names a package the workspace lacks. Rejected: the export inside xtask. It would cross, and its tables of what to guard against would cross with it. Rejected: a separate repository for the export. The allowlist, the readiness record, and the tool that reads them would stop changing in one pull request.

Two lockfiles can disagree. publish/Cargo.lock starts as a copy of the root lockfile, relocked offline, and a test in the private workspace fails when a package both lockfiles name resolves to different versions in each. cargo xtask set-version relocks publish/Cargo.lock too, where it exists, because the private workspace reaches the six crates' exact pins through xtask. The first task of that pull request proves that a path dependency on ../xtask, whose manifest inherits from the root workspace, builds from the private workspace, before the port builds on it.

The title rules stay the ref's own. Today title_faults runs scripts/check-pull-request's text as it stands at the ref, because the public guard runs the copy inside the exported tree. After the port, the export builds the exported tree in its scratch repository, as it does now, and runs that tree's own xtask check-pull-request on the title there, before it commits anything. It shares a target directory with the suite it then runs inside the same tree, so the build is paid once. A ref whose tree has no such subcommand states no rules, and the export refuses it, as the requirement says. That includes every ref from before the port, which the publish runbook never exports, because it exports origin/main. The export reaches that tool through its command-runner capability, so a test's synthetic source repository needs no buildable workspace: the fake runner applies a rule the synthetic ref states, and records which tree it was asked to run in. The dry run against this repository's own head, before the Python export is deleted, runs the real build once.

The exported tree is staged before the suite runs in it. Today the export extracts the tree into a fresh git init repository, runs scripts/check there (lines 463 to 466 of publish/export), and only then runs git add -A, so the scratch repository's index is empty while the suite runs. The no-python stage chooses its files by the index (decision 9), and against an empty index it would read nothing. So from the first pull request the export stages the exported files before it runs the suite, and stages again afterwards, as it does now, before it writes the tree. The tree it writes and reviews is unchanged. The Rust export keeps the order.

The export reads files out of the ref with git's own plumbing (ls-tree, cat-file, and checkout-index into the scratch tree) rather than through git archive and a tar reader, so the private workspace needs no archive crate. It reads the ref's declared version with cargo metadata --no-deps --offline on that scratch tree, the one manifest reader the tools share. Both are my choices.

4. One reader for each format, through a library target on htmlspec-cli hidden from its documentation

htmlspec-cli gains src/lib.rs, under a crate comment saying the library exists for this repository's tools and promises no stability. It holds the binary's modules, with the parser and the dispatch of main.rs behind one entry point, and exports only version, runbook_release, and project, each #[doc(hidden)] pub, as decision 22 settled. Every other module stays private, and main.rs shrinks to a call of the entry point. The tools read through it:

  • Versions. Version::parse is the one grammar. Release tooling takes a ReleaseVersion: a Version whose text is its own canonical rendering. It refuses "01.2.3" and "1. 2.3", as set-version does today, without changing what the program accepts in a spec.nix or a runbook's VERSION.
  • Changelog headings. runbook_release::changelog_headings. staging.rs's release_record_versions carries its own copy of dotted_numbers, and becomes a call to the same reading.
  • The archive and the inventory. Inventory, Adoption, ContentDigest, and the history, read through runbook_release.rs, the code archival runs.
  • A change's recorded version. project::RECORDED_VERSION, read as a ProjectVersion.

The 23 shared cases stay in fixtures/release/ as test data for the one reader, and gain cases at a two-part and a four-part version. The Rust test that "keeps two implementations of one format honest" becomes an ordinary test of it. tests/migrate.rs's check that reads check-release's source for (0, 1, 0) checks the Rust baseline constant instead.

The user asked for solid type definitions instead of tests, and the types exist already. What is missing is a way for a second program to call them. Two readers have cost a stage, 12 fixtures, two self-tests, and a comment at line 184 of runbook_release.rs claiming the two "cannot disagree", and they disagree.

Rejected: a seventh published crate for the shared modules. It would be a new crate on crates.io, a new co-owner step, and a new entry in every list, for code nobody outside this repository uses. The ratchet. The stage lands in the first pull request, before any tool moves, with a list of debt: each live Python file, and each workflow, flake, and runbook file that still names Python. A finding in a debt file is excused only by an entry that pins the file, in one of two ways:

  • A Python program, a file that is a finding as a whole by its name or its first line, is pinned by the SHA-256 of its content and by a ceiling, its line count when the ratchet began. The stage fails when the content differs from the pin, and refuses an entry whose file holds more lines than its ceiling.
  • A file that names Python on some of its lines is pinned by the exact text of each such line. A new line naming Python fails, a changed one fails, and a removed one fails as a stale pin.

So the guarantee is exact. No byte of a Python file changes unless its entry changes in the same commit, no Python file grows past its starting size, and no other file gains a line that names Python. What an edit inside those bounds does, such as deleting dead code, or the one-line change task 1.5 makes to the export, is for the review that sees the entry change. The failure message prints the entry the file now has, for a reviewer who means the edit. A finding count alone would not have been enough: a Python file is one finding however much it holds, so Python added inside a debt file would have passed. Each pull request removes the entries it pays, and the last one deletes the debt type with its last entry, so debt cannot come back without a visible change to the code. That is how the user's order, "delete the Python and turn on the ban", is kept while no new Python enters from the first commit.

The stage reads the flake's source in the sandbox and the index everywhere else. If the two ever disagreed, the stage would pass in one place and fail in the other, the divergence toolchain-packaging's "Project checks are runnable as one command" exists to prevent. An index that does not cover the tree, as the export's was until this change, would make the stage read nothing.

The flake's source is the tracked tree, so the two ways name the same paths. They can differ on a mode in a dirty tree, where Nix copies the working tree's and the index records the staged one, so in a checkout the stage counts a file executable when either says so, and the two refuse the same files. The stage fails closed: with neither a source tree nor a repository, it fails rather than passing. The pins make an empty read fail too: a debt entry or an allow-listed path the stage cannot find fails it as stale or absent, so a read that saw nothing cannot pass while debt remains. Each pull request's export rehearsal runs the stage inside a freshly staged exported tree. Task 1.7's check shows the sandbox reads files the old filter excluded.

A pin is updated to bless an edit that adds Python

A content pin makes every edit to a Python debt file update its entry, and an entry can be updated for an edit that swaps old Python for new within the file's starting size.

Accepted, and held as far as a check can. The ceiling stops a debt file from growing, and the entry change is in the same diff as the edit, so a reviewer sees that a Python file changed and by how much. Edits to the Python during the port are few and named in the tasks: task 1.5's staging line, and task 2.3's read of the facts file. A check cannot tell a deletion of dead code from a rewrite of the same size, so this part rests on the one review each pull request takes.
