Keep Python out of the repository

The contract this change leaves: the repository holds and runs no Python, every program it runs is built from one of its Cargo workspaces but four shell files named by path, and neither the development shell nor the suite's sandbox supplies an interpreter, which the flake checks of each before anything else runs. The no-python stage of the check suite holds it, with an exact allow-list. One accepted scenario that named the shell's interpreter is withdrawn, and the release refuses a tag naming another version before it builds anything the release ships. The program's surface does not change, and the project archives at 1.3.1.

toolchain-packaging

The repository holds and runs no Python req-the-repository-holds-and-runs-no-python

The repository's tools, tests, and checks SHALL run no Python interpreter. No file the repository tracks, outside the allow-list, SHALL be a Python program, by a Python file name or by a first line that runs a Python interpreter. No file that runs SHALL name a Python interpreter, or a launcher that runs one, in any case: a workflow, a composite action, a shell script, a Git hook, Cargo's configuration, a Nix expression, a Makefile, a justfile, .envrc, a Dockerfile, or a pre-commit configuration. No runbook's preflight declaration SHALL name one as a tool, and no Rust source SHALL start one through Command::new.

Every program the repository runs SHALL be built from a member of one of its Cargo workspaces, except four shell files: scripts/check, scripts/install-hooks, .githooks/pre-push, and publish/export, each of which SHALL begin #!/usr/bin/env bash. The check suite SHALL fail on any other tracked file that begins with #!, carries the executable bit, bears a shell script's name, or sits under scripts/, and on any other tracked file that a file that runs hands to a shell or an interpreter to run.

Only an allow-list SHALL excuse what the check suite finds, and it SHALL name each exempt path exactly, never a prefix, with the reason it stays. It SHALL admit the archived evidence and survey fixtures that are data nothing runs, which SHALL never carry the executable bit; the three permitted shell files that cross to the public repository; and, by its exact text, the one line of flake.nix that asks whether the suite's sandbox or the development environment supplies an interpreter. That line SHALL be excused once, for the names it asks about and for no other finding, and the same text in another file, or a second time, SHALL be a finding. publish/export never crosses, and SHALL be permitted by a list that never crosses either, publish/no-python, which SHALL permit it and nothing else. An allow-listed path or line the tracked files no longer hold SHALL fail the check suite.

Neither the development environment nor the build sandbox the check suite runs in SHALL supply a Python interpreter, and the flake SHALL fail a build where either resolves one, printing where: the suite's derivation before the suite runs, and a check built with exactly the development environment's packages, and nothing of the machine's, on its search path.

The check suite SHALL read every tracked file, the flake's source in the build sandbox and Git's index elsewhere, each as the working tree holds it, and no untracked or ignored file. It SHALL fail on each violation, naming the file, the line where there is one, and what in it is Python or a program, and SHALL fail rather than pass where it cannot tell tracked files from anything else.

What the check suite SHALL refuse is what an ordinary edit adds: a new file, a new first line, a new step, a new stage, a new hook, a new input to the flake, a new Command::new, and a script handed to a shell by its tracked path. A handoff a reader cannot see without running the line is outside what it SHALL refuse, and is left to the review each pull request takes: a program named through a variable, a computed value, or a workflow expression; eval of a string the line builds; a Rust program named by anything but a string literal; a file that is not tracked when the suite runs; and Python inside a container image or a fetched artifact. Prose SHALL NOT be a finding: Markdown, the changelogs, run records, HTML other than a preflight declaration, YAML that neither runs nor is a workflow or an action, and a Rust string that no Command::new takes. The requirement covers what the repository holds and runs, and no contributor's machine.

A release reaches every channel from one tag req-a-release-reaches-every-channel-from-one-tag

Every release SHALL be cut from one tag, vX.Y.Z, whose version equals the version the workspace declares, and the binaries, the crates, and the Homebrew formula the release produces SHALL each name that version. The release SHALL refuse a tag that names another version before it builds anything the release ships.

Publication SHALL begin only from a version tag in the public repository, Firefly-Projects/htmlspec, only for a commit that repository's main holds, and only after the check suite has passed on that commit. A tag in any other repository SHALL publish nothing. A release SHALL publish only from a run in which the binary of every target it releases was built and the formula passed its check, though runs elsewhere leave some of those jobs out.

A publication interrupted partway SHALL finish when run again, and SHALL NOT publish any version twice: the crates publish one at a time, a version the registry already holds is skipped, and a rate limit is waited out within a stated budget, after which the run stops and names the crates that remain. Every request the release makes to crates.io SHALL carry a fixed User-Agent that names the project, and no personal information.

Each channel that ships the binary SHALL ship its notices with it: each release tarball holds them beside the program, the Homebrew formula installs them, and the Nix package installs them under share/doc/htmlspec/. The formula SHALL declare exactly the licenses the binary credits. The check suite SHALL fail when CRATE-LICENSES differs from what the lockfile reaches, naming each crate added, removed, or changed, and when the formula's template declares other licenses than the binary credits, so a pull request that changes either meets it, on Linux as well as where the macOS jobs run.

A release SHALL become the repository's latest, the release releases/latest names, only when its version is the highest among the repository's published releases, and only that release SHALL reach the Homebrew tap, whose formula holds one version. A release on an older line SHALL NOT be made the latest, and its run SHALL leave the tap as it was.

After a release that is the repository's latest is published, its workflow SHALL install it through the README's documented Linux commands, verbatim, on both Linux targets, and through the README's Homebrew-on-Linux commands once the formula is in the tap. The run SHALL fail when an installed binary does not name the tag's version. A release on an older line SHALL be reported as untested by the Linux commands, not failed, and the Homebrew commands SHALL not run for it.

The check suite SHALL hold the README's install and upgrade commands without the network: each marked install or upgrade block SHALL parse, each upgrade block the README gives SHALL be present and marked as an upgrade block, no upgrade block SHALL be run, the Linux block SHALL check its download against SHA256SUMS before it unpacks or installs it, SHALL ask only for a target the release builds, and SHALL read SHA256SUMS as the release writes it.

What was built

The repository's tools are Rust. The nineteen Python files of 1.3.0, fifteen under scripts/ and four under publish/, and the bash scripts/check-formula are gone. The public tools are the subcommands of one unpublished member, xtask/, run from the root as cargo xtask TOOL through .cargo/config.toml's alias, with the pull-request rules in a member of their own, xtask/pull-request. The export is a workspace of its own under publish/, which never crosses, and publish/export is a launcher of it. The tools read versions, changelog headings, the archive, and the runbook inventory through a library target on htmlspec-cli that exports three modules hidden from its documentation, and the workspace through cargo metadata. Their clocks, the crate index, cargo, Homebrew, git, and GitHub are values their tests replace. scripts/ holds check and install-hooks, and the suite has 14 stages.

The ban is the no-python stage, cargo xtask no-python, which holds req-the-repository-holds-and-runs-no-python. Its allow-list is the typed constants ALLOW_LIST, the four archived data files and three shell files by exact path, and ALLOWED_LINES, the one line of flake.nix, both in xtask/src/no_python/allowed.rs; publish/no-python permits publish/export. The debt that pinned the Python while the port removed it, xtask/python-debt and its reader, is deleted.

The flake supplies no interpreter. The development shell and the suite's derivation lost pkgs.python3, and the flake states one question, if command -v python3 || command -v python; then, which prints what it found and exits 1. The suite's derivation asks it before the suite, and a check, shellHasNoInterpreter, asks it in place of the development shell's own build phase, so it builds with exactly the shell's packages on its search path; check.yml builds it beside the suite. The form the tasks first named, each lookup negated with ! and joined by &&, never fails under the set -e a Nix build phase runs under.

The runbooks' requirements changed in the runbooks. A runbook's specification is its own contract, so each changed there, in the pull request that moved it, and takes a release. The release runbook, at 0.6.0: req-the-version-moves-with-its-pins is "The version moves only through the tool that moves its pins" and names cargo xtask set-version and cargo xtask check-release in its statement, its prose, and its scenarios; req-the-pinned-toolchain-is-what-runs names cargo and rustc, its declaration's tools are ["cargo","rustc"], the paragraph that explained declaring python3 and the scenario of an interpreter outside the shell are withdrawn, and the risk that the inputs are prose counts no interpreter. The publish runbook, at 0.4.0: req-the-pinned-toolchain-is-what-runs changed as the release runbook's did; req-the-tag-names-the-public-merge-commit-and-the-archived-version names the release check's --tag mode, xtask check-release --tag, in its prose and its scenario "A tag naming another version". The publish runbook's req-the-public-repository-is-reached-only-through-the-export-and-the-api and the release runbook's req-version-before-regenerate are unchanged. Both runbooks' tasks documents name the Rust tools.

The probe runner's deadline is read from a clock passed in, so the preflight host's two tests of a real child, stopped at the deadline and cancelled while it runs, wait no real time. The binary passes the monotonic clock, as before.

What the contract leaves as it was

The design's contract table names each accepted requirement the change reaches. Beside the three this specification states, these hold as accepted, and the change was built inside them.

toolchain-packaging's req-project-checks-are-runnable-as-one-command: scripts/check is still the one command, every stage reads the working tree, and the stages' names stay distinct. Its "Every file a stage reads SHALL be present in that snapshot" is why the suite's derivation receives the whole tracked tree, and why the ban reads the flake's source there. req-a-development-environment-is-provided: the shell still supplies the compiler, the test runner, and the project's tools, which build with the compiler; it lost python3 and gained curl. req-the-public-repository-receives-only-reviewed-exports: the export's Rust, its allowlist, rewrites, pattern file, and tests stay in the private repository, and the title rules the export holds a pull request to are the exported tree's own, now built from it. req-the-command-surface-is-stable-within-a-major-version: no operation, flag, or exit code changed, and every payload keeps each field's name, type, and meaning. One reading changed, for malformed input alone: htmlspec migrate survey's greatestVersion and sharedVersions order and group recorded versions as archival reads them, so a VERSION of four parts is no longer the greatest, 01.2.3 and 1.2.3 are one shared version, and a VERSION that is no version is listed among those that record none. A library target is not command surface. req-the-project-records-what-changed-in-each-version-it-ships: the changelog has a 1.3.1 entry.

project-bootstrap's req-archival-requires-the-project-version-to-advance: spec.nix moves to 1.3.1 at this archival. req-archival-checks-the-versions-of-runbooks-it-publishes: each runbook whose canonical documents changed took a greater release, with a changelog heading. req-the-release-suite-checks-published-runbook-version-history: cargo xtask check-release asks it, through the code archival runs.

The contract is silent on the language the tools are written in beyond what the new requirement states, on where they live inside the Cargo workspaces, on how they are invoked, on the workflows' shape, on the test framework, and on how long the suite takes. The design decided each.

Risks

A handoff the stage cannot see risk-a-disguised-handoff

A contributor who means to hide Python can: a program named through a variable or a workflow expression, a constructed eval, a Rust program named by a constant, a file a step downloads, or a spelling no word on the line names. Accepted, because a check that chased every spelling would never end and would refuse ordinary work on the way, and req-the-repository-holds-and-runs-no-python leaves these to the review each pull request takes. For Python itself in the sandbox, the missing interpreter holds the variable-named case: the script cannot start there.

The pinned toolchain ships scripts that name Python risk-the-toolchain-ships-scripts-that-name-python

Five helper scripts of the stdenv's clang, analyze-build, hmaptool, intercept-build, run-clang-tidy, and scan-build-py, sit on the development shell's search path, and gettext's spit is in the suite derivation's closure, each beginning #!/usr/bin/env python3. In the sandbox none can start, because no interpreter is there; in the shell, one run by hand would reach a machine's own python3 after the shell's entries. Accepted, because they come with the compiler the flake pins and no file the repository holds runs them, which is what the requirement covers.

A tag naming another version is refused before anything the release ships is built verify-the-tag-is-refused-before-the-release-is-built

a_tag_that_does_not_name_the_declared_version_fails holds cargo xtask check-release --tag to refusing a tag that names another version than the workspace declares, naming both. In release.yml, verify builds the tools crate and runs that check before any other job starts, and build, sums, and release each need verify, directly or through another job, so a refused tag stops the run before a binary, a crate, or the formula is built. Pull request 104's run of the workflow, labelled release-check, passed verify, plan, the four builds, sums, and formula.

No version tag ran in this change, so the refusal was not seen on a tag's own run; the first tag the reshaped workflow meets is v1.3.1.
