Release a repository that is its own project: design

How the release runbook's regeneration step stops removing the project, how it describes the version htmlspec archive records, which other statements are corrected and which are kept, and why the runbook is released as 0.2.0 and the program as 0.30.2.

Subject
Release a repository that is its own project: design

What this settles

evidence/the-runbook-read-against-the-project-2026-10-14.md lists every statement of the runbook that is false for the repository as it stands, and every one that holds. One is destructive: the regeneration step's removal, and the requirement that makes it a MUST. One describes the OpenSpec workflow's archival rather than htmlspec archive's. The rest are statements of fact that are no longer true. The procedure stays four steps in the same order, and the program does not change.

Decisions

1. The regeneration step removes nothing, and stops when init did not extend the project

task-regenerate-the-instructions keeps everything it says about the regeneration itself: this repository's set of tools and not all, never a no-op after the version advances, and regenerated through the command rather than by editing the stamp. Its last two sentences, which tell a run to remove htmlspec/ and spec.nix and name self-assets as the stage that catches them, are replaced. The step says to run init from the repository root, and to remove nothing afterwards. It names what init reports when it extends this repository's project and what it reports when it does not, says to compare what git status lists after init with what it listed before, so that the only new paths are the installed files under .claude/, .codex/, and .pi/ and any asset init reports establishing in the store, and says to stop the run if init reports that it created a project or any other path is new. Then scripts/check runs, as it did.

The measurement found nothing to remove. In the project, from the root, init reports extending the project in the root and spec.nix already exists, so it was left as it is, and changes nothing outside the installed files. project-bootstrap's "Bootstrapping is repeatable without loss" requires exactly that of a project it already established. What remains is init not standing in the project, from another directory or with the project missing. Then it reports created the project structure and declared the project at version 0.0.0, and writes a second project where it ran.

The run stops there rather than removing what init made. By name, what it made is htmlspec/ and spec.nix, the project's own names. Only whether git tracks a path tells the two apart, and a step that deleted on a check a run makes by hand is the kind of step this change exists to remove. Everything init writes in that case is untracked, so git status lists it, and nothing of the project is lost by leaving it for a person.

The report and git status are both named, so the step does not rest on init's wording alone. If the wording changes, the status still lists a new path outside the installed files, and the step says to stop on that too.

Amended 2026-10-14, from the code review. The step first said to stop on any change git status showed outside the installed files, and that holds on every run: the step before it leaves Cargo.toml and Cargo.lock changed and uncommitted, and the change being released can be uncommitted too. So the step compares the listing after init with the listing before it. In the project, init writes nothing outside the installed files except an asset the binary pins and the store lacks, which it reports as established so many shared asset(s) in the store. That is a write the project wants, and stopping on it would stop every release that ships a new runtime asset, so the step expects it. A path already listed before is not compared again, and in the project init rewrites no such path outside the installed files.

self-assets is no longer named. Measured, it passes after the removal 0.1.0 prescribes, and it passes after init establishes a new project. The step says to run the whole suite, and says which stages read the project: the release stage and the self-runbooks stages, each of which exits 2 with the project gone.

2. The inverted hazard is a new requirement, and the one it replaces is removed

The specification loses req-init-bootstraps-a-stray-project, "Regenerating inside this repository leaves a stray project behind", with its two scenarios. It gains req-regenerating-leaves-the-project-in-place, "Regenerating inside this repository leaves its project in place": a run MUST regenerate from the repository root, MUST NOT remove htmlspec/ or spec.nix, and MUST stop rather than continue when the regeneration changed anything but the installed instruction files. Its three scenarios are the ones measured: the 0.1.0 removal followed, init in the project, and init from another directory.

runbook-authority's "A runbook records what its history taught" requires the hazards a procedure has met to be stated as requirements rather than as remarks. The hazard this procedure has met at this step has turned over. It was a stray project that had to be removed, and it is now a project that must not be. Rewording the old requirement in place would keep its identifier for the opposite obligation, so a reader holding the identifier would hold the wrong one. A new identifier says the obligation is new.

The old requirement's history is kept where history belongs. evidence-nine-duplicate-assets stays, retold in the past tense as what the repository did before 0.29.0, and refers to the new requirement as the history behind it. A new evidence unit records the measurement of the removal against the project. verify-the-stray-project verified the removed requirement, and it is replaced by a verification of the new one.

3. The recorded version is written by htmlspec archive, from spec.nix, raised to the workspace version

req-the-recorded-version-waits-for-archival keeps its identifier and its title, "The change's recorded version is written at archival". Its statement becomes: a run MUST NOT write the VERSION file beside the change's documents itself, MUST raise spec.nix at archival to the version it set in Cargo.toml, and MUST leave the release check's question about the archived version open until archival has run. It gains a scenario for spec.nix raised to another version, and its verification, verify-the-recorded-version-cannot-be-early, gains the archival rehearsal that checks both. task-confirm-the-release-check says the same in its note.

The obligation the identifier names holds: the recorded version still waits for archival, because the directory it goes in does not exist until then. What changed is who writes it. Under the OpenSpec workflow a run wrote it by hand, and under htmlspec archive the program writes it from spec.nix, as archive.md says: archival "records the declared version in a VERSION file". So the identifier is kept, and the text says who writes it.

The version is declared twice. Cargo.toml's is what the binary reports and what scripts/check-release reads as declared. spec.nix's is what archival compares and records. Nothing compares the two. The contract is silent on whether they must agree, so this preserves what exists: each of the three releases since promotion advanced Cargo.toml during implementation, left spec.nix to archival, and raised it there to the same version. The runbook requires that of a run, as its own requirement and not the project's.

Raising spec.nix is not a fifth step. The archive workflow's step 3, "Advance the project's version", is where a contributor does it, and the runbook's last step already waits for archival. Naming it there keeps the procedure the four steps its documents say it is.

4. Every statement the evidence found false is corrected, and every other one is kept as it was

Corrected: the specification's masthead, which names the second hazard; the tasks document's input "A repository that is not already an html-spec project", which becomes a repository whose project is in place; risk-the-inputs-are-prose, whose inputs include the same and whose mitigation says the pinned shell supplies all four inputs; the count of the release check's questions in task-confirm-the-release-check and verify-the-increment-is-not-derived; and risk-this-runbook-goes-stale, which gains what happened. Kept word for word: the other two steps, the other four requirements and their scenarios, both decisions, the first evidence unit, and the other three verifications. The tasks document's masthead, the history of the five releases before 0.1.0, and the 0.1.0 changelog entry are kept, because they describe the procedure as it was and direct nothing.

The risk about inputs is corrected rather than extended. Its claim that the shell "supplies all four" was false when it was written: flake.nix's development shell lists no python3. Its "Not mitigated" was overtaken by the same release, whose preflight declaration checks the toolchain before a run starts. The correction says those two things and no more. That the system python3 on macOS fails inside the shell is recorded in the evidence and left to a change of its own.

risk-this-runbook-goes-stale said a step that becomes unnecessary would go unreported. What happened is worse, and it is the history this runbook exists to keep: promotion made a removal step into one that removes the project, and nothing reported it. govern-this-repository-from-htmlspec found it by reading.

5. The runbook is released as 0.2.0, and the program as 0.30.2

htmlspec/runbooks/release/VERSION becomes 0.2.0, and CHANGELOG.md beside it gains a ## 0.2.0 entry, newest first, naming the project release that publishes it and stating what the release does not do. The workspace version becomes 0.30.2, relocked offline, with a CHANGELOG.md entry saying the program is unchanged, and the installed instruction files are regenerated by the runbook's own revised step. spec.nix waits for archival.

project-bootstrap's "Archival checks the versions of runbooks it publishes" refuses changed canonical documents without a strictly greater version, and does not choose the increment. The choice is mine. It is a minor, because a run of 0.2.0 does something at the regeneration step that a run of 0.1.0 did not, and a requirement is replaced by one with the opposite obligation. A patch would say this is the same procedure reworded, and a runbook carried to another machine has only its version to say which procedure it is. Below 1.0 the minor is the largest increment that claims no stability the runbook has not shown.

runbook-authority's "A runbook carries an independently checked release version" asks the changelog for "a reference to the source project release when published through a project archive". That is 0.30.2, provided govern-this-repository-from-htmlspec is archived first at 0.30.1, as the FOLLOWS file says.

The program's increment follows the predecessor's reasoning. project-bootstrap's "Archival requires the project version to advance" and toolchain-packaging's "An archived change records the version it shipped in" need a new, distinct version for each archival, and none exempts a change that leaves the program alone. A patch is the smallest increment archival accepts.

6. The revised runbook is checked by everything short of running it

Both documents are validated under default and strict strictness and checked for canonical form; the self-runbooks stages run as scripts/check runs them; htmlspec preflight release runs inside and outside nix develop; and htmlspec run release --check runs, followed by git status to show it wrote nothing. Archival is rehearsed in a scratch copy: the predecessor archived at 0.30.1 and then this change at 0.30.2, once with the runbook at 0.2.0 and once with its version left at 0.1.0, and scripts/check-release run on the result.

htmlspec run release --as … is not run. It writes a record under the runbook's directory, which runbook-execution's "A run leaves a record where the runbook keeps them" treats as a run that happened, and no release is performed here. This change's own release uses the revised regeneration step, and that use is recorded in the tasks, not as a run of the runbook.

Risks

The predecessor is archived in a tree that holds this change's runbook

This change is stacked on govern-this-repository-from-htmlspec, which is not archived. Archived in a tree that already holds this change's edits, it would publish release at 0.2.0 under 0.30.1, its task 5.2 would record the wrong version, and this runbook's changelog would name the wrong project release.

The FOLLOWS file makes htmlspec list show the order, and makes archival of this change report a predecessor that is not archived. Nothing stops the predecessor's archival from reading this change's runbook. The rehearsal in the tasks archives in the right order and records what each archival publishes, and the order is stated in this change's report.

Nothing compares spec.nix with Cargo.toml

The runbook now requires a run to raise spec.nix to the workspace version, and that is still prose a run follows. An archival with the two different records a version the binary does not report.

Partly held down. scripts/check-release wants a changelog heading for every recorded version and for the declared one, so a mismatch fails the suite unless a heading names both versions. The rehearsal checks this. A check comparing the two is a change to the repository's scripts, and this change makes none.

A copy of 0.1.0 still says to remove the project

A copy carried elsewhere, or a run record made from 0.1.0, keeps the removal step. The change bears this. A copy names its version, 0.1.0, and the 0.2.0 changelog entry says what changed and why. The runbook's directory holds no run record.
