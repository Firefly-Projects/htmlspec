Release a repository that is its own project

The release runbook tells a run to delete this repository's project. Its step for regenerating the instruction files says to remove the htmlspec/ and spec.nix that htmlspec init creates, and since #55 those are the project and its declaration. This change revises the runbook for a repository that is its own project, as its release 0.2.0, so that no step of it removes anything of the project. The program does not change.

Release a repository that is its own project

Why

The runbook at htmlspec/runbooks/release/ is 0.1.0, written when this repository kept its specifications in openspec/ and was not an html-spec project. Pull request #55 promoted the project into htmlspec/ at 0.29.0, and govern-this-repository-from-htmlspec, which this change follows, moved the runbook into it unchanged. Its 0.30.1 changelog entry says not to follow the regeneration step and names this change as the one that revises it. Nothing stops a run in between: htmlspec list --runbooks lists release, and htmlspec run release can start it.

evidence/the-runbook-read-against-the-project-2026-10-14.md read both documents against the repository and measured each step in a scratch copy:

  • The removal deletes the project. htmlspec/ holds 504 files: 13 accepted specifications, 38 archived changes, this runbook, the asset store, and the change under way. After rm -rf htmlspec spec.nix, scripts/check-release and the self-runbooks stage exit 2, and the self-assets stage, which the step names as the one that catches a mistake, passes. A change under way that no commit holds is not recoverable.
  • There is nothing to remove. init run from the root reports extending the project and spec.nix already exists, so it was left as it is, and writes only the installed instruction files.
  • Its authority is a requirement whose premise is false. req-init-bootstraps-a-stray-project says a run MUST remove both, because This repository governs itself with openspec/ markdown, so it is not an html-spec project. Its scenarios, its evidence of nine duplicate assets, its verification, the tasks document's input A repository that is not already an html-spec project, and a risk all say the same.
  • The recorded version is described as the OpenSpec workflow made it. req-the-recorded-version-waits-for-archival has a run write the archived change's VERSION by hand at archival. htmlspec archive writes it, from spec.nix, which the runbook names nowhere, and nothing compares that version with the one Cargo.toml declares.
  • Two counts are stale. The last step and a verification say scripts/check-release asks three questions of the archive. It has asked four since 0.15.0.

What working looks like

  1. No step, requirement, or scenario of the runbook tells a run to remove htmlspec/, spec.nix, or anything else. The regeneration step says to run init from the repository root, to remove nothing afterwards, to confirm that only the installed files under .claude/, .codex/, and .pi/ changed, and to stop if init reports that it created a project.
  2. The specification states that hazard as a requirement with a new identifier, and the 0.1.0 requirement it replaces is gone. Its scenarios are the removal followed, init in the project, and init from another directory, each as measured.
  3. The runbook says the archived change's VERSION is written by htmlspec archive from spec.nix, and that a run raises spec.nix at archival to the version it set in Cargo.toml.
  4. Every statement the evidence found false is corrected, and every step it found right reads as it did.
  5. The runbook's VERSION is 0.2.0, and its CHANGELOG.md has a ## 0.2.0 entry naming the project release that publishes it.
  6. Both documents validate under default and strict strictness and are in canonical form, the self-runbooks stages pass, htmlspec preflight release passes inside nix develop, and htmlspec run release --check writes nothing.
  7. Archiving this change after its predecessor, rehearsed in a scratch copy, publishes release at 0.2.0, and the same archival with the version left at 0.1.0 is refused.
  8. This is release 0.30.2, and scripts/check passes.

What changes

The regeneration step removes nothing. The step and the requirement behind it say what init does in a repository that is its own project, what it says when it is not standing in that project, and that the run stops there rather than deleting anything.

The recorded version is described as htmlspec archive writes it. The requirement and the last step name spec.nix, and say that the version a run sets in Cargo.toml is the one it raises spec.nix to at archival.

What else the evidence found false is corrected. The specification's masthead, the consumed inputs, the risk about them, the release check's questions, and the evidence and verification of the replaced requirement. The risk that predicted a stale step gains what happened.

The runbook is released as 0.2.0, and the program as 0.30.2, unchanged.

Alternatives considered

Revise the runbook inside govern-this-repository-from-htmlspec. Rejected. Its design decision 2 moves the runbook byte-identical, so that the move reviews as a rename and archival publishes it at 0.1.0 against 0.29.0's snapshot, which its rehearsal checked. A revision there would make that rehearsal wrong and the move unreviewable as a rename.

Delete the removal sentence and nothing else, as a patch. Rejected. The step's authority is a requirement that says a run MUST remove both, with scenarios, evidence, and a verification, and the inputs and a risk repeat its premise. Deleting the sentence would leave the specification requiring what the procedure no longer does.

Keep a removal, of what init creates when it creates a project. Rejected. By name, those paths are the project's, htmlspec/ and spec.nix. Only whether git tracks them tells them apart, and that is a check a run would make by hand before an irreversible step. Stopping removes nothing and loses nothing.

Make init refuse to establish a project beneath one. That would remove the hazard of running it from the wrong directory, and it is a change to the program. It is named under scope.

Scope

In scope. The release runbook's specification.html, tasks.html, VERSION, and CHANGELOG.md. The 0.30.2 release: Cargo.toml, Cargo.lock, CHANGELOG.md, and the installed instruction files' generatedBy line. spec.nix waits for archival, as it did for the three releases before this.

What still holds is kept as written. The version is advanced first, the increment is judgment, the changelog heading names the version, and the toolchain is the flake's. The history of the five releases before 0.1.0, and the 0.1.0 changelog entry, describe the procedure as it was, and they stay.

The four Python stages failing inside nix develop on macOS is not addressed. Every release since promotion met it and ran them outside the shell. It is a fact about the machine rather than about the repository's layout, and it destroys nothing. This change corrects only the runbook's false statement that the shell supplies every input. Stating it as a hazard of the procedure is a change of its own.

init run beneath a project establishes a second one, measured from crates/. project-bootstrap's "Commands resolve the project from any directory beneath it" requires that search of "every command whose subject is a project", and the contract is silent on whether init is one. The runbook names the root. Settling it is a change to the program, bootstrap-beneath-a-project.

The runbook's documents keep their contract version, 0.1.0. Moving them to a newer schema is not needed for any correction here, and it would change every line's meaning for a reviewer.

Requirements. This change adds, modifies, and removes no accepted requirement. A runbook's requirements are what it requires of a run, and the runbook's own specification says so. The obligations it meets are runbook-authority's "A runbook records what its history taught", which makes the inverted hazard a requirement rather than a remark, and "The canonical procedure carries no completion state", which keeps every new unit unchanged and every step todo. The contract is silent on whether spec.nix and Cargo.toml must declare the same version. The runbook preserves what the three releases since promotion did.

The runbook's release. project-bootstrap's "Archival checks the versions of runbooks it publishes" requires a strictly greater version for changed documents and does not choose the increment, and runbook-authority's "A runbook carries an independently checked release version" requires a changelog heading per release that refers to the project release publishing it. The size is judgment, and the choice is mine: a minor, 0.2.0. A step now does the opposite of what it did, and a requirement is replaced, so a run of 0.2.0 does something a run of 0.1.0 did not. A patch would say the procedure is the same one, reworded.

The program's release. As for govern-this-repository-from-htmlspec: archival needs the version to advance and to be distinct, and nothing exempts a change that ships no program change. The choice is mine: a patch, 0.30.2, with a changelog entry that says the program is unchanged.
