Name each runbook an asset upgrade or the fallback rewrites

What this change established. When htmlspec format --upgrade-assets or htmlspec format --fallback rewrites a runbook's specification or procedure, or checking with either would, the report names that runbook once and says what its version needs before the next htmlspec archive, judged as archival judges it: a greater version and a heading where an archive already released the one it declares, a first version above 0.0.0, a missing heading, or nothing more. A runbook is named only for a document the formatter accepted, when checking, or wrote, when writing, and only for the two documents archival compares. The exit status is unchanged and nothing is added to the command surface.

deterministic-formatting

Formatting preserves meaning req-formatting-preserves-meaning

Formatting SHALL NOT change a document's semantic content. It SHALL preserve every semantic unit, every identifier, every attribute value, every cross-reference, and the document order of content. It SHALL NOT add, remove, or reorder semantic units.

One kind of attribute value is excepted. Where an asset reference names bytes the project's store does not hold, formatting SHALL fill it with the address of the bytes the toolchain ships. A reference that names bytes the store holds SHALL be left as written, even when the store also holds a newer revision, because the reference records what the document was authored against.

An asset reference SHALL be the value of an attribute through which an element loads an asset. These are the same attributes that document-validation's "An asset reference must match the bytes it names" judges, so the formatter and the validator SHALL NOT disagree about which values are references. A hyperlink is a citation, not something the document loads, and SHALL NOT be filled. Text SHALL NOT be read as an asset reference. Prose that quotes one, whether as characters in a code element or escaped in an example, is content, and formatting SHALL leave it as the author wrote it.

A second exception is made only on a contributor's request. Where the request is made, formatting SHALL add the fallback stylesheet that "A document stays readable when its stylesheet cannot load" describes to a document that lacks one, SHALL replace a fallback whose text differs from the current one, and SHALL change nothing else. It SHALL NOT do so for a document of an archived change or a run's record, which are history, judged by the project the document resolves into wherever formatting is run from, whether reached directly or through a symbolic link. Without the request, formatting SHALL leave a document's fallback present, absent, or stale as written. Where the request adds or replaces the fallback in a runbook's specification or procedure, the two documents project-bootstrap's "Archival checks the versions of runbooks it publishes" compares, or checking with the request would, formatting SHALL name that runbook once, after the documents it reports, and SHALL say what the runbook's version needs before the next archival, as that requirement judges it: a version greater than the one an earlier archive released, with a changelog heading for it, where the runbook declares a released version or one below it; a first version above 0.0.0 where nothing is released and it declares 0.0.0; a changelog heading where it declares an unreleased version its changelog does not head; and otherwise that the next archival releases it as it now stands. It SHALL name a runbook only for a document it accepted, when checking, or wrote, when writing, and SHALL NOT name one for another document in a runbook's directory or for a run's record. Naming a runbook SHALL NOT change formatting's exit status.

A third exception is made only on a contributor's request as well. Where the request is made, formatting SHALL rewrite each asset reference a document carries to the store location of the bytes the toolchain ships for the same asset, SHALL write those bytes into the store where it lacks them, from the copy the toolchain carries, and SHALL make no network request. It SHALL add no reference the document does not already carry. It SHALL leave as written a reference to an asset the toolchain ships no revision of, one whose stored bytes disagree with its address, and one the store holds other bytes for at the current revision's address, and SHALL say how to restore that file. It SHALL NOT rewrite a document of an archived change or a run's record, judged as the second exception judges them. Checking with the request SHALL name each document it would rewrite and write nothing, and SHALL succeed where it would write nothing, blocked references included. Where the request rewrites a runbook's specification or procedure, or checking with it would, formatting SHALL name that runbook and say what its version needs before the next archival, as the second exception does.

Evidence

The gap at 1.2.1, and the line at 1.2.2 evidence-the-gap-and-the-line

On 2026-10-28, in a scratch project, a runbook demo on an earlier stylesheet was published at 0.1.0 by a first archival, and then upgraded. With 1.2.1, built from main at 5aea6ce, format --upgrade-assets printed only its per-document lines and exited 0, and the next htmlspec archive second --check exited 1: "the runbook demo declares 0.1.0, which 2026-10-28-first already published with different canonical content". Nothing between the two said the runbook needed a release. With 1.2.2, the same steps printed after the per-document lines: "the runbook demo changed with its documents, and 0.1.0 is the version 2026-10-28-first already released: give it a greater version in …/htmlspec/runbooks/demo/VERSION, and a heading for that version in its CHANGELOG.md, before the next htmlspec archive, which otherwise refuses it", and checking printed the same with "would change". Archival's refusal then also named --upgrade-assets, --fallback, and plain formatting's fill as likely causes, and after 0.1.1 with its heading, archive second --check exited 0.

Verification

The upgrade names each runbook it rewrites, as archival judges it verify-the-upgrade-names-runbooks

Integration tests in crates/htmlspec-cli/tests/runbooks.rs run the built binary in scratch projects. upgrading_a_released_runbook_names_it_and_says_its_version_must_advance publishes a runbook, upgrades it with and without checking, and checks the line names it once and asks for a greater version, that checking writes nothing, that archive --check refuses naming the upgrade, and that it accepts once the version and its heading advance. Others check a never-published runbook is told the next archival releases it as its first release, an unheaded version is told to add the heading archival then asks for, and that no runbook is named for a run's record, a document outside every runbook, notes.html in a runbook's directory, a document the formatter refuses, or one it cannot write, while a runbook reached through a link is named once by its own name. The two that expect a line failed against 1.2.1's sources, and the review's seven failed against the pull request's second head before its fixes. The unit test what_a_changed_version_needs_agrees_with_archival holds the decision to compare_release in eight cases. Repeat with cargo test -p htmlspec-cli --test runbooks and cargo test -p htmlspec-cli --bin htmlspec runbook_release.
