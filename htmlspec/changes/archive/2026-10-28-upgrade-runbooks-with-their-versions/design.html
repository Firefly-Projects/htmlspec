Upgrade runbooks with their versions: design

How format --upgrade-assets and format --fallback tell a user that a runbook they rewrote needs a new release, what they read to say which, and why they tell rather than skip. Both options' behaviour and exit status stay as they are; only their report, archival's refusal wording, and the guide change.

The gap

Reproduced in a scratch project with 1.2.1. A runbook demo on an older stylesheet was published at 0.1.0 by a first archival. htmlspec format --upgrade-assets then rewrote htmlspec/runbooks/demo/specification.html and tasks.html, reported each move, and exited 0. A second change's htmlspec archive second --check refused: "the runbook demo declares 0.1.0, which 2026-10-28-first already published with different canonical content". Nothing between the two said the runbook now needed a release.

What the contract says

Accepted requirement Effect at archival
deterministic-formatting's "Formatting preserves meaning" Modified. Its second exception, the fallback made on request, and its third, the upgrade made on request, each gain one statement: where it rewrites, or checking would rewrite, a runbook's specification or procedure, it names that runbook and says whether its version must advance before the next archival. One scenario is added for each.
runbook-authority's "A runbook carries an independently checked release version" Unchanged. It is why a rewritten runbook needs a release, and nothing about it moves.
project-bootstrap's "Archival checks the versions of runbooks it publishes" Unchanged. The gate compares exactly as before. Only the words of its refusal gain a sentence, and the requirement does not fix those words.
toolchain-packaging's "The command surface is stable within a major version" Unchanged, and the reason this is a patch: the new lines are human-readable output, which that requirement leaves out of the stable surface, format writes no payload, and no flag is added. tests/surface/1.2.json does not move.

The contract is silent on what the formatter reports about the documents it rewrites beyond the blocked references the third exception already names, and silent on how a release is chosen for a runbook. The first is what this change settles. The second stays the author's.

Decisions

Tell the user, and keep upgrading runbooks decision-tell-not-skip

The upgrade keeps rewriting runbook documents, and names each runbook it rewrote at the end of its report. --fallback rewrites runbook documents the same way, adding or replacing the fallback stylesheet, so it names them the same way, with the same line. The README and each option's help say the same. Archival's refusal names both as likely causes.

Of the four options, docs alone are forgotten by the time it matters, and the program is the one party that knows which runbooks it just rewrote. Skipping runbooks by default narrows what 1.1 and 1.2 do, so a project relying on the upgrade reaching its runbooks would stop getting it with no word, and an opt-in flag is new surface, a minor release. A runbook on an older stylesheet is exactly what the upgrade is for: the right outcome is an upgraded runbook released at a new version, which telling makes easy and skipping makes impossible. Naming the cause in archival's refusal costs one sentence and catches a user who upgraded with an older release.

Find a runbook as archival does, and record it once its document is settled decision-a-runbook-is-what-archival-compares

A runbook is what archival compares: a directory runbook_release::present lists in the project's runbooks directory, under the name it lists, whose release is its specification.html and tasks.html and nothing else in it. A document names a runbook only when it resolves to one of those two files in such a directory, each directory resolved, so a runbook directory that is a link is found where it resolves and named by its own name, and any other file in a runbook's directory names none. The project asked is the one the document resolves into and the one the walk reached it through. A runbook is recorded only once its document is settled: when checking, once the formatter has accepted it, and when writing, once it is written. So a document the formatter refuses, or one that cannot be written, names no runbook. What moved is recorded per runbook as one of three values, the assets, the fallback, or both, never two flags, so a runbook is only recorded with something rewritten.

Finding a runbook through present rather than by where a directory sits keeps one definition of a runbook for archival and the line, which the review found the first version lacked: it named a runbook for any HTML file in its directory and missed one reached through a link. Recording only settled documents keeps the line from naming a change that was never made, which the review found the first version did for a document the formatter refused or could not write.

Say what the runbook's version needs, from the published history decision-what-it-says

For each runbook recorded, the report gains one line, in name order, after the per-document lines. It reads the runbook's VERSION and CHANGELOG.md and the project's published runbook history, which it reads once per project, the same things archival reads, and decides with runbook_release::version_after_a_change, the version half of archival's comparison for changed content with its heading check, which says one of six things:

  • Released at its current version, or above it: the runbook changed (or would change) and an earlier archive, named, released its version or a greater one, so its version must exceed that one, with a changelog heading for the new one, before the next htmlspec archive, which otherwise refuses it.
  • Never published, at 0.0.0: the version is not a release, so it needs a first version above 0.0.0, with its heading, before the next archival.
  • Not released yet, with no heading for it: the changelog needs a heading for the version before the next archival, which otherwise refuses it. Where an earlier version is published, the line says the heading should say what moved.
  • Never published, at a version its changelog heads: the next archival releases the runbook as it now stands, as its first release. Its heading is the first release's, so the line says nothing about what it should say.
  • Raised above what is published, at a version its changelog heads: the next archival releases the runbook as it now stands, and the heading for that version should say what moved: onto the current assets, the current fallback stylesheet, or both.
  • Any of the three files, or the history, cannot be read: the runbook changed, and if its version is already released it needs a greater one before the next archival.

The version comparison is the gate's own question once content has changed, so the line says what archival will say without archiving. Comparing content as well would need the rewritten documents' fingerprints, which checking does not write. The version alone is the right test anyway: a runbook at a released version whose documents changed is exactly the gate's refusal, and the heading check is the gate's other refusal a changed release can meet. Stating that half of the gate as its own pure function beside compare_release keeps one statement of the rule, and a unit test holds the two to the same answer for every case but a changelog that heads one version twice, which the line does not judge. Running it after the walk keeps one line per runbook however many documents moved, and name order keeps the output deterministic.

Show every name and path the report holds decision-names-are-shown

Every name and path the line holds, and every document's path in the report's other lines, reaches the terminal through terminal::shown, as run shows a runbook's name, and so do the runbook's name, directory, and archive in archival's release faults. A name is whatever a directory is called, so it can hold an escape sequence a terminal would act on.

The review found the new lines escaping names with the listing's rendering and the per-document paths and archival's faults not escaping them at all. One rendering, the one run and preflight use for text that reaches a report, keeps the whole report to one rule, and the change is small: one shown path per document in format, and the name, directory, and archive in each release fault.

Report it on standard output, and leave the exit status alone decision-where-it-goes

The lines go with the report, standard output, beside each document's "formatted" or "behind" line, not with the per-reference progress on standard error. The exit status is what it was: success for a write, and for a check, the existing rule.

The line asks the user to act, so it belongs with the results a user reads rather than the progress a user scrolls past. Making it change the exit status would turn advice into a failure for a project that is about to raise the version anyway, and would change a behaviour scripts already depend on.

Risks

Plain formatting can change a runbook too, unnamed risk-unfilled-references

Plain htmlspec format fills a reference to an asset the store lacks, as it has since before 1.2.1, and filling changes a runbook's canonical content as the two options do. The line is not given for it.

Out of scope: the change is about the two options a user asks for. Archival's refusal names the fill beside them, a one-sentence change, so a user who meets the refusal is told of it.

The line could disagree with archival risk-wrong-advice

If the line read the history differently from archival, it could say a version is fine that archival then refuses, or the reverse.

It calls the same functions archival does, runbook_release::present, history, and predecessor, and decides with a function a unit test holds to compare_release's answer for changed content at 0.0.0, at a first release, below, at, and above a published version, each with and without its heading. Integration tests publish a runbook, upgrade it or give it the fallback, and check that the line and archive --check agree before and after the version advances, and that an unheaded version is told to add the heading archival then asks for.
