Upgrade runbooks with their versions

htmlspec format --upgrade-assets rewrites a runbook's specification and procedure along with every other living document, and a rewritten runbook needs a new release before the next archival. Nothing says so until archival refuses. This change makes the upgrade name each runbook it rewrites and say what its version needs, and makes the upgrade guide say the same, as a patch release, 1.2.2.

Subject
Upgrade runbooks with their versions

Why

Release 1.1.0 added htmlspec format --upgrade-assets, which moves a project's living documents onto the stylesheet and scripts the current release writes. A runbook's specification.html and tasks.html are living documents, so the upgrade rewrites them too. That is right: a runbook should read with the current stylesheet as much as a specification should.

But a runbook's documents are versioned. runbook-authority's "A runbook carries an independently checked release version" gives every runbook a version of its own, and project-bootstrap's "Archival checks the versions of runbooks it publishes" refuses an archival that would publish different canonical content under a version an earlier archive already released. Moving a document's asset references changes its canonical content. So after the upgrade, the next htmlspec archive refuses: "the runbook demo declares 0.1.0, which 2026-10-28-first already published with different canonical content".

Nothing on the way warns the user. The upgrade reports each document it moved and exits 0. Release 1.2.1's Upgrading section in the README says the upgrade is optional and moves living documents, and says nothing about runbooks. A user following that guide learns about the runbook only at archival, perhaps days later and in a change about something else.

This happened. Bringing a project up to 1.2.1, the upgrade rewrote that project's one runbook, and the agent doing the work had to put both documents back by hand to keep the next archival from refusing. This project's own 1.1.0 knew the rule and moved its release runbook to 0.5.0 when it upgraded its assets, but a user has no way to know it.

What changes

  • The upgrade names each runbook it rewrites. When format --upgrade-assets rewrites a runbook's specification or procedure, or with --check would rewrite it, it says so once per runbook at the end of its report. Where the runbook's version is one an earlier archive already released, it says that version must advance, with a changelog heading for the new one, before the next archival. Where the version is not released yet, it says the next archival releases the runbook as it now stands.
  • The fallback does the same. format --fallback rewrites runbook documents the same way, adding or replacing the fallback stylesheet, so it names each runbook it rewrites with the same line.
  • Archival's refusal names the likely causes. The refusal for changed content under a released version says that asset references the upgrade moved, and a fallback stylesheet --fallback added or replaced, are changes too.
  • The guide says it. The README's Upgrading section, its paragraph on --upgrade-assets, and its note on --fallback, and each option's own help, say that a runbook either option rewrites needs a new version before the next archival.

What working looks like: a user runs htmlspec format --upgrade-assets --check before upgrading and reads that the runbook demo, at 0.1.0, would change and needs a greater version. They run the upgrade, raise htmlspec/runbooks/demo/VERSION to 0.1.1 with a changelog heading saying the runbook moved onto the current assets, and the next archival publishes it.

Alternatives considered

  • Documentation alone. Necessary and not enough: a user who has read the guide once forgets it by the time a runbook changes, and the program is the one party that knows which runbooks it just rewrote. The guide changes as well.
  • Leaving runbooks alone unless asked. A new option, or a default that skips runbooks, would avoid the surprise by not doing the work. But it narrows what 1.1 and 1.2 do, so a project that relies on the upgrade reaching its runbooks would silently stop getting it, and a new option is new command surface, which is a minor release rather than a patch. A runbook on an older stylesheet is the case the upgrade exists for. It should be upgraded and released, not skipped.
  • Raising the runbook's version for the user. Choosing between a patch and a minor increment, and writing the changelog's words, are the author's. project-bootstrap's archival gate compares and never edits for that reason, and the formatter should not edit what the gate leaves to the author.

Scope

  • It changes nothing about which documents the upgrade rewrites, how it rewrites them, or its exit status. The new lines are human-readable output, which toolchain-packaging's "The command surface is stable within a major version" leaves out of the stable surface. format writes no payload, so there is no field to add.
  • It does not raise a runbook's version, write its changelog, or block the upgrade.
  • It does not change archival's gate, only the words of its refusal.
  • It is a patch release, 1.2.2.
