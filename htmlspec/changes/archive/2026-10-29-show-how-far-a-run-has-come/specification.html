Show how far a run has come: as built

What the change show-how-far-a-run-has-come established, as built: htmlspec run <runbook> --status reports how far each run of a runbook has come, and whether it finished and passed by the rule a prerequisite run check applies, and --status <record> reports one run's steps, outcomes, and release.

runbook-execution

A run's progress is reported from its record req-a-run-s-progress-is-reported-from-its-record

htmlspec run <runbook> --status SHALL report every file under the runbook's runs/, one line each, in name order, and SHALL say that the order is name order, because a record states no time. For each run it SHALL state the steps done of the total and the steps dropped, and then the steps in progress, or the first step neither done nor dropped where none is in progress, or that the run finished and whether it passed.

Whether a run finished and passed SHALL be decided by the rule runbook-portability's "A prerequisite run is met by a finished, passed record" states, without a lowest release, and by the code the run check applies, so the report and preflight give one answer about every record. A run that did not pass, and a file not read as a run's record, SHALL be named with the first reason that rule gives, in its words.

htmlspec run <runbook> --status <record> SHALL report the run recorded under that name, matched byte for byte against the names the runbook's runs/ holds: every step in order with its state and its heading, each dropped step's reason, each requirement the record carries with an identifier and does not withdraw, with the outcomes recorded for it, the outcome of every other verification the record holds, the runbook release the record's head states, and whether it is finished and passed. An absent or empty outcome SHALL be shown as no outcome, as the rule reads it, and every verification the rule reads SHALL be shown, so a verdict never names an outcome the report leaves out.

The report SHALL write nothing, and SHALL exit 0 whatever the runs say. It SHALL exit 2 when the runbook or the record is not there, naming the records the runbook has. With --json it SHALL write the payload run's published schema states. A name or text a record or a directory holds SHALL reach the terminal with each character a terminal would act on written by its code point.

Every run on one line

Given
a runbook backup with a finished, passed run, a run whose fifth step is in progress, and a finished run that recorded failed for a requirement
When
htmlspec run backup --status runs
Then
each run is one line in name order, reading "finished and passed", "step 5 in progress", and "finished, not passed: recorded failed for" the requirement, and the report exits 0

One run in full

Given
a run whose first step was dropped with a reason and whose second is in progress
When
htmlspec run backup --status names that run's record
Then
both steps are listed with their states and headings, the dropped one with its reason, each requirement with the outcome recorded for it, the release the record states, and that the run is not finished and passed, with the rule's reason

The report and preflight agree

Given
a runbook another runbook requires, with records of every kind, a record holding a verification that references no requirement, and a record whose only requirement is withdrawn
When
preflight on the requiring runbook and the report each read them
Then
the records preflight counts are the ones the report calls passed, its open runs are the ones the report calls open, and each record it does not count carries the reason the report gives

An outcome no requirement shows

Given
a finished record whose requirement passed, and which also holds a verification that references no requirement and recorded failed
When
the run is reported
Then
that verification is listed among the other outcomes, and the run is not finished and passed, naming it

An empty outcome

Given
a finished record whose one verification states an empty outcome
When
the run is reported
Then
its requirement is listed with no outcome, and the run is not finished and passed, having recorded no outcome

A file that is not a run's record

Given
an empty file and a file whose markup needs error recovery under the runbook's runs/
When
the runbook's runs are reported
Then
each is named with the reason it is not read, and the report exits 0

A record that is not there

When
htmlspec run backup --status v9 names no record the runbook holds, or names one with its .html, as a path, or in another case
Then
it exits 2, naming the records the runbook has, and writes nothing

Evidence

A scratch project, and this repository's own runs evidence-a-scratch-project-and-this-repository

On 2026-10-28, in a scratch project with a runbook backup made by htmlspec new runbook, three runs gave "dropped 1/2 done, 1 dropped, finished and passed", "finished 2/2 done, finished and passed", and "open 1/2 done, step 2 in progress", and --status dropped printed the dropped step's reason beneath it. In this repository, htmlspec run publish --status read the four publish records, including those of 1.0.0 and 1.1.0, which were written before a record stated its runbook release: v1.0.0 as not passed for a partial outcome, v1.1.0 and v1.2.1 as finished and passed, and the stopped v1.2.2 run as 4 of 9 done, 5 dropped, not passed for a not-run outcome.

Verification

The report, through the built binary verify-the-report-end-to-end

cargo test -p htmlspec-cli --test progress passed its 10 cases: twelve records of every kind in one listing, byte for byte and twice; one run in text under both spellings and in its payload; each outcome and a requirement with no verification; agreement with preflight over every kind of record, a stray verification, and a withdrawn requirement, met and unmet; what is not there; the refused pairings of options; a runbook typed in another case; a linked record; escaped names and text; and a project unchanged after the report. A copy of the rule in progress.rs that judged only the listed requirements was tried against the agreement test and failed it, naming the two records it called passed.

The report's parts, and its payload verify-the-report-in-parts

The unit tests in src/progress.rs passed: each line, each outcome, each reason a file is not read, the one-run text, an empty outcome, a stray verification and a withdrawn requirement, each release case, the listing, the payload's fields, escaping, and the refusal for a record that is not there. The tests of the rule in src/prerequisites.rs passed unchanged after it was split into the reading and the verdict both use. Every test that ran the binary held its payload to run's published schema, the payload scenario carried every field the new shape declares, and the surface tests held 1.3.json to the program and to the files of 1.0, 1.1, and 1.2.
