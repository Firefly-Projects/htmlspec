How far each run of a runbook has come

A run's record holds every step's state and every outcome the run recorded, and no command reads them back: to learn how far a run has come, a person or an agent opens the record and counts by eye. htmlspec run <runbook> --status lists each run of a runbook with its steps done and whether it is finished and passed, and --status <record> shows one run's steps, outcomes, and release. "Finished and passed" is decided by the rule a prerequisite run check already applies, so the report and preflight cannot disagree about a record. The change is released as 1.3.0, which also carries 1.2.2.

Subject
How far each run of a runbook has come

Why

The user asked, while working through a runbook, whether there is a command to see how much of it is done. There is none. A run is one record from start to finish, by runbook-execution's "A run is one record from start to finish", so a run stopped at step five and picked up later is the ordinary case, and the first thing anyone resuming one needs is where it stands. Each operation that touches runs today answers a different question:

  • htmlspec status --change <change> counts a change's tasks, and takes no runbook.
  • htmlspec run <runbook> --check reports which requirements each run has recorded an outcome for. It never mentions a step.
  • htmlspec list --runbooks shows no completion fraction, as runbook-authority's "The canonical procedure carries no completion state" requires. It counts a runbook's open runs only where another runbook requires it.
  • htmlspec preflight <runbook> names a prerequisite's open runs, as "v1.3.0 (4 of 9 steps done)", but only for a runbook another one requires, and only to explain why a check is unmet.

So the answer is in the record's data-state and data-outcome attributes, and reading them means opening the HTML. A second question has the same gap. Whether a finished run counts for another runbook is decided by runbook-portability's "A prerequisite run is met by a finished, passed record", and today the only way to ask it is to run preflight on a runbook that requires this one.

What changes

run gains a third report beside starting a run and --check: --status, with an optional record name. What working looks like, for a publish runbook with three records, one of them under way:

  1. htmlspec run publish --status prints one line per run, in name order:

    publish has 3 runs, in name order:
  v1.1.0  7/9 done, 2 dropped, finished and passed
  v1.2.1  7/9 done, 2 dropped, finished and passed
  v1.3.0  4/9 done, 1 dropped, step 6 in progress

    A run that finished without passing says why, in the words preflight uses: "9/9 done, finished, not passed: recorded failed for req-each-channels-version-is-recorded". A file that cannot be read as a run's record says that instead.

  2. htmlspec run publish --status v1.3.0 lists every step in order, numbered, with its state and heading, and each dropped step's reason beneath it. It then lists each requirement the record carries with the outcome recorded for it, or "no outcome", says which runbook release the record states, and ends with "Finished and passed: no, it is still open, with 4 of 9 steps done", or "yes".
  3. With --json, both forms write one payload, which run's published schema states as a fourth shape.
  4. The report writes nothing and exits 0 whatever the runs say. It exits 2 when the runbook or the record does not exist, and the refusal names the records there are.
  5. A bare htmlspec run, htmlspec run --help, the README, and the instructions init installs for creating a runbook all name the new option.

The option is a new flag, so the release is a minor one, 1.3.0. 1.2.2 was archived and never published, so 1.3.0 is the next public release and carries 1.2.2's changes, and its changelog's Upgrading note says so.

Alternatives considered

  • htmlspec status --run <runbook> [<record>]. It reads well beside status --change, and a contributor who knows one would guess the other. It cannot be built within 1.x. status's payload has change, artifacts, and tasks always present, every released surface since 1.0 records that, and toolchain-packaging's "The command surface is stable within a major version" requires that "a field always present SHALL stay present". A report about a run has no change to name, so the schema would need a second shape, and every recorded fact about the first would move beneath it, which the surface check reports as a loss. run's payload already has three shapes, and run already has a report, --check.
  • Widen run --check. It answers whether each run attests to what the runbook requires, which runbook-execution's "A run's conformance to its runbook's contract is reported and never gated" makes its own question. Steps and verdicts in the same report would make a reader find one answer inside the other, and the conformance report already reads as a list of what is missing.
  • A new operation, such as htmlspec progress. It would be a name OpenSpec does not have, a second request-verb spelling to fix, and a second command about runs beside run, for one report.
  • --status as a plain flag, selecting a record with --as. --as names the record a run creates. Using it for a record that exists would give one option two meanings, depending on another flag. A second positional, run <runbook> <record> --status, would be an argument that means something under one flag only.

Scope

  • Records only. The report reads the runbook's runs/ and never its canonical procedure, whose steps stay unstarted by runbook-authority's "The canonical procedure carries no completion state".
  • No chronology. Runs are listed in name order, which says nothing about which ran first. A record states no time, by runbook-execution's "A run is one record from start to finish", so there is no latest run to single out.
  • No release bound. "Finished and passed" is the run check's rule without atLeast. The record's release is shown beside it, so a reader can compare it with a bound themselves.
  • No writing. Nothing marks a step done or records an outcome. A record is edited as it is today, and the report reads what the edit left.
  • No other listing changes. list --runbooks, run --check, and preflight report what they report now.
