How far each run of a runbook has come: design

How htmlspec run <runbook> --status [<record>] is built: a third mode of run, a report module that reads each record through the same reading and the same verdict the prerequisite run check uses, a fourth shape of run's payload, and the 1.3.0 release that carries it and 1.2.2.

Subject
How far each run of a runbook has come: design

The shape of it

Everything the report says is already in each record, and most of the reading already exists. The prerequisite run check in prerequisites.rs reads every file under a runbook's runs/, refuses a link, parses each record without recovery, counts its done and settled steps, and decides whether it is finished and passed. What it throws away is the detail: which step is under way, why a step was dropped, and which outcome each requirement got. This change keeps that detail and prints it.

Four pieces, in the order they are built:

  1. 1.3.0 opens first. The version moves before anything is added, so tests/surface/1.3.json exists, equal to 1.2's but for its version, and the addition is recorded against it.
  2. The reading is shared. prerequisites.rs splits its private decide into a reading of one record and a verdict on the reading, and exposes both with the records of one runbook, each read once. The run check is rebuilt on them and decides exactly what it decided.
  3. The report. A new module, progress.rs, turns each reading into a run's status and renders it, as text or as a payload. run's dispatch gains the mode.
  4. The surface. run.schema.json gains a fourth shape, the surface records that --status's value is optional, and the README, the help, a bare run, the new instructions, and the changelog say what it does.

What the contract says, and where it is silent

Accepted requirement What this change does with it
runbook-portability's "A prerequisite run is met by a finished, passed record" Unchanged. The report applies its rule, without atLeast, through the same code, and names a record that falls short with the first reason in the order it fixes.
runbook-execution's "A run is one record from start to finish" Unchanged. A record states no time, so the report lists runs in name order and names no latest run.
runbook-authority's "The canonical procedure carries no completion state" Unchanged. The report reads records and never the runbook's own tasks.html.
toolchain-packaging's "The command surface names its operations as OpenSpec names them" Unchanged. No operation is added. run keeps post run, because "the verb names the most the operation writes in any invocation", which is how run --check already reads under it.
toolchain-packaging's "The command surface is stable within a major version" Unchanged. --status and the payload's fourth shape are additions, which a minor release may make, recorded in 1.3.json, and permanent in 1.x from then on.
toolchain-packaging's "Exit codes distinguish outcomes" Unchanged. A report exits 0, and a runbook or record that is not there is an operation that could not run, exit 2, as run --check exits for a runbook that is not there.
toolchain-packaging's "The project records what changed in each version it ships" Unchanged. The changelog gains a 1.3.0 entry.

The specification adds one requirement to runbook-execution at archival, "A run's progress is reported from its record": htmlspec run <runbook> --status reports each run's steps done and whether it is finished and passed, by runbook-portability's rule; naming a record reports each step's state, each dropped step's reason, each requirement's recorded outcome, and the record's release; the report writes nothing, never gates, and exits 0 whatever the runs say.

The contract is silent on the report's wording, its layout, and its payload's shape. Those are my choices, made under decisions 3 and 4. The wording can change in any release. The payload binds every later 1.x release once 1.3.0 ships it, so it is kept to what the text shows.

Decisions

1. The report is a mode of run: --status, with an optional record

htmlspec run <runbook> --status reports every run of the runbook, and htmlspec run <runbook> --status <record> reports one. --status is exclusive with --as and with --check.

The proposal sets out the alternatives. The deciding fact is status's payload: its three fields are recorded as always present in every released surface, and a run has none of them, so status --run is out of reach until 2.0. run is where a contributor already goes for runs, it already has a report, --check, and its payload already has several shapes. An optional value keeps one flag for both forms, and reads the way the user's own example did.

2. One reading of a record and one verdict, shared with the run check

The report decides "finished and passed" by calling the code that decides a run check. It never restates the rule.

prerequisites.rs keeps its rule and changes its seams. decide(source, at_least) becomes two functions it is made of: read(source), which turns a file's text into a Reading (the projected model and the release its head states) or the reason it is no run's record, in the existing order (empty, needs recovery, not a tasks document); and judge(reading, at_least), which gives the verdict and, for an open run, its done and total steps. A step's state is read once, by a StepState with five values, the schema's four and Undeclared for a state that is absent or not one of them, which is the word status and list already use for such a task, and "settled" is Done or Dropped, so the count the rule makes and the steps the report lists cannot disagree. The set of requirements a record owes an outcome for, each it carries with an identifier and does not mark withdrawn, becomes one function, owed, which the rule checks and the report lists. A verification's outcome is read once too, by outcome_of, which reads an absent and an empty data-outcome alike as none, and the name the rule gives a verification by named_by; both serve the rule and the report. judge_records(runs, at_least) reads every file under runs/ once, refusing a link before reading as today, and returns each record's name, verdict, progress, and reading. read_records, which the run check uses, is a fold of it.

The user asked for this code to be reused, never duplicated, and the reason is the one decision 3 of require-a-run-of-another-runbook gave for the rule itself: an operator who sees "finished and passed" here and "still open" in preflight about the same record has two answers and no way to choose. The existing tests of decide are kept unchanged, as the check that the split decides what the whole did.

3. What the report says

Every run gets one line, in name order, with the record names padded to one column, as the first example shows. A named run gets every step in order, its requirements and their outcomes, its release, and its verdict, as the second shows.

publish has 4 runs, in name order:
  v1.1.0  7/9 done, 2 dropped, finished and passed
  v1.2.1  9/9 done, finished, not passed: recorded failed for req-b
  v1.3.0  4/9 done, 1 dropped, step 6 in progress
  stray   not read: is not a run's record: not a tasks document
publish run v1.3.0
Steps: 4 of 9 done, 1 dropped
  1. done         Start from the archived release
  2. dropped      First run only: bootstrap the public repository
                  reason: the public repository already has its main
  3. done         Push the export and merge it
  …
  6. in progress  Watch the release workflow to its end
  7. to do        Check each channel
Requirements: 2 of 3 have an outcome
  passed      req-a
  failed      req-b
  no outcome  req-c
Runbook release: 0.3.0
Finished and passed: no, it is still open, with 4 of 9 steps done

An open run's line names the steps in progress ("step 6", "steps 5 and 6", "steps 4, 5 and 6"), or, where none is, the first step neither done nor dropped, as "step 6 next". A finished run that does not pass, and a file not read as a record, give the run check's first reason in its own words. A step is numbered by its place in the record, its heading is the task's heading as a reader names it, without the identifier the template writes beside it (htmlspec-parse's HeadingName, which a rename is compared by), and a dropped step with no reason says "reason: none given". A requirement is listed where the record carries it with an identifier and does not mark it withdrawn, which is the set the rule's "records no outcome" check asks about, with every outcome a verification referencing it records, in document order. The rule's outcome check reads every verification, though, so a verification that references none of those requirements, one referencing nothing or only a withdrawn requirement, is listed after them under "Other outcomes", by the name the rule gives it: the requirement it references first, or else its identifier. So every verification the verdict can name is one the view shows. An empty outcome is no outcome, in the view as in the rule. The release line says "not stated", "stated more than once", or "not three dot-separated integers" and the text, where the head holds no single well-formed release. A runbook with no runs says so and how to start one. Every name, heading, reason, identifier, and outcome reaches the terminal through terminal::shown.

The one-line form is the answer to "how far has it come", so it carries the count, the step in hand, and the verdict, and no more. The one-record form lists every step rather than only the open ones, because a person resuming a run reads where it stands from the steps around the one in hand. Name order is the order gather already gives every run report. It is stated in the header so that nobody reads it as chronology.

4. The payload: runbook and records

Both forms write one shape, with one entry in records where a record is named. It is run's fourth shape, told apart from the others by its required fields.

{
  "runbook": "publish",
  "records": [{
    "record": "v1.3.0",
    "state": "open",
    "reason": "is still open, with 4 of 9 steps done",
    "done": 4, "dropped": 1, "total": 9,
    "steps": [{"number": 2, "id": "task-bootstrap", "heading": "First run only: …",
               "state": "dropped", "reason": "the public repository already has its main"}, …],
    "requirements": [{"id": "req-a", "outcomes": ["passed"]}, {"id": "req-c", "outcomes": []}],
    "release": {"stated": "one", "version": "0.3.0"}
  }]
}

state is one of passed, open, not-passed, and unreadable. reason is present in every state but passed. done, dropped, total, steps, requirements, and release are present wherever the file was read as a record and absent where it was not, so absent means "not known" and never "none". The schema states the two as the two branches of a runStatus definition, a read record with all of them required and a file not read, whose state is the constant unreadable, so a consumer can rely on them where the state is not unreadable. A step's state is one of todo, in-progress, done, dropped, and undeclared. Its id, heading, and reason are present where the record gives them. release.stated is one of one, none, malformed, and several, with version for one and given for malformed. Names and text are the raw text, because JSON escapes them.

One shape for both forms means a script reads one schema whichever it asked. A read record also carries otherOutcomes, each with a name and an outcome where it has them, for the verifications decision 3 lists apart; the schema declares it as an optional property, and the program writes it on every read record, empty where there is none. The record's release is a small sum type, not a nullable string, because "no release stated" and "a release nobody can read" are different facts and a null would make them one. Nothing is in the payload that the text does not show, because every field becomes permanent with 1.3.0.

Settled after the review of pull request 95. Two refinements were left as prose rather than encoded in the schema: requiring reason where the state is open or not-passed, and stating release as a oneOf of its four cases. The surface names a oneOf branch by its required fields, so either would rename a branch 1.3.json already records, and the writer refuses a surface that loses a fact a recorded file holds. The program writes both as decision 4 says, and the schema's descriptions state it. A record-level reason is the rule's sentence in the form preflight's notSatisfying reason carries, with each character a terminal would act on written by its code point, and the schema now says so; every name and text elsewhere in the payload is the raw text.

5. Names resolve as run and preflight resolve them

The runbook is found as run --check finds it, by 1.0's name rule, and then known by its enumerated name, as run --as and preflight know it. The record is matched byte for byte against the names the runbook's runs/ holds.

A typed runbook name that a case-folding filesystem finds, PUBLISH for publish, reports under publish, as decision 2 of require-a-run-of-another-runbook settled for run and preflight. A name that reaches a directory listed under no one name is refused, exit 2, with the message run --as gives. A runbook that is not there is refused, exit 2, with run --check's message. A record that is not there is refused, exit 2, naming the records the runbook has. The record is never opened by its typed name, so a path, .., or a name that differs only in case finds nothing on any filesystem.

The runbook rule keeps every name 1.2 ran working. The record rule is the run check's: a name means the same record on every machine.

6. The modes are exclusive, and a wrong pairing is named

run's options are read together into one of three modes, starting a run, --check, and --status, by a total match on the three options. Each other pairing is refused, exit 2, with a sentence that names which option is surplus and both commands it could have meant.

This is how main.rs already pairs --check and --as, for the reason its comment gives: naming what is surplus is a better report than clap's generic conflict. A start with no record name now also names --status beside --check.

7. The surface records that a value is optional

An argument whose value may be left out records "valueOptional": true in the surface, and the comparison treats it as a fact a later 1.x release must keep.

--status is the first option whose value is optional, and the surface records only that an option takes a value. A later release that made the value required would break run publish --status and pass every check. The fact is written only where it holds, so every argument already recorded keeps its record and 1.3.json differs from 1.2.json only by what 1.3 adds.

8. Where the option is named, and where it is not

A bare run names it beside --as and --check, as does the refusal for a start with no record name. run --help, the README's runbook section and command reference, and the new workflow's instructions, where they say how to start a run, name it too. list --runbooks does not change.

A bare run is where a contributor who has forgotten run's modes lands, so it lists them. The installed instructions are what an agent working a run reads, and that is the reader the user's question came from. The listing's rows describe runbooks, not runs, and it already counts a prerequisite's open runs. Putting a command in every such line would lengthen the one table a reader scans to choose a runbook.

9. Release 1.3.0, which carries 1.2.2

The workspace moves to 1.3.0 before anything is added, and spec.nix moves to 1.3.0 at archival. The changelog's 1.3.0 entry has an Upgrading note saying 1.2.2 was archived and not published, that 1.3.0 carries it, and that a project upgrading from 1.2.1 follows 1.2.2's note too.

The user decided on 2026-10-28 to publish one release, 1.3.0, and skip publishing 1.2.2. A new flag is a minor release's addition. Opening the minor first means 1.3.json exists before the addition, so the writer records it as an addition to 1.3 and never as a rewrite of 1.2, as 1.2's opening did.

Risks

Name order is read as the order the runs happened

A reader who sees v1.10.0 listed before v1.2.0, or the last line taken for the latest run, draws a conclusion the records cannot support.

The header says "in name order", and the README says a record states no time. Nothing in the report or the payload names a latest run.

"Finished and passed" is read as meeting a check with atLeast

A record can be finished and passed and still miss a run check that declares a lowest release.

The one-record view and the payload carry the record's release beside the verdict, and the README says the verdict is the rule without atLeast. preflight on the dependent runbook stays the answer to whether its check is met.

The optional value takes the runbook's name

htmlspec run --status publish reads publish as the record, and finds no runbook.

A run with no runbook already lists the runbooks and refuses, exit 2, and that listing now spells htmlspec run <runbook> --status. Nothing is read or written on the way.

The report and the run check come to disagree

A later change to one rule and not the other would show a record as finished and passed here and refused in preflight.

There is one rule, in prerequisites.rs, and the report calls it (decision 2). A test drives one project through both: each record preflight names as open is open here, and each record it counts is passed here.

A record writes an escape sequence to the terminal

A record's name, a step's heading or reason, and an outcome are text a document holds, and any of them can carry a control character or a bidirectional override.

Every one goes through terminal::shown, the rule the preflight report and the listing read. A test writes a record whose name, heading, reason, and outcome each hold an escape and a right-to-left override, and checks the report names each by code point.

A runs/ folder that cannot be read reads as a runbook with no runs

Where the runbook's runs/ exists and cannot be listed, the report says the runbook has no runs on record, as if nobody had run it. The review of pull request 95 found it. The behavior is runs::gather's, which run --check and preflight's run check share, so all three answer the same way today.

Accepted in this change, because the fix belongs in the one place all three read from and would change what --check and preflight report too. A follow-up change makes gather tell an absent folder from one it cannot read, and names the second in every report that reads it.

The payload's shape is fixed for every later 1.x release

A field added here that later proves wrong stays until 2.0.

Accepted, as every minor addition is. The payload is kept to what the text shows (decision 4), and a later release can add a field without removing one.
