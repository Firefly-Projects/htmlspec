1. The check, before the fix

  • 1.1 Add a test in crates/htmlspec-cli/src/install.rs that installs for every tool in TOOLS into a scratch directory, reads every skill and command file written, extracts the name: value, and asserts it matches lowercase letters, digits, and hyphens only.

    Read the produced files rather than the table: the malformed value is assembled by a format string at write time, so a check on workflow.name and workflow.directory — both already conforming — cannot see it

  • 1.2 Make the failure name the file, the offending value, and the character that failed.

    Across 35 generated files, "a name is malformed" is not actionable

    Migration note: the figure 35 is carried as the author wrote it. At commit 4972234 an install for all five tools writes 49 files that declare a name, and the test this task shapes reads those 49. 35 is the count for the three tools this repository selects, claude,codex,pi, as evidence/loading-after-rename-2026-08-19.md records. evidence/failing-name-check-2026-08-19.md gives 35 as its total while its per-tool rows sum to 50.

  • 1.3 Run the test and watch it fail on the 21 command files three tools currently receive, each carrying /htmlspec:…, $htmlspec-…, or /htmlspec-….

    A check that has never failed proves nothing, and this is the only naturally occurring failing case

    Migration note: the record of this run, evidence/failing-name-check-2026-08-19.md, shows the 21 failing files carrying /htmlspec:… for Claude Code and /htmlspec-… for Cursor and Pi. None carried $htmlspec-…: that is Codex's invocation, and Codex receives skills only, so no command file was written for it.

  • 1.4 Record the failure output as evidence, including the count of failing files per tool.

    That count is what shows the check reads every file rather than the first one

2. Separate the name from the invocation

  • 2.1 Change write_commands in install.rs to use workflow.directory for the name: field instead of tool.invocation(workflow.name), so a command file and its skill file declare one identity.

    workflow.name is rejected for this: a flat command directory already needs the htmlspec- prefix on the file name to avoid colliding with another tool's unrelated apply.md, and a bare apply in the name field reintroduces that ambiguity

  • 2.2 Leave the rest of the command frontmatter as it is — description, allowed-tools, and generatedBy are unaffected

  • 2.3 Record in a comment why the invocation is not the name, and where the invocation does belong.

    The next reader will see a name field that no longer matches what they type and will be tempted to put it back

  • 2.4 Confirm Tool::invocation now has exactly one non-test caller, report_next_command.

    That single-producer property is the decision, not a side effect of it

  • 2.5 Re-run the test from task 1 and confirm it passes

    Migration note: no record this change carries states this result. Only the message of commit 4972234 does, in saying that the full suite is green at 322 tests.

  • 3.1 Confirm the command file names are untouched: .claude/commands/htmlspec/apply.md and .cursor/commands/htmlspec-apply.md are what determine the invocation, and this change must not move them

4. Prove a renamed field does not break loading

  • 4.1 Regenerate this repository's own instructions with htmlspec init --tools claude,codex,pi, as the previous change did, and confirm the 21 command files now declare htmlspec-*-change names

    — 14 here, not 21: this repository selects claude,codex,pi and Codex is skills-only. 21 is the all-tools figure, confirmed separately by the new test

  • 4.2 Confirm the seven /htmlspec:* commands still load and are still invocable by their old spelling.

    This is the risk that would make the change wrong rather than merely different, and it must be checked by loading rather than by reasoning: if a loader derived the command name from the name: field, the spelling would change

  • 4.3 Record the result as evidence, including the vendored opsx comparison — name: "OPSX: Apply" registers as /opsx:apply, which is neither the name nor derivable from it, so the file path is what determines the command.

    That comparison is the reason to expect this to hold, and the load is the proof

  • 4.4 Confirm the AGENTS.md region is untouched by the regeneration, since it carries no frontmatter and this change does not reach it

Migration note. evidence/loading-after-rename-2026-08-19.md, the record of tasks 4.1 to 4.4, shows that the invocations did not move. It does not show that a command file declaring the same name as its skill file, as task 2.1 made it, was harmless. 2026-08-21-distinguish-command-names-from-skill-names later called that shared name a regression this change introduced, made command files declare no name, and withdrew the scenario One identity per workflow that this change added.
