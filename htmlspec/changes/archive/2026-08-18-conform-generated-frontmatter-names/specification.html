Conform generated frontmatter names

This change made the names the bootstrap operation generates part of the contract, in Bootstrapping installs agent instructions for the tools a project uses. It requires every generated file's declared name to be composed only of lowercase letters, digits, and hyphens, checked against the files produced rather than the values they are derived from, and a generated name to identify the workflow rather than be the invocation a contributor types, with one identity for every kind of file a workflow produces.

project-bootstrap

Bootstrapping installs agent instructions for the tools a project uses req-bootstrapping-installs-agent-instructions-for-the-tools-a-project-uses

The bootstrap operation SHALL install, for each selected AI coding tool, the instructions that tool needs to drive the HTMLSpec workflow. Where a tool supports invocable commands, the operation SHALL install those as well as the instructions.

The instructions SHALL cover the project's lifecycle from an idea to an archived change, rather than a single stage of it. A contributor who has bootstrapped a project and lists what was installed SHALL find the stage they are at. Instructions covering only the final stage leave every earlier stage to be improvised, which is the case the project's own contract for artifact kinds exists to prevent.

A workflow SHALL be installed whether or not a command performs it. Archival is already agent-driven — the program checks a specification it does not produce — so a stage whose work is judgment is the ordinary case rather than the exception.

An installed workflow's instructions SHALL NOT name a command the program does not provide, and this SHALL be checked mechanically rather than by review. Naming an absent command sends an agent to an error, and it is the hazard that a rule limiting how many workflows are installed was attempting to avoid.

The set of supported tools SHALL be data rather than logic, so that supporting an additional tool is an entry in that set. The set of workflows SHALL likewise be data, so that covering an additional stage is an entry in that set together with its instructions.

The order of the workflows SHALL be the order the lifecycle moves through them, because instructions written into a shared file are presented in that order and a reader meets them as a document.

How a tool receives instructions SHALL be a property of the tool with one value per tool, rather than a combination of independent settings. A tool for which no instructions could be written is a state the program SHALL NOT be able to reach.

Instructions SHALL record the version of the program that generated them, so an installation predating the instructions it should carry is identifiable.

Every generated file's declared name SHALL be composed only of lowercase letters, digits, and hyphens, because a tool that reads it may reject any other character. This SHALL hold for each kind of file the operation writes, and SHALL be checked against the files produced rather than against the values they are derived from — a name is assembled at the moment of writing, so a fault introduced there is invisible to a check on the inputs.

A generated name SHALL NOT be the invocation a contributor types. The invocation is a property of a tool's command surface, it differs per tool, and it SHALL have one producer; a name field holding it states that fact a second time and states it where a stricter reader rejects it. The name SHALL instead identify the workflow, and the same identity SHALL be used for every kind of file a workflow produces, so that a workflow has one generated identity rather than one per file kind.

Migration note: as this change built it, the AGENTS.md region the operation writes for the shared-file tool carries no frontmatter and declares no name, so not every file the operation writes declares one: what holds is that every name a written file declares is of lowercase letters, digits, and hyphens only. The change's own record counts the region as meeting these words, and they were kept: evidence/failing-name-check-2026-08-19.md lists it as "a marked region, no frontmatter", with nothing malformed, and task 4.4 says it "carries no frontmatter". The check, every_generated_name_is_loadable at commit 4972234, reads the skill and command files an install writes and not the region, although that record's table lists the region as one file read.

Migration note. Each unit below summarizes a record carried unchanged in this change's evidence/, which it links, and the record is the authority.

The check fails before the fix evidence-failing-name-check-2026-08-19

Tasks 1.3 and 1.4: every_generated_name_is_loadable, run with cargo test -p htmlspec-cli every_generated_name_is_loadable against the tree before write_commands was changed, failed. It named seven command files each for Claude Code, Cursor, and Pi, 7 malformed files of 14 for each of those tools, every name carrying /: /htmlspec:<workflow> for Claude Code and /htmlspec-<workflow> for Cursor and Pi. The seven skill files per tool passed, and Codex, which receives skills only, had none malformed. The record reads seven failures per tool, rather than one, as what shows that the check reads every file an install produces rather than stopping at the first. evidence/failing-name-check-2026-08-19.md

Renaming the field does not change what a contributor types evidence-loading-after-rename-2026-08-19

Tasks 4.1 to 4.4, run against this repository after the write_commands change, with htmlspec 0.1.0 built from the tree. htmlspec init --tools claude,codex,pi modified 14 files, all of them command files for Claude Code and Pi, each by one line that replaced the invocation in name: with the workflow's directory name, and left the 21 skill files byte-identical. Claude Code 2.1.220 still listed the seven /htmlspec:* commands by their old spelling beside the seven skills, and Pi's own loader, loadPromptTemplates, named each command from its file stem. The vendored opsx commands register by file path: Claude Code's, declaring name: "OPSX: Apply", as /opsx:apply, and Pi's, declaring no name, as /opsx-apply. The closing message still printed /htmlspec:new, $htmlspec-new, and /htmlspec-new, from Tool::invocation in report_next_command, its only non-test caller, and the AGENTS.md md5 was 591c6fc316bd89ffd645223aed6a481c before and after. evidence/loading-after-rename-2026-08-19.md

Migration note: this record shows that the invocations did not move. It does not show that a command file declaring the same name as its skill file was harmless. 2026-08-21-distinguish-command-names-from-skill-names later called that shared name a regression this change introduced, made command files declare no name, and withdrew the scenario this specification states as One identity per workflow.
