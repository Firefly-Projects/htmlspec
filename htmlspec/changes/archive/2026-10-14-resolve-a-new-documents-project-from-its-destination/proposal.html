Resolve a new document's project from its destination

htmlspec new document decides which project a new document belongs to from the directory the command runs in, not from where the document will live. In three of the four ways those two can differ, it writes a document that fails validation or gives the project a second copy of its runtime. This change makes the destination decide.

Kind
proposal
Contract
0.7.0
Subject
Resolve a new document's project from its destination

Why

document-template's "A project can be initialized with a conforming document" requires a new document that "already conforms to the element contract, the visual system, and the runtime conventions, without hand-assembly". Its scenario "Starting a new change" says "the resulting file passes validation immediately", and the requirement says initialization "SHALL NOT copy a runtime asset that the project already stores".

The program does not do either reliably. new_document in crates/htmlspec-cli/src/commands.rs resolves the project from the working directory, ProjectRoot::resolve(Path::new(".")), and points the new document at that project's store. Validation looks for a document's store elsewhere: the first assets/ directory in the document's own directory or above it. So the two agree only when the working directory and the destination sit in the same place. evidence/the-four-cases-measured-2026-10-13.md measured the four arrangements in a scratch project:

Run from Destination What happens
inside a project outside it new document exits 2, and the document fails validation with 7 asset/unresolved errors
inside a project inside the project, outside htmlspec/ new document exits 2, and the document fails validation with 7 asset/unresolved errors
outside a project inside its htmlspec/ new document exits 0, and the project now holds two stores, which htmlspec assets reports as duplicates
outside a project outside it correct

This repository met the first row the day it became an html-spec project. The CLI test new_document_creates_a_document_that_validates_immediately runs new document from inside the repository and writes to a temporary directory. Before the promotion, the repository held no project and the test passed. After it, the test fails with exit 2, and so does scripts/check.

The contract is silent on how a new document finds its project. project-bootstrap's "Commands resolve the project from any directory beneath it" governs "every command whose subject is a project", and the program applied that rule to a command whose subject is a document.

What working looks like

  1. From inside this repository, htmlspec new document proposal /tmp/x/proposal.html --subject X exits 0, writes /tmp/x/assets/ beside the document, and htmlspec validate /tmp/x/proposal.html accepts it.
  2. From outside a project, htmlspec new document proposal <project>/htmlspec/changes/y/proposal.html references the project's existing store at <project>/htmlspec/assets/, and writes no second store. htmlspec assets still finds each asset once.
  3. A destination inside a project but outside its htmlspec/, such as docs/notes.html, gets a store beside it and validates, wherever the command runs.
  4. A destination inside a project whose store does not exist yet still establishes the store in the project's htmlspec/, as "Initializing into a project without assets" requires.
  5. new_document_creates_a_document_that_validates_immediately passes when run inside this repository, and scripts/check passes with the promoted project in place.

What changes

new document finds the project from the destination's directory, searching it and its ancestors and stopping at the destination's repository, as project resolution already stops at a repository's boundary. A destination beneath that project's htmlspec/ directory references the project's store, and establishes it there if it is absent. Any other destination gets a store beside the document, as a document outside every project does today. The directory the command runs in no longer enters into it.

The accepted requirement gains the rule, so it is checked rather than remembered: initialization decides which project a document belongs to from the document's own location. This is a patch release, 0.29.1. It changes no document format and no other command.

It is the first change written in this repository's own html-spec form, so its archive is the first that htmlspec archive writes here.

Alternatives considered

Change only the test, so it runs from a scratch directory. Rejected. The test would pass and the three failing arrangements would remain. A contributor writing a standalone document from inside any project's repository meets the first row.

Find the project from the destination, and reference its store wherever the document lies. Rejected. It fixes the first and third rows and leaves the second: a document in docs/ would reference htmlspec/assets/, which validation never finds, because that store is not above docs/.

Reference whatever store validation would find above the destination, and create one beside the document where there is none. Rejected. It mirrors validation exactly, and it fails the fourth line of what working looks like: in a project whose store is not established yet, it would put a store beside the document instead of in htmlspec/.

Refuse a destination outside the working directory's project. Rejected. Writing a standalone document from inside a repository is a legitimate use, and it is the very case the CLI test exercises.

Scope

  • new change is not changed. Its subject is a project, so it resolves from the working directory, as "Commands resolve the project from any directory beneath it" requires.
  • init is not changed, and neither is validation's search for a store.
  • No existing document is rewritten. A document already written into the wrong arrangement stays as it is, and validation reports it as before.
  • None of the other disagreements between the program and its contract that the migration recorded is in scope here. Each is a change of its own.
