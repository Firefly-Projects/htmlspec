1. Tests first

The tests come first, because they are what proves the defect and then its repair. Each runs the built binary, as new_document_creates_a_document_that_validates_immediately does.

  • 1.1 Add a CLI test for each of the four arrangements in evidence/the-four-cases-measured-2026-10-13.md, each run in a scratch repository with a scratch project. task-1-1

    For each arrangement, assert that new document exits 0, that htmlspec validate accepts the document it wrote, and that htmlspec assets run in the project finds each stored asset once. Run them against the unrepaired build and record in this change's evidence which fail: the measurement predicts that A, B, and C fail and D passes.

  • 1.2 Add a CLI test for a destination beneath htmlspec/ in a project whose store is not established yet. task-1-2

    Assert that the store is established at htmlspec/assets/ and that no store is written beside the document. This pins the arrangement design decision 2 keeps from the rejected alternative.

  • 1.3 Confirm that a test pins new change resolving its project from the working directory, and add one if none does. task-1-3

    Its subject is a project, so this change must not alter it.

2. The fix

  • 2.1 In new_document, resolve the project from the destination's directory and choose the store as design decision 2 states. task-2-1

    Normalize the destination to an absolute path first, joining a relative one to the working directory and dropping . and .. segments lexically. A destination beneath the project's htmlspec/ references htmlspec/assets/. Any other gets a store beside it.

  • 2.2 Run the tests from 1.1 to 1.3 and new_document_creates_a_document_that_validates_immediately, from inside this repository, and see every one pass. task-2-2

  • 2.3 Correct new_document_and_post_document_agree in crates/htmlspec-cli/tests/verbs.rs, which asserted the outcome the repair removes. task-2-3

    Found while running 2.2. The test wrote notes.html into a project's root and asserted that the document was the one file written, so that it referenced the project's store. That document's references descend into htmlspec/, and validation checks none of them when no store is above the document: a reference naming bytes no store holds was accepted. The test now asserts the document and a store beside it, and keeps the one-file assertion for a destination beneath htmlspec/. Design decision 2 and its risks record the decision.

3. The contract

  • 3.1 At archival, state the rule in a modification of "A project can be initialized with a conforming document". task-3-1

    Initialization decides which project a document belongs to from the document's own location, never from the directory it runs in, with a scenario for each arrangement 1.1 tests and for the project without a store that 1.2 tests.

  • 4.3 Regenerate the installed instruction files for 0.29.1, with htmlspec init --tools claude,codex,pi. task-4-3

The regeneration changed one line in each, generatedBy: htmlspec 0.29.0 to 0.29.1, and nothing else, and check-installed then passed.

5. Review and archival

  • 5.1 Prove the tests can fail: put the working directory back as the place the project is found, and record that the tests from 1.1 fail for A, B, and C. task-5-1

    Record the run in this change's evidence, then restore the repair.

  • 5.2 Take the code review, and settle each finding. task-5-2

    The review of pull request #56 (medium) found one issue, and it was taken: on a filesystem that ignores case, new document into HTMLSPEC/changes/ found the project but compared the destination with htmlspec/ by spelling, so the document got a second store inside the project. The comparison now asks the filesystem whether the two are one directory, which also covers a link at that level (design decision 2). Two unit tests pin it, and both fail under the reviewed comparison (evidence/mutation-testing-2026-10-13.md). It also noted that CHANGELOG.md says the requirement "now states the rule" while task 3.1 writes it at archival. Kept, because the change is archived on this branch before it merges, so the line is true when it lands.

    The review of pull request #55, the promotion this change is stacked on, found that its branch alone fails new_document_creates_a_document_that_validates_immediately, which this change repairs. That is settled by the order in which the two merge, not by this change.

  • 5.3 Archive the change with htmlspec archive, and record the runbook inventory the archive writes. task-5-3

    Design risk "The first archive's runbook inventory" expects it to list no runbook, because the release runbook still sits outside the project. The migration plan's follow-on change starts from what this records.

    Archived on 2026-10-14 as 2026-10-14-resolve-a-new-documents-project-from-its-destination, at version 0.29.1, the first change this repository archives with htmlspec archive. The archive's runbooks.json is {"format": "htmlspec-runbook-inventory/v1", "runbooks": []}: it lists no runbook, as the design's risk "The first archive's runbook inventory" expected, because the release runbook still sits at runbooks/release/, outside the project. htmlspec/runbook-releases.json was not changed, and still names 0.15.0. The migration plan's follow-on change, which moves the runbook into htmlspec/runbooks/release/, starts from this record. Archival asked about this task, the only one still open while it ran, and was answered with --yes.

    The code review of pull request #57 found that archival moved the change one level deeper, from htmlspec/changes/ to htmlspec/changes/archive/, without rewriting its documents' relative references. All four documents pointed at ../../assets/, a store that does not exist from the archive, so none rendered its stylesheet or loaded its scripts, and task 3.1's link to the accepted requirement led nowhere. htmlspec validate accepted all four. The 29 references were rewritten by hand, to ../../../assets/ and ../../../specs/, and every relative reference in the project's 161 documents was then checked against the files on disk. None names nothing. The two defects behind this, archival not rewriting the references it moves, and validation resolving an asset reference by the address it names rather than by its path, are left to a change of their own.
