Resolve a new document's project from its destination: design

A new document finds its project, and so its store, from its own destination. Only a document beneath that project's htmlspec/ uses the project's store, because only those documents can reach it when validation looks.

design

Subject
Resolve a new document's project from its destination: design

The rule

A new document's store is decided by where the document will live. The proposal measured what happens when the working directory decides instead (evidence/the-four-cases-measured-2026-10-13.md). The rule has to agree with validation's search for a document's store, because "Starting a new change", a scenario of document-template's "A project can be initialized with a conforming document", says "the resulting file passes validation immediately". So the rule is built from that search.

Validation looks for the first assets/ directory in the document's own directory or above it (store_for in crates/htmlspec-cli/src/commands.rs). A project keeps its store at htmlspec/assets/, and document-validation's "A project must not store one asset's bytes more than once" names htmlspec/ as "the project's own directory". That store is above exactly the documents beneath htmlspec/. So a document beneath htmlspec/ can reference the project's store and be found, and a document anywhere else cannot.

Decisions

1. The destination finds the project

new_document resolves the project from the destination's directory with ProjectRoot::resolve, the function every project command already uses, in place of ProjectRoot::resolve(Path::new(".")).

The function searches a directory and its ancestors, and stops at the first one holding .git. Called on the destination's directory, it applies the repository boundary that project-bootstrap's "Commands resolve the project from any directory beneath it" states, to the destination's repository rather than the working directory's. It works on a directory that does not exist yet, because it tests each candidate for an htmlspec/ directory and climbs whether or not the candidate exists. So a destination such as htmlspec/changes/new-one/proposal.html, whose directory write_document creates later, still finds its project.

The requirement governs "every command whose subject is a project". The subject of new document is a document, so that requirement never chose the working directory here. The program borrowed it. new change keeps it, because its subject is a project.

2. Only a document beneath the project's directory uses its store

Where the project is found and the destination's directory is beneath its htmlspec/, the document references htmlspec/assets/, establishing it there if absent. Otherwise the document gets a store beside it, as a document outside every project gets today.

The first half is project-bootstrap's "A project has a declared root holding one asset store": "every document in the project SHALL reference that store rather than a store of its own". The second half follows from validation's search: a document in docs/ that referenced htmlspec/assets/ would fail validation, which is the second row the proposal measured. A store beside it lies outside the project's own directory, so it is not one of the project's stores, and document-validation's duplicate rule checks it on its own.

"Beneath" is a comparison of two absolute paths, each made by joining a relative path to the working directory and resolving . and .. lexically, so htmlspec/../docs/notes.html is not beneath htmlspec/. The program's normalize dropped . and kept .., which would leave the prefix in place while the path left the directory, so it now resolves .. too. Added during implementation.

The path is walked as spelled, because ProjectRoot::resolve and validation's store_for both walk a path the way the contributor typed it, and a store chosen through resolved links is one that validation's walk would not find. But whether the destination is beneath the project is asked of the filesystem, the way the walk that found the project asked it: the destination's first directory below the project's root is the project's own directory when the filesystem says the two are one directory. So HTMLSPEC/changes/ on a filesystem that ignores case, or a link to htmlspec/ at that level, uses the project's store, and the store is returned in the destination's own spelling, which is the path validation walks. Added during implementation, and revised after the code review of pull request #56, which found the first version comparing by spelling: on a filesystem that ignores case, the walk found the project through HTMLSPEC/, the comparison did not, and the document was given a second store inside the project.

A document directly in a project's root, beside htmlspec/, is outside the project's directory too, and gets a store of its own. Before this change it referenced htmlspec/assets/ through a path that descends. A reference that descends is one validation does not check when it finds no store above the document, and none is above it. The document rendered, and a reference naming bytes no store holds was accepted as readily as a correct one. With a store beside it, validation checks every reference. Added during implementation.

3. The requirement states the rule

The change modifies document-template's "A project can be initialized with a conforming document" to state that initialization decides which project a document belongs to from the document's own location, never from the directory it runs in, with a scenario for each arrangement the proposal measured.

The contract was silent, and the silence is how the defect lasted: no scenario named an arrangement in which the two directories differ, so no test exercised one until this repository became a project. A requirement with a scenario per arrangement gives each one a test that is owed. The specification is produced at archival, from what was built, so its exact words are settled then.

Alternatives

Mirror validation's search exactly: reference the first store at or above the destination, and create one beside the document where none is found. It is the simplest rule that always produces a document validation accepts. It fails in a project whose store is not established yet, where "Initializing into a project without assets" requires the assets to be established as part of initialization: no store exists above the destination, so the rule would put one beside the document, inside htmlspec/, and the project's own store would never be established. The rule in decision 2 establishes it.

Reference the project's store wherever the destination lies inside the project. It fixes the first and third arrangements and leaves the second, for the reason decision 2 gives.

Risks

A path through a symbolic link

A link that reaches into a project's htmlspec/ from outside the project's root is not seen: the walk that finds a project follows the path as spelled, finds none, and the document gets a store of its own inside the project. The change bears this. A link at the level below the project's root, and a name in another case on a filesystem that ignores case, are seen, because that one comparison asks the filesystem (decision 2). Resolving every link would make the outcome depend on the filesystem's layout rather than on the path a contributor typed, and the failure is not silent: htmlspec assets reports the second store as a duplicate.

A document in a project's root gets a second copy of the runtime

A document written directly into a project's root, outside htmlspec/, used to reference the project's store and wrote one file. It now writes a store of its own beside it, a second copy of the runtime in the repository. The change bears this, because the one-file version carried references that validation never checked, so its provenance was unverified (decision 2). The second store lies outside the project's own directory, so document-validation's "A project must not store one asset's bytes more than once" checks it on its own and never counts it against the project. Added during implementation, when the test new_document_and_post_document_agree was found asserting the one-file outcome.

An arrangement that worked changes

A contributor who relied on the working directory choosing the store gets a different store.

Every arrangement whose references validation checked and accepted before is unchanged: where the working directory and the destination agree, both rules choose the same store. The three failing arrangements change outcome, and so does the document in a project's root, as the risk above states. Tests pin the unchanged arrangement and every changed one.
