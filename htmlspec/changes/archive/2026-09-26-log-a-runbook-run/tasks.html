1. Re-measure the four claims the design rests on, before writing any of it

  • 1.1 Confirm a reference resolving within one document only, with a real run record on disk rather than from the proposal's word.

    The proposal says this was measured and the instruction is to confirm it still holds, because the whole design rests on the copying being forced rather than chosen

    • Confirmed, and it is an error rather than a warning. A verification in runs/probe.html naming req-version-before-regenerate in the runbook's specification.html one directory up: error: refs/unresolved … no unit in the document declares that identifier, exit 1. The copying is forced. Recorded in evidence/the-shape-is-forced-2026-09-18.md.

  • 1.2 Confirm kind=specification fails on every step, and confirm the accepting direction too: that a tasks document carrying requirements and verifications beside its tasks reports nothing

    • Both confirmed. Byte-identical bodies apart from the kind: as tasks, zero diagnostics under default and --strict; as specification, two kind/task-in-specification errors for two copied steps. So "on every step" is one diagnostic per task rather than one per document — a real release run copies four steps and would draw four.

    • The accepting direction matters more and the proposal only implied it: a tasks document carrying task units, requirements with scenarios, and verifications together is accepted with zero diagnostics, because the tasks rule is completeness rather than placement.

  • 1.3 Confirm the three further constraints — a scenario, a strong modal, and data-change="unchanged" — each with its own diagnostic from its own single edit

    • All three, each isolated: scenario removed → error: schema/invalid … /requirements/0/scenarios: [] has less than 1 item; MUST → should → error: schema/weak-modal; unchanged → added → warning: review/stale-verification. Two errors and one warning, which is the split the proposal states.

  • 1.4 Measure what the existing rules report about a run record whose copied requirement no verification names.

    This is the conformance rule's subject, so if something already reports it the rule is unnecessary

    • Nothing, at either strictness. no diagnostics: the document is accepted, twice. requirements_are_verified in rules/review.rs returns early unless the kind is specification, and task 1.2 forces the record to be tasks — so the two forced facts point in opposite directions, and the kind a record must be is exactly the kind the existing rule cannot see. That gap is the whole justification for the project-level rule, and it was measured rather than argued.

    • The early return is correct for its own reason, which the rule's own doc comment states: a requirement unit in a proposal is an author arguing for one. So widening it is not the fix, which is why an_unrecorded_requirement_is_not_reported_by_the_per_document_set asserts the silence rather than treating it as a defect.

  • 1.5 Confirm asset references resolve at runs/ depth, and that validate and format reach a run record with no work

    • href="../../../assets/sha256-…" — three levels, correctly, because runbooks/<name>/runs/ is three below htmlspec/. Needed nothing: the store is derived from the project by ProjectRoot::assets().

    • validate htmlspec/runbooks walks into runs/ and reports on each record; format --check likewise. Both are what is wanted, so this repository's self-runbooks stages would see a committed record with no change to them.

    • And list --runbooks does not see it, which is a finding rather than a defect: the enumeration reads which of RUNBOOK_DOCUMENTS a runbook holds, so a runbook with forty records lists identically to one with none. Recorded in the design; closing it is the aggregate, which is record-a-runbooks-history's.

3. Settle the three decisions the proposal leaves open, with reasoning

  • 3.1 Decide where run progress is reported.

    the-status-gap-2026-09-17.md measured the gap, so read it before deciding rather than deciding from the proposal's summary of it. workflow-reporting governs

    • status is left alone; run progress is htmlspec run --check's. The measurement decides it: the predecessor found that status --change <runbook-path> works and counts correctly, so the reusable part already reaches a runbook and what is wrong is the report's shape — absent proposal.html about documents a runbook never has. Teaching it a second shape means branching on what its argument turned out to be, and then --change is false for half its inputs.

    • workflow-reporting's A report answers the contributor in their own terms is the governing clause, and its scenario is exact: a report whose first claim names a document count does not show the request was understood. A contributor asking about a run asks what it recorded.

    • The stronger reason is that the two reports are not one report with a branch. A run's reader wants outcomes, not a fraction — which is a different report built from different units, and it is the conformance rule's output.

    • Not closed: status --change by name pointed at a runbook is still a refusal, which is the form a workflow would use. Recorded in the design's risks on the same terms the predecessor recorded it.

  • 3.2 Decide whether a run can be resumed, which decides whether a record is ever edited after it is written

    • A run can be resumed, so a record is edited after it is written. The argument is that the alternative contradicts the document's own kind: a tasks document's steps carry in-progress, and a record written once could never carry it honestly — it would mean "in progress at the instant the file was written and nobody knows what happened next". A model making a state in the vocabulary unreachable is the wrong model.

    • The batch abandoned at step 6 is the case, and two records would each be wrong about it: the first says six done and four unstarted, which reads as a run that stopped; the second cannot say done for the six it did not do, nor todo for six that are finished.

    • This is what makes the review/* severity necessary rather than convenient. A resumed run legitimately has requirements nothing has recorded, so an error would fail every run at the moment it began. Asserted rather than argued: a_just_started_run_has_recorded_nothing drives the real binary and asserts exit 0.

    • Cost stated: two runs a week apart are indistinguishable on disk from one run interrupted for a week. No timestamp is recorded, for project-bootstrap's reason about an uncompared version — the filesystem already has mtime, and when a run happened is record-a-runbooks-history's question.

  • 3.3 Decide whether run copies eagerly or lazily, and what it names the record.

    Name every rejected candidate and what it broke, because a naming scheme is exactly where runbook-authority's prohibition on deriving an ordering from a name gets violated quietly

    • Eagerly, and the name is the contributor's with no default. htmlspec run <runbook> --as <record>.

    • Eager because a lazy copy has no honest content for the steps it has not reached: between steps 2 and 3 the record would state a three-step procedure, and nothing in a list of steps says there are more. The record exists to say which version of the procedure ran, and a partial copy shows a version that never existed.

    • Two rejected naming schemes, each for a stated reason rather than taste. A date (2026-09-18.html) collides when a procedure runs twice in a day, and it would make the record's name the one place a time is recorded — which 3.2 declines to do. A sequence number (run-7.html) requires reading an ordering out of the directory's contents, and runbook-authority states that nothing SHALL derive an ordering, a version, or a history from a runbook's name; the maintained-list shape is what the contract refuses.

    • --as is required rather than defaulted, because an operation that invented a name would choose on the contributor's behalf and artifact-kinds requires a derived name to be reported. The failure message says why, so a contributor meets the reasoning rather than a bare usage error.

    • Checked through ProjectRoot::is_a_name, which is where the predecessor moved this invariant after re-litigating it at three call sites. Verified that a refused name leaves nothing on disk, including no runs/ directory — a name refused after a directory was created would have left the traversal's effect behind.

  • 3.4 Decide whether a run record is a canonical document, since runbook-authority already requires unchanged in a runbook's canonical documents and that sentence now binds.

    Decide from the measurement rather than from the word

    • It is, and the measurement decides it rather than the word "canonical". A copied requirement declared added draws review/stale-verification — the record's own verification attesting to an obligation the record says does not exist yet. The obligation existed before the run started, which is the same fact as the runbook's own documents arriving at the same attribute.

    • So the delta states it once for a runbook's documents including its records, rather than adding a second clause.

    • run is the operation that knows what it is writing, which narrows the-canonical-documents-change-state-2026-09-17.md's finding without closing it: an author writing a record by hand still meets the warnings, and so does an author writing a runbook by hand. The delta says so explicitly.

4. The contract

  • 4.1 State the new capability runbook-execution: what a run is, where its record lives, what the record carries, and that the record is history rather than contract

    • Five requirements. The fifth — that a record is history rather than contract, and is refused by the comparison — is the one contract-authority implies and that writing the delta showed was needed explicitly, exactly as the predecessor found for runbook-authority's last requirement.

  • 4.2 Modify runbook-authority so a runbook's specification states what its runs must record, and a runbook that states nothing has runs nothing checks

    Done, and it gained a clause the task did not anticipate: a log requirement is not distinguished in the markup from a hazard requirement, so every requirement a runbook states is one its runs must record. That reading is forced — distinguishing them needs an attribute the closed vocabulary does not have — and the delta states the cost rather than leaving an author to find it: a runbook stating ten hazards obliges every run to record ten outcomes.

  • 4.3 State the conformance obligation: that a run whose records do not satisfy the log contract is reported, that the report never gates, and what it deliberately does not report

    • Three exclusions, each with its reason: a runbook nobody has run, a run whose recorded outcome says the check did not pass, and a run recording more than it owed.

    • The second needed a distinction the proposal did not draw, and the implementation is where it appeared: a verification recording failed recorded an outcome and satisfies the obligation, while one recording not-run recorded none and does not. That line is drawn in the caller rather than in the rule, so "which outcome it was" is not representable in the rule's input type at all.

  • 4.4 Confirm document-schema, artifact-kinds, and document-validation are untouched.

    The proposal states this as a checkable claim; if one needs modifying, stop and report rather than widening scope

    • Untouched, checked against the diff. specs/ in the change holds exactly two capabilities, and git diff --stat crates/htmlspec-schema/ is empty.

  • 4.5 Run openspec validate --all.

    carry-a-runbook-to-another-machine fails for having no deltas — pre-existing, expected, not to be fixed

    • change/log-a-runbook-run passes. Totals: 12 passed, 1 failed, and the one failure is the successor holding only a proposal. Untouched.

6. The conformance rule

  • 6.1 Write crates/htmlspec-validate/src/rules/runs.rs, built the way topology.rs is built: a plain function over gathered facts, not a crate::engine::Rule.

    The module header states why a project-subject rule cannot be a per-document one, in this rule's own terms rather than by pointing at topology's

    • Done, and the reason is one step stronger than topology's: duplication is a fact about the directory around a document, and an unrecorded requirement is a fact about two documents at once. There is no document to attach it to, because validating the record cannot know what was required and validating the specification cannot know what was recorded.

    • The signature is the design: conformance(&RunbookUnderReview) -> Vec<Diagnostic>, taking gathered identifiers rather than paths, so the walk stays in the caller and the rule gets no filesystem capability. AGENTS.md §6.

  • 6.2 Leave it absent from rules::ALL, and add the assertion that keeps it absent.

    duplication_is_not_reported_by_the_per_document_set is the model

    • Absent, and an_unrecorded_requirement_is_not_reported_by_the_per_document_set asserts it — over a tasks document carrying a requirement no verification names, which is exactly what a short record looks like.

    • Its second assertion is the load-bearing one and it is not about this rule. It asserts the whole set reports nothing about that document, which is the measurement from task 1.4. A change widening review/unverified-requirement to every kind would fail here rather than quietly making this rule redundant — and that change would also start reporting every proposal arguing for a requirement.

  • 6.3 Confirm the severity comes from the namespace rather than from the rule, and that --strict cannot promote it.

    Assert it rather than reading it

    • an_unrecorded_requirement_is_a_warning_strict_mode_cannot_promote in the rule's own tests, and no_report_about_a_run_ever_gates in the fixture suite — the second asserting it from outside the validator across every fixture, which is where the other suites assert the safety/* floor.

  • 6.4 Unit-test the rule over its own cases: a conforming run, a run missing a verification, a runbook with no runs, a run recording failed, and a run verifying something the runbook does not require

    Eight tests, three beyond the five asked for. each_short_run_is_reported_separately, because a loop reporting the first short record and stopping would pass all five. a_run_that_has_recorded_nothing_yet_is_reported, which is the state run leaves behind and the other side of the failed/not-run line. And the severity assertion above.

7. The run operation

  • 7.1 Add the Run subcommand to crates/htmlspec-cli/src/main.rs with --as and --check

    • Done. The two modes are resolved in one match on (check, record), so the three wrong combinations each get a report naming which flag is missing or surplus rather than clap's generic conflict message.

  • 7.2 Implement the copy: read the runbook's two documents, compose a record carrying the procedure with data-change="unchanged", the copied requirements with their scenarios, and one not-run verification per requirement

    • The one substantive implementation decision is that the copy is a DOM clone rather than a re-render from the projected model, and it is stated in the module header. The projection flattens a unit's text to strings, and the release runbook's four task notes carry 30-odd inline elements between them — so a record composed from the model would read as a worse version of the procedure that ran, which defeats the point of carrying the steps. It would also still validate, so no other test would notice. a_record_carries_the_procedure_and_the_copied_requirements asserts the <code> and <strong> survive.

    • htmlspec_format::format makes the composed result canonical, so format --check is not a second step a contributor has to know about.

    • An absent specification.html is not a failure, because runbook-authority says a runbook stating no log requirement is not reported — so a run of a runbook that states nothing is still a run worth recording.

  • 7.3 Validate what was written before reporting success, which is what write_document already does and for the same reason: a failure is a defect in this program, not in a contributor's project

    • Through commands::validate_source_at, which resolves a real store rather than passing Absent — the strong form of the promise, since the record is checked against the bytes actually beside it. Asserted under both strictnesses, because the four constraints are each a diagnostic and one mis-implemented could pass by default and fail strict.

  • 7.4 Refuse to overwrite an existing record, and check the name through ProjectRoot::is_a_name

    • Both. starting_a_run_does_not_overwrite_a_record edits the record first and asserts the edited bytes survive, rather than asserting a file of the right name exists — otherwise a rewrite would pass.

  • 7.5 Implement --check: gather, evaluate, report, write nothing, exit zero

    • Exit zero whatever it finds, asserted. And it distinguishes its three silent cases — no runs, no stated requirements, and every run conforming — because a reader told "each run records what the runbook states" about a runbook with no runs would read it as a pass.

  • 7.6 Emit the structured payload for both modes

    • Both, keyed by the words the flags use. Asserted through parsed JSON rather than string matching.
