Log a runbook run

This change gave a runbook's runs a record. It made a runbook's specification state what its runs must record, made a unit in a run's record declare that it is unchanged, and required the operation that starts a run to declare that state itself (A runbook records what its history taught; The canonical procedure carries no completion state). It added the runbook-execution capability, which states where a run's record lives, that the record carries the procedure it ran and the obligations it attests to, that a run is one record from start to finish, that a run's conformance to its runbook's contract is reported and never gated, and that the record is history rather than contract (A run leaves a record where the runbook keeps them; A record carries the procedure it ran and the obligations it attests to; A run is one record from start to finish; A run's conformance to its runbook's contract is reported and never gated; A run's record is history rather than contract).

runbook-authority

A runbook records what its history taught req-a-runbook-records-what-its-history-taught

A runbook's specification SHALL state the hazards its procedure has met, as requirements rather than as remarks. A hazard stated as a remark in a procedure's steps is what the project already had: an archived tasks document, which nothing reads and which binds nothing.

Where the order of a procedure's steps is constrained by a hazard rather than by convenience, that constraint SHALL be stated with the hazard that forces it. An order whose reason is unstated is an order the next person reverses.

A runbook SHALL NOT be treated as stating an obligation of the project. A runbook is a procedure the project keeps, and the project's contract is what its accepted specifications state. A requirement in a runbook's specification states what that runbook requires of a run, not what the project requires of itself.

A runbook's specification SHALL state what its runs must record, as requirement units of the same kind the hazards are stated as. This is the runbook's logging contract, and it is stated where the runbook is authored because the person who knows a cookie run needs an oven temperature is the person writing the recipe. There is no single thing a run should record: a release run records the version it advanced to and whether the release check passed, and neither value means anything to a baker.

A log requirement SHALL NOT be distinguished in the markup from a hazard requirement, and the consequence is that every requirement a runbook's specification states is one its runs must record. That reading is the correct one rather than a simplification, because the sentence above already covers both: a hazard the procedure met and a value a run must record are each what this runbook requires of a run. Distinguishing them would need an attribute or a unit the artifact vocabulary does not have, and the vocabulary is closed.

The honest cost of that, stated rather than discovered by an author: a runbook whose specification states ten hazards obliges every run to record ten outcomes, and an author who wanted five obligations and five notes has no way to say so. What is available is to state fewer requirements and put the rest in the prose the specification already carries.

A runbook that states no log requirement SHALL NOT be reported. A procedure whose runs record nothing is a procedure nothing checks, which is a fact about that runbook rather than a fault in it — and a report firing on every runbook that has not yet stated a contract is one an author meets before they have anything to say.

The canonical procedure carries no completion state req-the-canonical-procedure-carries-no-completion-state

A runbook's tasks document SHALL carry its steps in the state they have before anyone works them, and that state SHALL NOT advance as a consequence of the runbook being run. The states advance in the copy a run makes, exactly as they advance in a change.

Nothing SHALL report a runbook whose steps are all unstarted. That is the correct state of a canonical procedure at every moment, so a report of it would fire on every runbook always, which teaches a reader to ignore the report.

An enumeration of a project's runbooks SHALL NOT present a completion fraction for the canonical procedure. The fraction is derivable and it is the same value forever, and a column that never moves is read once and then not read.

A unit in a runbook's canonical documents SHALL declare that it is unchanged. A change state describes a unit's relationship to a change in progress, and a runbook has none: its procedure exists and the hazards it records were measured before the document was written. This is the same fact as the preceding paragraphs rather than a second rule, arriving at a different attribute.

A unit in the record of a run SHALL declare that it is unchanged for the same reason, and this is that sentence reaching the one other document a runbook holds rather than a new obligation. A run's record carries the requirements it verifies, copied from the runbook, and a verification recording an outcome against a requirement declared added is reported — correctly — as attesting to an obligation that is not there yet. The obligation a run attests to existed before the run started, so the copy declares itself unchanged.

The consequence is what makes it worth stating. A verification that records an outcome against a requirement declared as added is reported, correctly, as attesting to an obligation that is not there yet — so a runbook whose units are declared the way a change's units are declared reports warnings whose cause is one attribute, and nothing states which. The operation that creates a document SHALL NOT be expected to know the difference, because it cannot: whether a document belongs to a change or to a runbook is not a fact about the document being written.

The operation that starts a run is the exception, and it SHALL declare the state correctly. It knows what it is writing — a copy of an existing procedure, attesting to obligations that already exist — so the reason the general document-creating operation cannot know does not apply to it. This narrows the preceding paragraph rather than contradicting it: an author writing a run record by hand still meets the warnings, and so does an author writing a runbook by hand.

A run leaves a record where the runbook keeps them req-a-run-leaves-a-record-where-the-runbook-keeps-them

A run of a runbook SHALL produce a record, and that record SHALL be a document beneath the runbook's own directory, in a place the runbook keeps for its records. A run that leaves no record SHALL NOT be treated as having happened, because the question a runbook exists to answer — which version of this procedure ran, and what did it produce — has no other source.

The place SHALL be derived from the runbook rather than composed by whatever operation writes into it, exactly as the runbook's own location is derived from the project. A location composed by a caller is a second statement of where a thing lives, and two statements agree until the day the layout moves.

The place SHALL be created by the operation that writes the first record rather than when the project is bootstrapped or when the runbook is created. This is narrower than the obligation on the project's own places and it is not in tension with it: the project's places are the four a contributor looks for and one of them cannot exist before its runbook does.

A run's record SHALL reference the project's one asset store, as every other document in the project does.

A run's record SHALL NOT be resolvable as a change, and the operations that take a change SHALL refuse it. A record archived is a run's history destroyed, which is the same failure archiving a runbook is, one directory further down.

A record carries the procedure it ran and the obligations it attests to req-a-record-carries-the-procedure-it-ran-and-the-obligations-it-attests-to

A run's record SHALL carry the runbook's procedure, copied, with each step's state advanced as the run advanced it. A record that referenced the procedure instead of carrying it could not say which version of the procedure ran, which is the question the record exists to answer: a procedure improves, and a record naming one that has since changed describes a run that did not happen that way.

A run's record SHALL carry the requirements it attests to, copied from the runbook's specification, each with the scenarios that make it checkable. This is forced rather than chosen. A reference addresses a unit within one document, so a record naming a requirement in the runbook's specification resolves to nothing and is reported as an error — a record that pointed outward would be invalid on the day it was written.

Each copied requirement SHALL state its obligation in a form that carries an obligation, and SHALL declare itself unchanged. Both follow from the copy being a faithful one: a requirement whose modal is weakened states a preference, and a requirement declared as being added claims an obligation that is not there yet.

A run's record SHALL record, for each requirement it carries, an outcome and how that outcome was reached, precisely enough that someone else could repeat it. The outcome and the method are the recorded values, and a record stating an outcome with no method is a claim nobody can check.

The copy SHALL be whole at the moment the run starts rather than grown as the run proceeds. A partial copy presents itself as a complete procedure — nothing in a list of steps says there are more — so a reader between two steps would see a version of the procedure that never existed.

A run's record SHALL be of the artifact kind that carries work, and the set of kinds SHALL NOT gain one for a run. A record is a copy of a procedure with its states advanced, which is what that kind already is; and the kind that carries obligations refuses a step outright, so a record declared as one would be invalid for every step it carried.

Migration note: as built, a requirement the runbook's specification declares removed is not copied into the record, because a verification naming it would be reported as the error refs/removed-target (document-schema's Cross-references address units by identifier). The delta's "the requirements it attests to" does not name a withdrawn requirement. The review round decided the exclusion, as finding 11 in evidence/the-review-fixes-2026-09-20.md, and the report leaves the requirement out too (A run's conformance to its runbook's contract is reported and never gated).

A run is one record from start to finish req-a-run-is-one-record-from-start-to-finish

A run interrupted and continued SHALL be one record rather than two, and a run's record SHALL therefore be editable after it is written. A procedure abandoned at step six and picked up an hour later is one piece of work, and two records would each be wrong about it: the first would state six steps done and four unstarted, and the second could state neither for the six it did not do.

A record SHALL be able to state that a step is under way. The vocabulary for a step's state includes that value, and a record written once and never touched could never carry it honestly — which would make a state in the vocabulary unreachable for the one document whose steps actually advance.

The operation that starts a run SHALL NOT overwrite an existing record. A run continued is that record edited; a run started is a new one. An operation that wrote over a record would destroy the history the record exists to hold.

A run's record SHALL NOT be required to state when the run happened. A recorded time nothing compares is accuracy without authority, which is the same objection that keeps a runbook from declaring a version of its own. The consequence, stated rather than left to be found: two runs a week apart are indistinguishable from one run interrupted for a week, and the question of when a run happened is settled where a runbook's history is settled.

Migration note: as built, the operation that starts a run composes the record, validates it, and only then writes it, so a record that does not validate never reaches disk and a retry under the same name is not refused as an existing record. No requirement states that order. The review round reordered it from writing first and validating after, which is how the design's last risk describes it, and recorded the reorder in evidence/the-review-fixes-2026-09-20.md.

A run's conformance to its runbook's contract is reported and never gated req-a-run-s-conformance-to-its-runbook-s-contract-is-reported-and-never-gated

A run whose record does not attest to every requirement the runbook states SHALL be reported, and the report SHALL name both the run and each requirement nothing in it attests to. A report naming only the run leaves a reader to find which requirement, and a report naming only the requirement leaves them to find which run.

The report SHALL NOT fail validation and SHALL NOT be promotable to a failure. A run under way legitimately has requirements nothing has verified yet, because a run is one record from start to finish, so a check that failed the run halfway through would gate the work that produces the very records it asks for. This is the same policy that keeps a specification in progress from failing: the report marks work for attention rather than blocking it.

The subject of the report SHALL be a runbook and its runs together, so the check SHALL be evaluated where both are in view rather than as part of validating one document. Neither document alone can decide it: the specification states the requirements and the record states the outcomes. A check that ran over each document would report one violation once per document, and none of it would be a fault of the document being validated.

The report SHALL NOT be produced for:

  • a runbook nobody has run. A procedure with no runs violates nothing, and a report firing from the moment a runbook is created is one a reader learns to ignore.

  • a run whose recorded outcome states that the check did not pass. The obligation is that the run recorded an outcome, not that the outcome was good. A batch that came out wrong is a bad batch and a correct record of one, and a report that treated a recorded failure as a document fault would teach an operator to record a pass.

  • a run attesting to something the runbook does not require. A run that recorded more than it owed is not at fault.

Migration note: as built, the report asks no outcome for a requirement the runbook's specification declares removed, which the record does not carry either (A record carries the procedure it ran and the obligations it attests to). The delta's "every requirement the runbook states" does not name a withdrawn requirement. The review round decided the exclusion for both paths, as finding 11 in evidence/the-review-fixes-2026-09-20.md.

A run's record is history rather than contract req-a-run-s-record-is-history-rather-than-contract

A run's record SHALL NOT be treated as stating an obligation, of the project or of the runbook. It records what one run did. The requirements it carries are copies of the runbook's, and the runbook's are what that runbook requires of a run rather than what the project requires of itself.

A run's record SHALL NOT be compared against the project's accepted specifications, and the operation that performs that comparison SHALL refuse one. A record's copied requirements belong in no accepted specification, so a report directing an agent to merge them would put obligations nobody wrote into the contract by the hand of an agent doing as it was told.

A count of a runbook's runs SHALL be derived from the records rather than stored. A maintained count is a value kept beside the facts it summarizes, which depends on a convention nothing enforces.
