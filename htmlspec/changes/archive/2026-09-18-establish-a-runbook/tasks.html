1. Build the recipe first, before anything else

  • 1.1 Build the chocolate-chip cookie recipe as a real runbook, nine steps from creaming the butter to the wire rack, with the citation links it came with.

    Before the release runbook and before any code, because the release procedure is made of commands and a proposal arguing only from it invites the reading that a runbook is a script with prose around it. Nothing in a bowl of creamed butter automates

    • Nine task units, five citation links, in evidence/the-cookie-recipe-2026-09-17.md.

    • Built in a scratch project rather than in this repository, and that detail turned out to be the change's largest finding. This repository is not an html-spec project, so it has no htmlspec/ to put a runbook in — and creating one breaks the suite. Section 3 is where that lands.

    • Every one of the nine steps is a reading rather than a command: creaming time is read from colour and volume, the bake gives a range and says the range is the baker's judgment, and one step is named as the only irreversible one. There is no scripts/bake that could replace it, which is what the recipe exists to establish.

  • 1.2 Record that htmlspec validate, htmlspec validate --strict, and htmlspec format --check all accept it.

    The proposal claims this needs no code change — verify that claim and report the truth either way, since the whole approach rests on a runbook's documents being ordinary documents of existing kinds

    • The claim holds. All three accept it on the binary at 056df05 with no modification. validate --json reports accepted: true with an empty diagnostics array — zero, not zero errors alongside warnings.

    • Two properties fall out that the task did not ask for and neither needed adding: a runbook's tasks.html with no task unit is reported by kind/no-tasks, and a runbook's specification.html carrying a task unit is an error under kind/task-in-specification. So the forced split does work rather than merely being obeyed — the procedure cannot drift into the canonical document. Asserted as the_two_document_split_is_forced_by_validation.

  • 1.3 Confirm the citation links survive, and name the line that is why.

    href is deliberately unchecked on a at crates/htmlspec-validate/src/rules/safety.rs:37 — a hyperlink is a citation and the document renders offline without it — and checked on link, which loads

    • Confirmed, five links, none reported. The line is exactly where the proposal says it is and it predates any recipe.

  • 1.4 Record where the ingredients went and why.

    The proposal predicts this gap and forbids inventing a mechanism for it, so this task records what was hit rather than closing it. An ingredient is not a step somebody performs, so a task unit is the wrong home, and the reason each rejected option is wrong belongs in the evidence

    • A <table> in a document section titled "What the procedure consumes", with a paragraph in the document saying this is a finding rather than a design. Stated as the agent's choice, which is contract-authority's second route under silence — it is the cheapest thing to convert once inputs get a notion.

    • The rejected options and why: a task unit would make status count a list of quantities as work (measured — the document reports 0 of 9, and an ingredients task would make it 0 of 10); a requirement unit would draw schema/weak-modal, since "1 cup of butter" carries no modal.

    • The equipment is the harder half and it is why the proposal says the shape of the answer is not obvious. A stand mixer and two baking sheets are closer to a machine requirement — carry-a-runbook-to-another-machine's subject — than to an ingredient. So the input gap and the machine-requirement gap touch inside one paragraph of one document.

2. Verify the status --change gap the proposal corrects itself about

  • 2.1 Point htmlspec status --change at a runbook, by name and by path, and record the actual behavior.

    The proposal first claimed completion counting comes free and then withdrew it; confirm which parts of the withdrawal are right

    • The proposal is wrong about the path form, and its conclusion survives the correction. By name: refused, exit 2, no change named chocolate-chip-cookies in …/htmlspec/changes.     • So "reads only the changes directory" is false, and "the logic is reusable and it does not reach a runbook today" is true in a stronger form: it is reusable and correct, and what does not reach a runbook is the name form — the one a contributor or a workflow would use.     • Two artifacts of the report are wrong for a runbook and neither is a bug in status: it reports absent proposal.html and absent specification.html against CHANGE_DOCUMENTS, which is a change's four-document shape. 4. The contract

  • 4.1 State the new capability runbook-authority: what a runbook is, where it lives, that it is a directory of two documents of existing kinds, and which of them carries authority

    • Six requirements. The last of them — that a runbook is not cited as an obligation of the project — is the one contract-authority already implies and that writing two specifications side by side showed was needed explicitly. See task 8.3.

  • 4.2 State that a runbook's canonical procedure carries no completion state, because a run is a copy.

    The tasks stay todo forever because nobody works them

    • Gained a clause the task did not anticipate, from a finding the implementation produced: a unit in a runbook's canonical documents declares itself unchanged. That is the same fact about the same thing arriving at a different attribute, so it is stated in this requirement rather than as a second one. Two scenarios cover it. Measured in evidence/the-canonical-documents-change-state-2026-09-17.md.

  • 4.3 State that a runbook carries no version and no changelog of its own, with the accepted-specification analogy as the reason and the one exception named as carry-a-runbook-to-another-machine's

  • 4.4 State that the project enumerates its runbooks, and that discovery is from the filesystem rather than from a maintained list — the shape project-bootstrap refuses when it forbids reading the last archived version out of a directory name

    • Four scenarios, one of which — An enumeration nobody maintains — is pinned by a test that creates a runbook directory by hand and asserts it appears.

  • 4.5 Modify project-bootstrap's A project has a declared root holding one asset store so the layout sentence names the fourth place.

    Modified rather than quietly extended, and the reason that this is not a closed set being reopened belongs in the delta: the kind enum declares itself CLOSED and has a guard test, and this sentence has neither

    • Done, with that argument in the delta and generalized: a later change adding a fifth place owes the same stated reason rather than a new argument about whether it may.

    • A second requirement in the same capability needed modifying and the proposal did not name it. Bootstrapping is repeatable without loss protects "the project's accepted specifications, active changes, and archive" by name. A list naming three of four places would leave the fourth's protection resting on a reading, so runbooks is named in it with a scenario. Not scope creep — the same sentence, the same capability, and the omission would have been a real gap.

  • 4.6 Confirm artifact-kinds, document-schema, and document-validation are untouched.

    The proposal states this as a checkable claim. If any of them needs modifying, stop and report it rather than widening scope

    • Untouched, and this held without strain. specs/ in the change holds exactly two capabilities. The claim was checkable and it checks.

  • 4.7 Run openspec validate --all

    • change/establish-a-runbook passes. Totals read 11 passed, 2 failed, and both failures are the successor changes — log-a-runbook-run and carry-a-runbook-to-another-machine each hold only a proposal, so each reports "no deltas found". Deliberately out of scope and untouched.
