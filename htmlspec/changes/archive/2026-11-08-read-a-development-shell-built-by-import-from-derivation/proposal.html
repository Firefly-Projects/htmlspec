Read a development shell built by import from a derivation

A toolchain check refuses every Nix development shell that imports from a derivation, even when this machine already holds what the import reads, and its report quotes Nix's trace instead of Nix's error, so nobody can tell why. This change lets the check read such a shell from the store while still building and downloading nothing, and makes the report quote the error, as a patch release, 1.3.2.

Kind
proposal
Contract
1.0.0
Subject
Read a development shell built by import from a derivation

Why

A project whose development shell builds a tool with import from a derivation carries runbooks that each declare a toolchain check over its flake's default development shell. htmlspec preflight refuses every one, outside the shell and inside nix develop alike, and htmlspec run --as refuses too, because runbook-portability's "Preflight gates the creation of a run" makes the start take the same observation and allows no override. The shell is ordinary Nix, built the standard nixpkgs way. It passed the check until the project added that tool, and it has failed every check since.

The cause is one flag. The adapter evaluates the shell with --no-allow-import-from-derivation. A package from nixpkgs' callCabal2nix, for one, runs cabal2nix in a build and imports the Nix file the build writes, which is an import from a derivation, and with that setting off Nix refuses every such import, whether or not the store already holds the output. On the machine that reported it, the output was in the store, and Nix still said:

error: cannot build '/nix/store/….drv^out' during evaluation because the option 'allow-import-from-derivation' is disabled

The report never shows that line. The adapter quotes the first three lines of what Nix wrote, and Nix writes its trace first and its error last, so the operator reads:

observed: the manifest could not be evaluated read-only: error: /        … while calling the 'map' builtin /          at «string»:1:217: (make the environment inspectable from what this machine already holds — …)

and a remedy telling them to realize an environment their machine already holds. Nothing they can do in the shell changes the outcome.

Both halves break the contract. runbook-portability's "Package manifests retain authority over package pins" says the adapter "SHALL cover a local locked Nix flake's development shell" and that preflight SHALL NOT build or download. Its scenario "Resolving the environment would require provisioning" allows a refusal only when the environment "cannot be inspected using locally available data", and this one can. The same requirement makes a refusal come "with an explanation", and a quoted trace explains nothing. The flag came from the design of carry-a-runbook-to-another-machine, which archived the check at 0.15.0 and chose "import-from-derivation disabled" as its means of building nothing. The means was stronger than the end, and every release from 0.15.0 to 1.3.1 carries it. No test caught it, because the adapter's tests script Nix's answers, and the answer they pin came from this repository's own flake, which imports from no derivation.

What changes

  • The check reads an import from a derivation, and still builds nothing. The evaluation drops --no-allow-import-from-derivation and passes --option allow-import-from-derivation true --max-jobs 0 --builders '', beside the --offline it already passes. --max-jobs 0 leaves no local build slot and --builders '' no remote builder, so nothing builds. The review of the pull request found that --offline leaves substitution on wherever a configuration sets it, and that it never stopped a shell's own fetch, so the evaluation also passes --option substitute false and sends its child's every connection, by libcurl or git, to a closed local port. An import whose output the store holds is read. One whose output it lacks is refused, unbuilt, and the check reports the environment as unavailable, as it does today for any input this machine does not hold.
  • The report quotes the evaluator's error. Where Nix fails, the excerpt starts at the last line that opens with error:, which is where Nix states the cause. Output with no such line is quoted from its first lines, as now.
  • The remedy names the import. The refusal's remedy says that a file the shell imports from a derivation must already be built in the store, and that entering the shell once builds it.
  • Real Nix checks it. Beside the scripted tests, which keep pinning the argument vector, a test runs this machine's Nix against a small flake whose shell imports from a derivation, once with the import's output in the store, where the check passes, and once without it, where the check refuses with Nix's error and no output appears in the store. The suite runs inside the Nix sandbox, where no Nix is available, so this test is marked ignored and is run by hand, and the README says how.
  • The documents stop describing the old flag. The README and the release runbook said the evaluation runs with "import-from-derivation disabled". Both say instead that it runs with local builds and remote builders disabled. The release runbook's text changes, so it moves to 0.6.1.

What working looks like: in the project that reported it, inside nix develop, htmlspec preflight reports each of its runbooks with a toolchain check ready. Outside the shell, one whose tool the machine also has from another installation still refuses, naming that installation, which is that runbook's own scenario for a run started outside the shell. On a machine whose store has lost the import's output, preflight refuses as unavailable, and the observed line reads error: Cannot build '/nix/store/….drv'. / Reason: local builds are disabled (max-jobs = 0), which names the build it declined to do. Nothing in the store changed.

Alternatives considered

  • --read-only in place of the three settings. It reads like the guard this needs and is not one: with the import allowed under --read-only, Nix built an import's derivation the store had never held, on the machine where this was diagnosed and again on a scratch flake while this change was written. A flag that does not stop a build cannot be what keeps preflight from building.
  • Keep refusing and document it. Telling runbook authors that a shell with an import from a derivation cannot be checked contradicts "SHALL cover a local locked Nix flake's development shell", and the contract nowhere excludes such a shell. It would also leave a standard nixpkgs pattern outside the only adapter the project has.
  • Leave the setting to the operator's nix.conf. The adapter states the setting on the command line, which overrides nix.conf and NIX_CONFIG, and stating it is right: what preflight may do to a machine is the adapter's promise, not a setting the machine supplies.
  • A tool check in place of the toolchain check. A runbook could check each tool's version instead. That reads a version and not provenance, so it weakens the runbook's requirement to work around a defect in this program.
  • Change the flake. The project could stop importing from a derivation. That repairs a fault the flake does not have, in every project that meets it.
  • Quote the whole of Nix's output. The trace is long, and the excerpt's bound exists so a report stays readable. Starting where the error starts gives the reader the cause inside the same bound.

Scope

  • It changes no command, flag, exit code, or payload field. Only the wording of a refusal's observed text and remedy changes, which toolchain-packaging's "The command surface is stable within a major version" leaves out of the stable surface. It is a patch release, 1.3.2, and tests/surface/1.3.json does not move.
  • It does not change what preflight refuses to do. It still installs, builds, downloads, updates, and enters nothing.
  • It does not change the probe's ten-second deadline or its output limit, the expression it evaluates, or which inputs it reads.
  • It does not change how any other probe quotes a program's output.
  • It adds no adapter for another package manager, and it changes nothing in the project that reported the defect.
