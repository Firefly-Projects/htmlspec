Ship through four channels

The contributor chose four ways for people to install html-spec 1.0: the Nix flake, prebuilt binaries on a GitHub release, crates.io, and Homebrew. Today only the flake works, and only for someone who can read this private repository. This change makes the other three work from one release tag in the public repository, Firefly-Projects/htmlspec: it makes the six library and program crates publishable, adds a release workflow that builds the binaries, publishes the crates, and updates a Homebrew formula, and says in the README how to install through each channel. It releases nothing: the first tag is pushed after the 1.0.0 change. Revised on 2026-10-19 after the code review of #63.

Subject
Ship through four channels

Why

The contributor decided the channels on 2026-10-16: the Nix flake, GitHub release binaries, crates.io, and Homebrew. The crates are owned by the crates.io account smurphy8, with a Firefly-Projects GitHub team as co-owner, and the Homebrew tap is a repository in the same organization, Firefly-Projects/homebrew-tap. Each channel's state today, measured on this branch:

Channel Today What it needs
Nix flake flake.nix already declares packages.default and apps.default for four systems Nothing but a public repository: nix run github:Firefly-Projects/htmlspec then works
GitHub release binaries No release workflow. .github/workflows/ holds check.yml, pr-guard.yml, and publish.yml A workflow that builds macOS and Linux binaries on a version tag and attaches them with checksums
crates.io None of the names is taken: cargo search htmlspec found nothing on 2026-10-16 Three blockers fixed, then a publish from the tag within crates.io's limit on new crates
Homebrew Nothing A formula in Firefly-Projects/homebrew-tap that installs the release binary and checks its digest

The two crates.io blockers. First, the workspace names its own crates by path alone, in [workspace.dependencies], and a published crate needs a version on every dependency it names. Second, htmlspec-assets reads the document templates and vendor.lock.json from the repository's root assets/ through include_str!("../../../assets/…"), and its build script reads the vendored runtime from ../../assets. A published crate holds only its own directory, so built from crates.io it finds none of them. Third, no crate carries license text, and htmlspec-assets ships vendored files under the BSD-3-Clause license while its manifest names MIT alone.

Two more crates reach outside their directory without blocking a publish. htmlspec-parse's build script reads the workspace's Cargo.toml and Cargo.lock to record the pinned html5ever, and reports unknown when they are absent, which its own tripwire test catches. Several crates' tests read fixtures/ and README.md. Cargo builds a published package without its tests, so neither stops a crate from building. The first version of this proposal said that no other crate reads outside its directory, and that was wrong.

Publishing six new crates meets a limit. crates.io lets one account publish a burst of five new crates, so a single command publishing all six stops at the sixth, and a rerun stops at the first crate that already exists.

toolchain-packaging's "The program is distributable as a standalone artifact" requires that the toolchain can be packaged to run without a source checkout. It says nothing about where the artifact is published or how a release reaches it.

What working looks like

  1. cargo publish --workspace --dry-run packages and builds all six crates, in dependency order, from their own directories, each with its license text.
  2. scripts/set-version X.Y.Z moves the version and every internal pin together, and the release runbook's version step runs it.
  3. In the public repository, pushing a tag v1.0.0 whose version matches Cargo.toml runs one workflow. It builds the macOS and Linux binaries, attaches them to a GitHub release with a checksum file and the version's changelog entry, publishes the crates one at a time, and updates the formula in Firefly-Projects/homebrew-tap. A publication stopped by crates.io's rate limit finishes when the job runs again.
  4. A tag whose version does not match Cargo.toml stops the workflow before anything is built.
  5. After it: nix run github:Firefly-Projects/htmlspec, brew install Firefly-Projects/tap/htmlspec, cargo install --locked htmlspec-cli, and a downloaded binary each print htmlspec 1.0.0 with the revision it was built from.
  6. In this private repository the workflow builds the four binaries on a pull request that touches the release, and publishes nothing, whatever is tagged.
  7. The README's getting-started section names all four channels. This is release 0.33.0, and scripts/check passes.

What changes

The crates become publishable. Each internal dependency carries the workspace's version. The templates, the lockfile, and the vendored runtime move into htmlspec-assets's own directory, and every reader of the root assets/ moves with them, with no link left behind. Each crate carries its license text. One script moves the version and every pin together.

A release workflow. .github/workflows/release.yml checks and builds on every pull request that touches the release, in either repository, and publishes only from a version tag in Firefly-Projects/htmlspec. There it attaches the binaries, publishes the crates through a script that skips what already exists and waits out the rate limit, and pushes the new formula to the tap. Only the job that makes the release can write to the repository.

A formula, generated per release. The tap's Formula/htmlspec.rb names each binary's address and digest, written by the workflow from the release it just made.

The README says how to install. One line per channel.

The release runbook's version step runs the script, as runbook 0.3.0, which also gains the fallback stylesheet.

The program changes only in the revision it reports, which a build outside Git now finds instead of printing unknown.

Alternatives considered

Keep a link at the root to the moved assets. Rejected after the review: git archive does not match a link by a directory path, so the export stops, and the Nix source filter drops it, so three tests fail.

Publish the six crates with one cargo publish --workspace. Rejected after the review: the sixth new crate meets crates.io's limit, and cargo 1.90 cannot skip the crates a rerun finds already published.

Copy the assets into the crate at publish time. Rejected. A crate built from crates.io has no repository to copy from, so the files must live in the crate's directory, and keeping one copy there avoids two copies that drift.

Publish the program alone and vendor the libraries into it. Rejected. The libraries are separate crates with their own tests and boundaries, and the README already describes them as the public contract's implementation. Merging them to publish one crate would undo that.

Publish from a person's machine. Rejected. One tag, one workflow, and one log make every release repeatable and reviewable, which is the reason the contributor asked for a script for publishing too.

A Homebrew formula that builds from source. Rejected for now. It needs a Rust toolchain on the installing machine and takes minutes. The binary formula installs in seconds, and the release already builds the binaries.

Scope

In scope. Publishable crates, the version script, the release workflow and its tag check, the crate publisher, the formula and its generator, the README's install lines, the release runbook's 0.3.0, the export allowlist's two entries, and release 0.33.0.

Not in scope. The accounts: the contributor created Firefly-Projects/htmlspec and Firefly-Projects/homebrew-tap and stored both secrets on 2026-10-18. The steps that run after archival, among them the public tag and the co-owner step, belong to publish-releases-through-their-own-runbook. Windows binaries, and a submission to Homebrew's core repository, are left for later. Contract 1.0.0 belongs to commit-the-contract-and-the-command-line.

Settled by the contributor on 2026-10-18. The Firefly-Projects GitHub team that co-owns the crates is firefly-developers.

Requirements. toolchain-packaging gains one: a release reaches every channel from one tag whose version matches the declared version, each channel's artifact names the same version, and a publication interrupted partway finishes when run again.
