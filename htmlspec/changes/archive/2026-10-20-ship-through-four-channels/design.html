Ship through four channels: design

How one tag in Firefly-Projects/htmlspec reaches the Nix flake, a GitHub release, crates.io, and Homebrew: what makes the crates publishable, how the version and its pins move together, how the crates publish within crates.io's limit and finish after an interruption, what the release workflow builds here and publishes only there, how the formula is written and checked, and what the contract gains. Revised on 2026-10-19 after the code review of the plan's pull request, #63, found nine issues in this change.

Ship through four channels: design

What this settles

The contributor settled the channels and the owners on 2026-10-16: the Nix flake, GitHub release binaries, crates.io from the account smurphy8 with a Firefly-Projects team as co-owner, and Homebrew through Firefly-Projects/homebrew-tap. The contributor named the team firefly-developers on 2026-10-18, and created both repositories and both release secrets the same day. This design makes a single version tag drive all four channels, and records the choices those decisions left open.

What the review changed. The first version of this design kept a symbolic link at the root, published the six crates in one command, left the release runbook's version step as it was, ran the whole workflow only in the public repository, and checked the formula by path. Each of those fails, and the review reproduced each failure. Decisions 2 to 4, 6 to 9, and the risks below are the revised forms, and each says what failed.

Decisions

1. Each internal dependency carries the workspace's exact version

Every entry for an htmlspec-* crate in [workspace.dependencies] gains version = "=X.Y.Z", the workspace's own version, beside its path. scripts/check-release gains a question: does every such entry name the version Cargo.toml declares.

The six crates release together, from one tag, so a published htmlspec-validate mixed with a different htmlspec-parse is a combination nobody tested. An exact pin forbids it. Cargo cannot read the workspace version into a dependency entry, so the pins are strings a release must advance, and the release check makes a forgotten one fail the suite instead of a publish. The contract is silent on the form, so this is my choice.

2. One script moves the version and every pin together

scripts/set-version X.Y.Z writes the version under [workspace.package] and in every htmlspec-* pin in one edit, then runs cargo update --workspace --offline. The release runbook's first step, task-advance-the-version, runs the script instead of editing Cargo.toml by hand. The runbook becomes 0.3.0 with that step, and gains the fallback stylesheet that read-a-document-whose-stylesheet-cannot-load left to its next revision.

The review reproduced the failure with the pinned cargo 1.90: raising only the workspace version and relocking offline exits 101 with "failed to select a version for the requirement htmlspec-parse = =1.0.0", because each pin still names the old version. Ten of the 13 stages of scripts/check fail the same way before the release check could report the stale pin. A pin can only move with the version, so one command moves both.

The runbook step changes because this change is what made the old step fail. runbook-authority's "A runbook records what its history taught" asks for the hazard as a requirement, so the runbook's specification gains one: a run advances the version only through the script. project-bootstrap's "Archival checks the versions of runbooks it publishes" then requires the greater version, 0.3.0. The publishing steps that the first plan put in this runbook belong to publish-releases-through-their-own-runbook, which follows this change.

3. The asset files move into htmlspec-assets, and every reader moves with them

The root assets/, 6.2 MB of templates, lockfile, stylesheets, and vendored runtime, moves with git mv to crates/htmlspec-assets/assets/, and nothing remains at the root. Every reader of the old place is repointed in the same commit: crates/htmlspec-assets's include_str! paths in src/lib.rs and src/lockfile.rs, its build script, and the test that walks the store; flake.nix's assetLock and assetProvenance; the asset rules' agreement test in crates/htmlspec-validate/src/rules/assets.rs, whose list of places names assets; this_projects_topology_is_reported in conformance/tests/topology.rs, which discovers a store at the root; the self-assets stage's comment in scripts/check; and the README's source layout. The export's allowlist, publish/allowlist, loses its assets entry, because the files now cross under crates.

A crate built from crates.io holds its own directory and nothing else, so the files must be inside it. Moving them, rather than copying, keeps one copy. The published crate is about 6.2 MB before compression, under crates.io's 10 MB limit on the compressed package.

Revised from a symbolic link at the root, which the review showed breaks three things. git archive <ref> -- assets/ fails with "pathspec did not match any files", exit 128, because only a bare name matches a link, so the export would stop. The source filter in flake.nix drops the link, so nix flake check fails three tests and assetProvenance reads a broken store path. Repointing each reader is more edits once, and no reader ever meets a link.

4. The crates publish one at a time, in two waves, and a rerun finishes the set

scripts/publish-crates publishes the six crates with cargo publish -p <crate>, one at a time, in dependency order: htmlspec-schema, htmlspec-parse, htmlspec-assets, htmlspec-format, htmlspec-validate, then htmlspec-cli. Before each, it asks the registry's sparse index whether that version exists, and skips the crate if it does. When crates.io answers HTTP 429, it waits and retries, up to a stated budget of 30 minutes, then stops and says which crates remain. conformance declares publish = false and is never published. The program installs as cargo install --locked htmlspec-cli, whose binary is named htmlspec.

Revised from one cargo publish --workspace, which the review showed fails at the first release. crates.io lets one account publish a burst of five new crates and then refills slowly, so the sixth new crate, htmlspec-cli, the one a person installs, gets HTTP 429 "You have published too many new crates in a short period of time". A rerun of the same command uploads nothing, because cargo 1.90 checks every package first and stops at "crate htmlspec-schema@1.0.0 already exists", and it has no flag to skip existing versions. The burst limit applies to new crates only, so it binds the first release, and the script's skip and retry are what make any interrupted release finishable.

Every request the script makes to crates.io carries a fixed User-Agent that names the project and its public repository, htmlspec-release (https://github.com/Firefly-Projects/htmlspec), and no personal information. The code review's own probe once sent the contributor's email address to the crates.io API in that header, and the release must never repeat it.

The contributor decided the owner: the crates.io account smurphy8. Its API token is the public repository's secret CARGO_REGISTRY_TOKEN, stored on 2026-10-18. After the first publish, the team firefly-developers becomes each crate's co-owner. That step runs from the publish runbook that publish-releases-through-their-own-runbook adds, not from this workflow, because only an owner can add one.

Amended on 2026-10-19, during implementation. This decision did not say where the script's tests run, or what the script does in a workspace it should not publish from, and I decided both. The tests are scripts/check-publish-crates, run as a stage of scripts/check named publish-crates, because a test outside the suite is one nothing runs, and the suite runs in both repositories and in the Nix sandbox, whose loopback interface carries the stub index. The script refuses, before it sends any request, a workspace whose repository is not https://github.com/Firefly-Projects/htmlspec, because a published crate names where it came from and crates.io never replaces a version. In this repository that field holds its own address until the export rewrites it, so a publish started here stops. The script also runs cargo with CARGO_HTTP_USER_AGENT set to the fixed User-Agent, so cargo's own requests carry it as the script's do.

Amended on 2026-10-19, after the code review of the pull request. The review found four ways the script could misread a release, and each is changed. The 30-minute budget counted only waiting, so the builds cargo runs before each upload could carry a run past the job's timeout and get it killed partway; the budget is now time on the clock from the run's start, publishing and waiting together, and the script refuses to begin a step once it is spent. A 429 whose time to try again had already passed waited nothing and sent the next attempt at once, and the one after; every wait after a 429 is now at least ten seconds. cargo builds a crate before it uploads it, so a crate refused with 429 has built, and the next attempt passes --no-verify. And "already exists" or "429" anywhere in cargo's output, a compile error included, read as crates.io's answer, so a failed build could count as published; the script now reads only cargo's own error, the last error: line and the causes under it, and after any other failure asks the index whether the version landed, because cargo can fail after its upload succeeded. The crates, the public repository, and the User-Agent now live in scripts/release_facts.py, which the script and its tests import, so the order the tests check is the order it publishes in.

5. Four binaries, statically linked on Linux, each with its license texts

The release builds aarch64-apple-darwin, x86_64-apple-darwin, x86_64-unknown-linux-musl, and aarch64-unknown-linux-musl with cargo build --release --locked, packs each as htmlspec-X.Y.Z-<target>.tar.gz with LICENSE and the vendored libraries' license texts beside the binary, and writes one SHA256SUMS. The release's notes are the version's CHANGELOG.md entry.

The contributor asked for macOS and Linux binaries. I chose musl on Linux because a static binary runs on any distribution, which suits a tool whose point is documents that open anywhere. toolchain-packaging's "The program is distributable as a standalone artifact" requires an artifact that runs without the packaging tool present, and a static binary is the strongest form of that. A glibc build is the fallback if a dependency refuses musl, and the change is one target string.

6. One workflow: verify and build everywhere, publish only from a public tag

.github/workflows/release.yml runs on a pull request that touches the release's inputs (Cargo.toml, Cargo.lock, packaging/, the workflow itself, and the scripts it runs), and on a pushed tag v*. Its verify and build jobs run in both repositories. Verify refuses a tag whose version differs from Cargo.toml's, runs scripts/check-release, and runs cargo publish --workspace --dry-run. Build makes the four targets. The release, crates, and tap jobs each carry if: github.repository == 'Firefly-Projects/htmlspec' && startsWith(github.ref, 'refs/tags/v'). The workflow's default permissions are contents: read, and the release job alone declares contents: write.

Revised from a repository condition on every job, which the review showed makes the promised dry run here build nothing: every job is skipped, the run reports success, and a manual run only exists once the workflow is on the default branch. Building on the pull request that changes the release's inputs makes the musl and cross builds run before they are merged, in this repository, and the condition on the publishing jobs keeps a tag here from publishing anything.

The release job needs to create a release and attach files, and the public repository's default token is read-only, so it declares contents: write. No other job needs to write, so none can. The binaries precede the crates, because a publish to crates.io cannot be withdrawn, only yanked, so everything that can fail cheaply fails first.

Amended on 2026-10-19, during implementation. This decision did not say how verify compares the tag or how build packs a binary, and I decided both. scripts/check-release --tag vX.Y.Z asks the comparison beside the script's other questions, so the refusal is the code a contributor runs too. scripts/pack-release packs a binary with its license texts in fixed bytes, so packing one binary twice gives one digest, and a sums job writes SHA256SUMS after the four builds. scripts/release-notes prints the version's changelog entry for the release job. A formula job, which decision 7's amendment describes, runs after sums, and the release job needs it.

Amended on 2026-10-19, after the code review of the pull request. Five changes. The path list named only the release's own files, so a change to a crate, which is what breaks a musl build, never ran the builds; it now names Cargo.toml, Cargo.lock, rust-toolchain.toml, LICENSE, crates/, packaging/, scripts/, and the workflow. It stays a list, rather than every pull request, because of the runner-minutes risk below: a pull request that changes only documents builds nothing new, and scripts/check-release reads the archive and the changelog on every pull request as a stage of the suite. On a tag, nothing ran the suite and nothing checked that the tag's commit was on main: verify now checks out the whole history and refuses a tag whose commit main does not hold, and a suite job runs the check suite on a tag, which the release job needs, so nothing publishes until it passes. The release step failed when run again, because gh release create refuses a release that exists: it now creates the release when there is none, and otherwise uploads every file again with --clobber and publishes it, a draft left by an interrupted upload included. The crates job's timeout is 45 minutes: the publisher's 30 on the clock, one publish begun just inside them, and the toolchain. And the release's facts were stated in several scripts at once; scripts/release_facts.py now states the targets, the crates, the User-Agent, and the reading of [workspace.package] once, for pack-release, render-formula, publish-crates, and check-release. Two copies stay outside it and are compared rather than trusted: verify compares the workflow's CARGO_HTTP_USER_AGENT with the module's, and a build matrix that drifted from the module's targets makes pack-release --sums and render-formula refuse in the formula job, because a workflow cannot import a script's list. scripts/set-version keeps its own reading, because it rewrites the version line in place and must find exactly one.

7. The formula is written from the release it describes, and checked in a local tap

packaging/homebrew/htmlspec.rb.in is the formula with placeholders for the version and each target's digest, and scripts/render-formula fills them from SHA256SUMS. The tap job pushes the result to Firefly-Projects/homebrew-tap as Formula/htmlspec.rb with the secret HOMEBREW_TAP_TOKEN, a token that can write to the tap and nothing else. The formula's test runs htmlspec --version. Before release, the rendered formula is checked in a tap made for the purpose: brew tap-new --no-git creates it, the formula goes into it with addresses pointing at locally built tarballs, and brew audit --strict and brew install name it through that tap. packaging joins the export's allowlist.

The tap is the contributor's decision. A formula written by hand per release is a digest someone copies, and a copied digest that does not match is a failed install. Rendering it from the file the build wrote makes the two agree by construction.

Revised from brew audit on a file path, which the review found current Homebrew refuses, as it refuses an install from a path. A local tap is how Homebrew checks a formula that is not yet published. Without packaging on the allowlist, the public tree would lack the template, and the tap job would fail at the first public tag after the release was made.

Amended on 2026-10-19, during implementation. This decision did not say where the tap check runs, and I decided that the release workflow runs it. Its formula job renders the formula from the run's own SHA256SUMS, with addresses pointing at the run's tarballs, and runs scripts/check-formula on a macOS runner, on the pull request as on a tag. The release job needs it, so a formula that fails the check reaches neither the tap nor a release. The check could not run on the machine this change was built on, whose Homebrew is installed through Nix: its taps directory is a read-only store path, so brew tap-new is refused, and brew style cannot install the gems it needs. A check that only some machines can run belongs where such a machine is always available.

Amended on 2026-10-19, after the code review of the pull request. The formula job failed its first run, at ea54d92: brew audit --strict reported that version 0.33.0 is redundant with the version scanned from the URL. The template no longer states the version, because Homebrew reads it from the tarball addresses, and the test still reads it as #{version}. Its license is the license field of htmlspec-assets, which decision 9's amendment widens, and scripts/render-formula refuses a template whose license names other licenses than that field, or whose tarballs are not the four targets, so neither can drift from what it copies.

8. The program reports its revision when built outside Git

crates/htmlspec-cli/build.rs takes the revision, in order, from the environment variable HTMLSPEC_REVISION when it is set, from .cargo_vcs_info.json, which cargo writes into every packaged crate with the commit it was packaged from, and from Git. Only when all three are absent does it report unknown. flake.nix sets the variable from the flake's own revision, and the release workflow sets it from the commit it builds.

Amended on 2026-10-19, during implementation. This decision first ordered Git before .cargo_vcs_info.json. That order reads the wrong commit whenever a packaged crate's source sits inside an unrelated repository. cargo install unpacks a crate under the cargo home, so a home directory kept in Git would lend a crates.io build that repository's commit. cargo package verifies each crate under this checkout's target/package/, where Git answers with the checkout's commit instead of the one the package records. A checkout holds no .cargo_vcs_info.json, because cargo writes it only into the package, so reading it first changes nothing in a checkout and makes a packaged build name the commit it was packaged from.

The review found that a Nix build and a crates.io build both print (unknown) beside the version, which leaves a bug report unable to name what was installed. The program's behavior is unchanged apart from the revision it reports.

The first version of the proposal claimed that no crate but htmlspec-assets reads outside its own directory. That is false. htmlspec-parse's build script reads the workspace's Cargo.toml and Cargo.lock to record the pinned html5ever, and reports unknown when they are absent, which its own tripwire test catches. Several crates' tests read fixtures/ and README.md. Neither stops a published crate from building, because cargo builds a package without its tests, and the proposal now says so.

9. Each crate ships its license text, and the vendored files keep theirs

Every published crate carries a LICENSE file, a copy of the root one, and a release-check question fails when any copy differs from it. htmlspec-assets ships the vendored libraries, so it also carries THIRD-PARTY-LICENSES, holding the license text each vendored archive declares, and declares license = "MIT AND BSD-3-Clause": Mermaid is MIT, and Vega, Vega-Lite, and Vega-Embed are BSD-3-Clause. The other five crates keep license = "MIT".

The review found that no published crate would carry license text, and that one would ship BSD-3-Clause files under a field naming MIT only. The MIT license asks that its notice travel with the software, and so does BSD-3-Clause. A copy per crate is the only way, because a crate holds its own directory alone, and the release check keeps the copies equal.

Amended on 2026-10-19, after the code review of the pull request. The field named only the four libraries, and the review found that each file is a bundle holding libraries of its own, under licenses the field did not name. Mermaid's source map names every package its build holds, and Vega-Embed's names its own; Vega-Lite's names only Vega-Lite's sources; Vega publishes no map, so its whole production dependency tree stands for it. Mermaid's build also holds its parser, which holds Langium and Chevrotain, as the parser's files say. Between them the builds carry d3's modules under ISC, Chevrotain under Apache-2.0, DOMPurify under MPL-2.0 or Apache-2.0, robust-predicates under the Unlicense, and some forty libraries under MIT, js-yaml among them, as Mermaid's own license comment says. htmlspec-assets now declares MIT AND BSD-3-Clause AND ISC AND Apache-2.0 AND Unlicense, taking DOMPurify under Apache-2.0, and THIRD-PARTY-LICENSES gains, after the four libraries' own texts, the license file each of the 125 bundled packages publishes, copied unchanged, with the method that found them, so a pinned library's change regenerates the list the same way. The release tarballs carry the file, as before. The binary also links Rust crates statically, under licenses of their own, and no file gathers their texts yet; a tool such as cargo-about could, and that is left for a later change.

10. The README names all four channels, each install reproducible

Getting started opens with one line per channel: nix run github:Firefly-Projects/htmlspec, brew install Firefly-Projects/tap/htmlspec, cargo install --locked htmlspec-cli, and the release page. The build-from-source lines stay below them.

A reader who has decided to try the tool needs one command for the package manager they already use. --locked makes cargo install build with the dependency versions the release tested, instead of the newest each requirement allows, which the review found missing. toolchain-packaging's "The command surface names its operations as OpenSpec names them" records that adopters arrive from OpenSpec, where installing is a single command too.

11. A release reaching every channel becomes a requirement

toolchain-packaging gains one requirement: a release is cut from one tag whose version equals the declared version, the binaries, the crates, and the formula it produces each name that version, and a publication interrupted partway finishes when run again. Its scenarios: a mismatched tag refused before any build, a tag in this private repository that publishes nothing, a formula whose digests match the release's SHA256SUMS, and a crates publication stopped by the rate limit that a rerun completes without republishing.

The contract is silent on publication beyond the standalone artifact. Four channels that each name a version are four places a version can disagree, and the requirement makes one tag the only source.

12. Release 0.33.0

A minor increment, from 0.32.0, made with scripts/set-version 0.33.0. Cargo.toml, Cargo.lock, the internal dependency pins, and CHANGELOG.md advance during implementation, and spec.nix waits for archival, which also publishes the release runbook at 0.3.0.

The plan the contributor reviewed numbers it 0.33.0. project-bootstrap's "Archival requires the project version to advance" leaves the size to judgment. The repository gains its release pipeline and a reshaped crate, and the program changes only in the revision it reports.

13. The export refuses any file changed since its read

publish/export compares each file under an allowlisted path at the exported commit with the same file at the commit its read names, by blob, and refuses any that was added or changed since. A file deleted since needs no read, because nothing of it crosses.

Added on 2026-10-19, after the code review of the pull request. The export refused only a file added after its read. The reads in publish/READINESS.md were recorded at 1b165ea, and the commits after it, e431ba5 and ea54d92, changed files the export publishes, which it would have let cross unread. A read covers the content it read, so a changed line is a line nobody read. The reads were recorded again at this change's last commit, after every line changed since 1b165ea under an allowlisted path was read.

The gap a squash merge opens remains. A read is recorded at a commit of this branch, and squashing the pull request into main leaves that commit out of main's history, so an export of main refuses every read until they are recorded again at a commit main holds. That step belongs to the release runbook publish-releases-through-their-own-runbook adds, which runs the export.

Risks

A crates.io publish stops halfway

A rate limit, a network fault, or a cancelled job can stop the crates job after some crates are published, and crates.io never accepts a version twice.

Held down by decision 4. The verify job packages and builds every crate first. scripts/publish-crates skips each version the index already holds and waits out HTTP 429, so a rerun of the job finishes the set. Its tests run it against a stub index that already holds three of the six, and against a stub that answers 429 once.

The first real release is the first time the publishing jobs run

The publishing jobs only run on a public tag, so their first run is the first release.

Partly held down. Verify and build now run on this repository's pull requests, so the builds and the tag check are proven before merge, the formula is checked in a local tap, and the crate script is tested against stubs. What stays unproven is three short steps against the live services, and the publish runbook watches them at the first release.

A dependency does not build for musl

The workspace's dependencies are Rust without known system libraries, but a build for musl has not been tried. The change bears this: the pull request's build tries it, and a failure switches that target to glibc, as decision 5 says.

Builds on this repository's pull requests spend paid runner minutes

macOS runners cost more minutes on a private repository. The change bears this: the workflow runs only on pull requests that touch the release's inputs, which is a few per release.

Amended on 2026-10-19, after the code review of the pull request. The inputs now include every crate and every script, so most pull requests that change code run the builds, and a pull request that changes only documents does not. That is the cost of finding a broken build before a tag finds it, which decision 6's amendment chose.
