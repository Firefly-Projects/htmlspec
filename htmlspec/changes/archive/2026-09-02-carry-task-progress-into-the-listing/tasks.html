2. The contract states what an enumeration carries

  • 2.1 Modify The command surface reports what a project holds so the enumeration of active changes carries, for each change, how much of its work is complete

  • 2.2 State that the completion carried is a count per task state rather than a single fraction, with the reason: a fraction cannot separate an untouched change from one wholly in progress, nor a finished change from one with outstanding work

  • 2.3 State that the counts are derived from the same source as the completion operation and archival, so no two of the three can disagree about one change.

    This is the fault the version gate demonstrated and the reason it must be a requirement rather than a convention

  • 2.4 State that a change with no tasks document is enumerated with its completion absent rather than zero, because a zero fraction reads as finished work and an unwritten tasks document is the opposite

  • 2.5 State that the enumeration of accepted specifications is unaffected, so the requirement does not read as though a specification had tasks

  • 2.6 State that the order is unchanged.

    A listing that reorders itself as work progresses cannot be selected from twice

  • 2.7 Run openspec validate --all

    Migration note: nothing this change carries records the result of this run.

3. One counter

  • 3.1 Lift the per-change completion status computes into a function the enumeration also calls, returning the count per state rather than the open/total pair the current callers use

  • 3.2 Derive status's existing { total, open, openTasks } from that function, so its reported numbers are unchanged and there is still one traversal of a change's tasks

  • 3.3 Leave archival's behavior unchanged; it keeps deriving findings from the same source

  • 3.4 Add a test asserting the enumeration and the completion operation report the same numbers for one change, in the shape of the accepted scenario Archival and the report agree

4. What the enumeration emits

  • 4.1 Carry the per-state counts into the structured payload for each active change, leaving the accepted-specification enumeration as it is

  • 4.2 Render the human report as name, done/total, and the change's overall state, derived from the breakdown rather than stored beside it

  • 4.3 Make the denominator every task including dropped ones, so a change's total does not shrink as work is abandoned.

    Add the test that pins it: dropping a task changes the numerator's meaning and not the denominator

  • 4.4 Render a change with no tasks document with its completion absent, and confirm the payload omits the counts rather than emitting zeros

  • 4.5 Keep the columns aligned across changes whose names differ in length, since the report is read as a column and a ragged one is read wrong

  • 4.6 Confirm the empty-project case still reports no active changes rather than an empty table
