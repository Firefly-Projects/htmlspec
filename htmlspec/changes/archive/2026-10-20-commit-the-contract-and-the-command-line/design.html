Commit the contract and the command line: design

What contract 1.0.0 is and what it does to the documents already written, the two requirements that state the 1.0 promises and the tests that hold them, the record of the accounts the first release needs, and why the release itself is a run of the publish runbook rather than a task here. Subject
Commit the contract and the command line: design

What this settles

The contributor decided on 2026-10-16 that 1.0 commits the contract and the command surface, and declined to change the request-verb spellings before they are frozen. This design states what each promise covers, where it is written, and what fails when it is broken.

What the review changed. The publishing steps and the release runbook's 0.3.0 left this change: the version step and the fallback stylesheet went to ship-through-four-channels, and the steps after archival to publish-releases-through-their-own-runbook, which this change now follows. The semver promise covers errors rather than every diagnostic, the payload snapshot is built from published schemas, and the fixtures and the contract test that a kept 0.x would break are named.

Decisions

1. Contract 1.0.0 is the 0.7.0 vocabulary, and every earlier version stays accepted

The schema's list of accepted versions gains 1.0.0 after 0.7.0 and keeps 0.1.0 to 0.7.0. CONTRACT_VERSION, the four templates, and the projection specification's contract-version line move to 1.0.0, and the contract's changelog gains its 1.0.0 entry. No unit, field, or projection rule changes. Two things that read the version change with it. a_minor_bump_keeps_accepting_the_versions_it_succeeded in crates/htmlspec-schema/tests/contract.rs requires every accepted version to share the newest one's major, so it fails by design when 1.0.0 keeps the 0.x versions. It becomes: every version of the newest major is accepted, and the 0.x versions are accepted beside 1.x as decision 2's requirement states. And the fixture generator, conformance/src/bin/generate_fixtures.rs, stamps a fixture with the template's version, so regenerating at 1.0.0 would move the 20 fixtures that use 0.7.0's vocabulary. The generator pins those at 0.7.0, and one fixture declaring 1.0.0 is added, with its row in crates/htmlspec-validate/tests/schema_rust_split.rs.

The contributor decided that 1.0.0 freezes the vocabulary. What it does to documents written under 0.x was not decided, and I chose this reading. A strict reading of a major release withdraws every earlier version, and every document written so far would stop validating, this repository's accepted specifications and its archive among them, for a vocabulary that did not change. No validation rule keys on the declared version today, so a document's verdict does not depend on which accepted version it declares.

The review found the two readers this decision breaks. Keeping 0.x makes the major test fail, and regenerating the fixtures would change 20 of them from 0.7.0 to 1.0.0 without anyone choosing it. Both now change on purpose, in this change's tasks.

As built, implementation found a third reader. The templates have carried the fallback stylesheet since 0.31.0, and the committed fixtures were never regenerated after that, so regenerating rewrote all 76 of them by nine lines rather than moving 20. The generator now freezes the fallback out of its base, as it already froze the example risk, and pins the 20 at 0.7.0 through a constant rather than the template's version. Regenerating at 1.0.0 leaves every committed fixture byte for byte. I decided this: the design was silent on the drift, and the base's policy is that a fixture's bytes change only where its rule needs them to. No test holds the committed fixtures to the generator, although the base's comment names one.

Settled at review. The conformance test that compares each fixture under 1.0.0 with the version it declares cannot fail while no rule reads the declared version, so it does not hold the promise that a document valid in one 1.x release stays valid in the next. Nothing in the suite does. That promise rests on review: a change to what a fixture expects is a change to the contract, and whoever reviews it reads it as one. The README says so rather than claiming the suite enforces it. A frozen corpus of documents 1.0.0 accepts would make it mechanical, and this change does not build one.

2. The contract's versioning becomes a requirement of document-schema

document-schema gains a requirement: the contract's version is a semantic version. A major release may withdraw or reshape a unit, a field, or a projection rule. A minor release adds vocabulary, and may add warnings and review findings. A patch release changes wording and fixes defects. Within a major version from 1 on, a document that one version accepts is accepted by every later version of that major: no later minor or patch reports an error on it that the earlier version did not, except where the earlier version accepted what a requirement stated at that version refused, a defect the release's changelog names. Warnings are outside this promise. The schema keeps accepting every version a minor or patch release succeeded, keeps 0.1.0 to 0.7.0 beside 1.x, and a new document declares the newest. Its scenarios: a document declaring 0.7.0 validates under 1.0.0 with no new error, a minor that adds a warning keeps the promise, a minor that would report a new error on an accepted document needs a major instead, and a version the schema does not list is refused.

The rule exists today only as the doc comment on CONTRACT_VERSION and the policy table in the contract's changelog, and contract-authority's "The project's obligations are what its accepted specifications state" makes both non-normative. A 1.0 resting on a rule that binds nothing promises nothing. document-schema already holds "The element contract is published as a machine-readable schema", so the rule for how that schema's version moves sits beside it.

Revised from "the same diagnostics at every later version", which the review showed this project has never kept. A fresh template specification validates with ten warnings, and minor releases 0.10.0 and 0.12.0 added review warnings that fire on documents already accepted. Contract 0.7.0's data-response also turned a document that was valid into schema/invalid, which the 0.x major allowed and a major from 1 on will not. An error is what decides whether a document is valid, so the promise covers errors, and a new warning stays ordinary minor work.

3. A run's record declares the current contract version, in its head and its masthead

The head that htmlspec run composes for a record declares CONTRACT_VERSION, not the 0.1.0 it writes today, and the record's masthead names the same version where it reads Contract.

document-template's "A document declares its identity and provenance" requires a document to declare the version it conforms to. A record is written by the current program and links the current stylesheet, so 0.1.0 understates it. The review found that fixing the head alone would leave the masthead saying 0.1.0, so both read the one constant.

As built, the program reads htmlspec_schema::CONTRACT_VERSION through a direct dependency on htmlspec-schema, which was already in its tree through the validator. Reading the schema's newest version at run time would have been the other route, and it returns an option the record has no honest way to fill.

4. The command surface's stability becomes a requirement of toolchain-packaging

toolchain-packaging gains a requirement: within a major version, every operation keeps its name in both spellings, the OpenSpec spelling and the request-verb spelling, every flag keeps its name and meaning, every exit code keeps its value and meaning, and every field of every --json payload keeps its name, its type, and its meaning. A minor release may add any of them. Only a major release removes or renames one. The wording of human-readable output is not covered, so messages can keep improving.

The contributor decided the scope: names, flags, exit codes, and payloads. The request-verb spellings are frozen as they are, at the contributor's word. The requirement builds on "Exit codes distinguish outcomes", "Output is available in human and machine forms", and "The command surface names its operations as OpenSpec names them", which state what the surface does and not that it stays. Leaving human-readable wording out is my choice: a script that reads prose has --json to read instead.

The two requirements carry the headings the README names, so a reader who searches the accepted specifications for either finds it: document-schema's "The contract's version is a semantic version" and toolchain-packaging's "The command surface is stable within a major version".

5. Published payload schemas and a per-minor snapshot hold the promise

The parser surface, every operation and request-verb object with its flags and the exit codes, is read from the program's own parser into crates/htmlspec-cli/tests/surface/1.0.json. The payloads are a different problem: the CLI builds them with serde_json::json! at 83 places, and only the validator's report is a typed structure, so no payload type exists to derive a snapshot from. Each operation that offers --json therefore gets a published JSON Schema, crates/htmlspec-cli/schema/payload/<operation>.schema.json, written from the code and listing every field it can emit, the optional ones included. The suite reads each with every object refusing a property it does not declare, and the published file admits one, as decision 11 settles. Three tests hold them. Every payload any test produces validates against its schema, so an undeclared field or a changed type fails. Every property a schema declares appears in at least one payload the tests produce, so a field the code stopped emitting fails, and so does one only rare inputs produce until a test produces it. And tests/surface/ holds one file per released minor of the major, parser surface and schemas together: the suite fails when the declared version's major and minor have no file, and when a later file lacks anything an earlier one holds.

Revised from fields "gathered by running each one over fixtures", which the review showed misses the fields ordinary fixtures never produce: results[].error, report.curtailed, and recoveredErrors from validate, the diagnostic fields schemaPath, projectionRule, and note, list's follows, state, total, and tasks, the elements of followsCycles, and show's variants. A snapshot built from what fixtures happened to produce would let a minor rename any of them. A schema states each field once, and the coverage test makes a test produce it.

The review also found that the per-minor refresh was in no task and no runbook step. The file-per-minor rule puts it in the suite instead: a change that moves the version to a new minor cannot pass until it adds that minor's file. Reading the parser rather than --help keeps the snapshot to the surface and out of the wording.

As built. The program is a binary with no library, so the parser is read from inside it: src/surface.rs, compiled for tests only like invocations, builds the surface from clap's declaration and compares surfaces as sets of facts, one per argument attribute, spelling, exit code, and schema type, requirement, enumeration value, and constant. A fact a released surface states that the current one does not state with the same value is a loss. An argument becoming optional and a field becoming always present are not losses, and their opposites are. Operations that write no payload, six of the nineteen, record that, so a payload added later is an addition. The thirteen schemas share a diagnostic, a rename, and a content difference by definition, and a test requires a definition shared by name to be the same in every file.

Every helper in tests/ that runs the binary passes its arguments and output to tests/support/mod.rs, which validates each payload against its operation's schema, so the first test runs wherever a payload is produced. The coverage test is tests/payloads.rs: it builds the projects that write the rare fields and fails on any declared property no payload carried. A property inside a shared definition counts wherever the definition is used. Coverage is counted in that one test rather than across every test, because test binaries share no state and run in no promised order. Its first run found two fields the schema declared and the program never writes: a paragraph only one side holds is one unmarked run, and the schema now says so.

I added one rule the design did not state: the current minor's file must equal the current surface, not only hold the released ones. Without it, a flag added in 1.1.0 after 1.1.json was written would be recorded nowhere, and a later minor could drop it with every test passing. An ignored test, write_the_current_minors_surface, rewrites the file from the program, and the test that compares the two names it.

Settled at review: run --as, refused because the machine falls short, writes the preflight report on standard output in place of a run, and run's schema did not admit it. I kept the behaviour, because the report is what an automated caller needs to act on, and recorded it. run.schema.json gains a third shape, a reference to its preflightReport definition, which states the fields preflight.schema.json states. A unit test requires the two to agree, and tests/payloads.rs now runs --json run release --as second on a machine short of a prerequisite.

Settled at review: the writer could rewrite the current minor's file to drop what it recorded, and the failing test told a contributor to run it. The writer now refuses wherever the program lacks anything a released file of its major holds, and names each loss. The comparison test reports a loss as a loss, to restore in the program, and names the writer only for an addition. Before a minor is released its file can still be corrected, by deleting it and recording it again. That is a visible act in the diff, and this change took it once, to withdraw the archived resolution the archive payload never writes.

Settled at review: the surface recorded long-flag aliases and aliases on the OpenSpec leaf only. The walk now covers the whole parser. Each command is spelled by its name or any alias, visible or hidden, at every level, so an alias on a verb or a parent is a spelling of every operation beneath it. An argument records its short aliases too. A command no operation spells fails the walk, and so do a command that no longer takes --help and a flag subcommand, which the surface has no place for. The surface also records what clap supplies the whole program: --help and -h, --version and -V, and the help subcommand, because a package manager's test runs htmlspec --version. The parser has no aliases today, so the nineteen operations keep their two spellings each.

Settled at review: two smaller gaps. The exit-code list is checked by a match with no wildcard, so an outcome added to the type does not compile in the test until it is placed in OUTCOMES. A match cannot enumerate the type, so an outcome placed in the test's match and left out of the list passes. The match brings whoever adds an outcome to the list, and closing the gap entirely would take a dependency that enumerates the type, which this change does not add. The released files are compared with the program only within the declared major, so 2.0 can remove what 1.x recorded without deleting the record.

6. Publishing belongs to the publish runbook, not to this change

This change no longer revises the release runbook or adds publishing steps. The release runbook's version step and its fallback stylesheet are ship-through-four-channels's 0.3.0, and the steps after archival, the export, the bootstrap, the public tag, the co-owner, and the channel checks, are the publish runbook that publish-releases-through-their-own-runbook adds.

The first version of this decision appended four publishing steps to the release runbook. The review found that the tag step, as written, makes publishing the private history the natural recovery from an error, and that a run after archival would repeat the release runbook's finished steps. Moving them to a change of their own, before this one, leaves this change the two promises and nothing else.

7. The accounts exist, and are recorded with their dates

On 2026-10-18 the contributor had Firefly-Projects/htmlspec created, public and empty, with ruleset 25362895, "Protect main", requiring a pull request into main and refusing its deletion and a force push, with no bypass; had Firefly-Projects/homebrew-tap created, public and empty; stored CARGO_REGISTRY_TOKEN, from the crates.io account smurphy8, and HOMEBREW_TAP_TOKEN, a token limited to the tap, as secrets of the public repository; granted crates.io access to the organization; and named firefly-developers as the crates' co-owner. On 2026-10-19 the contributor turned on GitHub's "Keep my email addresses private".

The first version of this decision said the contributor would prepare the accounts before archival, and the review found the changes disagreeing on when. They are done, so this change records them as done rather than asking for them.

8. The first public release is the first run of the publish runbook

After archival, htmlspec run publish --as v1.0.0 starts the release. Its record, beneath the publish runbook's runs/, records the bootstrap, the export's pull request, the tag, and each channel's result.

The export reads the archived state, so it cannot run inside this change. runbook-execution's "A run leaves a record where the runbook keeps them" gives the release a record of its own, and a run of the publish runbook copies only the steps that happen after archival.

9. The README states the promises

The project status says 1.0.0 is released and what it promises, and names the two requirements. The paragraph that says the 0.x vocabulary is provisional goes.

The README is where a reader looks first. It binds nothing, so it points to the requirements that do.

As built, the project status names the two requirements by the headings decision 4's note gives, points at tests/surface/1.0.json and the payload schemas, and says that the human-readable wording stays free. The paragraph calling the 0.x vocabulary provisional is gone.

Settled at review: the README claimed that the suite fails when either promise breaks. It fails when the command surface loses anything. For the contract it checks only that each fixture gains no error under 1.0.0, and the README now says that review holds the rest, as decision 1's note records.

10. Release 1.0.0

A major increment, from 0.34.0, made with scripts/set-version 1.0.0. Cargo.toml, Cargo.lock, the internal dependency pins, and CHANGELOG.md advance during implementation, the installed instruction files are regenerated, and spec.nix waits for archival.

The contributor decided that this is 1.0. It withdraws nothing, and project-bootstrap's "Archival requires the project version to advance" leaves the size to judgment: the major says the vocabulary and the surface are now promised.

11. A published payload schema admits a property it does not declare, and the suite reads it strictly

Every payload schema under schema/payload/ leaves undeclared properties admitted, and says in its description that a later 1.x release can add a property to any object and that a consumer ignores a property it does not know. The suite reads the same files with every object that declares properties refusing any other, through tests/support's oracle, and holds every payload a test produces to both readings. Each schema's $id carries the major, https://html-spec.dev/schema/payload/1/<name>.schema.json, because one schema now describes every minor of 1.x and 2.0's will describe something else.

The review found the contradiction. The schemas refused every undeclared property, and the requirement lets a minor add a field, so a consumer validating 1.1's output against the 1.0 schema it was given would reject a change the project calls compatible. A schema per minor, each closed, would keep consumers strict and make every addition a break for them. Tolerant reading is what the promise already assumes. The strict reading stays where it does its work: the program cannot write a field before its schema declares it. Holding every payload to the published reading as well catches what tolerance alone could open, a payload two branches of a oneOf admit once neither refuses the other's fields.

Risks

A meaning changes under a name the snapshot still finds

The snapshot holds names, values, and types. A flag that keeps its name and changes what it does passes it.

Partly held down. The requirement covers meaning, so a review can refuse such a change by citing it, and the existing behavior tests catch the meanings they already pin. What no test catches is a meaning nobody tested.

A mistake in the 1.0.0 surface is kept until 2.0

Every name and field frozen at 1.0.0 stays for the whole major, including any that turn out badly chosen. The change bears this: a minor can add a better name beside a worse one, and the worse one goes at 2.0.
