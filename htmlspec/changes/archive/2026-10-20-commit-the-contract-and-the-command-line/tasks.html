1. The contract

  • 1.1 Make the contract 1.0.0, keeping every earlier version. task-1-1

    Append 1.0.0 to the schema's accepted versions, set CONTRACT_VERSION, the four templates, and the projection specification's contract-version line to it, and add the contract changelog's 1.0.0 entry. A test validates one document under every accepted version and finds no error under 1.0.0 that an earlier version did not report (design decisions 1 and 2).

    The test runs over every conformance fixture rather than one document: no_document_gains_an_error_under_the_newest_contract_version in conformance/tests/conformance.rs redeclares each of the 77 fixtures at every accepted version and finds no error under 1.0.0 that the earlier declaration did not report. The schema's $id and its schemaVersion description moved to 1.0.0 with the rest, the templates' pinned hashes in vendor.lock.json with the templates, and the contract changelog's policy now describes the promise.

  • 1.2 Restate the contract test that kept every accepted version within one major. task-1-2

    a_minor_bump_keeps_accepting_the_versions_it_succeeded requires every version of the newest major and keeps 0.1.0 to 0.7.0 beside it, as decision 2's requirement states. See it fail against the old rule with 1.0.0 added, then pass under the new one.

    With 1.0.0 appended and the old rule in place, it failed with "0.1.0 is accepted beside 1.0.0, and a major bump is where versions leave the set". Under the new rule it requires 0.1.0 to 0.7.0, every version of the newest major the changelog dates, and nothing from another major, and passes.

  • 1.3 Pin the fixtures that use 0.7.0's vocabulary at 0.7.0. task-1-3

    The fixture generator pins the 20 fixtures that declare 0.7.0, so regenerating at 1.0.0 leaves them byte for byte as they are, and adds one fixture declaring 1.0.0, with its row in crates/htmlspec-validate/tests/schema_rust_split.rs.

    Pinned, and one fixture added, valid-declaring-the-current-contract-version. The generator also had to freeze the fallback stylesheet out of its base: the templates carry it since 0.31.0, the committed fixtures were never regenerated after that, and a regeneration rewrote all 76 of them by nine lines. With the fallback frozen out, as the example risk already was, regenerating at 1.0.0 leaves every committed fixture byte for byte. Nothing checks that the committed fixtures match the generator: the base's comment names a harness test that does not exist.

  • 1.4 Make a run's record declare the current contract version, in its head and its masthead. task-1-4

    The record's head and masthead in crates/htmlspec-cli/src/runs.rs read CONTRACT_VERSION instead of 0.1.0, with a test that reads both from a new record (design decision 3).

    The CLI now depends on htmlspec-schema directly, already in its tree through the validator, to read CONTRACT_VERSION. The test is a_new_record_declares_the_current_contract_version_in_its_head_and_its_masthead in tests/run.rs. An existing assertion there, that a run's release stays out of the htmlspec-version tag, passed only because both were 0.1.0, and now names the contract version and refuses the runbook's.

2. The surface

  • 2.1 Record the 1.0 command surface from the program's parser. task-2-1

    Every operation and every request-verb object with its flags, and the exit codes, into crates/htmlspec-cli/tests/surface/1.0.json (design decision 5).

    Recorded by write_the_current_minors_surface, an ignored test in src/surface.rs that reads clap's declaration: the two global options, the nineteen operations with both spellings and their arguments keyed as a contributor types them (--strict, <1>), the payload each writes or null, and the five exit outcomes with their codes. Both spellings of every operation are read, and the surface refuses to build where they take different arguments.

  • 2.2 Publish a schema for each --json payload. task-2-2

    crates/htmlspec-cli/schema/payload/<operation>.schema.json for every operation that offers --json, written from each place that builds its payload, with every field it can emit and additionalProperties false. Copy them into 1.0.json.

    Thirteen schemas, one per operation that writes a payload, each self-contained, every object declaring its properties. They were written with additionalProperties false on every object, and the review moved that strictness into the suite's reading of them, as design decision 11 records. The diagnostic, the untaken rename, and the untaken content difference are shared definitions, and a test holds each to one text. list and run are a oneOf of their shapes, and show's variants are told apart by a constant. The coverage test's first run tightened one: a paragraph only one side holds never carries onlyThisSide.

  • 2.3 Hold every payload to its schema, and every schema field to a payload. task-2-3

    One test validates every payload the tests produce against its schema, and fails on an undeclared field and on a changed type. Another fails when a field a schema declares appears in no payload the tests produce. Add the cases the review named until it passes: validate's results[].error, report.curtailed, and recoveredErrors, the diagnostic fields schemaPath, projectionRule, and note, list's follows, state, total, and tasks, the elements of followsCycles, and show's variants.

    Not one test each, but a check and a test. Every helper in tests/ that runs the binary hands its arguments and output to support::held, which validates the payload against its operation's schema, so every payload any of the 264 existing integration tests produces is held where it is produced, and an undeclared field or a changed type fails that test. Coverage is counted in one test, tests/payloads.rs, over the payloads it produces, because test binaries share no state and run in no promised order. It builds the cases the review named: an unreadable document, the repository's fixtures for a curtailed report and every diagnostic field, a change with a tasks document and a predecessor, two changes following each other, every comparison, paragraph, and scenario variant of show, and a promotion plan whose gate finds an unknown disposition, an unreadable derivation, and a collision. All 251 declared properties are carried.

  • 2.4 Fail the suite when a released surface is lost, or a minor has none. task-2-4

    The test passes when the current surface holds everything in every file of tests/surface/, with additions allowed, and when the declared version's major and minor have a file. It is seen failing on a renamed flag, a changed exit code, a removed payload field, and a version moved to a minor with no file.

    Seen failing on each of the four, against the program and then reverted: --strict declared as --strictly failed the surface test with four lost facts; the cancelled exit code changed from 3 to 4 failed it with exitCodes/cancelled: 3, now 4; openTasks removed from status's payload failed the payload test, "openTasks is a required property"; and the workspace moved to 1.1.0 failed with "the crate declares 1.1, and tests/surface holds no 1.1.json". Unit tests keep each case failing on a surface edited the one way, with a changed type, a field no longer always present, a withdrawn value, a lost spelling, and an optional argument made required beside them, and an addition passing. One rule more than the task asked: the current minor's file must equal the current surface, so an addition is recorded in the minor that makes it (design decision 5's note).
