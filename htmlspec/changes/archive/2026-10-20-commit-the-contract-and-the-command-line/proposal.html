Commit the contract and the command line

Version 1.0 is a promise, and today nothing states it. The contract is at 0.7.0, and the rule for how its version moves lives in a code comment and the contract's own changelog, which bind nothing. The command line has no stated stability at all. This change makes both promises requirements: contract 1.0.0 freezes the document vocabulary under semantic versioning, and the command surface, in both its spellings, with its flags, exit codes, and structured payloads, stays stable within the major version. It is release 1.0.0. The first publication is the first run of the publish runbook that publish-releases-through-their-own-runbook adds, after this change is archived. Revised on 2026-10-19 after the code review of #63, which moved the publishing steps out of this change.

Commit the contract and the command line

Why

The contributor decided on 2026-10-16 what 1.0 commits: the contract and the command surface. Contract 1.0.0 freezes the document vocabulary under semantic versioning, and command names, flags, exit codes, and --json payloads become stable.

No accepted specification states how the contract's version moves. The rule exists in two places. The doc comment on CONTRACT_VERSION in crates/htmlspec-schema/src/lib.rs says that a major bump withdraws or reshapes, a minor adds without invalidating a document, a patch changes wording only, and that while the major is 0 any release can break a document. crates/htmlspec-schema/CHANGELOG.md states the same policy as a table. contract-authority's "The project's obligations are what its accepted specifications state" makes both non-normative, so the contract is silent on its own versioning. document-schema's "The element contract is published as a machine-readable schema" publishes the vocabulary, and document-template's "A document declares its identity and provenance" requires every document to declare the version it conforms to. Neither says what a version promises.

The command surface is described and not promised. toolchain-packaging's "Exit codes distinguish outcomes", "Output is available in human and machine forms", and "The command surface names its operations as OpenSpec names them" each state what the surface does now. None states that it stays that way, and nothing fails when a flag is renamed or a payload field disappears.

Publishing is not this change's work. The first plan put the publishing steps in the release runbook here. The review showed that a run after archival would repeat the steps done inside the change, and that the obvious tag command would publish the private history. publish-releases-through-their-own-runbook, which this change follows, gives publishing a runbook of its own, so this change states only the two promises.

What working looks like

  1. A new document declares contract 1.0.0, and so does a run's record, which declared 0.1.0 until now. Every document that declares 0.1.0 to 0.7.0 still validates, with no error that it did not have before.
  2. document-schema states that the contract's version follows semantic versioning: within a major, a later version reports no new error on a document an earlier one accepted, and a minor may add warnings. toolchain-packaging states that the command surface is stable within a major version.
  3. Renaming a command, a request-verb object, or a flag, changing an exit code, or removing a field from a --json payload fails the suite, including a field only a rare input produces. Adding one passes, once its schema declares it.
  4. A run's record declares the current contract version in its head and in its masthead.
  5. Firefly-Projects/htmlspec and Firefly-Projects/homebrew-tap exist, with a branch ruleset on the public main and the two release secrets in place, as they have since 2026-10-18.
  6. The README states the 1.0 promises. This is release 1.0.0, and scripts/check passes.
  7. After archival, htmlspec run publish --as v1.0.0 is the first public release, and its record is the record of the publication.

What changes

Contract 1.0.0 is the 0.7.0 vocabulary, unchanged. The schema accepts 1.0.0 beside every earlier version, CONTRACT_VERSION and the templates declare it, and a run's record declares it too. The vocabulary does not change at 1.0. Its stability does.

Two requirements, and the tests that hold them. A committed snapshot of the 1.0.0 command surface, from the program's own parser, and a published schema for every operation's --json payload, fail the suite when anything in them disappears or changes. Every field a schema declares must appear in a payload the tests produce, so a field rare inputs produce is held too.

The fixtures that use 0.7.0's vocabulary stay at 0.7.0, and the contract test that kept every accepted version within one major states the kept 0.x versions as the requirement does.

The accounts exist. The contributor's repositories, ruleset, secrets, crates.io access, and co-owner team are recorded as done, with their dates.

Alternatives considered

Drop the 0.x versions at 1.0.0. A strict reading of a major release withdraws everything before it. Rejected: every document written so far would stop validating, this repository's 13 accepted specifications and archive among them, for a vocabulary that does not change.

Promise stability in the README only. Rejected. A promise nothing checks is the failure contract-authority exists to prevent, and a README binds nothing.

Change the request-verb spellings before freezing them. Considered and declined by the contributor on 2026-10-16. They are frozen as they are.

Publish 1.0.0 as a task of this change. Rejected. The export reads the archived state, so it runs after archival, and a release is a run of the publish runbook, not work in a change.

Promise the same diagnostics at every later minor. The first version of this plan did. Rejected after the review: this project's minor releases have added warnings on documents they already accepted, so the promise covers errors, which is what decides whether a document is valid.

Scope

In scope. Contract 1.0.0 in the schema, the templates, the fixtures, and the run record. Two requirements, the payload schemas, and the snapshot tests that hold them. The README's status and promises. The record of the accounts. Release 1.0.0.

Not in scope. Any change to the vocabulary or to a command's behavior. A deprecation process for 2.0. The release runbook, which ship-through-four-channels takes to 0.3.0, and the publish runbook, which publish-releases-through-their-own-runbook adds. Running the release itself, which is the first run of the publish runbook.

Requirements. This change adds one requirement to document-schema, on the contract's version, and one to toolchain-packaging, on the command surface's stability.

The release. 1.0.0, a major increment, as the contributor decided. It withdraws nothing. The major says the vocabulary and the surface are now promised.
