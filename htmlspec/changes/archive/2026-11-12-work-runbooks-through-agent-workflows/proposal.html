Writing, running, and reviewing a runbook through agent workflows

html-spec installs nine agent workflows, every one of them for a change, and none for a runbook. So each publish run of this release cycle, v1.3.0, v1.3.1, and v1.3.2, was worked by hand: 28 to 31 exact string edits to one HTML record per run, and a stop for a person's go before the push and the tag that held only because the agent working the run remembered to make it. This change adds three workflows. runbook writes a runbook or revises one inside a change, run works a run from preflight to its report and stops for a person's go before anything that writes outside the working copy, and review reads a finished record before it lands and writes nothing. It revises the publish runbook to 0.5.0, so that its own words ask for that go, widens the bootstrap requirement to a runbook's lifecycle, and adds a requirement for the run stage. It adds no command, no flag, and no schema field, so it ships as the minor release 1.4.0, after 1.3.3.

Why

No workflow serves a runbook. The WORKFLOWS table in crates/htmlspec-assets/src/instructions.rs holds nine rows, from migrate to archive, and every one serves a change. htmlspec instructions run exits 2 with "no workflow named run". The set is scoped that way by project-bootstrap's "Bootstrapping installs agent instructions for the tools a project uses", which says the instructions "SHALL cover the project's lifecycle from an idea to an archived change". The new workflow sends a repeated procedure to htmlspec new runbook and stops, and nothing installed tells an agent how to work a run, settle a step, or record an outcome.

The gap was deferred on purpose, twice, and never closed. The proposal of establish-a-runbook, at 0.13.0, excluded "A workflow for authoring one" and named its successor, author-a-runbook-through-the-change-lifecycle. The design of log-a-runbook-run, at 0.14.0, excluded a workflow again. Nobody created the successor. This change is it, and more: it covers running and reviewing as well as writing.

This release cycle's publish runs were worked entirely by hand. The publish runbook has nine steps and six requirements each run records. In each run, preflight, the start, and the two reports were commands. Everything else was an edit to one HTML file: each of the nine step states, each dated note or reason, and an outcome and a method for each of the five requirements the start did not settle.

Each write is an exact string edit inside long lines of markup, and nothing checks most of them. The element schema does not require a verification's method. The start writes the method "Not run yet. State how this requirement was checked during this run…" as a placeholder, and --check, --status, and a prerequisite run check all read the outcome alone, so a passed outcome beside that placeholder satisfies every one of them.

The stop for a person was a habit, not a rule, and the records show it. Nothing in the publish runbook asks for a go at the push or the tag. Its specification says that "a person reads its diff" at step 2, and that switching the ruleset off "is a person's act", and its tag step says nothing of a person at all. The contract is silent on which steps need a person: a task in the element schema carries no field that marks one. So each run kept the go its own way. All seven records note a go before the push, and each of the six that made the tag notes one before it, but only the last two quote every go in its own step's note:

The stop held at the push in all seven runs and at the tag in all six that made it, and that is the habit worth keeping. What the records show is that nothing fixed its form: a reader of v1.0.0 cannot tell what the contributor's words were, and a reader of v1.3.0's tag step finds no go there at all. The one safeguard against a tag made unasked was the memory of the agent working the run.

The publish runbook is the run workflow's only real user here. The release runbook's four steps run inside each change, copied into its tasks, and htmlspec run release --status reports no runs. So the 1.4.0 publish run is where the run workflow meets real work first.

What changes

Three rows join WORKFLOWS after archive, each with a body in crates/htmlspec-assets/instructions/, written in the voice of the nine bodies that exist and held by the tests that hold them.

The three workflows, as Claude Code users invoke them. Codex users type each skill's name, $htmlspec-write-runbook, $htmlspec-run-runbook, and $htmlspec-review-run, and Pi and Cursor users /htmlspec-runbook, /htmlspec-run, and /htmlspec-review.
Workflow Directory What it does What it refuses
/htmlspec:runbook htmlspec-write-runbook Writes a new runbook with htmlspec new runbook, or revises one inside a change. States the hazards and what each run must record as requirements, writes the steps in the order the hazards force, declares what the machine needs for preflight, writes "stop for a go" into each step that needs a person, and raises the version with its changelog entry. Starts no run and edits no record. Advances no step in the canonical tasks. Revises no runbook outside a change.
/htmlspec:run htmlspec-run-runbook Reads the runbook whole, runs preflight, then starts a record or resumes the open one. Works one step at a time: settles its state, adds a dated note or reason, and runs htmlspec validate on the record. Stops for a person's go before anything that writes outside the working copy. Records each outcome with its method, and ends with --status and --check. Opens no second record for an open run. Takes no gated step without a go. Rewrites no earlier note. Turns no recorded failure into a pass.
/htmlspec:review htmlspec-review-run Reads a finished record beside its runbook before it lands. Checks that each note holds what its step asks for, that each dropped step's reason meets the step's own condition, that each gated step quotes its go, and that each method can be repeated and is not the start's placeholder. Runs validate, --status, and --check. Writes nothing. Its tools are the read-only ones verify has.

Beside the workflows, the publish runbook moves to 0.5.0. Its bootstrap, push, tag, and co-owner steps say in their own words to stop for a go, and so does its watch step before it reruns a failed job or renews HOMEBREW_TAP_TOKEN, since a rerun of the crates job publishes. Its specification gains a requirement that each of those writes waits for a person's go and that the run quotes the words. So the stop holds for a person who works the runbook without the workflow, and every run's record attests to it.

Two accepted requirements move. project-bootstrap's "Bootstrapping installs agent instructions for the tools a project uses" widens from a change's lifecycle to a change's and a runbook's, and that specification's summary follows it. toolchain-packaging gains a requirement beside "The workflow instructions carry a stage for applying a change's contract", saying what the run stage's instructions must state: preflight first, a record worked until it lands and never restarted, each step settled as it lands, a go quoted before any write outside the working copy, the record reviewed before the step that lands it, and each outcome with its method.

One fix rides along. init tells a Codex user to type $htmlspec-new, but Codex knows a skill by the name its SKILL.md declares, htmlspec-new-change, so the line names nothing. It is fixed here, for the nine workflows and the three new ones.

Concretely, once this change is archived:

  1. htmlspec instructions runbook, run, and review each print their workflow, and htmlspec init installs twelve workflows: 60 files in this repository, where it installs 45 today.
  2. /htmlspec:run publish works the one record that has not landed from where it stands, and starts no new one. A record --status calls finished, whose steps are all settled but which the main line does not hold, still takes its outcomes, its review's fixes, and its landing. A landed record is not resumed, and takes only a correction note a person asks for. With every record landed, it runs preflight and starts the record under the name the runbook's words give, vX.Y.Z. With more than one record not landed, it lists them and asks which.
  3. After each step the record validates with no error, and the step has its state and a dated note or reason.
  4. Before a push, a tag, a merge, a publication, a remote API write, a deploy, or an installation into the machine, the agent stops and asks, and quotes the answer in the step's note before the write. A go that names several steps is quoted in the note of each step it allows. A go covers only the steps it names, and none carries across an interruption.
  5. Each requirement's outcome has a method someone else could repeat, recorded before the review. Once the record lands, htmlspec run publish --status v1.4.0 ends "Finished and passed: yes", and --check names nothing for that record.
  6. /htmlspec:review publish v1.4.0 writes nothing. On a record with a passed outcome whose method still reads "Not run yet.", a gated step whose own note quotes no go, or a dropped step whose reason does not meet its condition, it names each one.
  7. The publish runbook at 0.5.0 asks for a go at steps 3, 4, 5, and 7 in its own words, and at step 6 before a rerun or a renewed secret, and a run of it owes an outcome for seven requirements.
  8. htmlspec init --tools codex tells a Codex user to type $htmlspec-new-change, a skill Codex has.

The release is 1.4.0, a minor one. Three workflows are added and none is removed. instructions takes its stage as a free argument, and the instructions payload states stage as a plain string, so no recorded fact of the command surface changes. It follows 1.3.3, which shipped first, archived as 2026-11-11-count-only-the-checks-a-run-ran, and which makes --status count only outcomes whose check ran, as --check does, so the run workflow can report the two without a caveat. The change declares that order in its FOLLOWS file.

Alternatives considered

  • Five workflows, with one to carry a runbook to another machine and one to revise a runbook. A revision is the same work as a first draft, the same two documents and the same rules, plus a raised version, and archival already refuses a changed runbook whose version did not move. Carrying one is htmlspec store add once and --store on preflight and run, which is a paragraph of the run body. So runbook covers both, and neither earns a row.
  • A command that settles a step without a hand edit, in this change. It would remove the string edits and could refuse a bad shape at the moment of the write, and it is worth building. It is not built here, for three reasons. Its design is open: it needs a way to name the record and the step, rules for which flags go together, a note argument that takes or escapes markup, an outcome and its method in one call, and runbook-portability's "Preflight gates the creation of a run" keeps "checking or editing an existing record" out of preflight. Its size is that of the change that added --status: each flag joins the recorded surface and the payload schema, and each refusal needs its own test. And its evidence is the 1.4.0 publish run worked under run, which shows which edits go wrong. Until it ships, the run body teaches the markup edit, because project-bootstrap's requirement above forbids a body naming a command the program does not provide.
  • A field in the task schema marking a step that needs a person. The element schema gives a task eight fields and none is a gate. runbook-authority's "A runbook records what its history taught" declines an attribute for a similar distinction, because the artifact vocabulary is closed. A rule in the run body, with the runbook's own words as a second line, covers every runbook today. A field waits for evidence that the rule is too coarse.
  • Leaving the stop to the tool's permission prompts. A session that skips permission checks, as agent sessions here often do, asks nothing before git push. Where checks are on, pre-approving only htmlspec commands does make the tool ask before a push, and the run row does that, but the instruction has to be the gate.
  • One workflow, run, as the first sketch of this gap proposed. The review earns a row of its own. The last two publish records, v1.3.1 and v1.3.2, each landed after a read-only fact check that its pull request names, and the change lifecycle already keeps its read-only check, verify, apart from apply: a reader who did not work the run catches what the worker read as they meant it.
  • check-run instead of review. Held in reserve, in case review collided with something. It collides with nothing: no workflow, operation, request-verb spelling, skill directory, or installed file name uses it.

Scope

  • No settle command. Settling a step's state from the command line is its own change, named here so it is not lost as author-a-runbook-through-the-change-lifecycle was: settle-a-step-of-a-run-from-the-command-line. The review of the 1.4.0 publish run's record decides whether to draft it, and with what further refusals. Two of its parts are already settled: it adds a run --check finding, advisory like the rest of that report, for an outcome recorded beside the start's placeholder method, and its settle command refuses to set an outcome without a method.
  • No new schema field, command, flag, exit code, or payload field. Which steps need a person is a rule in the run body and words in each runbook.
  • No workflow for carrying a runbook to another machine, or for revising one. --store and the runbook workflow cover both.
  • No change to runbook-execution, runbook-authority, or runbook-portability. The workflows rest on what they already state. 1.3.3 adds one sentence to runbook-execution's "A run's progress is reported from its record", in its own change.
  • No change to the release runbook, which stays at 0.6.1.
  • Not 1.3.3's fixes. The status count, the topology test race, and the stale instructions --help were one patch of their own, which shipped first as 1.3.3, in count-only-the-checks-a-run-ran.
  • No run of this repository's publish runbook. The instructions are proved by a dry run against a scratch runbook in a scratch project. The 1.4.0 publish run comes after archival, under the run workflow, and it is the workflow's first real test.
