2. The contract states the second site, once

    • Stated in the delta as the fourth clause of the opening sentence, so it reads as one list of things carrying no authority rather than as an appended exception.

  • 2.2 State that validation reports a document whose summary is a template's placeholder, and that every operation applying a contract refuses while a specification carries one

    • The existing "SHALL refuse while that change's specification carries one" became "carries either", so the refusal covers both sites without a second sentence stating the same obligation twice.

  • 2.3 Keep the existing sentence about identifiers and bound it to units rather than deleting it.

    "The check SHALL be on the identifier rather than on the example's text" is deliberate and its reason holds — a half-replaced unit keeps its identifier. The summary is not a narrower case of that rule, it is a case the rule does not reach, because the header paragraphs carry no identifier

    • Kept verbatim, prefixed with "Within a unit". Its scenario "A half-replaced example" is kept and gains "because within a unit the check reads the identifier rather than the text", so the bound is pinned by a scenario rather than only by prose.

  • 2.4 State that the comparison is against the whole projected summary rather than a fragment, so an author who quotes the template's wording inside their own statement is not reported.

    A rule that fires on documents discussing it is a rule an agent learns to ignore

  • 2.5 State that an absent summary is not reported as example content, because an absent summary and a placeholder summary are different facts and one reported as the other sends an author to delete a paragraph that is not there

  • 2.6 State that the placeholder text is derived from the templates, so a template reworded needs no second edit

    • Written as "Both the identifiers and the placeholder text SHALL be derived", replacing the identifier-only sentence, with the staleness reason widened to "gains a unit or rewords a placeholder".

    • 11 passed, 0 failed.

3. The placeholder set, read out of the templates

  • 3.1 Add htmlspec_assets::example_placeholders(), returning the masthead paragraph text of every template, normalized.

    Cached in a OnceLock and scanned from the compiled templates, exactly as example_identifiers() is and for the reason its doc comment already states

    • Returns &'static [String] rather than &'static [&'static str] as the identifier set does. The difference is forced: an identifier is a slice of the template's own bytes, and a normalized paragraph is a new string.

    • The scan locates the paragraphs by the first header element, not by class="hs-masthead", because that is what projection 9.1.1 reads. Selecting on the class would be a second, different rule for finding the same paragraphs. the_scan_reads_the_masthead_alone asserts the first header is the masthead in every template, so the two are pinned rather than assumed equal.

  • 3.2 Add is_example_placeholder(text: &str) -> bool, the membership test, matching is_example_identifier's shape so a caller reads one pattern rather than two

    • It normalizes its argument before comparing, which is_example_identifier has no need to do. Without it a caller reading text by any route other than the projection gets a silent false negative — the exact failure the check exists to remove.

  • 3.3 Normalize the same way the projection does, which is split_whitespace().join(" ") per projection specification section 6.1.

    Note the constraint: htmlspec-parse depends on htmlspec-assets rather than the other way round, so this cannot call the projection's own normalized_text — it is private and the dependency runs the wrong way. Two implementations of one rule is the drift this project has been bitten by, so pin them against each other in 3.4 rather than trusting them to agree

    • Confirmed the constraint holds as stated, and the second implementation is normalized_whitespace, whose doc comment names the first and what pins them together.

    • Two divergences from the projection that normalization alone does not cover, both recorded in the doc comments rather than handled: character references (projection 6.3 resolves them first; the scan cannot, since that needs the parser this crate has no dependency on) and the elements contributing no text (projection 8.5 — script, style, template, noscript; the scan would keep their content). No template's masthead carries either, and 3.4's test is what fails if one gains them, rather than the rule quietly stopping.

  • 3.4 Assert that the scanned placeholder equals the projected summary of a document htmlspec new document just wrote, for every artifact kind.

    This is the test that catches the normalization drifting apart: a rule that silently stops matching is worse than one that never matched, and no other test here would notice

    • crates/htmlspec-assets/tests/placeholders.rs, driven from TEMPLATES. Needed no new dependency: the crate already dev-depends on htmlspec-parse for rendered_save.

    • Asserts twice, and the second is the stronger one: that is_example_placeholder accepts the projected summary, and that the scanned set contains it as an exact string. The first alone would pass through a whitespace drift, because the membership test normalizes its argument and would hide it from every caller comparing raw strings.

  • 3.5 Assert the set holds one entry per template and that none is empty.

    A template whose masthead scan returned nothing would make the rule quietly inert for that kind

    • Per template individually, so a single kind going quiet is reported as that kind. The count is asserted against TEMPLATES.len() rather than 4.

  • 3.6 Assert the scan reads the masthead only.

    A template's body paragraphs are also text the program wrote, and treating them as placeholder summaries would report a document for prose that is not its summary

    • Two assertions: against every real template (each has 3 to 7 body paragraphs, and the test fails if a template ever has none, since it would then be asserting nothing), and against a document the test writes, since the property is "the body is not reached" and the real templates can only show what they carry today.

    • A wrong expectation I wrote and then corrected, recorded because it is the reason an_inline_element_in_a_masthead_projects_the_same_text exists: I asserted <em>paragraph</em>. normalizes to "paragraph .". It does not — neither the scan nor the projection inserts a separator at a tag boundary. A hand-written expectation pins what its author believed, so that case is now asserted against the real projection.

4. The rule

  • 4.1 Extend example_content_is_replaced in crates/htmlspec-validate/src/rules/review.rs to report a document whose projected summary is a template's placeholder, under the existing review/example-content identifier.

    A second rule identifier would need its own coverage requirement and would divide one obligation across two names

    • As summary_is_the_authors_own, called from example_content_is_replaced rather than inlined into it. The identifier closure reports per unit and this reports once per document, so one function doing both would read as two loops sharing a name.

  • 4.2 Locate the diagnostic at the document rather than at a unit, since the summary has no identifier.

    The message names the summary and says what to do — a contributor sent looking for a unit that does not exist is worse served than one told nothing

    • Location::document(). The message names "the masthead paragraph" specifically, since "the summary" alone names the projected field and the thing to edit is a paragraph.

  • 4.3 Compare the whole summary, joined across paragraphs where a header carries several, against each placeholder.

    Assert that a summary quoting the placeholder inside a longer statement is not reported, which is the case the substring approach would have got wrong

    • Three shapes asserted unreported: the placeholder quoted mid-sentence, the placeholder plus the author's own second paragraph, and the placeholder at the end of the author's sentence. The test then asserts the whole-summary case is still reported, so it cannot pass by the rule having stopped firing.

    • Joining across paragraphs settles the second shape deliberately: comparing per paragraph would report an author who added their own paragraph beside the template's, making the boundary depend on whether they edited in place or added below.

  • 4.4 Assert a document with no summary is not reported by this rule

    • Both shapes projection 9.1.1 names: a header with no paragraph, and no header at all.

  • 4.5 Assert every artifact kind is covered, driven from the template set rather than from a list of four kind names.

    A list would go stale the first time a kind is added, which is the same defect one layer up

    • Renders each template through render_kind — the code htmlspec new document uses — and asserts exactly one review/example-content diagnostic located at the document. Filtering on the location is what isolates the summary's, since a rendered document also carries its template's example units and the total count varies by kind.

  • 4.6 Assert the severity is a warning and that strict does not promote it, which is the review/* ceiling the conformance suite already pins from the outside

    • Asserted for this diagnostic specifically, under both strictnesses, and that the report stays accepted.

5. The refusal at archival

  • 5.1 Extend example_content_in in crates/htmlspec-cli/src/commands.rs to report a placeholder summary alongside an example identifier, so archival and the comparison operation both refuse.

    One function because two would drift, which is why it is already shared

    • It now returns an ExampleContent struct rather than a Vec<String>. A divergence from the obvious implementation, and the reason is 5.2: both call sites explain themselves with a sentence about what an example requirement costs, and that sentence is false for a document whose only fault is its summary. Appending the summary to one list would have produced a refusal whose stated reason a contributor could check and find wrong — which is worse than a vaguer one, because it makes the refusal itself look unreliable. So each call site now selects its reason from what was actually found.

  • 5.2 Name the summary distinctly in the refusal rather than listing it among unit identifiers.

    "archival does not proceed while the specification carries a template's example content: the masthead summary" reads correctly; listing a bare summary among req-example does not

    • ExampleContent::named() appends "the masthead summary" last, so a refusal naming both reads as identifiers followed by the one thing that is not one.

  • 5.3 Assert archival refuses a specification whose summary is the placeholder and whose units are all the author's own — the case that is invisible today

    • a_placeholder_summary_warns_at_validation_and_refuses_at_archival, written as one test for the reason the existing identifier test gives: apart, each half passes while the split is broken in the direction the other covers. It also asserts the refusal gives the summary's reason and not the example-requirement one, which is what 5.1's divergence exists to make possible.

    • The placeholder is read by rendering the real specification template and projecting it, not written into the test. So the test cannot pass against a derivation that has stopped finding anything: the fixture would go empty, an empty summary is not refused, and the assertion still fails.

  • 5.4 Assert the comparison operation refuses the same specification, since its report would otherwise direct an agent to merge a contract from a document that does not say what it is for

    • Asserts the absence of the merge instruction and of req-established, not only the presence of the refusal.

    • Two tests beyond what the task asks, both guarding the boundary from the other side: both_operations_proceed_once_the_masthead_is_the_authors_own (so the gate is not "a specification with a masthead is refused", asserted at both operations because both read one function) and a_specification_quoting_the_placeholder_is_not_refused — the design's central decision at the operation where getting it wrong costs most, since a substring search there would refuse the change that introduced this rule.

6. Prove it, and prove the tests can fail

  • 6.1 Add a conformance fixture for a document whose units are replaced and whose summary is not, declaring review/example-content, valid: true.

    This is the case no existing fixture covers and the reason this change exists

    • fixtures/conformance/warning-review-placeholder-summary/. Reports exactly one diagnostic. The first draft carried data-change="added" on its units, copied from the fixture it was modelled on, which added a review/stale-verification warning — a second subject in a fixture pinning one rule. Removed.

  • 6.2 Add a fixture for a summary that quotes the placeholder inside the author's own statement, declaring no rules.

    Without it, nothing stops a later change from replacing the equality test with a substring search

    • fixtures/conformance/valid-summary-quoting-the-placeholder/, whose masthead quotes the specification template's placeholder in full — so a substring search reports it and whole-summary equality does not.

    • As specified, this fixture guarded nothing, and mutation testing is what showed it. See 6.3.

  • 6.3 Mutate and confirm each test fails.

    Revert the equality comparison to a substring search and confirm 6.2's fixture fails. Break the normalization and confirm 3.4 fails. Restrict the rule to the specification kind and confirm 4.5 fails. A test written for a defect is not the same as a test that fails when the defect is present, and this change exists because a check whose subject was real did not reach it

    • Seven mutations, each alone, all recorded with their exact failure lists in evidence/mutation-testing-2026-09-13.md. --no-fail-fast is required: plain cargo test stops at the first failing target and reported one failure where there were three.

    • The substring mutation did not fail 6.2's fixture. every_fixture_reports_exactly_the_rules_it_declares does if expected.rules.is_empty() { continue; }, so a fixture declaring no rules is never validated — the fixture would have sat there looking like a guard. Confirmed directly: with the mutation, that fixture reports review/example-content and the conformance suite passed. Fixed by adding a_summary_quoting_the_placeholder_reports_nothing, which names the fixture and asserts its report is empty; the mutation then fails 4 tests including it.

    • The absent-summary guard mutation failed nothing, and no test was added. The early return is genuinely redundant — an empty summary joins to "", and no template writes an empty paragraph, so is_example_placeholder("") is false either way. The property is real and is asserted where it lives, one layer down. What was wrong was the doc comment implying the return carried it; it now says the measurement. A comment claiming a line is load-bearing when it is not is this change's own defect one scale down.

    • My first normalization mutation (join(" ") → trim()) also failed 3.4 — a mistake in the mutation, not a gap: the templates write each masthead on one line, so both produce the same string and the two sides still agreed, which is exactly what 3.4 asserts. Re-done as join(" "), a normalization the projection never produces, and 3.4 failed.

    • 4.5 failed under the specification-kind restriction, as required. Sections 5.3 and 5.4 each failed alone under a mutation disabling only the refusal, with the validation half still passing — the severity split visible in a measurement.

  • 6.4 Confirm no existing fixture breaks.

Verify rather than assume — the proposal's reasoning about the harness is the kind that is right until it is not

    • The alarming-looking number and why it is not a change: the new diagnostic fires on 50 fixtures, 48 of which do not declare review/example-content. But 49 of 50 already reported at least one undeclared rule before this change, and 49 do after — the count of fixtures in that state moved by zero. The new diagnostic joins an existing set rather than creating one.
