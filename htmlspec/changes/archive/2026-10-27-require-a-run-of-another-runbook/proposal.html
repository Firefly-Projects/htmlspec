Let a runbook require a passed run of another runbook before its own run starts

A runbook cannot say that another runbook must have run first. Today the order lives in prose that no program reads, so nothing stops a migration starting before its backup, and nothing shows a reader which procedure comes next. This change lets a runbook declare, in its specification, that a passed run of another runbook in the same project must exist before its own run starts. htmlspec run --as and htmlspec preflight check the declaration and refuse a start that has not met it, and htmlspec list --runbooks shows each runbook's prerequisites and whether they are met.

Subject
Let a runbook require a passed run of another runbook before its own run starts

Why

A project that keeps more than a few runbooks soon has an order among them. A database is backed up before it is migrated. An account exists before a database is provisioned for it, and the database exists before a service is deployed onto it. The procedures are separate, because each has its own hazards, its own grants, and its own history, and merging them into one runbook would lose all three. Yet the order between them is real, and getting it wrong is the expensive kind of mistake.

htmlspec 1.1.0 has no way to say so. Its one ordering link, a change's FOLLOWS file, joins changes and orders their archival, never runs. Preflight checks only what a machine holds: a tool, a toolchain, a skill, and the state of the working directory. And a runbook's documents reach only themselves, by document-schema's "Cross-references address units by identifier". So the prerequisite is written as prose in the procedure's "What this procedure consumes" section, and a comment in runs.rs says that prose is the only place a prerequisite can live. Prose is read by a person, and only when the person remembers to.

A downstream project's runbooks showed the cost. One chain of procedures carries each item through eight runbooks, and every prerequisite between them was a sentence in a consumes section that a person checked by eye before each start. The project's question, which procedure must run first and which one can start now, had no answer except reading every record by hand.

What changes

A runbook states a prerequisite the way it already states a machine requirement: as a requirement in its specification, with a scenario, and a declaration in the requirement's note that preflight reads. The declaration names another runbook in the same project, and optionally the lowest release of it that counts.

preflight/v3 {"kind":"run","runbook":"backup","atLeast":"1.4.0"}

What working looks like, for a project with a backup runbook and a migrate runbook whose specification carries that declaration:

  1. htmlspec list --runbooks shows that migrate runs after backup, and whether that prerequisite is met now, naming the backup run that meets it.
  2. With no finished backup run, htmlspec run migrate --as 2026-11-02 refuses, creates no record, and says why: no record of backup, or its run 2026-11-01-nightly is still open with three of seven steps done, or that run recorded failed for one of its requirements, or it ran release 1.3.0, below 1.4.0.
  3. Once a backup run has finished and passed, the same command starts the migration. Its record carries a verification saying which backup run satisfied the prerequisite, and at which release.
  4. htmlspec preflight migrate reports the same check without starting anything, as it does for a missing tool.
  5. htmlspec list --runbooks --graph prints the project's runbooks and the order among them as a Mermaid diagram, ready to paste into a document. Each arrow says whether that prerequisite is met now, and shows its lowest accepted release.

A chain of three works the same way: deploy-service requires provision-database, which requires create-account. Each runbook declares only its own prerequisites, and the listing shows the whole order. A runbook that names itself, or whose prerequisites lead back to it, is refused as an invalid contract, because no order could satisfy it.

Alternatives considered

  • Keep it downstream. A project can write its own tool that reads its records and refuses an early start, and the downstream project above planned exactly that. It works, but every project writes the same tool again, and htmlspec keeps calling a run ready that its own author knows is not. The start path in runs.rs already refuses a run whose prerequisites are unmet. This change gives it one more kind of prerequisite to check.
  • Merge the runbooks into one. One procedure with stages loses each runbook's own version, history, and records, and every change to one stage becomes a release of all of them. The order would be enforced, but at the price of the reasons the procedures were separate.
  • A FOLLOWS file for runbooks. FOLLOWS orders archival between changes, and it names one predecessor. A runbook's prerequisite gates a run, which preflight already gates, can name several runbooks, and is a requirement a run records an outcome for. A file beside the documents would be a second place a runbook states what it needs.
  • A cross-reference from one runbook to another. A reference reaches a unit, and a runbook's documents reach only themselves. The declaration names a runbook as data, which the rule does not touch, and asks about its runs rather than its units.

Scope

The change checks runbook-level runs, and only within one project.

  • No per-item verdicts. A run that handles many items, such as hosts or accounts, can pass for some and not others. Whether a particular item may go on to the next runbook is the downstream project's business, stated in its own files. htmlspec asks only whether a run of the prerequisite runbook finished and passed.
  • No freshness. A run's record does not state when the run happened, by runbook-execution's "A run is one record from start to finish". So "a backup from today" cannot be checked, and any finished, passed run of the named runbook satisfies the declaration. A procedure that needs a recent run says so in its own steps.
  • No other projects or worktrees. Records are read from the project the declaring runbook belongs to. A run recorded in another worktree counts once its record lands there.
  • No override. There is no flag to start a run whose prerequisite is unmet, as runbook-portability's "Preflight gates the creation of a run" already rules out any skip-preflight option.
  • No orchestration. htmlspec never starts a prerequisite run on its own. A parent runbook that walks its children in order is an ordinary runbook, and needs nothing new.
  • No new command for the graph. The drawn order is an option of the listing, list --runbooks --graph, not a command of its own. The user decided on 2026-10-27 to include it in 1.2.0.

It ships as 1.2.0, because it adds to the command surface and introduces a new declaration format. The contract's vocabulary does not change. It follows install-through-wsl-without-nix, which archives at 1.1.1 first, so this change opens only after that one has archived.
