Let a runbook require a passed run of another runbook before its own run starts: design

A prerequisite run is a preflight check of a new kind, run, declared in a new format, preflight/v3, in a requirement of the dependent runbook's specification. Preflight matches the declared name exactly against the project's runbooks and reads that runbook's records, and the declaration is met by any finished tasks record that did work and passed every requirement, at or above an optional release. Records gain a release value the program writes and reads back, the start path refuses an unmet prerequisite as it refuses a missing tool, and a self-reference or a cycle through the runbook is an invalid contract. The runbook listing shows each prerequisite's state in text, in JSON, and with --graph as a Mermaid diagram. It ships as 1.2.0, after install-through-wsl-without-nix archives at 1.1.1, with the contract's vocabulary unchanged.

Subject
Let a runbook require a passed run of another runbook before its own run starts: design

The shape of it

The start path already refuses a run whose machine prerequisites are unmet, and preflight already reports each declared check with its expectation, observation, outcome, and remedy. A prerequisite run is one more thing a run needs before it starts, so this change gives preflight one more kind of check rather than building a second gate beside it. Everything a preflight check already does follows for free: the refusal before any record is created, the exit codes, the human and JSON reports, the runbook's own remedy text, and the verification the new record carries for each check that passed.

What is new is narrow: a declaration form that names a runbook, a rule for when a record satisfies it, a release value in each new record so a version constraint has something structured to compare, prerequisite fields in the runbook listing, and a drawn form of that listing.

Decisions

1. A prerequisite run is a preflight check of kind run, in a new format, preflight/v3

The declaration lives where every other prerequisite lives: in the note of a requirement in the runbook's specification, read by preflight from the projected note, never inferred from prose.

preflight/v3 {"kind":"run","runbook":"backup","atLeast":"1.4.0"}

preflight/v3 reads every form preflight/v2 reads, with its optional remedy, and one more kind, run, with the fields runbook (required) and atLeast (optional). Both earlier formats keep refusing the new kind as unknown, because the forms table is closed and that is how it should stay.

The start path already refuses a run whose declared prerequisites are unmet, and preflight already reports, records, and explains each check. A second mechanism beside it would duplicate all of that and give a runbook two places to state what it needs. A new format, not a new kind inside preflight/v2, decides what an older program says. I checked 1.1.0 against a preflight/v3 note, and it refuses with "is not a format this program reads; it reads preflight/v1 and preflight/v2", which tells the reader to upgrade. A run kind inside v2 would instead be refused as an unknown kind, which blames the runbook. This is the same reasoning that made install hints a new format in 1.1.0.

Built on 2026-10-27, with one addition the decision did not give. A run check under preflight/v1 or preflight/v2 is still refused, and the fault names the note's format and the forms it reads and says to begin the note with preflight/v3, so the author is told the fix rather than only the refusal. A declaration with no kind is told the forms of its own format, and an empty runbook is refused as empty rather than as the shape of a path. A test that used preflight/v3 as its example of a format this program does not read now uses preflight/v4.

2. The declaration names a runbook as data, matched byte for byte against the project's runbook directories

The runbook field holds a runbook's name, as the listing prints it. It must pass the name rule run and preflight apply, so a declaration cannot name a path. It names a runbook only when it equals, byte for byte, the name of a directory the project's runbook enumeration finds. Self-references and cycles are found on that same identity.

Today htmlspec preflight PUBLISH finds the publish runbook on a case-insensitive filesystem, because the lookup asks the filesystem whether a directory of that name exists. A run check must not inherit that. A declaration naming Backup beside a backup directory names no runbook on every filesystem, and is unmet as missing. So the check never resolves a name through a path test such as named_runbook(..).is_dir(). It compares against the enumerated names. The existing lookup for run and preflight on the command line is left as it is.

A cross-reference reaches a unit, and a runbook's documents may reach only themselves. A name in a declaration is not a reference: it is a value preflight resolves against the project's runbooks at check time, the way FOLLOWS names a change. Matching it exactly makes a declaration mean the same thing on every machine. A filesystem-dependent match would let a runbook pass preflight on one laptop and fail on a Linux server, and would make two spellings count as one runbook for a self-reference on one machine and not on another. Renaming a runbook is moving its directory, and a declaration naming the old name then reports "no runbook named …" until it is corrected, which the listing makes visible across the project.

Built on 2026-10-27. The check compares against the names runs.rs's enumeration of runbooks/ finds, and never asks the filesystem whether a path exists. Disabling that comparison in favour of a path test makes the case test fail on this macOS filesystem, so the test guards the decision where it matters. A declared name must pass the same name rule as a command-line runbook name, and reaches human output through the terminal escaping.

Settled after the review of 2026-10-27. The command line's lookup is left as it is, so on a filesystem that folds case preflight MIGRATE still finds the migrate directory. From loading on, that runbook is known by its enumerated name: the one name the enumeration finds for the same directory, by device and inode. Before this, the typed name reached the cycle check, so preflight MIGRATE exited 1 where preflight migrate exited 2, and run TWO was not refused inside a cycle. A typed name that reaches a directory listed under no one name, as a symbolic link beside its target would, is refused with exit 2. The report, the payload, and the new record all name the runbook as the listing does.

Settled in the pre-archival review, 2026-10-27: every name 1.1.1 ran must still run, and the first resolution refused a runbook with a symbolic link beside it, because two enumerated names reached its directory. A typed name now resolves in order: to itself, when it is an enumerated name; else, among the enumerated names for the same directory, to the one equal to it ignoring case, so OUTSIDE beside outside and a link outside-link is outside; else to the directory's only name. Only a directory with several names, none equal to the typed one even ignoring case, is refused as ambiguous. The cycle check reads the resolved name, and the report's source path and the record's location carry it.

3. A record satisfies the declaration when it is a finished tasks document that did work and passed every requirement, and any such record counts

Preflight reads every .html file under the named runbook's runs/. A record satisfies the declaration when all of these hold:

  • it can be read, and parses without error recovery;
  • it declares the tasks kind;
  • it has at least one task, at least one task is done, and every task is done or dropped, so the run finished and did something;
  • every requirement it carries has a verification, and every verification's outcome is passed, so nothing is unrecorded and nothing failed, was blocked, was not run, or was only partly checked;
  • its release meets atLeast, where the declaration has one (decision 4).

Any record that satisfies it meets the declaration. When none does, the check names each file and the first reason it fails, in this order:

  • cannot be read;
  • needs error recovery to parse;
  • is not a tasks document, which covers an empty or stray file;
  • has no task done;
  • still open, with N of M steps done;
  • an outcome other than passed on a named requirement;
  • a requirement with no recorded outcome;
  • a release problem from decision 4.

Naming is bounded. The report, the new record's method, and the listing name at most three satisfying records, the first three in name order, and say how many more there are. Name order is used only to choose which three are printed, and says nothing about which run was first. Every non-satisfying file is named when none satisfies, because each one is a reason the check is unmet. The report also names any open run of the named runbook, even when the check is met, so a backup in progress beside an older finished one is in view (see the risks).

The implementation decides from the projected model, in a new module, prerequisites.rs. It reuses runs.rs's gather() to find and read the files, and the recovery check runs.rs already applies on its read path. It does not reuse or widen RecordedRun in htmlspec-validate. That type is a public struct with public fields in a crate published on crates.io, so adding a field to it would break any downstream code that constructs it, and it is deliberately reduced to the one set of identifiers the conformance rule needs.

The rule uses only what a record already holds: its kind, its task states, and the verifications htmlspec run --check already reads. "Finished" excludes a run under way, because a backup half taken is no backup. "At least one task done" excludes a vacuous pass: a tasks document with no tasks, or with every task dropped, records no work, and an empty or stray file under runs/ is not a run at all. "Every outcome passed" is strict on purpose. A partial verification states that part of its requirement went unchecked, and a dependent run that starts on a partly checked prerequisite is the mistake this change exists to prevent. "Any satisfying record" follows from the contract: records state no time, so there is no latest record to prefer, and choosing one by its name would derive an order from a name. A procedure that needs a recent prerequisite says so in its own steps, where a person can judge it.

Built on 2026-10-27, with two details the decision did not state. An empty or whitespace-only file is decided as not a tasks document before the recovery check, because the parser recovers an empty input, and the decision's own list puts an empty file under "is not a tasks document". A verification whose outcome is not passed is named by the first requirement it references, and one with no outcome at all reads as "no outcome".

4. Each new record carries its runbook release in a head meta, and atLeast compares within one major

htmlspec run --as writes <meta content="1.4.2" name="htmlspec-runbook-release">, in the canonical form the formatter writes, into each new record's head, beside the two metas every document carries. A run check with atLeast reads it. The declaration is met by a release at or above atLeast whose major equals atLeast's, so "atLeast":"1.4.0" accepts 1.4.0 and 1.9.2 and refuses 1.3.0 and 2.0.0.

A declaration without atLeast does not read the meta. Under a declaration with atLeast, a record whose meta is a problem is non-satisfying, with one of three reasons. "States no release": the meta is absent, which is true of every record written before this change, though the program cannot know when a record was written. "States a release that is not three dot-separated integers": its content is malformed. "States more than one release": the head holds two such metas.

A record today states its release only in its masthead's prose ("at the 0.2.1 release of that runbook"), and the project refuses to read a version out of display text: runbook-authority's "A runbook carries an independently checked release version" says a version "SHALL NOT be inferred from a directory name or an HTML schema-version declaration", and the reasoning applies to prose too. So a version constraint needs a structured value. A head meta the program writes and reads is the smallest one. It is outside the projected model, so the contract's vocabulary does not move. I checked that 1.1.0's validation and formatting both keep such a meta as written, and the build task proves it again before relying on it. Comparing within one major follows the project's own reading of a major release, a change that breaks what came before.

The user decided on 2026-10-27 to keep atLeast and the record's release meta in 1.2.0, as drafted. The version-free alternative, which would have shipped the declaration without atLeast and added the meta later, was set aside.

Built on 2026-10-27. run --as writes the meta directly after the htmlspec-kind meta, and a new record validates under --strict and passes format --check with it in place, so neither drops nor refuses it.

Settled after the review of 2026-10-27. Only a meta in the record's head states its release. One written in the body states nothing, so it can neither stand in for the head's nor make a second one. A check without atLeast does not read the release for its verdict. Its report still names what a satisfying record states: a release, no release, one that is not three dot-separated integers, or more than one. It does not show a malformed or duplicated meta as no release.

A known looseness, older than this change and left as it is: the version parser that reads both the meta and atLeast accepts surrounding whitespace, a leading +, and leading zeros, so " +00.1.0 " reads as 0.1.0. Tightening it would change what a 1.1 program accepted as a runbook's VERSION, so it belongs to a change of its own.

5. Records are read from the declaring runbook's project only

A run check resolves the named runbook in the project that holds the declaring runbook: the current project, or the registered project --store selects. It reads that runbook's runs/ there and nowhere else. No flag points it at another project, branch, or worktree.

toolchain-packaging already says store selection "SHALL locate the runbook and its records", and a run check is exactly a question about records. Reading a second location would need a new selector and a rule for when two locations disagree, and a run recorded somewhere else is one nobody has landed. The way to make it count is to land it, and that is the project's own policy about where history lives. Machine checks keep being evaluated against the invocation's working directory, as today.

Settled in the pre-archival review, 2026-10-27: a record under runs/ that is a symbolic link, or resolves outside the runbook's runs/ folder, does not satisfy a run check, because the run it records may have happened in another project, and only this project's runs count. It is named among the records that do not, with its own reason, "is a link", decided before the file is read. The rule lives in the run check, not in gather, so run --check still reviews such a file as 1.1.1 did.

6. An unmet run check refuses the start, standalone preflight reports it, and a passed one is recorded

htmlspec run RUNBOOK --as RECORD refuses before creating anything, exits 1, and names each unmet run check and why, exactly as it does for a missing tool. htmlspec preflight RUNBOOK reports the same checks. When every check passes, the new record carries a verification for the requirement holding the run check, with outcome passed and a method naming up to three satisfying records with their releases and a count of the rest, which is what the start path already writes for a passed machine check. There is no override.

This is what a declared check already does, so a run check inherits it rather than inventing it. Naming the satisfying records in the new record answers the question a reader asks later: which backup did this migration rely on. It is the one place that link is written down.

Built on 2026-10-27, with two texts the decision did not give. The method recorded for a passed run check ends "which reads this project's runs afresh", where a machine check's ends "which observes the machine afresh". The refusal's last line on standard error, which said the machine does not satisfy every prerequisite, now says not every prerequisite is satisfied here, because a run check is about the project's records. In --json, each run check carries a run object: runbook, atLeast when declared, state (met, unmet, missing, or unavailable), satisfiedBy with at most three names, satisfying as the count, notSatisfying with each record and its reason, and openRuns. A met run check in a report that is not ready still carries its satisfying records, so the not-ready payload keeps every passed check's observation.

Settled after the review of 2026-10-27:

  • The human report that is not ready names a met run check whose required runbook has a run still under way, as decision 3 asks, under "met run check(s) have a run still under way". Its closing line says how to supply what is missing "here", not "on this machine".
  • A missing runbook's remedy says to add it or correct the name. An unavailable check's remedy is the one its observation gives, naming the specification to repair. Only records found wanting are told to run the required runbook again.
  • The line run --as prints counts "check(s) passed", and a new record's opening counts "prerequisite(s)", because both include run checks.
  • preflight --help names the run check, and says it reads the runbooks and records of the project the runbook is read from, the store's under --store.
  • Every runbook name the loading, the report's header, and the started line print is shown through the terminal escaping. The fault for a contract this program cannot read printed the name raw in 1.1.1 too, and that gap is closed.

Settled in the closing pull request, 2026-10-27: a parse recovery's message quoted the character the parser stopped at raw. A run started for a runbook whose directory name holds an escape sequence composes a record the formatter refuses, because the name reaches its markup, and the refusal printed the escape to the terminal. A document holding one did the same through the formatter and validation, in 1.1.1 too. The message is now escaped where it is made, in htmlspec-parse, through the same rule the listing and the preflight report read. That rule moved from the command-line program's terminal module into htmlspec-parse's visible module, because the parser's crate cannot depend on the program, and a second copy of the set of characters a terminal hides could drift from the first. The program's terminal module re-exports it and keeps the listing's own rendering. The parse diagnostic's code is still read from the parser's own text, before it is escaped. The gap is closed.

7. A missing runbook is unmet, an unreadable specification on the way is unavailable, and a self-reference or a cycle through the declaring runbook is an invalid contract

A run check that cannot be met as written makes the contract invalid, a check whose answer cannot be established is unavailable, and one that is not met yet is unmet. Each case is one of the three:

  • No runbook directory of that exact name in the project: unmet, with the observation "this project has no runbook named NAME". The declaration is well-formed, and the project may simply not have that runbook yet, which matters most for a carried runbook (decision 10).
  • A runbook that names itself: an invalid contract. Preflight and run --as exit 2 with a fault on standard error identifying the requirement, as the scenario "The contract is malformed" already requires for an invalid declaration. No report is written.
  • A cycle through the declaring runbook, where migrate requires backup and backup, directly or through others, requires migrate: an invalid contract. It exits 2, and the fault names the requirement and the whole cycle in order, starting from the declaring runbook. Only cycles that pass through the runbook being checked are looked for. A cycle elsewhere in the project, among runbooks this one does not reach, is not this runbook's fault, and the listing reports it there.
  • A runbook reached on the way whose specification cannot be read, needs error recovery, or does not validate: the check is unavailable, naming that runbook and the fault. Whether its declarations lead back cannot be established, and preflight already reports an observation it cannot make as unavailable, never as met.
  • An unknown field, a missing runbook, an atLeast that is not three dot-separated integers, or a name that fails the name rule: an invalid declaration, exit 2, as for every form.

"Malformed" is not a new report outcome. The report's outcomes stay as they are, and an invalid contract is reported, as today, by refusing with exit 2 before any report.

Invalid and unmet stay distinguishable, as toolchain-packaging requires: an invalid contract means the runbook can never start as written, and unmet means it cannot start yet. A cycle is invalid because its declarations cannot all hold as an order: whichever runbook runs first breaks one of them. Records made before the declarations were written can exist for some runbooks in the cycle, so a check of records alone might even pass. That would hide the contradiction, not settle it, which is why the cycle is refused before records are read. htmlspec validate does not check another runbook's existence or a cycle, because validation looks at one document, and runbook-authority's "A machine requirement is still an obligation of the run" keeps project and machine inspection in preflight and run creation.

Built on 2026-10-27. Self-references and cycles are refused when the runbook is loaded, before any check runs, so preflight and run --as both exit 2 with the fault and write no report. A cycle is named from the declaring runbook, as "two requires a run of three requires a run of one requires a run of two". An unreadable specification on the way refuses nothing when the runbook is loaded: the search goes on through the other declarations, so a cycle it can still see is refused, and otherwise the check reports the unreadable runbook as unavailable when it runs. The check is made on the runbook's enumerated name, whatever case the command line typed (decision 2's note).

8. The runbook listing shows each runbook's prerequisites and their state, and --graph draws the same as a Mermaid diagram

htmlspec list --runbooks and the bare run listing gain, per runbook, the runbooks it requires and the state of each now, with the records that meet it, and htmlspec list --runbooks --graph draws the same facts as a Mermaid flowchart.

The JSON follows the precedent the change listing set for follows: a resolution per edge, and the project's cycles at the top level.

  • Each runbook entry gains prerequisites , one object per declaration with:
    • requirement: the requirement holding it;
    • runbook: the name it declares;
    • atLeast, where declared;
    • state: one of met, unmet, missing, self, cycle, or unavailable;
    • satisfiedBy: an array of up to three record names;
    • satisfying: how many records satisfy it in all;
    • openRuns: the names of the named runbook's records still open, as in preflight and run.
  • Each runbook entry gains declarations, one of readable, malformed, or unreadable. A runbook whose specification cannot be read, needs recovery, or holds a malformed declaration lists no edges it cannot know.
  • Each runbook entry gains prerequisitesMet, which is true only when declarations is readable and every entry's state is met. A runbook with no prerequisites and readable declarations is met.
  • The payload gains prerequisiteCycles at the top level: every cycle in the project, each as the list of its runbook names in order, starting from the least name. It is empty when there are none.

Human output shows the same, with names escaped as the listing already escapes them. A runbook's declarations fault and a cycle are shown in its rows. The help says "met" covers prerequisite runs only, and not machine checks.

The graph. For the example project, with one passed backup run at 1.4.2 and no runs of the others, htmlspec list --runbooks --graph prints:

  r2["create-account"]
  r3["deploy-service"]
  r4["migrate"]
  r5["provision-database"]
  r1 -->|"met, at least 1.4.0"| r4
  r2 -->|"unmet"| r5
  r5 -->|"unmet"| r3
  linkStyle 0 stroke:#2e6b3a,stroke-width:2px
  linkStyle 1,2 stroke:#a33333,stroke-width:2px,stroke-dasharray:5 4

Its layout, line by line:

  1. flowchart LR.
  2. One node line per name, sorted byte for byte. The names are the project's runbooks together with every declared name that matches no runbook, so a missing runbook's node takes its place in name order. Nodes are numbered r1, r2, and so on, in that order.
  3. One edge line from each prerequisite to the runbook that declares it, sorted by prerequisite and then by runbook. Two declarations in one runbook naming the same prerequisite make one edge. Its label lists each distinct atLeast in ascending order, and it is met only when both declarations are met.
  4. classDef lines for the classes the diagram uses, in this fixed order: missing, drawn with a dashed border, then malformed, drawn with a red border.
  5. class lines, one per class in that same order, each listing its node identifiers ascending.
  6. linkStyle lines, one per style used, in this fixed order: met, unmet, then cycle. Each lists its edge indices ascending, separated by commas.

Edge cases in the graph.

  • An isolated runbook is a node with no edges.
  • A declared name matching no runbook gets a node labelled with the name and "(no such runbook)", in the missing class, and its edge is unmet.
  • A self-reference is a loop labelled "requires itself", in the cycle style.
  • Every edge of a cycle is labelled "cycle" and drawn in the cycle style.
  • A runbook whose declarations are malformed or unreadable is labelled with its name and "(declarations cannot be read)", in the malformed class, and has no incoming edges, because its declarations cannot be known.
  • A project with no runbooks prints flowchart LR alone.

Escaping in the graph. A runbook name never becomes a Mermaid identifier: the name appears only as a node's quoted label. A label is built in two steps. First, each character a terminal would not show as itself is written in shown's code-point form, <U+001B>. That covers every control character, so a newline, a carriage return, or a tab can never reach a label as a line break. Then the characters Mermaid or HTML would read are written as Mermaid entity codes: " as #quot;, # as #35;, % as #37;, ` as #96;, < as #lt;, > as #gt;, and & as #amp;. So a name holding ESC comes out as #lt;U+001B#gt;, and one holding %% cannot begin a Mermaid directive. The characters Mermaid uses inside its parser to carry an entity code, ﬂ, °, ¶, and ß, are written in the code-point form, so a name holding them cannot render as another name. Titles are not shown, so the diagram stays one short label per runbook. The output never contains a raw < or &.

Output, exit, and options. The diagram goes to standard output with nothing before or after it, so it can be pasted into a document's <pre class="mermaid"> as it stands, and htmlspec format then writes the arrows' > as &gt;, as for every diagram. The exit code is the listing's: the graph reports and never gates. --graph without --runbooks is refused as a usage error, exit 2, and the bare run listing has no graph form. With --json, --graph changes nothing: the payload is the listing's, which expresses every node, edge, state, and cycle the graph draws. Refusing the combination would leave a request for structured output unanswered, against toolchain-packaging's "Output is available in human and machine forms". A second schema for the same facts would be a second place to keep them right.

Determinism: nodes and edges are sorted as above, by bytes, never by directory listing order, so the same project gives the same bytes on every run and every machine.

The user decided on 2026-10-27 to add --graph to 1.2.0, where the draft had left it for a later minor.

Settled on 2026-10-27, in group 2's review: a run check whose answer cannot be established is reported with state unavailable. That covers a specification on the way that cannot be read, needs recovery, or does not validate. The word is the outcome preflight already reports for an observation it cannot make. It is the value in the preflight and run payloads, and the listing uses the same word when group 3 merges group 2's work. Group 2's draft called it unknown, and 1.2.0 never shipped that word.

The listing answers both of the user's questions, what must run first and what can start now, and the graph answers them at a glance for a project with more than a few runbooks. It also gives a document a picture of the order that the program drew, rather than one a person drew and has to keep in step. Putting it on list --runbooks, rather than a new command, keeps it inside the operation that enumerates runbooks, as runbook-authority requires. Giving the JSON every state the graph draws is what lets --json --graph equal --json honestly.

Built on 2026-10-27, group 3. Three things this decision left open are settled, each in the task it affects. The listing's state also reads unavailable (first built as unknown, renamed when group 2's review renamed it in preflight), as group 2's preflight payload does, so that prerequisitesMet is never true where a start would report a check unavailable (task 3.1). The graph labels such an edge cannot be checked, draws it unmet, joins two atLeast values with "and", and draws the cycle style as stroke:#7a3fa3,stroke-width:3px (task 3.3). The schema's runbooks branch keeps runbooks as its only required field, because the surface keys a branch by its required set (task 3.1). Human rows read requires NAME at least X.Y.Z: followed by the state in words.

Settled on 2026-10-27, after PR #89's review, which found five things the first build got wrong and the coordinator decided one more.

  • % is escaped. %% begins a Mermaid directive or comment even inside a quoted label, so a name holding %%{init: …}%% restyled or broke the diagram. It is written #37;. The characters Mermaid uses internally to carry an entity code, ﬂ, °, ¶, and ß, are written in shown's code-point form, so a name holding them cannot render as a different name. Both were rendered once in headless Chrome: each label read as written and the diagram kept its theme.
  • Only met and unmet carry records. The first build read the named runbook's records for every state, so a self-reference or a cycle could list a satisfying record that preflight, refusing the contract, never reads. The state is now a type whose met and unmet variants alone hold records, so that combination cannot be built. The other four write an empty satisfiedBy, zero satisfying, and an empty openRuns.
  • openRuns is an array of record names everywhere, by the coordinator's decision. It was a count in the listing and an array in the run object preflight and run write. Preflight names every open run, with no bound, so the listing does too. The human listing still prints a count.
  • Cycles are searched for only within strongly connected components. Walking every path from every runbook was exponential even with no cycle: 51 runbooks in 17 layers took seconds. A cycle lies inside one component, so a path leaving its start's component is never followed. The cycles found, and their order, are unchanged. The start path's refuse_cycles in group 2 walks with a visited set and is linear, so it does not share the problem.
  • prerequisiteCycles stays optional in the schema. The program writes it on every runbook listing from 1.2.0 on. Requiring it would change the required set the surface keys the runbooks branch by, which reads as the 1.0 branch withdrawn. A consumer of 1.x reads it where present, which is every 1.2.0 listing.

Settled in the pre-archival review, 2026-10-27: prerequisiteCycles lists one cycle per group of runbooks that lead back to one another, a strongly connected component, and not every elementary cycle, which grows factorially: nine runbooks that each require all the others held 125,664 cycles, a 14 MB payload. The representative is the shortest cycle through the component's least runbook, found breadth first over names in order, and components are listed by their least runbook, so the output is the same everywhere. The human listing names a met prerequisite's open runs too, ", 1 run still open", as the JSON's openRuns already did.

9. A parent runbook needs nothing special

A runbook that walks other runbooks in order is an ordinary runbook. Its steps say to start each child, and each child declares its own prerequisites, so each start is checked where it happens. A parent that must not start before a child has passed declares that child as a prerequisite like any other.

The downstream project's sketch of a parent was a ledger: it starts children and records which runs it started. Both are already possible. What it lacked was a check that the order held, and that is now each child's own declaration. Giving parents a special kind would add a concept to solve a problem the declarations already solve.

10. A carried runbook's prerequisite is required from the receiving project

A runbook carried to another project and run there with --store checks its prerequisites against the runbooks and records of that project. If the prerequisite runbook was not carried, or has no passed run there, the check is unmet with that reason.

runbook-portability already requires tools and skills "from the receiving machine rather than vendor them". A prerequisite run is the same kind of need, met where the work happens. Carrying old records to satisfy it would be a run that did not happen in that place. The contract table says which of that requirement's sentences and scenarios change.

Built on 2026-10-27. Under --store, the run check reads the selected project's runbooks and records, and machine checks still read the invocation's working directory, which the existing test for that keeps proving.

11. Per-item verdicts, freshness, other locations, and starting runs on the user's behalf are out of scope

htmlspec checks that a run of a runbook finished and passed. It does not know which items inside that run passed: a run over many hosts or accounts whose items each have a verdict keeps those verdicts in the project's own files, and deciding which items go on to the next runbook is the project's business. It does not check how recent a run is, read records outside the project, or start a prerequisite run itself.

Each of these needs a fact htmlspec does not have (an item's verdict, a run's time, another location) or an action it does not take (starting work). Stating them as boundaries keeps a reader from assuming the check covers more than it does.

12. It ships as 1.2.0, after install-through-wsl-without-nix archives at 1.1.1

This change follows install-through-wsl-without-nix, and its FOLLOWS file says so. That change archives at 1.1.1 first. This one opens after it: the workspace moves from 1.1.1 to 1.2.0, and spec.nix stays at 1.1.1 until this change archives at 1.2.0. Branching only after 1.1.1 has archived avoids both. Risks

An old passed run satisfies a declaration that meant a recent one

Records state no time, so a backup from last month satisfies migrate's declaration as well as one from this morning.

Accepted as a stated boundary (decision 11). A runbook that needs a recent run says so in a step, and its record carries the operator's judgment. atLeast at least excludes runs of a release the dependent runbook no longer trusts.

A dependent run starts while a newer prerequisite run is still under way

An older finished backup run satisfies the check even while a new backup run is open, so a migration can start in the middle of a backup.

The report and the listing name every open run of the named runbook, even when the check is met. The JSON carries openRuns, so the person starting the migration sees the backup in progress. Refusing while any run is open was set aside, because one abandoned open record would block every dependent run until someone edited it. A runbook that must not start during its prerequisite says so in a step.

The strict rule tempts an operator to record a pass

A prerequisite run with one failed or partial outcome blocks every dependent run, so an operator in a hurry can be tempted to change the outcome to passed. runbook-execution warns against exactly this: a report that treats a recorded failure as a fault "would teach an operator to record a pass".

The refusal names the record, the requirement, and the outcome, so the way forward is plain: run the prerequisite again and let a new record pass. The README says so beside the check: a failed run is a correct record, and the fix is a new run, never an edited outcome. The rule stays strict, because a softer one would let a dependent run start on a prerequisite that is known to have failed.

A record edited by hand reads as passed

A record is an editable document, so its task states and outcomes can be changed to satisfy a check.

Accepted. A record is a person's account of a run, and runbook-authority already says a copied version "does not attest that the copy is authentic". The check makes the order visible and refuses honest mistakes. It is not a security boundary, and the README says so.

A formatter or validator drops or refuses the release meta

If htmlspec format or a future validation rule removed an unknown head meta, records would lose their release and fail every atLeast.

Task 2.2 proves that validation and formatting keep the meta, with a test that fails if either drops it. Version 1.1.0 already keeps it, which I checked on a copy of a real record.

A runbook with many records makes preflight slow

A run check parses every record of the runbook it names, and reads specifications to find cycles through the declaring runbook.

Accepted. A record is one document, and parsing a few hundred takes well under a second at the speeds the suite measures. Naming is already bounded to three satisfying records. If it ever matters, the check can stop counting once it no longer needs a total.
