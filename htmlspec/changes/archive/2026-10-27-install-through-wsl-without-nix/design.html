Install htmlspec on Windows through WSL, without Nix: design

Windows is served through WSL 2 and the Linux build, and native Windows is not a goal. The README installs htmlspec on Linux and WSL without Nix, using a block that names no version and checks the binary against SHA256SUMS, and it names what a contributor without Nix needs. The block is run verbatim against every release on both Linux architectures, and the publish runbook records the result. There is no install script: the README block is the installer, by the user's decision.

Subject
Install htmlspec on Windows through WSL, without Nix: design

What a person without Nix meets today

Measured on 2026-10-26 against main at 246cf19 and the published v1.1.0.

  • README.md's "Getting started" puts nix run github:Firefly-Projects/htmlspec first, then brew install and cargo install --locked htmlspec-cli in the same block. It follows with one sentence: "Or download a binary for macOS or Linux from the releases page". It gives no commands for that, and no word on Windows, WSL, or Homebrew on Linux's PATH step.
  • "Building" gives four Nix commands, then cargo build --release and cargo run "without Nix". It does not say that scripts/check runs without Nix, or what it needs.
  • Each release publishes htmlspec-X.Y.Z-x86_64-unknown-linux-musl.tar.gz and htmlspec-X.Y.Z-aarch64-unknown-linux-musl.tar.gz, static binaries, beside SHA256SUMS. Each tarball holds one directory of its own name, with htmlspec, LICENSE, THIRD-PARTY-LICENSES, and CRATE-LICENSES.
  • https://github.com/Firefly-Projects/htmlspec/releases/latest/download/SHA256SUMS answers with the latest release's sums. Each line is a digest, two spaces, and a tarball's name, so the name of the right tarball can be read out of it without knowing the version. Run against v1.1.0's file, grep -- "-$target.tar.gz\$" SHA256SUMS | cut -d' ' -f3 printed the expected name for both Linux targets.
  • scripts/check needs cargo with rustfmt and clippy, a C linker for cargo to link with, bash, python3 with the standard library only, and git, the last for the prompt stage. The flake's checkSuite supplies the toolchain, bash, python3, and git in the sandbox (flake.nix, its nativeBuildInputs), and its standard environment supplies the linker. scripts/check --list prints the stages. Throughout 1.1.0 this repository's suite ran outside nix develop, with the pinned Rust toolchain first on the path and macOS's own /usr/bin/python3 3.9.6, and passed every stage each time. The Nix shell's Python is 3.13.14. Those two versions are what was checked. Nothing in continuous integration holds a lower bound.
  • scripts/check-prompt drives target/debug/htmlspec unless it is given --binary (its line 243). It does not read CARGO_TARGET_DIR, so a contributor who sets it builds the binary elsewhere and the prompt stage drives a stale one or none.

Decisions

1. Native Windows is not a goal. Windows means WSL 2

The user decided on 2026-10-26 not to support native Windows, and withdrew the unscheduled release-a-windows-build proposal in this change's branch. A person on Windows installs WSL 2, opens a Linux distribution (Ubuntu is the default), and runs htmlspec there like any Linux user.

Everything around the program assumes a POSIX shell: scripts/check and the other bash and Python scripts, the git hooks, the Nix development shell, and preflight's model of PATH, executables, and process groups. A native build would be the binary alone, and every one of those would need a Windows counterpart or an exception. WSL 2 runs a Linux kernel, so the Linux build and every one of those tools work there unchanged.

2. The README installs by platform, and Nix is one route among several

"Getting started" opens with a short "Installing" part in three places. Each route there has its own commands:

  • Linux, and Windows through WSL: the release block (decision 3), Homebrew on Linux with the line that puts it on PATH (eval "$(/home/linuxbrew/.linuxbrew/bin/brew shellenv)", added to the shell's start-up file), and cargo install --locked htmlspec-cli after rustup, naming build-essential for the linker Ubuntu lacks.
  • macOS: Homebrew, and the release tarballs for the two macOS targets.
  • Nix, anywhere: nix run and nix profile install, stated as optional.

The Windows part sits at the top of the Linux one: install WSL with wsl --install, then follow the Linux route inside it.

Homebrew's Linux prefix, /home/linuxbrew, is a home directory by shape, and publish/patterns.tsv row 36 refuses every /home/<name> except /home/operator. Left as it is, the README's Homebrew lines would stop the 1.1.1 export at its scan. Task 1.3 widens that row's allowance to /home/(operator|linuxbrew)\b, with a publish/test case, before the README gains the lines.

A reader looks for their platform, not for a package manager they might not have. Placing Nix first told a reader on Ubuntu or Windows that Nix was expected. The colleague who could not run a Homebrew install shows the cost of leaving out a route's last step. The README is non-normative, so these are its own words. The commands in them are held to the release by decision 7.

Built on 2026-10-27, with one shape the decision did not give. The Homebrew-on-Linux block's first line is eval "$(/home/linuxbrew/.linuxbrew/bin/brew shellenv)", so the block runs as written in a terminal where brew is not on PATH yet. That is the state of a fresh install, and of the runner the install-homebrew job uses. The line that adds it to the start-up file follows in a block of its own. The cargo route runs rustup toolchain install stable, because a reader installing htmlspec has no rust-toolchain.toml for the bare form to read. The README also gained a short "After installing" part, which keeps the license paragraph and the first commands "Getting started" held.

Settled after the review on 2026-10-27. Row 36's allowance is /home/(operator|linuxbrew)(?![A-Za-z0-9._-]), not \b: a word boundary ends at a dash or a dot, so it excused a home directory whose name merely began with an excused one. publish/test now refuses both shapes. The Ubuntu commands run apt-get update before apt-get install, and the PATH advice says the change takes effect in a new login shell, names ~/.bash_profile, and says what to do in a desktop Ubuntu terminal. The Windows-browser route is stated as resting on WSL 2's localhost forwarding and as not tried here.

3. The Linux block reads the latest release's sums and names no version

The block, as the README will hold it:

(
  set -eu
  target="$(uname -m)-unknown-linux-musl"
  base=https://github.com/Firefly-Projects/htmlspec/releases/latest/download
  tmp="$(mktemp -d)"
  trap 'rm -rf "$tmp"' EXIT
  cd "$tmp"
  curl -fsSLO --retry 3 "$base/SHA256SUMS"
  file="$(grep -- "-$target.tar.gz\$" SHA256SUMS | cut -d' ' -f3)"
  [ -n "$file" ] || { echo "no htmlspec build for $(uname -m)" >&2; exit 1; }
  curl -fsSLO --retry 3 "$base/$file"
  sha256sum --check --ignore-missing SHA256SUMS
  tar -xzf "$file"
  mkdir -p "$HOME/.local/bin" "$HOME/.local/share/doc/htmlspec"
  install -m 755 "${file%.tar.gz}/htmlspec" "$HOME/.local/bin/htmlspec"
  cp "${file%.tar.gz}"/*LICENSE* "$HOME/.local/share/doc/htmlspec/"
  "$HOME/.local/bin/htmlspec" --version
)

It needs curl with ca-certificates, and GNU coreutils, whose sha256sum has --ignore-missing (BusyBox's does not). Ubuntu under WSL has all three, and the README names them for a minimal image, where apt-get install curl ca-certificates adds what is missing. It runs in a subshell, so a failure stops the block without closing the reader's terminal, and its temporary directory is removed whichever way it ends. Each download is retried three times. It checks the tarball before unpacking it, and it installs the three license files where the Nix package puts its own. Running it again installs the newest release over the old one. That is the upgrade, and the README says so. A reader who wants a particular version replaces latest/download with download/vX.Y.Z. If ~/.local/bin is not on the reader's PATH, the README gives the one line that adds it. Ubuntu's own ~/.profile adds it at the next login once the directory exists, so the README says to open a new terminal first.

A block that names a version is wrong from the next release until someone edits it, and the public README changes only when a release is exported. Reading the name from SHA256SUMS keeps the block true for every release with no edit. It also makes checking the digest part of finding the file rather than an extra step a reader can skip. uname -m prints x86_64 or aarch64 on the machines the release builds for. Any other machine finds no line, and the block says so rather than downloading nothing.

Settled after the review on 2026-10-27. Two things the block relies on are now held, not just stated. scripts/check-readme-install refuses a Linux block with no sha256sum --check … SHA256SUMS line, or with one that comes after its tar -x or install line. And the release workflow keeps a patch on an older line from becoming the latest: the release job compares the tag with the published releases and passes --latest=false unless it is the highest version, on the create path and on a rerun's edit path. Without that, GitHub would mark the older patch Latest, and the block would install it for every reader.

4. No install script: the README block is the installer

The user decided on 2026-10-26: there is no install.sh, only the README block. No release asset is added, and the README offers no curl … | sh form. The block is the installer, and decision 7 runs it against every release.

An install script would turn the block into one line, curl -fsSL …/install.sh | sh, and it could also cover macOS. It would cost:

  • a release asset, listed in SHA256SUMS and built by scripts/pack-release;
  • a script in POSIX sh that has to run on every distribution's shell, unlike a block a reader runs in their own;
  • the trust question every curl | sh asks: people would run it unread, and the README would have to show how to read it first.

The block asks for none of that, and a reader sees every command before running it.

Proposed as a recommendation when this design was written, and accepted by the user's decision of 2026-10-26.

5. The Windows part says where projects live, how documents open, and where agents run

The Windows part of the README gives three pieces of WSL guidance, each in a line or two.

  • Where a project lives. Keep it in the Linux file system, under ~, not under /mnt/c, and use git from inside WSL. Under /mnt/c every file access crosses into Windows and is slow, and Windows' git is the one that would check the project out. With its common core.autocrlf setting it rewrites line endings, including in the asset store. Those files are named by their digests, so validation then reports asset/mismatch.
  • How documents open. explorer.exe . opens the project's folder in Windows, and a Windows browser can open a document from there, at a \\wsl.localhost\… path. The route known to work is the one the README already gives for Safari: python3 -m http.server in the project, then http://localhost:8000/htmlspec/specs/ in the Windows browser. It rests on WSL 2's documented forwarding of localhost from Windows to the Linux side, which is on by default. Whether a browser loads the store above a document over file://wsl.localhost/… is checked as decision 8 says, and until then the README states only what was checked.
  • Agent tools. Install the coding agent inside WSL, as its Linux build, so it runs where htmlspec and the project are. htmlspec init --tools … writes the instructions there. Editors reach the project through their WSL integration.

Each of these is a place a person on Windows goes wrong without being told, and each costs a line. The line-ending case matters most, because the failure it causes, asset/mismatch, points at the store, not at where the project was checked out.

6. A contributor without Nix is told what to install, and what only Nix checks

"Building" becomes two equal parts. The part without Nix names what a machine needs:

  • rustup, then rustup toolchain install in the repository, which reads rust-toolchain.toml and installs Rust 1.90.0 with rustfmt, clippy, and rust-src. It is run explicitly, as the release workflow runs it, rather than left to the first cargo command;
  • a C linker (build-essential on Ubuntu);
  • Python 3, standard library only, with the versions checked stated as such: 3.9.6 and 3.13.14, and Ubuntu's own in the job below;
  • bash and git.

It says that scripts/check runs every stage with those, the stages continuous integration runs, which scripts/check --list prints. It says that a contributor who sets CARGO_TARGET_DIR gets a prompt stage that finds the binary there, once task 3.5 has the stage read it. It also names what only the Nix sandbox and continuous integration check:

  • that every file a stage reads survives the flake's source filter and is tracked;
  • the provenance of the vendored browser libraries, re-fetched from their pinned addresses;
  • a reproducible nix build.

Publishing stays a maintainer's job. The publish runbook's preflight requires the flake's development shell on purpose, and the README says so in one line.

A continuous-integration job proves the claim continuously. It runs rustup toolchain install and then scripts/check on Ubuntu with the system's Python, with no Nix. It runs on a schedule once a week, and on pull requests whose paths match README.md, rust-toolchain.toml, Cargo.toml, Cargo.lock, crates/**, scripts/**, flake.nix, or its own workflow file. The README's "Two workflows check what arrives" table gains its row.

"Runs without Nix" is a claim the README would make about every stage, and stages are added often. A claim about the suite that nothing checks drifts, exactly as the Linux block would. The job runs the same scripts/check, so it adds no second list of steps, and toolchain-packaging's "Project checks are runnable as one command" holds. The job runs on Linux, whose minutes cost the normal rate in the private repository, unlike macOS's tenfold rate. So the filter is there to keep pull requests that touch only documents from running the suite twice, not to ration an expensive runner. It names every path the suite builds from, and the weekly run catches the slow drift of the base image.

Built on 2026-10-27. The workflow is check-without-nix.yml, and its job is named check-without-nix, not check, so its result is never mistaken for the check the branch ruleset requires. It can also be started by hand. The README's table now reads "Three workflows".

7. Every release installs itself through the README, on both Linux architectures

The check has three layers:

  • Offline, in the suite. A new stage, readme-install, runs scripts/check-readme-install, a standard-library Python script. It reads README.md and finds each install block by a marker comment just before its fence. It fails when a marked block is missing, when bash -n refuses it, or when the Linux block could pick a target the release does not build. That last check reads the targets from scripts/release_facts.py, where the release reads them. It also fails when the block's reading of SHA256SUMS no longer matches what scripts/pack-release --sums writes. It needs no network, so it runs on every pull request and inside the sandbox. The script joins the flake's patchShebangs line, and the source filter already admits README.md and the scripts.
  • Networked, in the release workflow: two jobs, after what each one tests.
    • install has needs: release and runs on ubuntu-24.04 and ubuntu-24.04-arm. Before running anything, it polls releases/latest for a bounded time, about five minutes, until the address it redirects to ends in /tag/$TAG. If the latest release names a newer version than the tag, the tag is a patch on an older line. The block, which always installs the latest, cannot test it, so the job reports that and ends as skipped without failing. If the bound passes and the latest still names an older version, the job fails with its own message, "latest is not $TAG". Otherwise it extracts the marked Linux block from the README at the tag and runs it verbatim with bash -x, so a failure names its line, with HOME set to an empty directory. It requires the installed htmlspec --version to name the tag's version, then runs htmlspec init --tools none, htmlspec new change smoke, and htmlspec validate in a scratch project.
    • install-homebrew has needs: tap, so it runs only after the formula is in the tap, and runs on ubuntu-24.04. The runner image carries Homebrew under /home/linuxbrew. It runs the Homebrew-on-Linux block verbatim with bash -x and reads the version the same way. An expired tap token fails tap and this job, and nothing else.
    • Both carry the condition every job after release carries: github.repository == 'Firefly-Projects/htmlspec' && startsWith(github.ref, 'refs/tags/v'). cargo install is left to the publish runbook, because it compiles for several minutes and the runbook already installs it.
  • Recorded, in the publish runbook. Step 6, "Watch the release workflow to its end", treats a failed install or install-homebrew job as something to carry to step 8, not as a reason to stop. Publication has already happened, and rerunning those jobs cannot change it. Step 8, "Check each channel", records each job's result beside the four channels it installs on the maintainer's machine. When a job failed because the README's commands were broken at the tag, step 8 records the failure and stays open. The fix ships as a patch release, and when that release's run of the job that failed, install or install-homebrew, passes, step 8 is settled with a note naming it, so the record can land. A job that failed for another reason, a timeout waiting for latest or the network, is run again and its rerun recorded.

The block is tested against the release it describes, the published one, because its whole job is to fetch that. The job therefore runs after publication and cannot stop it. What it changes is when a broken block is found: at the release, by a job whose trace names the line that failed, not later by a person who cannot tell a broken block from a mistake of their own. Polling latest keeps the job from testing the previous release in the moments before GitHub moves latest to the new one. The skip for an older line keeps a patch to a maintained older minor from failing a check that can only test the newest. Splitting Homebrew into its own job after tap keeps it from racing the formula's push. The offline layer catches the cheap failures, a syntax error or a target the release dropped, before anything is published. The job needs the network and a published release, so it cannot be a stage of scripts/check. It stands outside the suite for the reason the vendored-asset provenance check does, and its workflow comment says so, as check.yml's does.

Built on 2026-10-27, with two settlements. A running job cannot mark itself skipped, so for a patch on an older line install ends with a notice, the steps after the poll are skipped, and the job succeeds. scripts/check-readme-install also prints a marked block with --print, and both install jobs extract the block that way, so the jobs and the offline stage read the README one way. The stage also runs the script's --self-test, which proves each check refuses what it should. The polling step ran against the live latest release: the current tag was ready, an older one ended with the notice, and a tag that never became the latest failed with "latest is not" once its bound passed.

Settled after the review on 2026-10-27. scripts/check-readme-install requires all four marked blocks, linux-release, linux-homebrew, cargo, and macos-homebrew, so a route that disappears from the README fails the suite. Only the latest release reaches the tap, since the formula holds one version and an older line's would downgrade every Homebrew install, so on an older line tap and install-homebrew are skipped.

8. What only a Windows machine shows is checked by hand once, or stated as unchecked

Three things depend on Windows itself, and no runner has it:

  • explorer.exe . opening the project's folder;
  • a Windows browser rendering a document over file://wsl.localhost/… with its store above it;
  • the http.server route reaching the Windows browser at localhost.

The README's Windows part (task 2.4) is written after this check (task 3.4), so it states only what was checked. If the user or a colleague has a Windows machine with WSL 2, they run those three once. The result is recorded as evidence, and the README states what worked. If not, the README gives the http.server route as the way to read documents from Windows, and the change's specification records the file:// route as unchecked.

The Linux jobs prove everything that runs inside WSL. They cannot prove what Windows does with the result, and writing a route nobody ran into the README is the failure this change exists to remove.

No Windows machine with WSL 2 was available on 2026-10-27, so task 3.4 was dropped. The README gives only the http.server route, and says that opening a document straight from the Linux file system in a Windows browser is not described because nobody checked it. The specification records explorer.exe ., the file://wsl.localhost/… route, and the http.server route's reach into a Windows browser as unchecked.

9. The contract gains the install check, and stays silent on platforms

One accepted requirement is modified: toolchain-packaging's "A release reaches every channel from one tag".

  • A new statement. After a release that is the repository's latest is published, its workflow installs it through the README's documented Linux commands, verbatim, on both Linux targets, and through the README's Homebrew-on-Linux commands once the formula is in the tap. The run fails when an installed binary does not name the tag's version. A release on an older line is not made the latest, so the Linux install job reports it as untested, not failed, and the tap and the Homebrew job are skipped for it.
  • A new scenario. README commands that stopped working.

"Project checks are runnable as one command" is unchanged. The offline test is part of the suite, the job without Nix runs the same suite, and the install job is outside it for the reason decision 7 gives.

The publish runbook's "Each channel's version is recorded" is modified in the runbook's own specification to cover the two install jobs' results. It gains a scenario for the README broken at the tag: step 8 records the failure and stays open until the fixing patch release's run of the job that failed passes, then is settled with a note naming that release. Step 6 is amended so that an install job's failure is carried to step 8 rather than stopping the run. That makes the runbook 0.3.0, with a changelog heading.

The contract names no supported platform, only where checks run. This change keeps it that way. The README says which platforms are served and how, and the release's targets are stated where the release reads them. A requirement naming WSL would promise something about a system nothing can run in continuous integration.

10. Release 1.1.1

The change ships as release 1.1.1, a patch.

The program does not change: no command, flag, payload, or rule. The change is documentation, a test, two jobs, and a runbook release, which a patch release carries.

11. The withdrawn proposal's earlier mentions stay as written

The 1.1.0 archive's design and tasks, and publish/READINESS.md's read log, mention release-a-windows-build as an active change. They describe main as it stood on 2026-10-23 and stay unchanged.

Archived documents are not edited, and the read log records what was read on the day it was read. Rewriting either to forget the proposal would make the record describe a main that never existed.

Risks

GitHub changes the latest/download address, or the sums' layout changes

The block depends on GitHub answering releases/latest/download/SHA256SUMS and on the sums being one digest, two spaces, and a name.

The layout is the project's own: scripts/pack-release --sums writes it, and the offline test can read it from there. The address is GitHub's, documented for release assets. The install job runs the block against every release, so a change in either fails the release run that meets it, with the failing line named.

A broken block is found only after the release is public

The install job runs after publication, so it cannot keep a release with a broken block from going out.

Accepted. The offline test stops a syntax error or a dropped target before publication. What only a published release can show is found by the job, in the same run, and fixed in a patch release. The publish runbook keeps step 8 open until the fixing release's run of the job that failed passes.

~/.local/bin is not on PATH in the reader's current terminal

Ubuntu adds ~/.local/bin to PATH at login only if it already exists, so a reader who creates it with the block cannot run htmlspec by name until they open a new terminal.

The block ends by running the installed binary by its full path, so it shows success either way. The README says to open a new terminal, and gives the line to add if htmlspec is still not found. That is the case of the colleague's Homebrew install, met in advance.
