Install htmlspec on Windows through WSL, without Nix

A person on Windows can use htmlspec today, through WSL and the Linux build, but nothing tells them so, and the README reads as if Nix were the way in. This change makes WSL the documented Windows route and makes the routes without Nix as clear as the one with it: exact commands that install the published binary on Linux and WSL, run against the release on every release, and a contributor path that names what a machine without Nix needs. Native Windows is not supported, by the user's decision.

Subject
Install htmlspec on Windows through WSL, without Nix

Why

The README's "Getting started" lists nix run first, then Homebrew and cargo install, then says a binary can be downloaded from the releases page, with no commands. It never mentions Windows or WSL. Two things happened that this would have prevented:

  • A colleague installed htmlspec with Homebrew on Linux and could not run it. Homebrew on Linux lives under /home/linuxbrew/.linuxbrew, and the step that puts it on PATH is printed once by Homebrew's installer and appears nowhere in our README.
  • The same colleague then reached for Nix, which works. But a person on Windows or a plain Ubuntu machine has no reason to install Nix to run one static binary. Every release already ships that binary for x86_64-unknown-linux-musl and aarch64-unknown-linux-musl, and it runs under WSL as it is.

Contributors meet the same tilt. "Building" shows four Nix commands and two without, and it does not say that scripts/check, the whole suite, runs without Nix, or what a machine needs for it to.

What changes

What working looks like:

  1. A person on Windows reads one section: install WSL, open Ubuntu, and install htmlspec there with the commands below. Native Windows is not supported.
  2. On Linux or in WSL they paste one block. It picks the binary for their machine from the latest release, checks it against SHA256SUMS, and installs htmlspec to ~/.local/bin. Pasting it again upgrades. The block names no version, so it stays right from release to release.
  3. Homebrew on Linux and cargo install each get a few lines of their own. Homebrew's include the step that puts it on PATH, and cargo's name the linker Ubuntu needs.
  4. Nix is described as one route among several, optional everywhere.
  5. The README says where a project should live under WSL: in the Linux file system, not under /mnt/c. It says how a Windows browser opens the documents, and that agent tools run inside WSL beside htmlspec.
  6. A contributor without Nix reads what they need: rustup, a C linker, Python 3, bash, and git. They also read that scripts/check runs every stage with those, and what only the Nix sandbox checks.
  7. Every release installs itself through the README's own Linux commands, run verbatim on both Linux architectures after it is published, and the publish runbook records the result when it checks each channel. A README whose commands stopped working is found at the release, not by the next person to try them.

Alternatives considered

  • A native Windows build. Drafted as release-a-windows-build and withdrawn on 2026-10-26 by the user's decision. Everything around the program assumes a POSIX shell: the bash scripts, the git hooks, the Nix development shell, and preflight's model of PATH and executables. A native build would be the binary alone, and supporting it would mean supporting Windows' differences everywhere else. Windows users use WSL.
  • An install script published with each release, run as curl … | sh. It would shorten the Linux route to one line. Set aside by the user's decision of 2026-10-26: there is no install.sh, only the README block. A script would add a release asset that people are asked to run unread, and the block shows every command before it runs.
  • Documentation only, untested. Cheaper, and it is how the release-page sentence came to be: nothing ran it, so nothing noticed it gave no commands. Commands that nothing runs go stale.

Scope

  • Not a native Windows build, and no promise of one later. No Windows target, no PowerShell instructions, no .exe, and no change to how the program handles paths or executables.
  • No change to the program. The command surface and the documents the program writes are unchanged. This is documentation, its tests, the release workflow, the export scan's allowance for Homebrew's Linux prefix, and the publish runbook. The contract changes in one place: toolchain-packaging's "A release reaches every channel from one tag" gains one statement and one scenario, for the install check.
  • No new channel. The Linux tarballs, Homebrew, crates.io, and the flake already exist. This documents them for Linux and WSL and tests what the README tells people to run.
  • No WSL runner. GitHub provides none. WSL 2 runs a Linux kernel, so the Linux jobs run the same binary and the same commands. What only a Windows machine can show, a Windows browser opening a document stored in WSL, is checked once by hand where possible and stated as unchecked where not.
