Install htmlspec on Windows through WSL, without Nix

What this change established. Windows is served through WSL 2 and the Linux build, and native Windows is not a goal. The README installs htmlspec by platform, with a Linux block that names no version, checks its download against SHA256SUMS, and installs under ~/.local, and it names what a contributor without Nix needs. The check suite holds those commands offline, and every release that is the repository's latest is installed through them, verbatim, on both Linux targets. Only the latest release becomes the repository's latest and reaches the Homebrew tap, so a patch on an older line can neither redirect the README's block nor downgrade the formula.

toolchain-packaging

A release reaches every channel from one tag req-a-release-reaches-every-channel-from-one-tag

Every release SHALL be cut from one tag, vX.Y.Z, whose version equals the version the workspace declares, and the binaries, the crates, and the Homebrew formula the release produces SHALL each name that version. The release SHALL refuse a tag that names another version before it builds anything.

Publication SHALL begin only from a version tag in the public repository, Firefly-Projects/htmlspec, only for a commit that repository's main holds, and only after the check suite has passed on that commit. A tag in any other repository SHALL publish nothing. A release SHALL publish only from a run in which the binary of every target it releases was built and the formula passed its check, though runs elsewhere leave some of those jobs out.

A publication interrupted partway SHALL finish when run again, and SHALL NOT publish any version twice: the crates publish one at a time, a version the registry already holds is skipped, and a rate limit is waited out within a stated budget, after which the run stops and names the crates that remain. Every request the release makes to crates.io SHALL carry a fixed User-Agent that names the project, and no personal information.

Each channel that ships the binary SHALL ship its notices with it: each release tarball holds them beside the program, the Homebrew formula installs them, and the Nix package installs them under share/doc/htmlspec/. The formula SHALL declare exactly the licenses the binary credits. The check suite SHALL fail when CRATE-LICENSES differs from what the lockfile reaches, naming each crate added, removed, or changed, and when the formula's template declares other licenses than the binary credits, so a pull request that changes either meets it, on Linux as well as where the macOS jobs run.

A release SHALL become the repository's latest, the release releases/latest names, only when its version is the highest among the repository's published releases, and only that release SHALL reach the Homebrew tap, whose formula holds one version. A release on an older line SHALL NOT be made the latest, and its run SHALL leave the tap as it was.

After a release that is the repository's latest is published, its workflow SHALL install it through the README's documented Linux commands, verbatim, on both Linux targets, and through the README's Homebrew-on-Linux commands once the formula is in the tap. The run SHALL fail when an installed binary does not name the tag's version. A release on an older line SHALL be reported as untested by the Linux commands, not failed, and the Homebrew commands SHALL not run for it.

The check suite SHALL hold the README's install commands without the network: each marked install block SHALL parse, the Linux block SHALL check its download against SHA256SUMS before it unpacks or installs it, SHALL ask only for a target the release builds, and SHALL read SHA256SUMS as the release writes it.

Evidence

The README's Linux block, run against the published v1.1.0 evidence-the-install-block-against-v1-1-0

On 2026-10-27 the block, printed from the README by scripts/check-readme-install --print linux-release, ran on a macOS machine under GNU coreutils 9.11 against the published v1.1.0, with only its target line set to aarch64-unknown-linux-musl and its install directory moved to a scratch one. It read the latest release's SHA256SUMS, picked htmlspec-1.1.0-aarch64-unknown-linux-musl.tar.gz, checked it OK, and installed the binary and its three license files. Its last line, running the binary, failed because the machine is not Linux.

Which tag is the latest, read two ways evidence-the-latest-release-and-the-poll

The install job's polling step, run on 2026-10-27 against the live releases/latest, found v1.1.0 ready, ended for v1.0.0 with the notice that a newer release is the latest, and failed for v1.2.0 with "latest is not v1.2.0" once its bound passed. The release job's comparison, fed the published tags v1.1.0 and v1.0.0, makes v1.1.1 the latest and v1.0.2 not, keeps v1.1.0 the latest on a rerun, and orders v1.10.1 after v1.9.0.

Verification

The suite holds the README's install blocks offline verify-the-install-blocks-offline

scripts/check passed all 17 stages, among them readme-install, which runs scripts/check-readme-install --self-test and then checks the README. The self-test's 11 cases each refuse what they should: a missing block of each of the four, a syntax error, a block with no checksum line, one that unpacks before its checksum, a target the release does not build, a wrong field of SHA256SUMS, a marker with no fence, and a name marking two blocks. A copy of the README with the checksum line taken out of its Linux block failed the check, naming the block.

The release installs itself through the README, and only the latest is the latest verify-the-release-installs-itself

actionlint 1.7.12 with ShellCheck 0.11.0 reports no error in any of the five workflows. The install job's polling step and the release job's comparison ran as the evidence above records, and the Linux block ran against v1.1.0 as its evidence records.

No version tag has yet run the install and install-homebrew jobs, which run only on a version tag in the public repository, so neither has installed a release on a Linux runner, and no release has yet been created with --latest set by the comparison.

The Linux block was not run in an ubuntu:24.04 container, because no container runtime was available, and the Homebrew-on-Linux block was not run anywhere before its job.

What only a Windows machine shows was not checked, because none was available: explorer.exe . opening the project, a Windows browser rendering a document over file://wsl.localhost/…, and python3 -m http.server reaching a Windows browser at localhost. The README states the last as resting on WSL 2's localhost forwarding, and does not describe the first two.
