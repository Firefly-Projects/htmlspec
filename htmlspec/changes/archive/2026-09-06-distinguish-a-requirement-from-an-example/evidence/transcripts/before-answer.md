# OpenSpec → HTMLSpec migration mapping

Source root: `/tmp/transcript52/source` (an OpenSpec `openspec/` tree).
Destination root: `/tmp/transcript52` (project root holding `spec.nix` and `htmlspec/`).

| Source artifact | Destination | Why this destination |
| --- | --- | --- |
| `specs/<capability-path>/spec.md` (accepted specification, e.g. `specs/billing/spec.md`, `specs/identity/user-auth/spec.md`) | `htmlspec/specs/<capability-path>.html` (`htmlspec/specs/billing.html`, `htmlspec/specs/identity/user-auth.html`) | `project-bootstrap` puts the project's accepted specifications in their own place under `htmlspec/`, and the toolchain enumerates them by walking `htmlspec/specs/` for `.html` files, reporting each by its path relative to that directory — so a nested capability path survives as directories with the leaf capability as the file. The README's layout shows the same shape (`htmlspec/specs/theme-selection.html`): one document per capability, named for the capability, HTML because the HTML is the source of truth rather than a render of Markdown. The document declares `kind="specification"` and its schema version, each `### Requirement:` becomes a `requirement` unit with a stable `req-` id, each `#### Scenario:` a nested `scenario` unit with a `scenario-` id and `Given`/`When`/`Then` labels, and every unit reads `data-change="unchanged"` because an accepted specification is the settled contract rather than a delta. The `## Purpose` prose carries over as ordinary prose. The Markdown does not remain beside it: two representations would reopen the question of which file is canonical, and a leftover `.md` is invisible to project-wide validation. |
| `changes/<name>/proposal.md` | `htmlspec/changes/<name>/proposal.html` | A change is a directory of kinded documents, kept where the project keeps its active changes, and the proposal is one of the four kinds. The file name is the one `htmlspec new change` writes. A proposal's enforced structure is none, so the conversion is prose-to-prose — no requirement scaffolding is invented, because `artifact-kinds` reserves the contract for a `specification` and gives a proposal freedom of form. |
| `changes/<name>/design.md` | `htmlspec/changes/<name>/design.html` | Same change directory, the `design` kind. Also unconstrained: continuous reasoning stays continuous, and any decisions or risks it already marks become `decision`/`risk` units with `decision-`/`risk-` ids. |
| `changes/<name>/tasks.md` | `htmlspec/changes/<name>/tasks.html` | Same change directory, the `tasks` kind. This kind has an enforced rule — at least one `task` unit — and each task must be individually addressable with a machine-readable completion state, so the Markdown checkboxes become `task` units with `task-` ids and a state of `todo`, `in-progress`, `done`, or `dropped`; a dropped task states why. Task progress is read from this file, so the states have to survive the conversion. |
| `changes/<name>/specs/<capability>/spec.md` (a change's delta specs, `## ADDED/MODIFIED/REMOVED Requirements`) | `htmlspec/changes/<name>/specification.html` — **one** file, however many delta capabilities the change has | `artifact-kinds` allows a change directory at most one specification artifact, and it is the same file as the change's as-built record; `specification.html` is the name the toolchain looks for at archival. The per-capability split and the `ADDED`/`MODIFIED`/`REMOVED` headings do not survive as structure: delta status is per-unit in HTMLSpec (`data-change="added"`, `"modified"`, `"removed"`), and a removed requirement stays present so a reviewer sees what is being withdrawn. Merging several delta capabilities into one document is a judgment the contract reserves for an agent, not a parser. No `task` unit may appear here — the only placement rule in the vocabulary. |
| `changes/<name>/evidence/*` (findings, scripts, data) | `htmlspec/changes/<name>/evidence/*`, unchanged bytes; the findings a specification relies on additionally become `evidence` units (`evidence-` ids) inside `specification.html` | Nothing in the contract names an on-disk evidence directory, so these files are not documents and are not validated — project-wide discovery only walks `.html`. They ride along with the change so archival keeps them, while the claims a requirement's verification rests on have to be stated as units in the document, since that is where a consumer traces requirement → evidence → verification. |
| `changes/<name>/.openspec.yaml` (`schema:`, `created:`) | no destination — dropped | Schema version is declared per document in HTMLSpec, not per change directory, and a document declares no lifecycle status. The creation date has no consumer either: `artifact-kinds` forbids inferring a change's ordering from its creation date, so carrying the field would create a value nothing reads. A change's whole-directory facts that HTMLSpec does keep live in their own plain files (`FOLLOWS`, `VERSION`) rather than in a second configuration language. |
| A change's predecessor, wherever the OpenSpec project recorded it (prose in a proposal, a naming convention) | `htmlspec/changes/<name>/FOLLOWS` — one line naming the predecessor change | Ordering must be a declaration the program can read, never an inference from a name, a date, or shared requirement ids. OpenSpec has no field for it, so nothing migrates mechanically: where the source states a sequence in prose, an agent writes it here, and a change that follows nothing gets no file at all (absent and empty are one state, and neither is reported). |
| `changes/archive/<YYYY-MM-DD>-<name>/` (an archived change) | `htmlspec/changes/archive/<YYYY-MM-DD>-<name>/`, with its documents converted exactly as the active ones above | The archive is its own place under `htmlspec/changes/`, and an archived directory is named for the date of archival followed by the change's name — which the source directories already are, so the name carries over verbatim. Migration must not re-archive: archival refuses on a name collision and would demand a version advance. Every document survives intact, because the reason for keeping the stages separate is that a reader can open an archived change and find the argument, the reasoning, the work, and the contract. |
| The version an archived change shipped in (nothing records it in OpenSpec) | `htmlspec/changes/archive/<YYYY-MM-DD>-<name>/VERSION` | `toolchain-packaging` requires each archived change to record the project's declared version at archival, in a form the project's own suite reads without version control history, and the archival version gate reads that same file. It SHALL NOT be derived from the archive directory's name — a name is a display string that gets renamed. Recorded versions must be distinct, and versions must not be invented to satisfy that, so a migrated archive that genuinely shipped as one release records the shared version honestly and the changelog carries a single baseline entry naming those changes. |
| `openspec/config.yaml` — `context:`, `rules:`, `operations: guidance:` | no destination — dropped | The project declaration SHALL NOT carry authoring rules or project context: those have no consumer, and `project-bootstrap` excludes a field nothing reads. Per-artifact rules and per-operation guidance are instructions, and instructions live in the workflow files `htmlspec init` installs for each AI tool, not in project configuration. |
| Project name, version, and toolchain pin (OpenSpec declares none) | `spec.nix` at the destination root | `project-bootstrap` requires a declaration at the project root recording the name, the version, and a pinned reference to the expected program, expressed in the language the build already uses so the pin is a build input rather than a value a bespoke parser reads. `htmlspec archive` reads `version` and refuses unless it is ordered after the last archived version, which is the one command that makes the declaration checkable. Bootstrap writes `0.0.0`, ordered before every version a project can later declare, and re-running never overwrites an edited declaration. |
| OpenSpec agent instructions (`.claude/commands/openspec/*`, `AGENTS.md` OpenSpec region, and equivalents) | `.claude/commands/htmlspec/*.md` and `.claude/skills/htmlspec-*/SKILL.md` (plus each other selected tool's own location), written by `htmlspec init` | Not a migration: bootstrap installs, per selected tool, the instructions for the whole lifecycle from exploring an idea to archiving a change, recording the generating program's version. Hand-copying the OpenSpec files would leave instructions naming commands this program does not provide, which the project's own checks reject. Where a tool reads a shared file the contributor also writes, the install is confined to a marked region so existing content survives, and bootstrap deletes nothing it did not write — so the old OpenSpec instructions are removed deliberately, by hand, once the HTMLSpec ones are in. |
| Runtime assets (an OpenSpec project has none) | `htmlspec/assets/sha256-<hash>/<file>` — one store for the whole project | A project holds exactly one asset store, in its root, and every document references that store rather than a store of its own; the alternative measured at roughly 6 MB per change. Each asset sits at a location derived from the hash of its bytes and a document references the hash it was authored against, so the bytes a page renders with cannot change without changing the page. Converted documents reference the store relatively, which is what lets every page open from the filesystem with no network. |
| `openspec/` itself | removed once the conversion is complete; the project is identified by `htmlspec/` | An HTMLSpec project is identified by a directory containing `htmlspec/`, and commands resolve the project by walking up to it. Leaving `openspec/` in place leaves a second tree that no HTMLSpec command reads and that no longer states the contract. |

## Notes on the sample source

- `source/specs/billing/spec.md` → `htmlspec/specs/billing.html`.
- `source/specs/identity/user-auth/spec.md` → `htmlspec/specs/identity/user-auth.html` (the nested capability path is preserved as a directory).
- `source/changes/add-a-thing/proposal.md` → `htmlspec/changes/add-a-thing/proposal.html`. It has no design, tasks, or delta specs, and it needs none: a change is not required to have every kind present, and validation succeeds for a change that has only been proposed.
