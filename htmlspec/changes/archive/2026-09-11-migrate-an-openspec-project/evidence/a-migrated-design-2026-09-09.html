Content-addressing the runtime assets

This design settles how the project stores one copy of its browser runtime per distinct byte sequence while letting differing revisions coexist, from one mechanism: a content-addressed store whose paths name the bytes they hold. Six decisions, each with the alternative it rejected, and a six-step order whose fifth step is where rollback stops being free.

Context

The motivation and the defect are in this change's proposal. The requirements it established are in its specification. What this page records is the reasoning between them.

Five existing project facts shape everything below, and none of them was introduced by this change:

What the approach had to fit
Fact Why it constrains the design
assets/vendor.lock.json already records a lowercase-hex SHA-256 per vendored file, with the archive URL and archive hash it came from The hash this change needs already exists and is already audited, so no new provenance mechanism is required
crates/htmlspec-assets/src/lib.rs embeds every asset with include_bytes! at a literal relative path The compiler resolves these at build time, so any layout is fixed at compile time and cannot be computed from a runtime lookup without a build script
flake.nix builds ${./assets}/${file.path} from the lockfile's path field and compares committed bytes against the recorded hash The path field is load-bearing in Nix and in Rust at once, so a layout change touches both
Documents reference assets by relative path That is what makes them render offline, and it is the property no change here may cost
scripts/check is the single definition of a healthy revision Both nix flake check and continuous integration call it, so a check added there reaches every gate at once

Goals and non-goals

Four goals, and the first is the one the others serve: one stored copy per distinct byte sequence, and coexistence of differing revisions, from one mechanism. An asset reference should name the bytes it expects, so a mismatch is detectable without a second source of truth. The offline guarantee survives — a document opens from disk with no network and no build step. And the existing provenance chain, the lockfile hash and the Nix re-fetch, keeps working rather than being replaced.

Four things are deliberately out of scope. Garbage collection of unreferenced asset bytes, for the reason the decision below gives. Deduplicating anything other than runtime assets — document bodies are not content-addressed. Changing the set of approved libraries or their versions. And Git LFS together with README.html, both excluded in the proposal.

Decisions

Store assets at assets/<algo>-<hash>/<filename> rather than renaming the file decision-hash-named-directory

The stored path keeps the original filename inside a hash-named directory, so assets/sha256-18327bef…/mermaid.min.js. The alternative was renaming the file itself to the hash, as assets/sha256-18327bef….js.

Keeping the filename preserves the extension a browser and a text editor use to choose a content type and a syntax mode, and it keeps a directory listing legible to a person, who can still tell Mermaid from Vega. A hash-named directory delivers the same uniqueness guarantee, because the directory name is what carries the hash.

The <algo>- prefix is deliberate. It makes the digest algorithm explicit at every reference site, so a future migration to another algorithm is a visible change rather than an ambiguous one.

Truncate the hash in the path to 16 hex characters, and record the full digest in the lockfile decision-truncate-to-sixteen

A full SHA-256 is 64 hex characters, which makes every asset reference in every document unreadable and every diff wide. 16 hex characters is 64 bits of digest.

The truncation is safe because the store is closed. Entries come only from vendor.lock.json and the project's own stylesheets, all of which carry their full digest in the lockfile. Validation compares the full digest, not the truncated one. The truncated form is an addressing convenience, and a collision between two entries is detectable at store-build time by comparing full digests — which the check suite does.

Full 64-character paths were considered and rejected: the readability cost is paid in every document, in every diff, forever, and the collision risk the truncation introduces is eliminated by the closed store and the full-digest comparison.

Derive stored paths from the lockfile at build time, not at runtime decision-derive-at-build-time

include_bytes! needs a literal path. Rather than hand-maintaining hash paths in Rust source, a build script reads assets/vendor.lock.json, computes each stored path, and generates the asset table. The lockfile stays the single source of truth for what the runtime is, which is what it already claims to be.

This keeps flake.nix working with a one-line change to its path construction: it already reads the same lockfile and the same sha256 field, so it derives the same path by the same rule.

A runtime directory scan was considered and rejected, because it breaks the standalone-artifact requirement — a packaged binary must run with no source checkout, so its assets must be embedded at compile time.

Scope the reference rule by the presence of a store, not by a marker in the document decision-scope-by-the-store

The rule resolves a document's asset references against stored bytes. A conformance fixture references assets/htmlspec.css and no such file has ever existed beside it: the reference is symbolic, present so the parser and the projection see a realistic document. Applying the rule unconditionally rejects the 5 valid and 2 warning fixtures, which assert acceptance, and those 37 inputs are the pin for every rule the project already has.

So the rule fires only where a project has an asset store. A document with no store around it has no bytes to disagree with.

A reserved fixture class marking a document as exempt was rejected on three counts. It adds a suppression switch inside the document for a rule the specifications classify as non-downgradable, which is the same downgrade spelled as markup. It requires amending a closed vocabulary whose reserved classes each name a semantic unit of a specification rather than a file's role in a test suite. And the conformance requirement would then need a fixture proving the exemption works — a document declaring itself exempt, to prove that documents declaring themselves exempt are skipped — which is circular. It also edits all 37 inputs, so it saves no work over rewriting them.

A field in each fixture's expected.json was rejected as unnecessary once the store's presence already answers the question. It would add a harness concept and edit 37 files to record something derivable.

The specifications state the scope explicitly, including that a document cannot exempt itself, so the marker cannot be reintroduced later as an implementation convenience.

Never collect unreferenced assets decision-never-collect

An archived document must keep rendering, and the only way to be sure its bytes survive is to never delete asset bytes. The store therefore grows monotonically.

The cost is bounded and small. Each vendored file has changed once in the project's history, giving 8 distinct blobs in an 8.8 MB repository. A rule that can delete bytes an archived document needs is more expensive than the disk it saves.

Rewrite references in the formatter, not by hand decision-rewrite-in-the-formatter

Formatting rewrites a document's asset references to the current stored hashes, which makes the migration mechanical and keeps a document canonical.

This interacts with deterministic formatting in two ways, and both hold. Formatting must stay idempotent, so a second pass must be byte-identical — which holds because the rewrite is a pure function of the lockfile and the document. It must also not widen a diff beyond the units an edit touched, so reference rewriting must not reflow surrounding markup.

CAUTION: a formatter that rewrites references to current hashes silently re-points an archived document at newer bytes, which changes what a reviewed artifact renders with. The formatter therefore rewrites a reference only when the referenced bytes are absent from the store, and reports rather than rewrites when the document names bytes that exist. Re-pointing a document is an explicit operation, never a side effect of formatting.

Risks

The formatter silently upgrades an archived document's runtime risk-formatter-upgrades-an-archive

A rewrite that always points at current hashes would change what a reviewed artifact renders with, without anyone asking for it.

The formatter only fills in absent references, and reports a document naming bytes that exist rather than rewriting it. Re-pointing is explicit, and a fixture pins the behavior.

Truncated-hash collision between two store entries risk-truncated-hash-collision

64 bits of digest is fewer than 256, so two distinct byte sequences could in principle land on one stored path.

The store is closed and every entry carries a full digest in the lockfile. The check suite compares full digests and fails on any truncated-form collision.

Nix and Rust derive stored paths by different rules and drift apart risk-nix-and-rust-drift

Two build systems computing one path from one lockfile is two implementations of one rule.

Both read assets/vendor.lock.json and apply one documented derivation, and a check asserts the path Nix builds and the path the Rust build script generates agree for every lockfile entry.

Duplicate detection is a project-level property, so per-document validation cannot see it risk-duplication-is-project-level

A validator reads one document. Duplication is a statement about a whole tree, so no document is individually wrong when a project holds two stores.

The rule lives in the check suite as well as in the validator. Without that, the suite passes while the project violates the contract — which is the failure this change exists to fix.

Re-rendering the archived document alters a reviewed artifact risk-re-rendering-an-artifact

The archived document has been reviewed. Re-rendering it changes a file somebody already accepted.

The change is limited to asset references and the stylesheet the document renders with. Its semantic content is unchanged, which validation confirms by accepting the re-rendered document against the same contract.

The truncated path is not self-verifying to a reader risk-not-self-verifying

A person cannot confirm 64 bits by eye, so a wrong reference looks exactly like a right one.

This is why the rule is machine-checked and classified as a non-downgradable error rather than a warning a reader is expected to notice.

The order, and where rollback stops being free

Six steps, and the fifth is a boundary rather than a stage. Steps 1 and 2 are additive and leave the old layout intact, so a revert before step 5 restores the prior state with no data loss. After step 5 the duplicated copies are gone and recovery is by revert, which is safe because the bytes remain in history — but it is a different kind of recovery, and the diagram marks where that changes.
