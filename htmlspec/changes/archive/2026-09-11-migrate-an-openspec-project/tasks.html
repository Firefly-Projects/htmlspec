    Both directions audited. The conclusion holds — the contract states no layout beneath htmlspec/specs/, so the source's nested path is preserved — but the design's account of the fault is wrong: grep -n 'htmlspec/specs' README.md returns nothing.     The citation was true once: at cf11132^ the function sat at exactly line 1352 and scanned directory names. cf11132 is "Finish the archival, and fix the gate that never fired", and the requirement above is the contract it established. The design cites real code from before the fix whose subject was this defect. <date>-<version>-<name> comes from README.md:88, under "Proposed project layout" — non-normative per contract-authority, "The project's obligations are what its accepted specifications state".

    The other two claims hold — ProjectRoot::assets() at project.rs:179 (asserted 157) derives the store from the project root; write_document at commands.rs:577–583 (asserted 574) computes the reference from the document's own directory. So the staging-outside and mirror-the-depth decisions rest correctly.

  • 1.5 Take 2026-08-10-html-spec — five delta files spanning every capability the project then had — and write by hand what its single specification.html should contain.

    This is the hardest mapping in the set and the one with no rule; doing it once by hand before designing anything is what shows whether the constraint is expressible

    evidence/the-collapse-written-by-hand-2026-09-07.md. 47 requirements and 138 scenarios into one document, all five deltas ## ADDED. The constraint is expressible, but it is not the one the design states, and the hand-write produced six findings.

    Arrangement is the easy part. Grouping by capability is forced — 47 requirements flat is unreadable and the capability boundary is the only structure the source expresses. The design's "no rule to write here" is right about arrangement and wrong about what needs one.

    The hard part is the five ## Purpose paragraphs, which are not requirements and have nowhere to go: one document has one masthead and five statements cannot sit in it. They are also the current definitions of five of the project's nine capabilities. Taken: each becomes the paragraph introducing its capability's group. A rule written about requirement units alone would drop all five silently, so section 2 must state that non-requirement delta content is accounted for.

    A collapse can collide identifiers within one change — deterministic-formatting's "Formatting can be checked without writing" against toolchain-packaging's "Formatting can check without writing", both surviving in the accepted specifications today. Resolution is to slug the full heading, not to suffix and not to stop; an aggressively truncating rule manufactures the collision.

    The derivation table is keyed on (change, source heading), not heading alone. req-a-single-command-exposes-validate-format-and-init is renamed twice by later changes, so one continuous obligation legitimately holds four identifiers across the migrated project — each archived specification states its own change's contract, per artifact-kinds:193.

    Verification units are omitted with the reason recorded — the source format has no such unit, and manufacturing 47 from a tasks document invents a record. Evidence units are carried, since the 8 evidence files are real sources.

    The masthead summary is written rather than carried, the one text in the collapse existing nowhere in the source, needed because artifact-kinds' "The contract read without the change" scenario requires the specification to stand alone.

  • 1.7 Confirm no existing capability governs migration.

    project-bootstrap governs establishing a project, artifact-kinds governs documents that already exist, toolchain-packaging governs the command surface. None reaches a source project in another format, which is why a new capability is right and why nothing currently reports any of this

    evidence/no-capability-reaches-a-source-project-2026-09-07.md. All 97 requirements across 9 capabilities read. None reaches a project in another format. Two bear on migration without governing it: workflow-reporting covers the migrate report the moment the workflow exists (task 7.7 is written under it), and contract-authority governs how the migration decides under silence. So a new capability is right.

    The search independently confirmed the version fault from a second capability: toolchain-packaging — "An archived change is named for its date and refuses to collide" (spec.md:403) — states archival names the directory "for the date of archival followed by the change's name", with no version component. <date>-<version>-<name> contradicts a stated requirement, not just the gate's implementation.

    It also found a constraint no artifact mentions: "An archived change records the version it shipped in" (spec.md:310) requires recorded versions to be distinct, with a baseline for changes archived under one version before the obligation existed. Seven changes record 0.1.0. A migrated project inherits that collision, so the migration must carry the changelog's baseline entry or the migrated project fails scripts/check-release on arrival.

2. The contract states the operation, once

  • 2.1 Add a project-migration capability at openspec/specs/project-migration/spec.md

  • 2.2 State the survey requirement: mechanical enumeration, writes nothing, repeatable, available as a structured payload, and does not interpret what it finds

  • 2.3 State the stage order, with the obligation that the first four stages produce no document in the destination format and that migration stops and reports its plan before staging

  • 2.4 State the reading stage's obligation to record what each document does in the project rather than what it says.

    Without this the stage is indistinguishable from opening the files, and an agent that skipped it produces a plan whose per-entity lines say nothing

  • 2.5 State the evidence stage before document production, with the reason: nothing in a source document points at its change's evidence, so a bulk conversion loses it first

  • 2.6 State the plan requirement: every surveyed entity, a destination and a disposition each, a reason for anything folded or dropped, and an empty source field distinguishable from dropped content

  • 2.7 State that the plan is a tasks document and that no artifact kind is added.

    The closed set of four is a contract artifact-kinds already states, and a working record used once per project is not grounds to reopen it

  • 2.8 State the coverage gate: promotion refuses while an entity has no disposition, names what is unaccounted, and does not judge whether a disposition is correct

  • 2.9 State the staging requirements: outside the destination, a complete resolvable project, internal paths matching the destination so promotion is a move, and the destination unchanged if migration stops before promotion

  • 2.10 State that migration conforms to a layout the destination's contract states and preserves the source's where none is stated, that a nested capability path survives, and that a README example is not a stated layout.

    This is the requirement the flat-file mapping fault produced, and it generalizes: a migration decides a hundred files at once, so an invented convention arrives with a hundred instances and no requirement behind it

  • 2.11 State that the checks run last over the complete staged project and that migration does not halt at the first failure, with the systematic-fault reason.

    Also state that drafting checks remain permitted, so the rule reads as an obligation about where migration ends rather than a prohibition on validating

  • 2.12 State that conversion of meaning is agent-driven and that no converter exists, deriving it from the reason artifact-kinds already gives rather than asserting it fresh

  • 2.13 State that evidence crosses unchanged and is referenced from the documents that cite it

  • 2.14 State the delta collapse, that change state moves onto the requirement, that the arrangement is the agent's, and that the implemented result wins where it disagrees with what a delta stated

  • 2.15 State that identifiers are derived once, recorded in the plan, and that a collision is reported rather than suffixed

  • 2.16 State that migrated archives carry their versions where the gate reads them — the recorded-version file, not the archive directory name, per project-bootstrap "Archival requires the project version to advance" (spec.md:57) — that the declared version equals the greatest migrated version, and that a source change with no version does not get one invented.

    State that a shared version across several source changes is carried honestly with the project's release record explaining it, rather than resolved by inventing distinct versions, per toolchain-packaging "An archived change records the version it shipped in" (spec.md:310)

  • 2.19 State that a source entity the destination's contract has no state for is recorded as an open question naming the change that would settle it, rather than mapped to the nearest available state.

    ## RENAMED Requirements is the case: changeState has no renamed, and a rename states that one requirement is another under a new heading — the identity link the derivation table is keyed on. This is contract-authority "Silence is recorded and not filled" third route, and the requirement generalizes past this instance

  • 2.20 State that a delta's non-requirement content is accounted for too.

    Each of 2026-08-10-html-spec's five deltas carries a ## Purpose paragraph, and a rule written about requirement units alone drops all five silently — which task 1.5 found by writing the collapse by hand

  • 2.21 State that a source entity already in the destination format is not assumed usable.

    The 4 documents/*.html declare contract version 0.1.0 and reference an asset store that no longer exists, so "already converted" is not "ready to carry"

  • 2.17 State that the source survives and that generated agent instructions are not migrated

  • 2.18 Run openspec validate --all

    Totals: 10 passed, 0 failed. The project-migration delta carries 15 requirements and 61 scenarios and reports zero issues at any level. The 50 INFO notices in the run are pre-existing requirement-length hints on other capabilities, none of them on this change.

3. The survey, which is the only reading the program does

  • 3.1 Add htmlspec migrate survey <path>, enumerating capabilities, changes, change documents, delta specifications, evidence files, recorded versions, and configuration — and the four entity kinds the design's original table had no row for: documents/*.html, per-change .openspec.yaml, delta section headings including ## RENAMED Requirements, and evidence nested below evidence/.

    A survey built from the six original rows reports full coverage over a set that omits 15 files, which makes the gate in 4.2 vacuous for them. Recurse into evidence/ rather than globbing it, and read config.yaml's field set from the file rather than from a fixed list of names

    crates/htmlspec-cli/src/migrate.rs, wired as htmlspec migrate survey [path]. Kind has nine variants: the five the design anticipated, the four task 1.2's audit found (converted-document, change-configuration, nested evidence, delta-section recording), and unrecognized so a kind nobody anticipated still reaches the plan. Descends directories rather than matching names, and reads config.yaml's live keys rather than a fixed list.

    Migration note: a review after archival found that the survey did not descend the whole project. It named openspec/config.yaml, walked specs/, and walked each change directory, so a file loose in openspec/, openspec/changes/, or openspec/changes/archive/ was not enumerated. It was fixed before the change merged, and evidence/five-more-defects-a-review-found-2026-09-13.md records the defect, its reproduction, and the fix, as its first finding.

  • 3.2 Emit the enumeration under --json as the payload the coverage gate consumes.

    The gate must check the plan against the list the plan was written from, not against a second enumeration taken later

    Payload keys: root, counts, greatestVersion, sharedVersions, configuration, changes, entities. Entity paths are relative to the repository root, so two surveys of one project run from different directories produce identical payloads — a gate comparing a plan against a payload must not depend on where the migration ran.

  • 3.3 Report a path that is not an OpenSpec project as such, naming what was expected, and exit with the status for an operation that could not run

    Names the path, names what was expected (openspec/specs or openspec/changes), exits 2 per exit.rs's reservation for an operation that could not run. A project with capabilities and no changes is still a project — requiring both would refuse a young project for being young.

  • 3.4 Survey this repository and assert the counts from task 1.1 exactly — the measured ones in evidence/the-source-inventory-2026-09-07.md, not the stale ones 1.1 was written with: 193 files under openspec/, of which 161 markdown; 9 capabilities, 97 requirements, 401 scenarios; 16 archived changes, 28 delta specification files, 75 evidence files, 16 VERSION files, 8 .openspec.yaml, 4 documents/*.html, 1 config.yaml.

    A survey that finds 160 markdown files is a survey with a bug, and the number is known. Assert the breakdown as well as the total, so a survey that miscounts two categories in opposite directions fails

    Not asserted as literals, deliberately. The survey finds 198 entities, five more than task 1.1's 193 — the five evidence files this change wrote in the same session. That is the third stale count in this change, so a test carrying 198 would be the same defect one layer down. Instead the_survey_enumerates_every_file_the_project_holds compares the entity list against an independently-implemented walk, file for file and in order; every_file_in_this_repository_classifies asserts zero unrecognized and all eight kinds present; the_counts_account_for_every_entity asserts the per-kind counts sum to the total. Every kind also matches find exactly. Recorded in evidence/the-survey-against-this-repository-2026-09-07.md.

  • 3.5 Assert the survey writes nothing: run it against a copy, compare the tree before and after

    Asserted twice — against a constructed source and against this repository — both comparing the file list before and after, which is what catches a survey writing a cache or lock file.

  • 3.6 Assert repeatability: two runs against an unchanged source enumerate the same entities in the same order.

    Order matters because the payload is diffed by a person when a coverage failure is being read

    the_survey_is_repeatable_in_the_same_order compares two surveys and their payloads, then asserts the entity order is the sorted one.

  • 3.7 Survey a project with a change that has no VERSION file and confirm the absence is reported as absent rather than defaulted

    a_change_recording_no_version_reports_none asserts version: None and that the payload carries the field as null rather than omitting it, so a reader cannot mistake "recorded none" for "did not look". This repository supplies a real case: migrate-an-openspec-project has no VERSION, and the survey names it rather than defaulting it.

4. The plan, and the gate that checks it covers the survey

  • 4.1 Settle the plan's shape as a tasks document: one task unit per surveyed entity, carrying the source path, the destination path, the disposition, and the reason where one is owed

    Each fact is a note paragraph opening with its name and a colon — source:, destination:, disposition:, reason:, derives:. Not attributes, and the reason matters: the projection ignores an unknown data-* on a unit, so a gate reading data-source would parse the HTML a second way and could disagree with the model about what the document says. data-field="source" names no field of a task and is invalid. A note whose opening word is none of the five is ordinary prose, so annotating a plan line breaks nothing.

    reason: is read from the note or from the task's own data-field="reason", because a task whose data-state is dropped already carries one and the validator already requires it. Refusing one spelling would make the plan's shape depend on which of two equivalent markups an agent chose.

    Proven end to end rather than asserted: crates/htmlspec-cli/tests/plan.rs builds the plan with htmlspec init and htmlspec new document tasks, replaces the template's example units, and puts one document through validate, format, format --check, and migrate promote in turn. The format --check after the format is the load-bearing step — it proves the shape is a fixed point rather than something that parsed once, which a shape leaning on attributes would not be.

  • 4.2 Add htmlspec migrate promote, whose first act is the coverage comparison between the plan and the survey payload

    htmlspec migrate promote <plan> --survey <payload.json>. The comparison runs before anything is read from a staging tree, so a plan missing an entity kind is reported without touching it. Exit 1 for an incomplete plan — the plan is a document that failed a check, and the operation ran — and 2 for a plan or payload that could not be read, which says nothing about the source.

    The payload is read from a file rather than re-surveyed. project-migration requires the plan to be checked against "the list the plan was written from", and re-enumerating would compare it against a second opinion taken later.

  • 4.3 Refuse with every unaccounted entity named.

    Naming the first one turns a systematic omission into a sequence of individual repairs, which is the same fault the check-last rule exists to prevent

    Eight classes reported together, each in full: unaccounted, sourceless, no disposition, unknown disposition (with the word written), folded-or-dropped with no reason, one entity named twice, a source the survey never found, and identifier collisions. Checked by mutation: restricting unaccounted to the first entity failed every_unaccounted_entity_is_named and promotion_refuses_and_names_every_unaccounted_entity at both layers.

  • 4.4 Accept a disposition of dropped-with-a-reason as covered.

    Being accounted for is what the gate tests; being converted is not

    a_deliberate_drop_with_a_reason_is_covered, plus a_drop_with_no_reason_is_reported for the other side: without the reason the plan records that something is gone rather than what the decision was.

  • 4.5 Assert the gate does not judge a disposition: a plan sending a specification to the wrong destination passes coverage, because whether a disposition is right is what a contributor reviews the plan for

    a_disposition_a_reader_would_disagree_with_passes sends an accepted capability specification into a change's evidence directory — plainly wrong, plainly not this check's business — and asserts the coverage is complete. The passing report says so in words (the check says nothing about it), because a green coverage check otherwise reads as approval of the plan.

  • 4.6 Assert the gate fails when one entity is removed from a complete plan, so its subject is proven rather than assumed

    removing_one_entity_from_a_complete_plan_fails_the_check asserts the complete plan passes first, then removes one item. a_plan_missing_one_entity_refuses_with_the_violation_code does the same through the real binary, and asserts the shortened plan still validates — the omission is not a document defect, which is precisely why this is a gate rather than a validation rule.

  • 4.7 Record the identifier derivation table in the plan, keyed on (change, source heading) rather than on the heading alone, and check it for collisions before anything is staged.

    A collision found at staging time has already produced documents that reference an identifier belonging to something else. Derive from the full heading: task 1.5 found that deterministic-formatting's "Formatting can be checked without writing" and toolchain-packaging's "Formatting can check without writing" are distinct obligations a truncating rule would merge, manufacturing the collision the report-rather-than-suffix rule then fires on

    Each derives: line sits on the plan item for the file that stated the heading, so the keying holds by construction — a derivation cannot be recorded without its source. The collision check groups by the item's destination:, because a collision is two headings deriving one identifier within one destination document.

    two_headings_deriving_one_identifier_in_one_document_collide reports rather than suffixes, and the report names both headings with their sources.

    Migration note: a review after archival found two gaps in this check, both fixed before the change merged. A derives: note whose separator was not spelled exactly -> between spaces was silently ignored, so a plan misspelling it recorded no derivation and reported no collision; and a plan item with no destination: note had every one of its derives: lines left out of collision checking. evidence/five-more-defects-a-review-found-2026-09-13.md records both, as its fourth and fifth findings.

  • 4.8 Assert that one obligation renamed across changes holds a different identifier in each change's specification, and that this is not reported as a collision.

    req-a-single-command-exposes-validate-format-and-init is renamed twice, so it holds four identifiers across the migrated project — three archived, one accepted — and each is correct because artifact-kinds "A specification states the settled contract as built" requires each archived specification to state its own change's contract

    one_obligation_renamed_across_changes_is_not_a_collision pins the rename. But that test could not catch the fault it was written for, and a mutation proved it: keying the derivation table on the identifier alone, with the destination discarded, left the whole suite green. A rename produces distinct identifiers, so a wrong key still finds no duplicate among them.

    The case that needs the destination is the ordinary one, not the edge one: 17 headings in this repository are stated by more than one archived change, because a change that modifies an obligation restates its heading. Five changes each state "Bootstrapping installs agent instructions for the tools a project uses", so one slug lands in five archived specifications. An identifier-keyed table reports five collisions and sends a contributor to reconcile a conflict the source never contained. one_heading_stated_by_several_changes_is_not_a_collision uses those five real changes and fails under the mutation.

    a_repeated_derivation_line_is_not_a_collision covers the third case: one line written twice states one derivation.

5. Staging and promotion

  • 5.1 Establish the staging location outside the destination, and confirm the destination never holds a second asset store during the operation

    crates/htmlspec-cli/src/staging.rs. Staged::resolve(staged, destination) refuses when the staging root lies within the destination, and the report says why rather than only that: a staging tree beneath the destination puts a second store in a project that holds one, so htmlspec assets fires on the migration's own working directory and a contributor cannot tell that report from a real defect.

    Also refuses a staged tree holding two stores of its own, since promoting one would move that defect into the destination.

  • 5.2 Make the staged tree a complete project — declaration, specifications, changes, archive, one asset store — and confirm ProjectRoot::resolve resolves it, since every check depends on that

    Five paths checked, every absence named together. the_staged_tree_resolves_as_a_project asserts ProjectRoot::resolve returns the staging root itself rather than an enclosing project — the distinction matters, because resolution ascends and a staging directory inside some other project would otherwise "resolve" to the wrong thing.

  • 5.3 Stage every document at the relative path it will occupy after promotion, and assert that asset references resolve unchanged across the move.

    htmlspec/specs/x.html references ../assets/ and htmlspec/changes/y/proposal.html references ../../assets/; a staged tree at the wrong depth needs every reference rewritten after the checks that would have caught the rewriting

    asset_references_resolve_unchanged_across_the_move stages four documents at four depths (../assets, ../../assets, ../../../assets) and asserts each reference reaches the store before and after the move, with identical text. The test resolves .. by popping rather than by Path::components(), which keeps .. — a comparison leaving .. in both sides would hold for any depth at all and prove nothing.

    a_complete_migration_promotes_and_the_result_is_a_project closes it from the other end: the promoted project passes validate, assets, and format --check from its new location, which is only true if no reference needed rewriting.

  • 5.4 Carry each archived change's VERSION file across unchanged, and name the archived directory <date>-<name> from the source directory name.

    This task previously said to compose <date>-<version>-<name>, and two accepted requirements forbid it — project-bootstrap "Archival requires the project version to advance" (spec.md:57, the version "SHALL NOT be derived from an archive directory's name") and toolchain-packaging "An archived change is named for its date and refuses to collide" (spec.md:403, date then name, no version component). Assert the migrated directory names carry no version component, and that last_archived_version reads 0.10.0 from the carried files

    Fault::VersionInAnArchiveName refuses a composed name, and the report names both halves of the fault — a contributor who fixed only the naming would still have a version the gate does not read. a_date_and_name_archive_is_accepted pins the boundary in both directions, including 2026-08-10-2-more-fixes, where the component after the date is a single number and part of the name rather than a version.

    The 0.10.0 figure is not asserted as a literal, for the reason task 3.4 records. the_migrated_projects_version_gate_refuses_without_an_advance proves the property instead: it promotes a project carrying 0.1.0, creates a change, and asserts htmlspec archive --check refuses naming the carried version — which is only possible if the gate read the file the migration carried.

  • 5.5 Set the declaration's version to the greatest version found among the migrated archives — 0.10.0 for this repository — and confirm htmlspec archive then refuses without an advance.

    A migrated project whose next archival passes without advancing has lost its history's ordering

    Fault::DeclarationDisagrees refuses a declaration below the greatest recorded version, and a_declaration_below_the_greatest_archived_version_is_refused uses 0.9.0 against 0.10.0 — the pair a migration comparing version text would get backwards, which the survey's greatest_version already guards from the other side.

    A staged project with no archived change declares freely. Requiring the declaration to equal an absent value would refuse a young source project for being young.

  • 5.9 Carry the changelog and its baseline entry, and confirm scripts/check-release passes against the migrated project.

    Seven archived changes record 0.1.0, and toolchain-packaging "An archived change records the version it shipped in" (spec.md:310) requires recorded versions to be distinct with a changelog baseline naming the changes that shipped together. A migrated project whose changelog lost that entry fails its own release check on arrival, with a diagnostic naming seven changes and explaining none of them. Neither the design nor these tasks mentioned this before task 1.7 found it

    The obligation is enforced: CHANGELOG.md is one of the three entries promotion places, and Fault::UnexplainedSharedVersion refuses a shared version the release record does not name. a_shared_version_with_no_release_record_entry_is_refused uses this repository's real shape (three changes at 0.1.0, one at 0.2.0, a record naming only 0.2.0) and asserts every change is named — the repair is one entry covering all of them, and a contributor told only the first has to find the rest. a_shared_version_the_release_record_explains_is_carried pins the other half, which is the half that matters: inventing distinct versions would record releases nobody installed.
