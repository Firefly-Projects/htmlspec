Content-address runtime assets

This change made the project store each runtime asset once, at a location derived from the hash of its bytes, and have each document reference its assets by that hash, so that identical bytes occupy one location and differing bytes coexist (Documents share one pinned runtime), with initialization writing such references and no second copy (A project can be initialized with a conforming document). It made asset topology a checked property: a document's asset reference must resolve to stored bytes whose hash is the one it names (An asset reference must match the bytes it names), a project must not store one asset's bytes at more than one location (A project must not store one asset's bytes more than once), and the project's check suite evaluates both rules (Asset rules are checked as part of the project's check suite).

document-template

Documents share one pinned runtime req-documents-share-one-pinned-runtime

Diagram, chart, and equation support SHALL come from a fixed set of approved libraries at versions pinned by the project. The runtime SHALL be shared across documents in a project rather than duplicated into each file. Arbitrary generated scripts SHALL NOT be embedded in a document.

Each runtime asset SHALL be stored at a location derived from the hash of its bytes. Identical bytes SHALL therefore occupy exactly one location in a project, and bytes that differ SHALL occupy distinct locations rather than overwriting one another. A document SHALL reference each asset by the hash it was authored against, so the bytes a document renders with cannot change without changing the document.

An asset location SHALL NOT be rewritten in place. Replacing a library SHALL add a location and leave existing locations intact, so a document authored earlier continues to render as authored.

document-validation

An asset reference must match the bytes it names req-an-asset-reference-must-match-the-bytes-it-names

Validation SHALL reject a document whose asset reference does not resolve to stored bytes whose hash equals the hash named by that reference. A reference naming bytes the project does not store SHALL be reported as unresolved. A reference resolving to bytes whose hash differs from the name SHALL be reported as a mismatch, and the two SHALL be distinguishable diagnostics because they have different causes.

This rule SHALL apply only to a document validated within a project that has an asset store. A document validated outside such a project SHALL NOT have its asset references resolved, and SHALL NOT be rejected for naming bytes that no store holds. The rule states a relationship between a document and the bytes beside it, and where there are no bytes there is no relationship to violate.

A document SHALL NOT be able to exempt itself. The scope SHALL be determined by whether a store is present, never by a declaration inside the document, because a rule a document can switch off protects nothing.

This rule SHALL be an error rather than a warning, and SHALL NOT be reducible to a warning. A document that renders against bytes other than the ones it names is misreporting its own provenance.

Migration note: as built, a reference that names no hash, such as assets/htmlspec.css, resolves to NotAddressed, and no asset rule reports it; an_unaddressed_reference_is_not_this_rules_business pins that, as evidence/group-3-decision.md records. The archive's original defect had that shape, and section 8.4 of evidence/group-8-verification.md, under "A coverage boundary this exercise found", records that this rule does not catch it: htmlspec validate exits 0 on it, and htmlspec format --check exits 1. Task 8.4 records the same boundary. The record concludes that the defect therefore fails the suite through the formatter; at 86c33f4, though, the suite's format --check step ran over fixtures/dogfood only. It is still so in htmlspec 0.29.0, run when this document was migrated: a reference naming no hash, in a project with a store, passes validation and fails format --check.

Migration note: as built, the rule reads only the last two components of a reference, its address and its file name, "because a stored asset is an address and a file name however deep the document sits", as the comment on Store::resolve in crates/htmlspec-assets/src/store.rs records at 86c33f4. So a reference at the wrong relative depth, which does not reach the bytes from the document, still resolves. That was deliberate, and it is recorded only in that comment. Commit 86c33f4 records the formatter writing such references into the archived document, each naming the right bytes while the document rendered unstyled, and corrects the formatter. It is still so in htmlspec 0.29.0, run when this document was migrated.

A project must not store one asset's bytes more than once req-a-project-must-not-store-one-asset-s-bytes-more-than-once

Validation SHALL reject a project that stores identical asset bytes at more than one location. The report SHALL name every location holding the duplicated bytes, so a contributor can tell which copy to remove.

Two assets whose bytes differ SHALL NOT be reported as duplicates, however similar their names, versions, or purposes.

This rule takes a project as its subject rather than a document, so it SHALL be evaluated where a project is in view. A directory holding no asset store has nothing to duplicate, and SHALL NOT be reported.

Asset rules are checked as part of the project's check suite req-asset-rules-are-checked-as-part-of-the-project-s-check-suite

The asset reference and duplication rules SHALL be evaluated by the project's single check command, so a contributor and continuous integration verify the same asset topology. A project whose documents validate individually but whose asset topology violates these rules SHALL fail the check suite.
