Project bootstrap CLI

This change made a project, rather than one document, the subject of the bootstrap subcommand: a declared root holding one asset store, found from any directory beneath it, whose declared version archival requires to advance (A project has a declared root holding one asset store, Commands resolve the project from any directory beneath it, A project declares its name, version, and expected toolchain, Archival requires the project version to advance). Bootstrapping installs agent instructions for the tools selected, interactively or by argument, repeatably, inside a marked region of a shared file, and ends by naming the command to run next (Bootstrapping installs agent instructions for the tools a project uses, Tool selection is offered interactively and available without a terminal, Bootstrapping is repeatable without loss, Instructions installed in a shared file are confined to a marked region, Bootstrapping ends by naming the command to run next). Creating documents and changes became a subcommand of its own, a declined or interrupted operation exits with a status of its own, structured output suppresses prompts, and an ascending asset reference with no store above it is reported (A single command exposes validate, format, bootstrap, and create, A declined or interrupted operation is distinguishable from a failure, Exit codes distinguish outcomes, Output is available in human and machine forms, An asset reference must match the bytes it names).

project-bootstrap

A project has a declared root holding one asset store req-a-project-has-a-declared-root-holding-one-asset-store

An HTMLSpec project SHALL be identified by a directory containing an htmlspec/ directory. That directory SHALL hold the project's accepted specifications, its active changes, and its archive, each in its own place.

A project SHALL hold exactly one asset store, in its root, and every document in the project SHALL reference that store rather than a store of its own. A project storing one copy of its runtime is the whole point of the duplicate-detection rule the contract already states; a tool that gave each change its own copy would be reporting a defect it created itself.

A project declares its name, version, and expected toolchain req-a-project-declares-its-name-version-and-expected-toolchain

The bootstrap operation SHALL write a project declaration at the project root recording the project's name, its version, and a pinned reference to the program the project expects.

The declaration SHALL be expressed in the same language the project's build already uses, so that the pinned program reference is a build input rather than a value a bespoke parser must interpret. A second configuration language for three fields is surface the project does not need.

At least one command SHALL depend on the declaration. A declaration no command reads states nothing that can be wrong, so nothing reports it when it is, and it drifts from the project it describes without any signal.

The declaration SHALL NOT carry authoring rules or project context. Those have no consumer, and a field nothing reads is the case the preceding paragraph excludes.

Archival requires the project version to advance req-archival-requires-the-project-version-to-advance

Archival SHALL compare the project's declared version against the last archived version, and SHALL refuse unless the declared version is ordered after it. The accepted contract SHALL therefore carry a version history rather than a sequence of undated merges.

The comparison SHALL be an ordering rather than a test for difference. A declared version ordered before the last archived one SHALL be refused, and SHALL be reported distinctly from a version that has not moved, because the two have different causes: one is work not yet done, and the other is a version that went backwards.

The declared version SHALL therefore be a value the program can order. A version it cannot parse into an ordering SHALL be reported rather than accepted, because a gate that cannot compare its inputs is not a gate.

The bootstrap operation SHALL write an initial version that is ordered before every version a project can later declare, so that a project always has a version on record and the comparison is total. Archival SHALL NOT treat an absent previous version as grounds to pass. A project's first archival SHALL advance past the initial version exactly as a later one advances past its predecessor, because a rule with an exception that applies once per project is a rule exercised once per project.

Archival SHALL NOT modify the declaration. Advancing the version SHALL be the contributor's or the agent's act, and the program's part SHALL be the comparison alone.

That division is the one archival already uses: an agent produces the change's specification and the program validates it, because the judgment is judgment and the checking is exact. Deciding what a version increment signifies, and by how much, is judgment. Whether one version is ordered after another is not. A command whose stated job is checking SHALL NOT write to the project it checks.

Migration note: as built, archival took the last archived version from the archive directory's name, where task 9.1 placed it, and no archived change's directory name carries a version, this change's own included, so the gate compared every declared version against 0.0.0 (last_archived_version and archived_version in crates/htmlspec-cli/src/commands.rs at d88ca93). 2026-08-30-finish-the-archival fixed this defect: there the last archived version is read from the version each archived change records.

Commands resolve the project from any directory beneath it req-commands-resolve-the-project-from-any-directory-beneath-it

Every command whose subject is a project SHALL locate the project by searching the current directory and its ancestors, and SHALL operate on the project found rather than on the directory it was invoked in.

The search SHALL NOT ascend past the enclosing repository. A command run inside one repository SHALL NOT resolve to a project outside it, because writing into a neighboring project is worse than reporting that no project was found.

A command that requires a project and finds none SHALL say so, SHALL name the operation that would create one, and SHALL exit with the status for an operation that could not run.

Bootstrapping installs agent instructions for the tools a project uses req-bootstrapping-installs-agent-instructions-for-the-tools-a-project-uses

The bootstrap operation SHALL install, for each selected AI coding tool, the instructions that tool needs to drive the HTMLSpec workflow. Where a tool supports invocable commands, the operation SHALL install those as well as the instructions.

The set of supported tools SHALL be data rather than logic, so that supporting an additional tool is an entry in that set.

How a tool receives instructions SHALL be a property of the tool with one value per tool, rather than a combination of independent settings. A tool for which no instructions could be written is a state the program SHALL NOT be able to reach.

Instructions SHALL record the version of the program that generated them, so an installation predating the instructions it should carry is identifiable.

Tool selection is offered interactively and available without a terminal req-tool-selection-is-offered-interactively-and-available-without-a-terminal

The bootstrap operation SHALL detect which supported tools a project already shows evidence of, and SHALL offer the supported tools for selection with the detected ones already chosen.

Where nothing is detected, the operation SHALL offer every supported tool already chosen. An absent detection means a project nobody has configured, which is where a default matters most and where detection has least to say. A prompt that offers nothing there teaches that the prompt is decorative.

The operation SHALL accept the selection as an argument instead, including forms meaning every supported tool and no tool at all. When a selection is given as an argument, the operation SHALL NOT prompt, because the question has already been answered.

An interactive selection of no tools SHALL be refused, and the operation SHALL ask again rather than proceed. The refusal SHALL name the argument that means no tool, so that a contributor who intends it has somewhere to go.

The argument form SHALL continue to succeed. The asymmetry is the requirement: the argument is an answer to the question, and an empty confirmation at a prompt is usually a contributor who did not read the question. The prompt appears on a first run in a fresh repository, which is where fewest contributors know what the list decides. A bootstrap that installs nothing while reporting that the project is ready has answered a question nobody asked.

The operation SHALL NOT prompt when it is not running against a terminal, and SHALL NOT prompt when structured output is requested. In either case it SHALL proceed using the detected tools. A bootstrap that blocked waiting for a keypress inside an automated job would never complete.

Detection SHALL recognize a tool by any of several paths, so that a tool which has renamed its directory is still recognized by its former one.

Bootstrapping is repeatable without loss req-bootstrapping-is-repeatable-without-loss

The bootstrap operation SHALL be safe to run on a project it has already established. On such a run it SHALL refresh the instructions for the selected tools, and SHALL leave the project's accepted specifications, active changes, and archive unchanged.

The operation SHALL NOT overwrite a project's configuration once it exists. The operation SHALL NOT delete a file it did not write.

Where the asset store is already present, the operation SHALL verify it against the pinned runtime and report a discrepancy rather than silently replacing it. Bytes that differ from the pin are a fact the contributor needs, and overwriting them would hide it.

A single command exposes validate, format, bootstrap, and create req-a-single-command-exposes-validate-format-and-init

A single command exposes validate, format, and init

The requirement's subject changed rather than its topic. init used to create one document, and its subject is now the project, so a requirement naming init alongside validate and format no longer describes the command surface. The rename is stated rather than implied, because a MODIFIED block cannot find a header that moved.

The project SHALL provide one command-line program offering, at minimum, a subcommand to validate documents, a subcommand to format documents, and a subcommand to initialize a new document or projecta subcommand to bootstrap a project, and a subcommand to create documents. Each subcommand SHALL be usable without configuration in a conforming project.

The bootstrap subcommand's subject SHALL be a project and it SHALL require no arguments, because the operation a contributor needs first is the one that establishes the project they are standing in. The creation subcommand's subject SHALL be a document or a change.

These SHALL be distinct subcommands. One subcommand meaning both "establish this project" and "write this file" would leave a contributor unable to ask for either without also specifying which they meant.

InitializationCreation SHALL take the artifact kind of the document to create, and SHALL produce a document already shaped for that kind. A proposal SHALL be initialized as a page of prose with no unit scaffolding at all, and a specification SHALL be initialized with the units its kind expects.

The asymmetry is the requirement. A proposal that arrived full of empty requirement scaffolding would push its author toward stating a contract at the stage meant for arguing about one, and the emptiest possible starting point is the correct one for a document whose structure is the author's to choose.

InitializationCreation SHALL be able to create a whole change — the directory and its documents — rather than one document at a time, because a change is a directory of kinded documents. A change created in a project SHALL be placed where that project keeps its active changes, and the resolved location SHALL be reported.

Documents SHALL be created referencing the project's asset store rather than establishing one of their own.

document-validation

An asset reference must match the bytes it names req-an-asset-reference-must-match-the-bytes-it-names

Validation SHALL reject a document whose asset reference does not resolve to stored bytes whose hash equals the hash named by that reference. A reference naming bytes the project does not store SHALL be reported as unresolved. A reference resolving to bytes whose hash differs from the name SHALL be reported as a mismatch, and the two SHALL be distinguishable diagnostics because they have different causes.

This rule SHALL apply only to a document validated within a project that has an asset store. A document validated outside such a project SHALL NOT have its asset references resolved, and SHALL NOT be rejected for naming bytes that no store holds. The rule states a relationship between a document and the bytes beside it, and where there are no bytes there is no relationship to violate.

Where a document's asset reference ascends out of the document's own directory, and no asset store is found in any directory above it, validation SHALL report that reference. Such a reference asserts that a store sits above the document, and the absence of one contradicts the reference rather than placing the document outside the rule's scope.

A reference that does not ascend SHALL remain unreported when no store is found. This is what keeps a document whose references are symbolic — a conformance fixture, or a document written to be read rather than rendered — outside the rule, and the distinction is exact: a fixture's references name a store beside the document that has never existed, while an ascending reference names a store the document was generated against.

A document SHALL NOT be able to exempt itself. The scope SHALL be determined by whether a store is present and by the shape of the reference, never by a declaration inside the document, because a rule a document can switch off protects nothing. Reference shape is not such a declaration: it is written by whatever generated the document, and changing it to silence the rule breaks the reference it describes.

This rule SHALL be an error rather than a warning, and SHALL NOT be reducible to a warning. A document that renders against bytes other than the ones it names is misreporting its own provenance.
