Separate a change into four artifact kinds: design

The constraints that decided the approach

Three existing project facts shaped this more than any preference did.

The first is that status was projected, not merely declared. project.rs read <meta name="htmlspec-status"> into the model, and section 9.3 of the projection specification made that mapping normative. So replacing the field was a change to four things at once — the JSON Schema, the normative projection specification, the Rust model, and the projection code — rather than a metadata rename.

The second is that the projection specification is a public artifact in its own right. The archived foundation design settled that the contract is three pieces, not one: the schema for the projected model, a normative HTML-to-model projection specification, and conformance fixtures pinning the mapping. A new metadata field has to appear in all three or the contract is incomplete.

The third is that a test already draws the line between the schema and Rust. rule_code_does_not_restate_schema_expressible_values fails if rule code restates a value the schema could express. The kind vocabulary is a closed enumeration, so it belongs in the schema; the three rules are relational, so they belong in Rust. That line was drawn for us, and drawing it again cost nothing.

The vocabulary lives in the schema and the rules live in Rust

The four kind values are a closed enumeration on a required property, which is what JSON Schema expresses well. Rule code names a kind by a stem and resolves it through the schema at run time, the way the reference rules already read the change-state enumeration.

A Rust constant listing the same four strings would fail the existing schema-Rust split test, and correctly: two copies of an enumeration drift the moment one moves. The three enforced rules are relational — a unit's presence against its document's kind, a count of tasks, a requirement against the verifications naming it — and JSON Schema cannot express any of them.

The advisory rule is a review warning rather than a kind warning

An unverified requirement in a specification is reported in the review/* namespace, not in kind/* alongside the two placement and completeness errors.

This is the subtlest decision in the change and it turns on a property of the engine rather than on taxonomy. review/* is the one namespace strict mode refuses to promote. In kind/* the warning would be promotable, so --strict would fail a specification for being in progress — gating the work that produces the verification, which is exactly the phase gate the dependency model exists to avoid. The mutation testing bore this out: making the namespace promotable is invisible under default validation and fails only under --strict.

The kind is required, with no default

An unmigrated document fails with a diagnostic naming the missing declaration.

An optional kind with a default would make every unmigrated document silently become whatever the default is, and the most convenient default is specification — the strictest kind. A document that was a proposal would then acquire the one placement error the vocabulary has, and its author would be told their proposal must not carry tasks. Required and undefaulted means the migration is visible and the diagnostic names the actual problem.

Positive fixtures pin the guarantee about absence

A proposal carrying a requirement unit and a design carrying a task unit are committed as fixtures declaring valid: true with no rules.

"Validation reports nothing about which units a proposal carries" is a claim about absence, and absence is the hardest thing to pin: a rule that quietly stopped firing would pass every test written to assert silence. A positive fixture fails in the other direction. If someone later adds a placement matrix, the fixture declaring a proposal valid while carrying a requirement stops being valid, and the suite says so. A second guard states the boundary from the other side — a test asserting the kind namespace has exactly two rules — because a count is crude and it is the thing that fails when a third rule appears without a decision.

Archival synthesis is an agent's work and the program only checks

An agent produces the change's specification from the completed change. The program validates it and refuses while it reports an error. That is the whole of the program's part.

The upstream kinds have no imposed structure, so there is no grammar to parse. An extractor would have to guess which paragraph of a design states an obligation, and a wrong guess produces a specification that passes every check while misstating the contract — worse than producing nothing, because it looks authoritative. html-spec can hold this division in a way OpenSpec's Markdown sync cannot, because it has a validator: the agent's judgment is unconstrained and its output is not.

What the split of the template cost

One template served four purposes: the document init writes, the base every conformance fixture edits, the project's demonstration of all seven units, and the input to the presentation checks. Those agreed while there was one document shape. The declared kind pulled them apart, because a proposal must arrive with no unit scaffolding and a specification must not carry a task — so no single document can demonstrate all seven units any more.

The resolution was four templates and a union assertion: the vocabulary test still reads the unit list from the schema and now asks which shape demonstrates each unit, requiring the union to cover all seven. The available shortcut was to relax the test to "six of the seven", and it is worse — it turns a schema-derived check into a hardcoded exemption, and an eighth unit type added later would pass unnoticed.

I shipped three templates first and had the change directory write its design from the proposal template. Running it showed that wrong twice in one line of output: the tool announced "created a proposal" for a design, and it had imposed a proposal's headings on the one kind whose structure is explicitly the author's. An almost-empty design template is a different thing from no design template, and it is the honest one.

The reports-nothing guarantee decays silently

A rule added later could quietly begin constraining the upstream kinds, and every test asserting silence would keep passing.

Positive fixtures carrying would-be violations, plus a rule-count test. Both fail when a rule is added rather than passing quietly.

Agent-synthesized specifications vary between runs

Two agents synthesizing the same change can produce differently worded specifications that both validate, so archival is not reproducible in the strict sense.

Accepted deliberately, and bounded by validation plus review at archival. The requirement is idempotence in effect — running twice must not alter the specification's meaning — which is weaker than byte-identity and the strongest property available when the operation is judgment. The alternative is the extractor the specs forbid.

Four kinds prove to be the wrong number

The set is closed, so adding a fifth is a schema change with its own compatibility cost.

The same bet the seven-unit vocabulary made, and worth making again only because the four kinds come from OpenSpec's own working practice rather than from invention. A test asserts the count, so a fifth cannot arrive without a decision.
