Tasks

One task per group rather than per item, because the group is the unit a reader can act on and the fifty-four items live in the change's Markdown task list. Each task below names what the group established and what it cost.

  • Declare the kind in the contract task-declare-the-kind

    Added kind to the JSON Schema as a required, closed, undefaulted enumeration; rewrote section 9.3 of the projection specification to project it; removed status from both. A test asserts the enumeration holds exactly four values, so a fifth cannot arrive without a decision.

  • Project the kind task-project-the-kind

    Replaced the model's status field with kind, pointed the projection at the new meta element, and exposed the vocabulary through the schema-facts reader so rule code names a kind by stem rather than by literal.

  • Add the three rules task-the-three-rules

    Two errors in a new kind/* namespace and one warning in review/*. Seven items for three rules: the extra four are placement and proof rather than logic.

  • Reshape the conformance fixtures task-reshape-the-fixtures

    The generator's base became a task-free specification. Two fixtures needed the task back, not one as the plan said — the second was found by building the base and running the binary rather than by reading. Removing the tasks section also left a navigation link dangling, which the plan did not predict either.

  • Migrate the projection fixtures task-migrate-the-projection-fixtures

    Twenty-three fixtures whose expectation is the projected model, so the field name appears in committed test data rather than in markup. No generator to re-run. One of them existed to pin the clause being deleted and was rewritten rather than substituted.

  • Migrate the remaining documents task-migrate-the-documents

    The template split into four shapes, the two conflated dogfood documents split into four, and twenty-five Rust files carrying an inline metadata literal were substituted. The compiler finds none of those, so a missed one fails at run time — which is why the required-and-undefaulted decision mattered more here than it looked.

  • Pin the rules and the freedom task-pin-the-freedom

    Seven fixtures: one per rule, two positive ones carrying would-be violations to pin the upstream freedom, one proving the contract rules are not relaxed by kind, and one for a document declaring no kind at all.

  • Initialization and the change directory task-init-and-the-change-directory

    Extended init to take a kind, defaulting to proposal — the artifact a change begins with. Added a whole-change-directory mode. A test asserts every kind it can produce validates immediately, under strict mode as well.

  • Archival task-archival

    Wrote the skill an agent follows, and wired the checking half into a subcommand that validates the specification and refuses on an error. Four of the five items were instructions rather than code, and the fifth asserts the absence of a parser.

  • Verify the whole property task-verify-the-property

    Reintroduced each rule's defect and confirmed the suite fails; measured the document population before and after; recorded which rules fire from which units; and authored this change in the project's own format. The last item is the one this document is part of.

  • Land the migration in stages task-migration-in-stages

    Dropped because there is no useful intermediate state. A schema accepting both the old field and the new one during a transition would be a third document shape nobody wants to specify, and a half-migrated tree fails the check suite — so the revert unit is the whole migration commit.

What the vocabulary made awkward

This is the finding task 10.5 exists to produce, and it is worth more than the rest of this document: forty-eight generated fixtures cannot perform this test.

A reference resolves within one document, and a change is now four documents. This is the sharpest cost. Before the separation, a task carried data-refs naming the requirement it served, and the validator resolved it. Split the stages apart and that attribute names an identifier no unit in the tasks document declares — so the reference either dangles or disappears. It disappeared. Every task above says in prose which obligation it served, which carries the information for a reader and none of it for a tool. The dependency rules that mark a dependent for review when its target changes cannot see across the boundary either.

The tasks kind wants a smaller granularity than the vocabulary offers. The Markdown task list for this change has fifty-four items in ten groups. Writing fifty-four task units would have produced a document nobody reads; writing ten produced this one. But a state belongs to an item rather than to a group, and "in progress" above is doing work that four separate states would do better. The unit is individually addressable, as the contract requires — the awkwardness is that the useful granularity for a state and the useful granularity for a reader are not the same.

A design's decisions want to be both prose and units. The design beside this document reasons in prose and marks its decisions and risks as units, and the boundary between the two was a judgment call at every paragraph. The freedom is real and it is genuinely unconstrained. It also means two authors will produce differently shaped designs for the same change, and a reader who wants to find the decisions has to read rather than query. That was the trade the design kind made deliberately, and living inside it for one document is what confirms the trade is real rather than theoretical.

Authoring in HTML is heavier than authoring in Markdown, and not by a little. Every paragraph is a tag pair, every unit is four lines of attributes before any content, and a mistyped identifier prefix is a validation error rather than a typo. The init shapes help, and the validator catches what a Markdown file would have let through. The honest summary is that the format costs more to write and pays that back in what it can check.
