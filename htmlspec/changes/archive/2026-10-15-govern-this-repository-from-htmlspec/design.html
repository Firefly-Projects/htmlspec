Govern this repository from htmlspec: design

How the repository's checks, its release runbook, and its tests move from openspec/ to htmlspec/, where the OpenSpec project goes, what the two empty runbook inventories mean, and why this is release 0.30.1. Each move is preceded by the check that fails without it.

Govern this repository from htmlspec: design

What this settles

evidence/the-measurement-2026-10-14.md lists every reader of openspec/ and the root runbooks/, and what removing openspec/ does to each. Three fail loudly (the release check exits 2, nine survey tests fail, and the self-runbooks stages would name a missing path). Two fail silently: the presentation checks and the asset rules' agreement test skip a place they cannot read and pass. So the order is: make every reader read its new place, and fail when a place it reads is missing, then move. The program's behavior does not change, and no requirement is added, modified, or removed.

Decisions

1. The repository's checks read the project at htmlspec/

scripts/check-release names the project's directory once, PROJECT = Path("htmlspec"), and derives the archive (htmlspec/changes/archive), the adoption marker (htmlspec/runbook-releases.json), and the runbooks (htmlspec/runbooks) from it. The self-runbooks and self-runbooks-format stages of scripts/check run validate and format --check on htmlspec/runbooks.

The program reads the same files through its own project resolution, and this script cannot link the program: its docstring records that it runs where no build has happened. So the path is spelled in the script, once, and the format the two readers share stays tested through fixtures/release/, as it is today.

The stages keep their meaning, the project's runbooks checked as documents. Pointing them at all of htmlspec/ would turn them into a whole-project check, which the proposal leaves out of scope.

Each is checked before the move it depends on. The retargeted release check passes at once, with 38 archives, because htmlspec/ already holds the archive and the marker. The retargeted stages fail until the runbook moves, because htmlspec validate refuses a missing path with exit 2.

2. The release runbook moves byte-identical, with the two revisions it links

runbooks/release/ is moved with git mv to htmlspec/runbooks/release/: specification.html, tasks.html, VERSION (0.1.0), and CHANGELOG.md, unchanged. assets/sha256-e4f5de7cecc4f691/ and assets/sha256-0350261bb5666167/ are copied into htmlspec/assets/. The root assets/ keeps both.

The documents reference ../../assets/, which from htmlspec/runbooks/release/ is htmlspec/assets/, the project's one store, as runbook-authority's "A project keeps its procedures in a fourth place" requires. That store held five of the seven files they link. With the two stylesheets copied in, every reference resolves without editing the documents, so their fingerprints stay those of the last snapshot, and the version stays 0.1.0 under project-bootstrap's "Archival checks the versions of runbooks it publishes": "An unchanged runbook SHALL be allowed to retain its version".

The root assets/ is the toolchain's source copy and assets/vendor.lock.json records both revisions in it, so they are copied, not moved. The self-assets stage compares the stores inside the project with one another and checks each store outside it on its own, so a revision held in both places is not a duplicate it reports. That is checked by running the stage after the copy.

3. The OpenSpec project becomes the migration tests' fixture

openspec/ is moved with git mv to fixtures/migration-source/openspec/. crates/htmlspec-cli/tests/migrate.rs gains fn source(), returning fixtures/migration-source, and every survey and every independent walk reads it. The repository's CHANGELOG.md, scripts/check-release, the schema, and migrate.md are still read from the repository, because the tests cross-check the source against them.

The survey reads an OpenSpec project, and htmlspec/ is not one, so the tests cannot read htmlspec/. The fixture is the project as it stood when it was migrated: the 473 files the plan covers, 36 archived changes, the last recording 0.29.0. Every property the tests assert still holds of it. The greatest version it records has a changelog heading, its shared version is the baseline scripts/check-release keeps, and two of its changes rename a requirement.

The source filter in flake.nix admits a file by its extension wherever it is, and the fixture holds md, yaml, html, txt, py, json, and VERSION, all admitted today. So the filter does not change, and toolchain-packaging's "Project checks are runnable as one command", which requires every file a stage reads to be in the sandbox's snapshot, holds. every_extension_the_project_holds_reaches_the_survey is what would fail if it did not. Only the filter's comment changes, because it says the tests survey openspec/.

The tests' doc comments say "this repository's own OpenSpec project" and are reworded to say the fixture is that project as migrated. The test names keep "this repository", because the fixture is still this repository's project.

4. A test that reads the repository's places fails when one is missing

conformance/tests/presentation.rs reads the change documents from htmlspec/changes/*/evidence/documents/ and htmlspec/changes/archive/*/evidence/documents/, where migration put the four hand-converted documents, byte-identical, and fails when it finds no such directory. The asset rules' agreement test in crates/htmlspec-validate/src/rules/assets.rs reads README.html, assets, fixtures, and htmlspec, and fails when one of them is missing.

Both skipped a place they could not read, which is why removing openspec/ left them passing with less to check. Each assertion is added first, while the test still reads openspec/, and seen to fail with openspec/ moved aside. Then the places are changed.

htmlspec replaces openspec and runbooks in the asset test's list. It holds the runbook after the move, and the project's 172 HTML files, which no form of the test read before. The fixture's seven HTML files are still read, through fixtures.

5. The OpenSpec workflow files are removed

The 52 files the measurement lists, under .claude/skills/openspec-*, .claude/commands/opsx/, .codex/skills/openspec-*, .pi/prompts/opsx-*, and .pi/skills/openspec-*, are removed with git rm.

Each runs the openspec command against openspec/. Once the directory is gone, a workflow asked to start a change would recreate it, and the repository would hold two planning roots again. The files are another tool's installed output, and that tool's installer restores them.

scripts/check-installed compares only the htmlspec-prefixed entries in a shared directory, so its verdict does not depend on these files. It is run after the removal to confirm that.

6. The repository's prose follows the move, and the program's code does not change

Corrected: the comments of scripts/check-release and scripts/check that this change's edits touch, including self-assets's statement that "The root is not a project today"; scripts/check-installed's docstring and two comments, which say this repository keeps its specifications in openspec/; flake.nix's source-filter comment; and the header and doc comments of migrate.rs. Not changed: README.md and AGENTS.md, which name no such directory; the release runbook, by decision 2; archived records and past changelog entries; and the program's source comments that cite evidence by its pre-archive path.

The source comments are in shipped crates, and five of the six were stale before this change, since their changes were archived. Leaving them keeps this change's edits to the crates to test code: the survey tests, the presentation checks, and the test module of crates/htmlspec-validate/src/rules/assets.rs. repoint-the-sources-evidence-citations is the change that settles them.

scripts/check-installed keeps --tools claude,codex,pi and its byproducts. Its reasons change, and its behavior does not: all would install for tools this repository does not use and append the workflow bodies to the hand-authored AGENTS.md, and the htmlspec/ and spec.nix that init writes into the scratch directory are a new project's skeleton, not output to compare with this repository's project.

7. What the two empty runbook inventories mean

The archives for 0.29.1 and 0.30.0 each record {"format": "htmlspec-runbook-inventory/v1", "runbooks": []}. They are true records: at those releases the project held no runbook, because htmlspec/runbooks/ did not exist and the release runbook was outside the project. They stay as written.

project-bootstrap's "The release suite checks published runbook version history" requires each archive after adoption to "explicitly record its runbook inventory, including an empty inventory, so a missing inventory cannot masquerade as old history". These two are that, so the release check reports no missing record for them.

They do not end the release runbook's history. "Archival checks the versions of runbooks it publishes" identifies a runbook by its directory name, orders snapshots by recorded project version, and says "A deleted runbook SHALL not cause deletion of its snapshots". The program finds a runbook's predecessor as the last snapshot with its name across the whole ordered history (predecessor in crates/htmlspec-cli/src/runbook_release.rs), and the release check keeps the last release per name the same way. So when this change is archived, release is compared with 0.29.0's snapshot, its fingerprints match, and it publishes at 0.1.0. The release check then reads one release recorded again, which the same requirement counts as one release, with two archives between that recorded none.

The contract does not say whether a runbook absent from some archives and present again under its name is one lineage or two. It says a rename begins a new one, and the directory name is the identity, so a runbook that returns under its name continues. This change preserves what the program already does, and archival is where it is checked: task 5.2 records what htmlspec archive reports for release.

8. The plan and its review come into evidence, as written

The migration plan is carried byte-identical as evidence/the-plan-for-this-repository-2026-10-13.html (sha256 5dd3770f…). Its review logs come with it: the eleven files of the migration workspace's review/, byte-identical, in evidence/the-plans-review-2026-10-13/.

The plan records how this project arrived, and its decision 4 is what this change carries out. The review logs are the only record of why the archive the project now holds reads as it does: of the plan's 262 verification units the review kept 225, made 16 partial, made 1 passed, and removed 20, and each judgment call a drafter flagged is settled there with its reason. The workspace they live in is outside the repository, and nothing keeps it.

Both are carried as written. The plan's references name assets/ beside it in the workspace, so from evidence/ it opens without its stylesheet, as the earlier plan in 2026-09-11-migrate-an-openspec-project's evidence does. The logs cite briefs, packets, and drafts that are not carried, and one line names a local path. Evidence is not rewritten.

9. Release 0.30.1

A patch increment, from 0.30.0 to 0.30.1. Cargo.toml, Cargo.lock, and CHANGELOG.md are advanced during implementation, as the previous change did, and spec.nix waits for archival. The installed instruction files are regenerated with htmlspec init --tools claude,codex,pi, and only their generatedBy line changes.

Archival refuses a version that has not advanced, and the archive needs a version distinct from 0.30.0's. The contract leaves the size to judgment. Nothing the program does changes, so this is the smallest increment, and the changelog entry says the program is unchanged and what the repository does differently.

The release runbook's step for regenerating the instruction files is not followed past the regeneration. Its removal of htmlspec/ and spec.nix would delete the project. Measured, init in a project leaves both as they are.

Risks

The release runbook tells a run to delete the project

After the move, htmlspec list --runbooks lists release and htmlspec run release can start it, and its step task-regenerate-the-instructions says to remove htmlspec/ and spec.nix. The text was already wrong at runbooks/release/, where htmlspec run, which finds a runbook by name in the project, could not find it. The change bears this, because revising the runbook is a new release of it with its own version, and the plan's decision 4 moves it unchanged.

The proposal's scope and the 0.30.1 changelog entry say the step must not be followed. Version control restores a deleted htmlspec/. The next change, release-a-repository-that-is-its-own-project, revises the runbook. Nothing stops a run in between.

A frozen source cannot exercise a shape it does not hold

The fixture no longer grows. A survey defect that shows only on a shape this project never had passes these tests. The change bears this: the tests check properties of a real project, and a shape the source never held is exercised by the constructed projects the survey's other tests build.

A contributor still uses the OpenSpec workflows

Anyone who starts a change with /opsx:new or openspec-new-change in this repository finds it gone. The change bears this, because the project those workflows act on is gone, and OpenSpec's installer restores them.

The carried plan opens without its stylesheet

A reader opening the plan from evidence/ gets unstyled HTML, and its diagrams do not render. The change bears this, because evidence is carried as written. The text and the units are complete, and the revisions it names are the ones in htmlspec/assets/.
