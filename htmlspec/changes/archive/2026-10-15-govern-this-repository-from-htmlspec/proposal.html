Govern this repository from htmlspec

Promotion put this repository's project in htmlspec/ and left the OpenSpec project in openspec/, and the repository's own checks still read the old one. This change points them at htmlspec/, moves the release runbook into the project, and removes openspec/ and the OpenSpec workflows, so the repository is governed from one place. The program does not change.

Govern this repository from htmlspec

Why

Pull request #55 promoted the migrated project into htmlspec/ and left openspec/ and runbooks/ where they were, as project-migration's "The source project survives migration" requires. Two changes have been archived since, with htmlspec archive, into htmlspec/ only. So the repository holds its project twice, and its checks read the copy nothing writes any more. evidence/the-measurement-2026-10-14.md measured it:

  • scripts/check-release reads openspec/changes/archive/ and openspec/runbook-releases.json. It checks 36 archived changes, and the project has 38. The two releases archived with htmlspec archive, 0.29.1 and 0.30.0, are checked by nothing in the suite.
  • The self-runbooks stages check runbooks/, outside the project. htmlspec/runbooks/ does not exist, so htmlspec list --runbooks reports none, the project has no place for its procedures as runbook-authority's "A project keeps its procedures in a fourth place" requires, and the release runbook's documents reference the repository's root assets/ rather than "the project's one asset store". Both archivals since promotion recorded an empty runbook inventory.
  • Three tests read openspec/. With it moved aside, 9 of the 11 migration survey tests fail, and the presentation checks and the asset rules' formatter agreement test still pass while reading 4 and 7 fewer documents. Neither of those two reads htmlspec/ at all.
  • 52 OpenSpec workflow files under .claude/, .codex/, and .pi/ direct an agent to run the openspec command against openspec/.

The migration plan's decision 4 named this change, and the plan is its evidence: evidence/the-plan-for-this-repository-2026-10-13.html.

What working looks like

  1. scripts/check-release reports 38 archived changes, every archive under htmlspec/changes/archive/, and reads the adoption marker at htmlspec/runbook-releases.json.
  2. htmlspec list --runbooks lists release. Its four files are at htmlspec/runbooks/release/, byte for byte what runbooks/release/ holds at 4fa4e96, at version 0.1.0, and its two documents open with their stylesheets from htmlspec/assets/.
  3. The self-runbooks stages validate and format-check htmlspec/runbooks.
  4. The repository root holds no openspec/ and no runbooks/, and .claude/, .codex/, and .pi/ hold no OpenSpec workflow.
  5. The migration survey tests pass against fixtures/migration-source/, which holds the OpenSpec project this repository was migrated from, the 473 files the plan covers.
  6. The presentation checks and the asset rules' agreement test read the project's documents in htmlspec/, and fail rather than pass when a place they read is missing.
  7. At archival, htmlspec archive records release at 0.1.0, unchanged from the snapshot 0.29.0 published, and scripts/check-release accepts the history, including the two empty inventories.
  8. scripts/check passes.

What changes

The repository's checks read the project. scripts/check-release reads the archive, the adoption marker, and the runbooks under htmlspec/. The self-runbooks stages check htmlspec/runbooks.

The release runbook moves into the project unchanged. runbooks/release/ moves to htmlspec/runbooks/release/ byte-identical, and the two stylesheet revisions its documents link, sha256-e4f5de7cecc4f691 and sha256-0350261bb5666167, are copied into htmlspec/assets/ so its references resolve to the project's store. Its canonical documents keep the fingerprints its last snapshot recorded, so its version stays 0.1.0.

The OpenSpec project becomes the migration tests' source. openspec/ moves, byte-identical, to fixtures/migration-source/openspec/, and the survey tests run against it. The other tests that read openspec/ read htmlspec/.

The OpenSpec workflows are removed. With openspec/ gone they direct an agent at a directory that does not exist, or would make it again.

The repository's own prose stops saying it governs itself with openspec/, in the scripts, the build's source filter, and the tests this change edits.

Nothing in the program changes. This is release 0.30.1.

Alternatives considered

Point the migration tests at htmlspec/, as the plan's decision 4 words it. Not possible. The survey refuses a directory that is not an OpenSpec project, and measured, it says so: "is not an OpenSpec project: no openspec/specs or openspec/changes directory". The tests need an OpenSpec source.

Rewrite the migration tests against a constructed fixture. Rejected. Their header explains that this repository's own project is their test case so that each property is checked against a real one: two named changes that rename a requirement, a version shared by seven changes that scripts/check-release names as its baseline, a greatest version that has a changelog heading. A constructed fixture would assert what its author wrote into it. The moved project is a rename in version control and adds no stored bytes.

Delete openspec/ and leave it to version control history. Rejected. The suite's sandbox holds no repository, as toolchain-packaging's "Project checks are runnable as one command" records, so no test can read history.

Revise the release runbook as it moves. Rejected here, and named below as the next change. The plan's decision 4 moves it byte-identical so that its version stays 0.1.0 and the move reviews as a rename. A revision changes its canonical documents, which project-bootstrap's "Archival checks the versions of runbooks it publishes" makes a new release, with its own version and changelog entry.

Leave the OpenSpec workflows to a later change. Rejected. Between the two changes they would send an agent asked to start a change to openspec new change, which writes into the directory this change removes.

Scope

In scope. Everything that reads openspec/ or the root runbooks/: scripts/check-release, the self-runbooks stages of scripts/check, and three tests. The release runbook's move and its two stylesheet revisions. openspec/, moved to the fixture. The 52 OpenSpec workflow files under .claude/skills/openspec-*, .claude/commands/opsx/, .codex/skills/openspec-*, .pi/prompts/opsx-*, and .pi/skills/openspec-*, removed. Prose that says this repository governs itself with openspec/ or is not a project: the comments in the files above, flake.nix's source-filter comment, and scripts/check-installed's docstring and comments.

README.md and AGENTS.md do not change. Measured, neither names a directory of this repository called openspec/. README.md names OpenSpec, the project HTMLSpec started from, and shows runbooks/release/ only in the layout of a portable copy.

The release runbook's text is not revised, and it no longer describes this repository. Its specification says this repository "is not an html-spec project", and its step task-regenerate-the-instructions says to remove the htmlspec/ and spec.nix that htmlspec init creates. Since #55 those are the project and its declaration, and init leaves an existing project in place. That step must not be followed. The next change, release-a-repository-that-is-its-own-project, revises the runbook and advances it past 0.1.0.

Comments in the program's sources that cite evidence by its pre-archive path are not repointed. Five name openspec/changes/<name>/evidence/…, a path that has not existed since those changes were archived, and one in crates/htmlspec-cli/src/install.rs cites the .pi/prompts/opsx-*.md files this change removes. They are in shipped crates, and this change edits no code the program runs: its one edit inside a crate's sources is to a test module. A later change, repoint-the-sources-evidence-citations, settles them. Archived records and the changelog's past entries stay as written.

The repository's root assets/ does not change. It is the toolchain's source copy, recorded by assets/vendor.lock.json, and the two revisions are copied out of it, not moved.

No stage is added to check the whole project. htmlspec validate htmlspec and htmlspec format --check htmlspec pass, and running them on every check is a separate decision.

Requirements. This change adds, modifies, and removes none. The contract is silent on where this repository keeps its project. Promotion made it an html-spec project, and the obligations that name this repository, toolchain-packaging's "The project records what changed in each version it ships" and project-bootstrap's "The release suite checks published runbook version history", are met by its checks reading that project. The specification produced at archival records the silence.

The release. Archival refuses unless the declared version advances (project-bootstrap's "Archival requires the project version to advance"), recorded versions are distinct (toolchain-packaging's "An archived change records the version it shipped in"), and every shipped version has a changelog entry. None of them exempts a change that ships no change to the program, and none says how large an increment is: "Deciding what a version increment signifies, and by how much, is judgment." The choice is mine: a patch, 0.30.1, the smallest increment archival accepts, with a changelog entry that says the program is unchanged. The installed instruction files are regenerated, because each records the version that wrote it.
