Publish a public tree: design

How a release leaves this private repository: what the publish/ directory holds and why none of it crosses, how the export reads a committed ref and lands as a pull request on the public repository's own history, which rewrites it applies, how the scan refuses, why the suite runs inside the exported tree, and what this repository's contract gains.

Subject
Publish a public tree: design

What this settles

The contributor settled the destination on 2026-10-16: a fresh public repository, Firefly-Projects/htmlspec, with this repository kept private as the working record, an MIT license held by Firefly Systems LLC, a private organization's names replaced by example-corp, a private project treated as that organization's information and renamed missile-launcher, a branch ruleset in place of main-guard.yml, and a script modelled on the skills export that runs again for every later release. This design turns those decisions into a mechanism and records the choices that the decisions did not make.

Decisions

1. The road out is a publish/ directory, and none of it crosses

publish/ holds five parts: allowlist, the paths that may cross; rewrites.tsv, the rewrite table; patterns.tsv, the private pattern file; scan, the scanner; and export, the script. A sixth file, READINESS.md, is the checklist a person signs before a path joins the allowlist. The allowlist never lists publish/.

The rewrite table and the pattern file must name the strings they guard against, so publishing either would publish the material itself. The skills repository keeps its pattern file private for the same reason. Keeping the whole directory home makes the rule one line instead of five exceptions.

The tooling's own tests cannot be a stage of scripts/check. toolchain-packaging's "Project checks are runnable as one command" requires one command for the project's full suite, so that contributors and continuous integration check the same thing, and that suite runs here and inside the exported tree, where publish/ does not exist. A stage for tooling only one of the two trees holds would make the suite differ between them, which is the divergence the requirement exists to prevent, and the suite has no optional stage. So publish/test holds them as a second command for tooling that belongs to this repository alone, and contributors and continuous integration still run the same thing: a workflow that lives only here, .github/workflows/publish.yml, runs it on every pull request, and the allowlist excludes that workflow. Amended 2026-10-19, after the review of the plan: this rationale first said the contract is silent here, and it is not.

The skills repository writes its allowlist in Nix. I chose plain text, one path per line, because the export reads it without evaluating anything and a reviewer reads it at a glance. The contract is silent on the format, so this is my choice and a cheap one to change. The script is Python 3 with the standard library, as scripts/check-release and scripts/check-installed already are, also my choice.

Amended 2026-10-18, during implementation. As built, publish/ holds three more files than the five parts and the checklist: identity, the commit identity decision 11 requires; publishing.py, the module scan and export share, so the allowlist, the tables, and the readiness record are parsed in one place; and test, the tooling's tests. None of them crosses, for the same reason as the rest.

2. Each export is an ordinary commit on the public repository's own main

publish/export refuses a dirty working tree and an unknown ref. It fetches the target's main into refs/publish/main, checks it out into a scratch directory, replaces its contents with git archive of the allowlisted paths at the source ref, so a path the allowlist dropped disappears, and then rewrites, scans, and runs the suite. Only then does it commit, with the source ref and its full commit id in the message, on a branch publish/<short-sha>. --push pushes that branch and opens a pull request into main. --bootstrap pushes the first commit to an empty target, once. --dry-run stops before committing. --remote-url points the whole road at a scratch repository for testing.

This is the form of the pull-request export in the contributor's skills repository, and that script's header gives the reason: an orphan rebuild leaves GitHub two unrelated histories that it cannot open a pull request between. The contributor wants a branch ruleset on the public main requiring a pull request, and only this form satisfies it.

The export reads a committed ref, never the working tree, because git archive cannot see an untracked file and so cannot leak one. This repository tags no release today, so the ref is a branch or commit until commit-the-contract-and-the-command-line adds a release tag to the release runbook.

Amended 2026-10-18, during implementation, on four points the decision did not settle. Where the export is built. refs/publish/main lives in a scratch repository the export creates, not in this one, so no object of the public repository ever enters this repository and no branch of the export is ever made here. The export refuses a target whose main holds any commit this repository also holds, because a public history must never meet this one. The modes. With no flag the export commits in the scratch repository, keeps it, and prints its path for inspection. --dry-run runs every step except the commit. A target that is not on GitHub, such as a scratch bare repository, gets the push and a report of the pull request that would open, and no ruleset check.

What the bootstrap commits. The first commit of an empty target holds the exported README.md and LICENSE only, after the whole tree has been exported, rewritten, scanned, and passed by the suite. The whole tree then arrives as the first pull request, which a person reviews. This follows the onping export's README-only root, and it is my choice; the decision named --bootstrap and not its content.

The bootstrap and the target's ruleset. The contributor created Firefly-Projects/htmlspec empty, with an active ruleset on its default branch that requires a pull request and has no bypass actor. GitHub reports those rules for main before the branch exists, so a direct push of the first commit is refused. So the bootstrap is a recorded release step with three parts, done by the contributor: set the ruleset's enforcement to disabled, run publish/export --bootstrap, and set it back to active. The export checks both ends. --bootstrap refuses while any ruleset on the target's main is not disabled, naming the command that disables it, and prints the command that re-enables it after the push. --push refuses while any ruleset on main is not active, and when none protects main at all. Neither ever changes a ruleset itself: the export holds no credential that could, and loosening the public repository's protection is the contributor's act. The release runbook carries the three steps, in commit-the-contract-and-the-command-line.

Amended 2026-10-19, after the review of the plan (#63), on four points. No private history. The export builds every commit with git commit-tree in a scratch repository that git init makes fresh, from the exported files alone, so no object of this repository's history is in it. The bootstrap commit has no parent, and every later commit has exactly one, the target's main. The export reads the commit's parents back and refuses any other before it pushes, and publish/test holds the property itself: after a bootstrap and a push, no commit of the source repository, and no blob only its history holds, is in the target. A person reviews the exact tree before it leaves. A branch pushed to the public repository is public from that moment, and GitHub keeps a pull request's commits after the branch is deleted, so the pull request cannot be the first time a person sees an export. The local run is the review: it keeps the scratch repository and prints the exported tree's id and the command that shows exactly what the pull request would show. --push and --bootstrap refuse without --reviewed, and refuse unless the tree they build is the one named. The tree depends only on the exported files, so the same ref gives the same tree. A second export of one source replaces its branch. The branch is publish/<short-sha>, so an export of the same source after the target's main moved would collide with the first. The export now replaces that branch with a lease on the commit it found, and updates the pull request already open for it instead of failing to open a second. A dirty tree is one where a tracked file differs from its commit, staged or not. An untracked file does not count, because git archive cannot see it, so a run's own record, written and not yet committed, does not stop an export.

3. The public tree carries everything the suite reads

The allowlist lists every tracked top-level path: .claude/, .codex/, .pi/, .githooks/, .github/, .gitignore, AGENTS.md, assets/, Cargo.lock, Cargo.toml, CHANGELOG.md, conformance/, crates/, fixtures/, flake.lock, flake.nix, htmlspec/, img/, LICENSE, README.html, README.md, rust-toolchain.toml, scripts/, and spec.nix, with one exclusion inside them: .github/workflows/publish.yml, which tests tooling that does not cross. .github/workflows/main-guard.yml was a second exclusion until decision 12 deleted it.

The archive and the migration fixture are 969 of the 1,487 tracked files, measured 2026-10-19, and hold every private hit, so leaving them out looks like the cheap path. It fails: scripts/check-release exits 2 when a project has no archived changes, and nine migration survey tests read the fixture, as govern-this-repository-from-htmlspec measured when it moved the fixture. A public tree without them would check less than this one. Its accepted specifications and archive are also the clearest demonstration of what the project does.

A new top-level path does not cross until the allowlist names it, and READINESS.md asks a person to read it first. Every path above is signed once, in the tasks, before the first export.

Amended 2026-10-19, after the review of the plan. A directory on the allowlist admitted every file beneath it, including one added after the read, so a new private-only file inside a listed directory would cross by default. Each read in READINESS.md now names the commit it was made at, and the export refuses any file added beneath an allowlisted path after that commit, listing them, until a person reads them and records the read at a commit that holds them. A read at a commit that is not in the exported ref's history, as after a rebase, is refused too. The check is for added files: an edit to a file already read is the scan's to catch.

5. The whole private project is rewritten, not only its name

The contributor decided that the project counts as the private organization's information and becomes missile-launcher. The evidence also names the project's local directory and lists ten of its changes, and four of those change names describe its industry, its equipment, and its data sources. The directory and every change name are rewritten into the same neutral theme, keeping the counts, states, and argument of the evidence intact, because the names identify the project as surely as its title does. The rewrites reach the program text too: the example in the instruction source and its five installed copies name one of the changes, so the public binary's instructions read the neutral name, while this repository's program does not change.

The contributor's first decision covered the name, not the rest. Asked on 2026-10-16 whether the directory and every change name are rewritten too, the contributor answered yes, so this decision is accepted and task 2.4 writes those rows.

6. The scan refuses on any match, and binary files are read by a person

publish/scan reads patterns.tsv, rows of a section, a regular expression, a reason, and an optional allowed occurrence, and matches every text file case-insensitively. Exit 0 is clean, 1 is a match, reported by file and line, and 2 is a usage error, the skills scanner's convention. The patterns start from the audit: the private organization's name and both names derived from it, the private project's name, its directory, and every name decision 5 rewrites, the contributor's home directory and email address, the two other private project names the audit looked for, and this repository's address. Amended 2026-10-18: also the contributor's home directory on an earlier machine, and any home directory by shape (decision 4, amended), 25 patterns in all. Amended 2026-10-19: also a home directory written with dashes, as a session's scratch directory or a tool's project directory writes it, URL-encoded, or as a Windows path, and a session's scratch directory itself, 30 patterns in all.

A file holding a NUL byte is binary and is not matched. A raw search for the organization's name flags img/hero.png and img/runbook.png, whose compressed bytes happen to spell it, so a byte match would refuse every export for nothing. Instead the scanner lists every binary file it skipped, and the export refuses unless each one is named in READINESS.md as read by a person.

Amended 2026-10-18, during implementation, on how the readiness record is enforced, which the decisions left open. READINESS.md has three sections the export reads: a table recording who read each allowlisted path and when, the binary files read, and the contributor's sign-off. Every run refuses an allowlisted path the table does not record and a binary file the list does not name. Only --push and --bootstrap refuse an empty sign-off, because they are the runs that publish: a dry run and a local export can be read before anyone signs, and reading them is what the contributor signs after. I recorded the reads as mine, the agent's, and left the sign-off to the contributor.

Amended 2026-10-19, after the review of the plan. A binary file was signed off by its path alone, so a screenshot replaced after the read kept the old sign-off and crossed unread. Each line of "Binary files read" now names the blob id that was looked at, and the export and the scan refuse a binary whose bytes differ from it, saying it changed since its read, and a line that names no blob id. The scan also reads a PNG's text chunks, tEXt, zTXt, and iTXt, decompressed, as text, because a screenshot tool can write a path or a hostname there that nobody looking at the picture sees. The picture is still a person's to read.

7. The suite runs inside the exported tree before anything is committed

After the scan, the export runs scripts/check in the exported tree and refuses on any failure.

The skills export has no such step, and this one needs it, because the rewrites change files the suite reads: the archive, which scripts/check-release reads, and the migration fixture, which the survey tests read. toolchain-packaging's "Project checks are runnable as one command" requires every stage to read the working tree rather than history, which is what lets the suite run in a tree that is not this repository.

8. An MIT license, held by Firefly Systems LLC

LICENSE at the root holds the MIT text with Copyright (c) 2026 Firefly Systems LLC, in this repository and therefore in the export.

The contributor chose MIT and the holder. Cargo.toml already declares license = "MIT", so the file makes an existing declaration true.

9. The boundary becomes a requirement of this repository

toolchain-packaging gains one requirement, an obligation on the project's repositories: the project's public repository receives only trees exported from its private working repository, each from a committed ref through the allowlist, rewritten, found clean by the scan, passed by the suite, and reviewed by a person as the exact tree that is pushed, in a commit whose only parent is the public repository's own main, by a GitHub noreply identity, naming its source ref and commit, and no commit of the private repository's history reaches the public one. Its scenarios: a planted private string refused at the scan, a vanished rewrite refused, a failing suite refused, an unreviewed tree refused, a commit identity that is not a GitHub noreply address refused, no source commit in the public history, and the publishing tooling absent from every export.

The contract is silent on publication. Left as a script, the boundary holds only while someone remembers to run the script the same way, and a leak cannot be taken back. toolchain-packaging already holds obligations on this repository, among them "The project records what changed in each version it ships", so the new one sits beside them.

Amended 2026-10-19, after the review of the plan. The requirement crosses, as every accepted specification does, so it reads in the public repository too. Worded first as an obligation on "this repository", it would there describe a repository that is not the one holding it. It now names both: the private working repository that publishes, and the public repository that receives.

11. Every export commit carries a GitHub noreply identity

publish/identity holds one line, Name <id+login@users.noreply.github.com>, and the export makes every commit with it as both author and committer. The export refuses an identity that is not a GitHub noreply address before it reaches the target. After committing, it reads the commit's author and committer back and refuses either that is not a noreply address, and it scans the commit's author, committer, and message against the pattern file, which names the contributor's personal email address. The identity is smurphy8's noreply address.

Added at the main session's direction on 2026-10-18. A public commit's author and committer are public, and a fresh repository's history is made of nothing but export commits, so a personal address in one would be in the public history for good. A commit made with whatever identity the contributor's git happens to hold would put it there. Reading the identity from a file the export requires, and checking it before and after, keeps that from depending on anyone's local configuration.

Amended 2026-10-19. The export controls its own commits, and a squash merge made in GitHub's interface takes the merger's address from the account. The contributor turned on "Keep my email addresses private" in GitHub's email settings on 2026-10-19, so a merge of an export's pull request records the noreply address too, and READINESS.md lists the setting among what is checked before a push.

12. main-guard.yml retires here too, and the hook refuses any push to the public repository

A branch ruleset already protects this repository's main: it requires a pull request and the checks to pass, and has no bypass. So the account of the free plan in README.md and .githooks/pre-push is false here as well as in the public copy, and the README's own instruction applies: add the ruleset and delete main-guard.yml. This change deletes it, and corrects the README and the hook's comment at the source, so the rewrite table no longer carries them. The hook gains one rule: from a checkout holding publish/export, which only the private working repository does, it refuses every push to the public repository, tags included, with no override.

A push from this repository to the public one carries this repository's history whatever it names: a tag pushes every commit behind it, and the ruleset guards main only. The export pushes from a scratch repository of its own, which the hook never sees, and a release tag is made on GitHub on the public repository's own commit, so nothing legitimate pushes from here. In the public repository, which holds no publish/export, the rule does nothing. The publish runbook, a later change, names the safe tag command, and this guard is what refuses the unsafe one. publish/test holds the rule.

Risks

A private string that no pattern names crosses

The patterns are the markers an audit found. A private name that the audit missed, or one that a later change adds, matches nothing and crosses.

Partly held down. Every path is read once against READINESS.md before it joins the allowlist, a new top-level path or a file added under a listed one cannot cross unread, an image crosses only at the exact bytes a person looked at, and a person reviews the exact tree locally before any push. A pull request on the public repository is not the review, because it is public the moment its branch is pushed, and GitHub keeps its commits after the branch is gone. What is not held down is a private name a person misses in the local review, inside a file already read. The fresh repository bounds the damage to the trees exported, not the whole history. Amended 2026-10-19, after the review of the plan: this mitigation first counted the public pull request as the review.

The public archive differs from the private one

The exported archive carries the rewrites, so a public archived document no longer matches its private original byte for byte. The change bears this: the rewrites are the point, and each export commit names the source commit that holds the original.

The suite in the exported tree depends on the machine that runs it

On macOS the suite's Python stages fail inside nix develop, so the export runs scripts/check the way this repository runs it today, with the pinned toolchain on the path. The change bears this. The public repository's own continuous integration runs the same suite on every pull request, including each export.
