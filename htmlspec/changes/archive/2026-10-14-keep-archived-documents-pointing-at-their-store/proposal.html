Keep archived documents pointing at their store

htmlspec archive moves a change one level deeper and leaves its documents pointing one level short, at a store and specifications that are not there, and validation accepts the result because it checks an asset reference by the address it names rather than by where its path leads. This change makes archival keep each document's references reaching what they reached, and makes validation check where a reference leads.

Kind
proposal
Contract
0.7.0
Subject
Keep archived documents pointing at their store

Why

The first change this repository archived with htmlspec archive came out of it with every document broken. A change's documents reference the project's store and its accepted specifications by relative paths written for htmlspec/changes/<name>/. Archival renames the directory to htmlspec/changes/archive/<date>-<name>/, one level deeper, and rewrites nothing. So ../../assets/ now names htmlspec/changes/assets/, which does not exist. The archived documents opened with no stylesheet and none of their scripts, and a link to the accepted requirement led nowhere. The code review of pull request #57 found it, and 29 references were rewritten by hand.

htmlspec validate said nothing, and that is the second defect. Validation finds the store above a document and looks up a reference's address and file name in it, ignoring the path in front of them. A reference whose path reaches a directory with no store is accepted as long as its address is stored somewhere above the document. Archival's fault produces exactly the references validation's fault accepts, so neither could be seen. evidence/the-two-defects-reproduced-2026-10-14.md reproduces both in a scratch project with htmlspec 0.29.1: four archived documents referencing ../../assets/, a store that does not exist, and validation exiting 0.

Both disagree with the contract. artifact-kinds' "Archival produces the specification and then updates the accepted contract" archives the change directory "intact, with all four of its documents preserved", and requires that "A reader SHALL be able to open an archived change and find the argument that motivated it". document-validation's "An asset reference must match the bytes it names" requires validation to "reject a document whose asset reference does not resolve to stored bytes", and a path that reaches no store resolves to nothing. Neither requirement says how a reference is resolved, or what archival does to a document's references, and the program filled both silences the wrong way.

What working looks like

  1. In a scratch project, htmlspec new change sample, then htmlspec archive sample: every document in htmlspec/changes/archive/<date>-sample/ references ../../../assets/, and every relative link it carries still reaches the file it reached before the move.
  2. The change's evidence is byte for byte what it was before archival, whatever references it carries.
  3. A document whose asset reference's path reaches a directory that is not its store fails htmlspec validate with asset/unresolved, naming where the path leads and where the store is. A reference that reaches its store is accepted as before.
  4. An archival interrupted at any point is still settled by the next run, as it is today: rolled back where the change did not move, and completed where it did, with the rewritten documents in place.
  5. htmlspec validate htmlspec, the fixtures, and the release runbook in this repository keep their verdicts. evidence/what-a-path-check-would-change-2026-10-14.md measured that a path check changes the verdict on none of their 1143 accepted references.

What changes

Archival rewrites the relative references in the change's documents, and nothing else. Each reference that leads out of the change directory is rewritten to lead to the same file from the archive. A reference within the change, such as evidence/… or tasks.html#…, moves with the change and is left alone. Evidence is never rewritten, as artifact-kinds' "A change's evidence is kept in the change and is not one of its documents" requires. The rewrite is part of archival's existing transaction, so a refusal or an interruption leaves the change as it was.

Validation checks where an asset reference's path leads, as well as the address it names. A reference whose path does not reach the store validation found for the document is reported as unresolved. The formatter is unchanged: deterministic-formatting's "Formatting preserves meaning" leaves a reference naming stored bytes as it was written, and this change does not make formatting move one.

Both requirements gain the rule they were silent on. Because validation can now reject a document that 0.29.1 accepted, this is release 0.30.0.

Alternatives considered

Fix only archival. Rejected. The next fault that leaves a reference one level short would again pass every check. Validation's blindness is why this one was found by a reader, not a check.

Fix only validation. Rejected. Every archival would then end with a document that fails validation, and a contributor would repair it by hand, as #57 did.

Have htmlspec format repair a misplaced reference. Rejected. "Formatting preserves meaning" leaves a reference that names stored bytes as written, and the formatter's own module calls re-pointing one "an explicit operation, never a side effect of tidying". Archival is the operation that knows a document moved.

Archive changes at the same depth as active ones. Rejected. toolchain-packaging's "An archived change is named for its date and refuses to collide" and the project's layout put the archive inside changes/, and moving it is a change to the project's places, not to archival.

Scope

  • No document already archived is rewritten. The one archive this repository's own htmlspec archive wrote was repaired by hand in #57.
  • The three hand-converted documents under openspec/changes/archive/2026-08-14-separate-artifact-kinds/documents/, whose references reach openspec/assets/, and the three records under openspec/changes/archive/2026-09-11-migrate-an-openspec-project/evidence/, whose references reach an assets/ directory beside them, are not repaired. Neither directory exists, so validation now rejects all six. No check validates openspec/, the migration plan's follow-on change removes it, and the promoted project keeps them as evidence.
  • Absolute paths, URLs with a scheme, and fragments are not touched by either fix.
  • A change moved by hand rather than by htmlspec archive is not repaired by anything. Validation now reports its asset references.
