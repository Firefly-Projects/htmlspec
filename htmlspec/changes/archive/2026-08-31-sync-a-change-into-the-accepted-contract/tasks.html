1. Establish that the operation is absent before adding it

  • 1.1 Record as evidence that archival's message names a step with no command behind it: crates/htmlspec-cli/src/commands.rs:1352 says "Apply the change's contract before archiving", and the subcommand list in crates/htmlspec-cli/src/main.rs holds validate, format, assets, archive, init, list, status, store, instructions, new and nothing that writes or reports on the accepted specifications

  • 1.2 Record that OpenSpec provides the operation and this repository already carries its workflow: .pi/skills/openspec-sync-specs/SKILL.md exists, and .pi/skills/ holds seven htmlspec-* skills with no sync among them.

    This is what makes the naming a contract question rather than a preference

  • 1.3 Confirm against the accepted text that no requirement already covers this.

    Archival assesses the merge and never performs it excludes the operation from archival without assigning it anywhere; The command surface names its operations as OpenSpec names them fixes eight spellings and does not name sync. Quote both, so the change is shown to fill a hole rather than to reopen a settled decision

  • 1.4 Confirm the merge is reserved for an agent by reading artifact-kinds rather than by citing the archival comment that cites it.

    A design that derives its central constraint from a code comment has derived it from a summary

2. The contract states the operation and its exclusions

  • 2.1 Add a requirement to openspec/specs/toolchain-packaging/spec.md stating that the command surface provides an operation that reports whether a change's stated requirements have reached the accepted specifications

  • 2.2 State that the operation compares requirement identifiers and reads neither side for meaning, in the same terms Archival assesses the merge and never performs it already uses, so the two requirements cannot drift into different accounts of one comparison

  • 2.3 State the exclusion explicitly: the operation SHALL NOT modify an accepted specification and SHALL NOT propose the text of a merge.

    The name is inherited from OpenSpec and reads like an operation that writes, so the prohibition must be stated rather than left to be inferred

  • 2.4 State that the report distinguishes the requirements the change states, those the accepted specifications hold, and those absent from them, and that it is available as a structured payload

  • 2.5 State that an absent requirement is a finding and not an error, and that the operation succeeds while any remain.

    Give the reason: a change mid-implementation legitimately has absent requirements, and a withdrawn one is absent permanently

  • 2.6 State what it does refuse on — a change that cannot be resolved, an absent specification artifact, a specification that does not validate — with the reason that a comparison against an invalid contract has no meaning

  • 2.7 State that the operation and archival derive the comparison from one source, in the form The command surface reports a change's completion already uses for tasks.

    This is the requirement that prevents a contributor syncing clean and archival reporting unmerged requirements immediately after

  • 2.8 Modify The command surface names its operations as OpenSpec names them to carry sync in its fixed list of spellings, and leave the rest of the requirement as written

  • 2.9 State that the workflow instructions carry a stage for the operation, so the agent-driven half of the merge is written down where an agent reads it

  • 2.10 Run openspec validate --all

3. Extract the comparison so there is one of it

  • 3.1 Lift unmerged_requirements (crates/htmlspec-cli/src/commands.rs:1290) into a form both archival and sync call, returning the stated, accepted, and absent sets rather than only the absent one

  • 3.2 Leave archival's behavior unchanged.

    It reports absent identifiers as a finding and continues to; this change adds a caller, not a rule

  • 3.3 Add a test that the two callers agree, in the shape of the accepted scenario "Archival and the report agree" — a change with a known absent identifier, asserted through both paths

4. The subcommand

  • 4.1 Add the sync subcommand taking a change, with --store for the same reason every project-reading operation takes it

  • 4.2 Emit the human report: the three sets, each identifier named rather than counted, following report_findings' stated reason that a contributor can check three identifiers and cannot check "3 requirements"

  • 4.3 Emit the structured payload with the three sets as arrays

  • 4.4 Return the success exit code with a non-empty absent set, and the operational-failure code for an unresolvable change, an absent specification, or one that does not validate

    Migration note: an unresolvable change and an absent specification return the operational-failure code, and a non-empty absent set returns success, but a specification that does not validate returns the document-violation code. Shown in sync in crates/htmlspec-cli/src/commands.rs at ee4301c, the commit that carried this change, where that refusal returns Outcome::DocumentViolation (:1177).

  • 4.5 Add the subcommand to invocations.rs, whose hand-written list exists so the command surface is stated twice and checked against itself

    No action: the premise was wrong. invocations.rs resolves each invocation against clap's own command tree, and its module comment gives the reason — "A hand-written list states the command surface a second time, and it drifts in the direction that keeps this check passing while the instructions are wrong." There is no list to add to, and sync resolved the moment the subcommand existed. no_shipped_body_names_an_absent_command passes over sync.md, which is the property this task was reaching for

  • 4.6 Confirm help_documents_every_subcommand_and_option covers the new subcommand and its option

    Migration note: nothing this change carries records the confirmation. At ee4301c, the test (crates/htmlspec-cli/src/main.rs:412) asserts the top-level help names ten subcommands, of which sync is not one, and checks the options of five subcommands, of which sync is not one either.

5. The workflow stage

  • 5.1 Add a sync workflow to crates/htmlspec-assets/src/instructions.rs, so htmlspec instructions sync and the installed copy come from one source

  • 5.2 Write the stage's instructions: run sync, read the change's specification and the accepted specifications on both sides, merge each absent requirement into the specification that should hold it, never copy a change's specification wholesale into an accepted one, re-run sync to confirm the absent set is empty

  • 5.3 State in the instructions that a requirement deliberately withdrawn is left absent and named in the report to the contributor, not merged to make the list go quiet

  • 5.4 Confirm init installs the new stage for every supported tool, and that re-running init on this repository adds it without disturbing the existing seven

    Migration note: only the first part was done. The stage was added to the table init installs from, for every supported tool, but this repository's own installed copies were not regenerated: ee4301c, the commit that carried this change, adds crates/htmlspec-assets/instructions/sync.md and its entry in crates/htmlspec-assets/src/instructions.rs, and no installed copy under .pi/, .claude/, or .codex/. The later change 2026-09-06-distinguish-a-requirement-from-an-example regenerated them, and its record of the drift says that sync "existed in the binary and in no file an agent could read, for three releases".
