Tell users how to upgrade htmlspec and the projects that use it: design

The upgrade guide is a README section with two halves, the binary and the project, because those are two steps on two different schedules: a machine upgrades its binary once, and each project it works on is brought up afterwards. Every command in it was run, or read from its own help, before it was written down, and the stage that already checks the README's install blocks now checks the upgrade blocks too. The contract changes in one sentence, the one that says what the check suite holds of the README's commands.

What a reader has today

Measured on main at 1.2.0, before this change. A 1.1.0 project was made in a scratch directory with the 1.1.0 binary, committed, and then brought up with the 1.2.0 binary:

  • htmlspec init --tools claude,agents changed 19 files and touched nothing under htmlspec/ and not spec.nix. Sixteen changed only their generatedBy line. The new command, the new skill, and the marked region of AGENTS.md each gained 1.2.0's passage on declaring a runbook's order, 28 lines added and 3 removed. Measured again after the review: the first measurement counted only files and missed that.
  • htmlspec format --upgrade-assets --check found nothing behind, because 1.1.0 and 1.2.0 write the same stylesheet and scripts.
  • htmlspec validate reported 0 errors, as it did under 1.1.0.

That is the whole upgrade from 1.1 to 1.2, and no document says so.

Decisions

1. The guide is one README section, split into the binary and the project

A new ## Upgrading section follows "Getting started", and "After installing" links to it. Its first half says how to upgrade the binary on each channel the README installs from. Its second half says what to do in a project, from its root, once the binary is newer. Then it states what 1.x promises, and where to read what each release lets a project adopt.

The two halves happen on different schedules and often to different people: a machine's binary is upgraded once, and every project on it is brought up afterwards, possibly by whoever next works in it. A reader looking for one half should not have to read through the other. The README is where a reader already went to install, so it is where they look to upgrade.

2. Upgrading the binary uses each channel's own command

  • The release block on Linux and WSL: run it again. It reads the latest release, so a second run installs the newer one over the first. The README already said so, and the guide points back to it.
  • Homebrew, on macOS or Linux: brew upgrade htmlspec.
  • cargo: cargo install --locked htmlspec-cli again, which replaces an older installed version with the newest.
  • Nix:
    • a profile install: nix profile upgrade htmlspec, where htmlspec is the entry's name as nix profile list prints it;
    • nix run github:Firefly-Projects/htmlspec, which always runs the newest release and installs nothing to upgrade;
    • a project whose flake has htmlspec as an input: nix flake update htmlspec, run in that project, and committed with its flake.lock.

Each ends with htmlspec --version, or -v, which names the release and the commit it was built from.

Every channel already owns the file it installed, and upgrades it its own way, so the guide repeats those commands rather than inventing one. Each was read from its own help on this machine (Determinate Nix, Nix 2.34) before it was written down. A current Nix accepts a profile entry by its name and a flake input as a bare argument to nix flake update. An older Nix takes the entry's index from nix profile list, and updates one input with nix flake lock --update-input htmlspec, and the README says both.

Settled after the review on 2026-10-27. Three things a Nix reader meets are now said. A profile entry or a flake input that names a tag stays at that tag, so the reader names the new tag first. nix profile names its entries from Nix 2.20, nix flake update <input> arrived in 2.19, and Nix 2.34 refuses an index (seen here: "'nix profile' no longer supports indices"), the first two read from Nix's own release notes. And nix run github:Firefly-Projects/htmlspec runs the head of the default branch, which Nix reuses for tarball-ttl seconds, 3600 here, until --refresh. The macOS tarball route and the Homebrew-on-Linux brew shellenv step gained an upgrade line each.

3. Bringing a project up is init, an optional asset upgrade, and validate

In the project's root, once the binary is newer:

  1. htmlspec init --tools <the tools the project uses> rewrites the installed agent instructions to the new release's, and leaves the specifications, changes, archive, runbooks, and spec.nix as they are. Naming the tools skips init's question.
  2. Optionally, htmlspec format --upgrade-assets --check lists the documents whose stylesheet or scripts are behind the release's, and htmlspec format --upgrade-assets moves them. It never touches an archived change or a run record, and it downloads nothing.
  3. htmlspec validate.
  4. Commit what changed.

Where the project pins htmlspec, the pin moves too: the htmlspec field of spec.nix, or a flake input. The guide suggests the public address, github:Firefly-Projects/htmlspec/vX.Y.Z, for a pin that still names a private one.

project-bootstrap's "Bootstrapping installs agent instructions for the tools a project uses" says the instructions record the version of the program that generated them, so an installation that predates the instructions it should carry is identifiable. The guide gives the one line that shows that version, so a reader can tell whether a project needs the refresh. The asset step is optional because older references still validate, which is what "Formatting preserves meaning" protects by leaving them as written unless asked.

Settled after the review on 2026-10-27. The command that shows which release a project's instructions come from also reads AGENTS.md, which records the release as Generated by htmlspec X.Y.Z and not as generatedBy:; the first one printed nothing for a project made with --tools agents. Checked on a project made with agents only and on one mixing two releases. The guide also says init writes any of the release's assets the store lacks, which was seen to restore a deleted stylesheet. The asset files are byte for byte the same at 1.0.0 and now, so within 1.x that changes nothing, and --upgrade-assets has nothing to move.

4. The guide states what 1.x promises, and cites where

The guide says what stays true across a 1.x upgrade, names the accepted requirement behind each promise, and marks the one thing it reports that no requirement promises.

  • Commands, flags, exit codes, and --json payloads only gain things within 1.x. That is toolchain-packaging's "The command surface is stable within a major version", which leaves the wording of human-readable output out.
  • A document a 1.x release accepts stays accepted by every later 1.x release. That is document-schema's "The contract's version is a semantic version", whose promise covers errors, not warnings.
  • A runbook declaration in a newer format, preflight/v2 or preflight/v3, is refused by a binary that predates it, which names the formats it reads. That is runbook-portability's "Machine requirements are explicit and mechanically checkable". So everyone who runs a project's runbooks upgrades before the project adopts a newer format.
  • A run's record written by 1.2 states its runbook's release in its head. A 1.1 binary reads such a record and ignores the line. This is an observation, made when 1.2.0 was reviewed, not a promise, and the guide says so.

A reader who knows the promise upgrades without fear, and a reader who knows its edges, warnings and human-readable wording, is not surprised by them. The guide cites the requirements so a reader who doubts it can read the contract itself.

Settled after the review on 2026-10-27. The document promise now carries the requirement's exception, a document an earlier version accepted by a defect the changelog names, and says the promise is worded about the contract's version, which every 1.x release so far keeps at 1.0.0, not about the program's release. Records read both ways moved out of the list, below it, as observed and not promised, and it describes both directions. The README stated the promises twice, under Upgrading and under Project status; they are stated once, under Upgrading, and Project status links there.

5. Each changelog entry from 1.1.0 on says what upgrading to it asks

1.1.0, 1.1.1, 1.2.0, and the new 1.2.1 each gain a short "Upgrading" paragraph. Most say that refreshing the instructions with htmlspec init is the only step. 1.2.0's also names the two things a reader may notice: parse messages now show a hidden character by its code point, which changes validate --json's message text but not its codes, and a new run's record states its runbook's release. Entries before 1.1.0 are left as they are, because nobody upgrades to them now.

toolchain-packaging's "The project records what changed in each version it ships" keeps an entry's prose the author's and says a check shall not impose a structure on what an entry says. So the notes are written and not enforced. A check that refused an entry without one would contradict that requirement.

Settled after the review on 2026-10-27. Neither 1.1.1 nor 1.2.0 was published on its own, so every channel moves from 1.1.0 straight to 1.2.1, and 1.2.1's note says that an upgrade from 1.1.x follows 1.2.0's and 1.1.1's notes too, and what that means: init brings 1.2.0's new instruction text, and preflight/v3 needs 1.2 everywhere. The README says the notes are cumulative. The three notes written for entries already released are headed Upgrading (added in 1.2.1), because that requirement says an entry reconstructed after the fact says that it is a reconstruction.

6. The README's upgrade blocks are marked and checked like its install blocks

Each upgrade command block a reader runs is marked on the line before its fence with <!-- upgrade: NAME -->, beside the existing <!-- install: NAME --> markers, and the two share one set of names. scripts/check-readme-install requires four upgrade blocks, upgrade-homebrew, upgrade-cargo, upgrade-nix, and upgrade-project, and refuses one that is missing or that bash -n refuses. Its self-test gains the cases that prove it. The Linux release block needs no upgrade twin, because running it again is the upgrade.

A block a reader pastes is checked, as the install blocks are, because a broken one costs the reader the most. A command that names a placeholder in angle brackets would not parse, so each block names a real value, htmlspec for the profile entry and the flake input, and claude for the tools, with prose saying to substitute. The blocks are only parsed, never run: running them would upgrade the machine the check runs on.

Settled after the review on 2026-10-27. --print prints only an install block, and refuses an upgrade block, so nothing that runs what it prints can be handed one. The script refuses an install block marked upgrade: as it refuses the reverse, its messages say which marker to use, and its usage and scripts/check's comment name upgrade blocks. Its self-test has 19 cases, against 11 on main.

7. Release 1.2.1, a patch, and the publish runbook left alone

The release moves to 1.2.1 through scripts/set-version. Nothing the program does changes, so a patch fits.

No accepted requirement says how a release's number is chosen; the contract's own version stays 1.0.0 either way. This follows the project's practice that a release adding nothing to the command surface or the contract is a patch, as 1.0.1 and 1.1.1 were. The publish runbook's channel check already installs each channel, and upgrading is not part of publishing, so the runbook keeps its version.
