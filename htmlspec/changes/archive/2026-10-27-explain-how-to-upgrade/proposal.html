Tell users how to upgrade htmlspec and the projects that use it

A person who already uses htmlspec has nowhere to read how to move to a new release. The README installs a release, and says once that running its Linux block again upgrades, but it never says how to upgrade on Homebrew, cargo, or Nix, and it never says what to do in a project once the binary is newer. This change adds an "Upgrading" section to the README, an upgrading note to each changelog entry from 1.1.0 on, and checks that the upgrade commands the README gives still parse. It ships as 1.2.1, and it changes no behaviour of the program.

Subject
Tell users how to upgrade htmlspec and the projects that use it

Why

The question this answers was asked plainly: is there anything that tells a user how to upgrade? There is not. What exists is scattered, and none of it is written as an upgrade:

  • The README's Linux install block says that running it again upgrades. That covers the release tarball on Linux and nothing else.
  • htmlspec format --upgrade-assets is described in the command reference, as a formatting option, not as a step anyone takes after upgrading.
  • What to do in a project once the binary is newer is written nowhere. htmlspec init refreshes the installed agent instructions, but a reader learns that only from init's own help.
  • Each changelog entry says what its release adds. None says what upgrading to it asks of a reader.

Upgrading mostly asks for nothing, because 1.x keeps its promises from release to release. That is exactly why a reader needs to be told: a person who does not know that their documents keep validating, and that the agent instructions are the only thing to refresh, has to guess, and a cautious guess is to not upgrade.

What changes

  • An "Upgrading" section in the README, after "Getting started" and linked from it. It says how to upgrade the binary on each channel, how to bring a project up to the new binary, what 1.x promises and what it does not, and where to read what each release lets a project adopt.
  • An upgrading note in each changelog entry from 1.1.0 on, and in the new 1.2.1 entry. Most say that refreshing the instructions is the only step. 1.2.0's names the two things a reader might notice: escaped parse messages, and the release a new run's record states.
  • The upgrade commands are checked. The README marks each upgrade block, and the stage that already checks the install blocks offline refuses a missing or unparseable one.
  • Release 1.2.1, a patch: documentation and one check script, and no change to the program.

Alternatives considered

  • An htmlspec upgrade command. The binary cannot replace itself in a way every channel accepts: Homebrew, cargo, and Nix each own the file they installed. And bringing a project up to date is already one command, htmlspec init. A new command would only wrap those.
  • A warning when a project's instructions are older than the binary. The instructions already record the version that wrote them, so the warning is possible. It is new behaviour, so it belongs in a minor release, and it is left for one.
  • A check that every changelog entry has an upgrading note. The accepted requirement on the changelog says a check shall not impose a structure on what an entry says. So the notes are the author's prose, as the rest of each entry is.

Scope

This change writes documentation and extends one check. It does not change what the program does, add a command or a flag, or change any payload. It does not touch the publish runbook, because publishing is not upgrading. It does not cover upgrading across a major version, because there has been none.
