Tell users how to upgrade htmlspec and the projects that use it

What this change established. The README tells a person how to upgrade: each channel's own command for the binary, then the steps for a project, what 1.x promises with the requirement behind each, and what each release lets a project adopt. Each changelog entry from 1.1.0 on says what upgrading to it asks, and the notes are cumulative. The check suite now holds the README's upgrade commands as it holds its install commands: every marked block parses, the four upgrade blocks are present and marked as such, and no upgrade block is ever run.

toolchain-packaging

A release reaches every channel from one tag req-a-release-reaches-every-channel-from-one-tag

Every release SHALL be cut from one tag, vX.Y.Z, whose version equals the version the workspace declares, and the binaries, the crates, and the Homebrew formula the release produces SHALL each name that version. The release SHALL refuse a tag that names another version before it builds anything.

Publication SHALL begin only from a version tag in the public repository, Firefly-Projects/htmlspec, only for a commit that repository's main holds, and only after the check suite has passed on that commit. A tag in any other repository SHALL publish nothing. A release SHALL publish only from a run in which the binary of every target it releases was built and the formula passed its check, though runs elsewhere leave some of those jobs out.

A publication interrupted partway SHALL finish when run again, and SHALL NOT publish any version twice: the crates publish one at a time, a version the registry already holds is skipped, and a rate limit is waited out within a stated budget, after which the run stops and names the crates that remain. Every request the release makes to crates.io SHALL carry a fixed User-Agent that names the project, and no personal information.

Each channel that ships the binary SHALL ship its notices with it: each release tarball holds them beside the program, the Homebrew formula installs them, and the Nix package installs them under share/doc/htmlspec/. The formula SHALL declare exactly the licenses the binary credits. The check suite SHALL fail when CRATE-LICENSES differs from what the lockfile reaches, naming each crate added, removed, or changed, and when the formula's template declares other licenses than the binary credits, so a pull request that changes either meets it, on Linux as well as where the macOS jobs run.

A release SHALL become the repository's latest, the release releases/latest names, only when its version is the highest among the repository's published releases, and only that release SHALL reach the Homebrew tap, whose formula holds one version. A release on an older line SHALL NOT be made the latest, and its run SHALL leave the tap as it was.

After a release that is the repository's latest is published, its workflow SHALL install it through the README's documented Linux commands, verbatim, on both Linux targets, and through the README's Homebrew-on-Linux commands once the formula is in the tap. The run SHALL fail when an installed binary does not name the tag's version. A release on an older line SHALL be reported as untested by the Linux commands, not failed, and the Homebrew commands SHALL not run for it.

The check suite SHALL hold the README's install and upgrade commands without the network: each marked install or upgrade block SHALL parse, each upgrade block the README gives SHALL be present and marked as an upgrade block, no upgrade block SHALL be run, the Linux block SHALL check its download against SHA256SUMS before it unpacks or installs it, SHALL ask only for a target the release builds, and SHALL read SHA256SUMS as the release writes it.

Evidence

A project made by 1.1.0, brought up with the guide's steps evidence-a-project-brought-up

On 2026-10-27, in a scratch git repository, the 1.1.0 binary ran htmlspec init --tools claude,agents, and the result was committed. The 1.2 binary then ran the guide's project steps. init changed 19 files and nothing under htmlspec/ or spec.nix: 16 changed only their generatedBy line, and the new command, the new skill, and the marked region of AGENTS.md each gained 1.2.0's passage on a runbook's order, 28 lines added and 3 removed. format --upgrade-assets --check exited 0 with nothing behind, and validate reported 0 errors. With a stored stylesheet deleted, init wrote it back. The guide's command that names which release wrote a project's instructions printed htmlspec 1.1.0 for a project made with --tools agents alone, where the first version of it printed nothing, and both releases for a project whose tools were refreshed at different releases.

The upgrade commands, read and not run evidence-the-upgrade-commands-read

The Homebrew, cargo, and Nix commands were read from their own help on this machine and not run, because each would upgrade it. Nix 2.34 refuses an index ('nix profile' no longer supports indices, seen against an empty scratch profile), reports tarball-ttl as 3600, and its release notes date entry names to 2.20 and nix flake update <input> to 2.19. The asset files the program embeds are byte for byte the same at 1.0.0 and at 1.2.1, so every 1.x release writes the same assets.

Verification

The suite holds the README's upgrade blocks offline verify-the-upgrade-blocks-offline

scripts/check passed all 17 stages, among them readme-install, which runs scripts/check-readme-install --self-test and then checks the README, reporting its eight marked blocks, four of them upgrade blocks. The self-test's 19 cases include an upgrade block that is missing, one bash -n refuses, one marked as an install block, an install block marked as an upgrade block, and --print refusing an upgrade block, and each is refused. The script on main passes a README with an upgrade block missing and one that does not parse, and this one refuses that README, naming both. Repeat with scripts/check-readme-install --self-test and scripts/check-readme-install.
