Count only the checks a run ran

Three defects, fixed in one patch release, 1.3.3. htmlspec run --status counts a requirement whose only outcome is not-run as having an outcome, where --check, reading the same record, says nothing attests to it. Three tests of the asset-topology fixtures share two scratch directories and delete each other's files, which failed the check suite on main three times in October. And htmlspec instructions --help names seven of the nine stages the program installs. Each fix is small, none changes the recorded command surface, and the first gives the progress report's count a rule it does not have today.

Kind
proposal
Contract
1.0.0
Subject
Count only the checks a run ran

Why

The progress report counts a check that did not run

The two reports a runbook's runs have disagree about one record. With the 1.3.2 binary, on this repository's publish runbook:

$ htmlspec run publish --status v1.2.2
…
Requirements: 6 of 6 have an outcome
  passed   req-the-public-repository-is-reached-only-through-the-export-and-the-api
  not-run  req-the-tag-names-the-public-merge-commit-and-the-archived-version
  passed   req-the-first-run-leaves-the-ruleset-active
  passed   req-only-an-archived-and-merged-release-is-published
  not-run  req-each-channels-version-is-recorded
  passed   req-the-pinned-toolchain-is-what-runs
…
$ htmlspec run publish --check
…
2 unrecorded requirement(s) across 7 run(s). …

The two not-run requirements are the two --check names. htmlspec run --as writes one not-run verification per requirement, so the record lists what it owes, and by the progress report's count every new run reads "6 of 6" from the moment it starts.

--check is right. runbook-execution's "A record carries the procedure it ran and the obligations it attests to" requires a record to state an outcome and how that outcome was reached, and not-run states neither. The same specification's "A run's conformance to its runbook's contract is reported and never gated" is what --check carries out, and it reads not-run as nothing attested. "A run's progress is reported from its record", the requirement --status carries out, is silent on the count: it says only that an absent or empty outcome is shown as no outcome. The code answers one question two ways. The progress report counts any outcome that is not empty, through outcome_of in prerequisites.rs; --check asks has_run, private to runs.rs, which excludes not-run and any value the schema does not list. A test pins the defect: one_run_shows_its_steps_outcomes_release_and_verdict expects "1 of 1 have an outcome" beside a not-run line.

Three topology tests delete each other's files

In conformance/tests/topology.rs, Scratch::new names its directory htmlspec-topology-fixture-{label}-{pid}, and removes it at the start and again when it is dropped. The tests of one test binary run on threads of one process, so they share the process id. every_project_fixture_reports_the_duplication_it_declares builds all five fixtures, and two other tests each build one of them under the same label, so two threads can hold one directory, and one thread's removal deletes the tree the other is still writing or reading. The check suite failed on main three times this way, each a push run of check whose log still shows it:

  • 2 October, run 37021000931: every_project_fixture_reports_the_duplication_it_declares panicked at topology.rs:119, "the scratch store is created: … NotFound".
  • 23 October, run 39879572276: the same test, the same panic.
  • 27 October, run 40552369480: a_duplication_report_names_every_location_holding_the_bytes found "these 2 locations hold identical bytes" where its fixture builds four, and reported "the report omits proposal/htmlspec.js".

toolchain-packaging's "Project checks are runnable as one command" requires the one command contributors and continuous integration both run to verify the same thing, and a stage that fails at random verifies nothing a reader can trust.

The help names seven of nine stages

$ htmlspec instructions --help
…
  <STAGE>
          The stage: explore, new, continue, ff, apply, verify, or archive

The help is a doc comment on InstructionsArgs in crates/htmlspec-cli/src/lib.rs, written by hand on 30 August. sync joined the workflow table the next day and migrate on 13 September, and nothing held the comment to the table. The error for a stage the table lacks, in commands.rs, builds its list from WORKFLOWS, which is why it names all nine. Both spellings, instructions and get instructions, share the one struct, so both show the stale list.

What changes

  • One definition of a recorded outcome. has_run moves from runs.rs to prerequisites.rs, beside outcome_of, crate-visible, and the progress report counts a requirement as having an outcome only where a verification referencing it records one that says its check ran. Each requirement's line keeps its raw values, so not-run is still shown. runbook-execution's "A run's progress is reported from its record" gains a sentence saying so, with scenarios of a run just started and of a requirement recorded twice.
  • The pinned test states the right count. one_run_shows_its_steps_outcomes_release_and_verdict expects "0 of 1" beside its not-run line. New tests hold the count for each outcome and hold the report to --check on every record they write.
  • Every scratch directory is unique. Scratch::new adds the next value of a process-wide atomic counter to the directory's name, so two calls with one label get two paths, and a test holds that two scratches built with one label are distinct and that removing one leaves the other.
  • The help is built from the table. The stage argument's help is an expression over WORKFLOWS rather than a hand-written list, and a test holds the help of both spellings to every row.
  • Release 1.3.3. The workspace version, the installed instruction files' stamps, the changelog with an Upgrading note, and the README's line for the release.

What working looks like: on this repository, htmlspec run publish --status v1.2.2 reads "Requirements: 4 of 6 have an outcome", with the two not-run lines still listed, and --check still names those two. A run just started reads "0 of 6". The topology tests pass when the suite runs them on its threads, however the threads interleave. And htmlspec instructions --help reads "The stage: migrate, explore, new, continue, ff, apply, verify, sync, or archive", as get instructions --help does.

Alternatives considered

  • Count with outcome_of and let --check follow it. That makes the wrong report the rule. A record that has recorded nothing would conform from its first moment, which is the case the conformance report exists to catch.
  • Leave the count and change its words, to "6 of 6 have a verification". It describes what the code counts, and it counts nothing a reader asks about: the start writes a verification for every requirement, so the number is always the total.
  • Share the validator's has_run. rules/review.rs has a function of the same name for the stale-verification rule, and it counts a value the schema does not list as having run. That is right for its question, whether a recorded check can go stale, and wrong for this one, where a typo must not attest. Making either crate's function public to the other would change a published crate's interface to answer a question one crate asks.
  • Make tempfile a dependency of the conformance crate. It is in Cargo.lock, but only beneath proptest and rusty-fork. A counter does the same job in three lines, and adds nothing to review on the next upgrade.
  • Give each test its own label. It would fix these three tests, and leave the next test written against the same fixtures to pick a label nobody else uses. The counter makes the collision impossible however the tests are written.
  • List the stages as clap's possible values. clap would print them in the help, and also record them in the command surface, which crates/htmlspec-cli/src/surface.rs reads from the parser, so a stage would join the 1.3 surface as a value, a patch release would change the recorded surface, and clap's own error would replace the program's message for a stage it does not know.

Scope

  • It changes no command, flag, exit code, or payload field. The --json payload of run --status carries each requirement's outcomes and no count, so it does not change, and the help's wording is not part of the surface: toolchain-packaging's "The command surface is stable within a major version" says the wording of human-readable output is not covered. It is a patch release, 1.3.3, and tests/surface/1.3.json does not move.
  • It does not change what a run check, preflight, or --check decides about any record, or what the verdict line says. The verdict keeps reading not-run as "an outcome other than passed", as runbook-portability's "A prerequisite run is met by a finished, passed record" reads it.
  • It does not change the validator's own has_run or the stale-verification rule.
  • It does not change any other test file's scratch directories. The tools crate's Scratch already names each directory with a counter, as this fix does. A search of the other files found no label written into a test that two tests give a scratch directory, and found the repeated ones to be subdirectories inside one test's scratch; labels a helper passes on from its callers were not traced, and a later failure there takes the same fix.
  • It adds no stage and changes no workflow body.
