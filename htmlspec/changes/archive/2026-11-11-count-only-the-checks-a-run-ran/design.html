Count only the checks a run ran: design

How the three defects are fixed. The progress report and the conformance report share one function that says whether a recorded outcome attests to a check, the progress requirement gains a sentence and a scenario that give the count its rule, every scratch directory of the topology tests carries a process-wide count in its name, and the stage argument's help is built from the workflow table. It ships as the patch release 1.3.3.

What the contract says

The count. runbook-execution's "A run's progress is reported from its record" says what --status <record> lists: each requirement "with the outcomes recorded for it", and an absent or empty outcome shown "as no outcome, as the rule reads it". It says nothing of the line that counts them. Two neighbouring requirements say what an outcome is. "A record carries the procedure it ran and the obligations it attests to" asks a record for an outcome and how it was reached, and htmlspec run --as writes not-run only so the record lists what it owes. "A run's conformance to its runbook's contract is reported and never gated", which --check carries out, names each requirement nothing in a record attests to, and its code reads not-run as nothing attested. So the contract is silent on the count and clear on what an outcome means, and this change states the count in the requirement that owns the report, by the meaning the other two give.

The verdict. runbook-portability's "A prerequisite run is met by a finished, passed record" names a record that "recorded an outcome other than passed" as not counting, and the report's verdict line, "recorded not-run for", keeps that sense. It is a different question, whether a record passed, and nothing here changes it.

The surface. toolchain-packaging's "The command surface is stable within a major version" holds every payload field and every flag, and says "The wording of human-readable output is not covered". The --status payload, in crates/htmlspec-cli/schema/payload/run.schema.json and in tests/surface/1.3.json, carries each requirement's outcomes and no count, so the count is wording. The surface is read from the parser, not from --help, so the help is wording too. No requirement says what the stage argument's help must list: the contract is silent there, and the fix preserves what exists, a help that lists the stages.

The tests. toolchain-packaging's "Project checks are runnable as one command" makes scripts/check the one command contributors and continuous integration run. No requirement speaks to how a test names a scratch directory; the fix follows the tools crate's own Scratch, in xtask/src/scratch.rs, which already carries a counter for this reason.

Decisions

One function says whether an outcome attests to a check decision-one-definition-of-a-recorded-outcome

has_run moves from runs.rs to prerequisites.rs, beside outcome_of, as pub(crate), with its body, its documentation, and its unit test unchanged in what they hold: an absent outcome, not-run, and any value the schema's outcome vocabulary does not list attest to nothing, and passed, failed, blocked, and partial each attest to a check that ran. runs.rs's recorded_ids, which --check reads, calls it from there. The progress report's Owed gains a method, attested, true where any of its recorded outcomes is one has_run accepts, and the count reads it. The outcomes themselves are kept as the record states them, so a requirement whose only outcome is not-run is listed with not-run and not counted.

Two modules answered one question two ways, and the progress report's answer was the one no requirement supports. Putting the function where the run check's other readings of a record live, outcome_of, named_by, owed, and StepState, gives the three readers of a record one place to look. The count is computed from the list it summarises rather than from the verifications a second time, so the count and the lines beneath it cannot come from two readings.

Rejected: counting with outcome_of and moving --check to it. A record would conform from the moment it starts, which is the case the conformance report exists to catch. Rejected: renaming the line to "have a verification". It would describe the defect accurately and count nothing a reader asks about. Rejected: the validator's has_run, in crates/htmlspec-validate/src/rules/review.rs. It counts a value the schema does not list as having run, which suits its question, whether a recorded check can go stale, and would let a typo attest here; sharing it would also widen a published crate's interface for one caller.

The progress requirement states the count decision-the-requirement-states-the-count

runbook-execution's "A run's progress is reported from its record" gains one sentence, after the one on an absent or empty outcome: the report counts a requirement as having an outcome only where a verification referencing it records an outcome that says its check ran, one the schema's vocabulary lists other than not-run, as the conformance report reads a record, and a requirement whose outcomes are all not-run is still listed with them. It gains two scenarios: a run just started, whose every requirement reads not-run, listed and not counted, and named by --check; and a requirement recorded twice, once not-run and once passed, which is counted once. The other statements and the seven scenarios stay as accepted. At archival the requirement is stated whole and marked modified, with the new words marked as inserted.

A count with no rule is how this defect lasted from 1.3.0 to now: the test pinned what the code did, and nothing said what it should do. The sentence names the conformance report's reading rather than restating the vocabulary, so the two cannot drift apart in the contract as they did in the code.

The tests state the right count, and hold the two reports together decision-the-tests-state-the-right-count

one_run_shows_its_steps_outcomes_release_and_verdict, in crates/htmlspec-cli/tests/progress.rs, pinned the defect: it expects "1 of 1 have an outcome" above a not-run line. It now expects "0 of 1", with the line unchanged and the payload unchanged. every_outcome_is_shown_as_recorded asserts the count for each outcome: "1 of 1" for passed, failed, blocked, and partial, and "0 of 1" for not-run. A new test writes records of a runbook with two requirements, with outcomes of every kind, a typo, a requirement with no verification, and one recorded twice, once not-run and once passed, and holds each record's count to the requirements --check's payload says it recorded. Each new assertion is run against the code before the fix and fails there.

The test is changed and not weakened: it asserts the same lines and the same payload, and the one number it asserts is the one the requirement now gives. The test of agreement is what would have caught this defect, and it reads both reports through the built binary, as an operator does.

A process-wide counter names every scratch directory decision-a-counter-names-every-scratch

Scratch::new in conformance/tests/topology.rs names its directory htmlspec-topology-fixture-{label}-{pid}-{n}, where n is the next value of a static AtomicUsize, taken with fetch_add. It still removes a directory of that name before creating it, which now clears only what an earlier process with the same id left, and still removes its own on drop. A new test, two_scratches_with_one_label_never_share_a_directory, builds two scratches with one label at once, writes a file in each, drops the first, and asserts that the second's file is still there.

The collision becomes impossible by construction rather than unlikely by convention: no label, however chosen, gives two live scratches one path. xtask/src/scratch.rs does exactly this, "Tells apart the directories one process's tests make, which run in parallel", so the fix follows the repository's own pattern. The new test does not depend on how threads interleave: against the old Scratch::new the two scratches share a path and the first's drop deletes the second's file, every time.

Rejected: tempfile. It is locked only beneath proptest and rusty-fork, and a direct dependency of the conformance crate is more to review on every upgrade than three lines. Rejected: a label per test. It fixes these three tests and leaves the next one to choose well.

The stage argument's help is built from the workflow table decision-the-help-is-built-from-the-table

The stage field of InstructionsArgs takes #[arg(help = stage_help())], where stage_help, in crates/htmlspec-cli/src/lib.rs, joins the names in WORKFLOWS into "The stage: migrate, explore, new, continue, ff, apply, verify, sync, or archive", in the table's lifecycle order. It is total over the table: an empty table, one row, and two rows each read as English. Both spellings, instructions and get instructions, carry the struct, so both show it. A test renders each spelling's help from the parser and asserts that its stage argument names every row of WORKFLOWS, and that the rendered help shows it.

The error for an unknown stage already reads the table, and the help now does too, so a stage added to the table is in both without anyone remembering the comment. clap's derive takes an expression for help, and a String becomes the styled text clap prints.

Rejected: clap's possible values. crates/htmlspec-cli/src/surface.rs records an argument's possible values in the command surface, so the stages would join tests/surface/1.3.json in a patch release, and clap's own error would replace the program's message for a stage it does not know. Rejected: a test comparing the doc comment to the table. It would catch the next omission and keep a list that must be edited by hand.

A patch release, 1.3.3 decision-a-patch-release

No command, flag, exit code, or payload field changes, and tests/surface/1.3.json does not move: the count and the help are human-readable wording, which toolchain-packaging's "The command surface is stable within a major version" leaves out of the surface. The release runbook's steps open it, cargo xtask set-version 1.3.3 and the 1.3.3 binary's htmlspec init --tools claude,codex,pi, and archival records it. No runbook changes, so neither runbook's version moves.

The fixes are worth shipping before the next minor, not inside it. The workflow for working a run, planned for 1.4.0, reports --status, its pull requests run the topology tests many times, and its three new stages would be missing from the help as two are now. A patch first lets that release quote the count, run a suite that does not fail at random, and list its stages with no further work.

Risks

A script that reads the count from the text sees a lower number risk-a-script-reads-the-count

A script that parses "N of M have an outcome" from the text, rather than reading the payload, sees N fall for every record holding a not-run outcome. The change bears it: the text is wording, which the surface does not cover, the payload is unchanged and carries every outcome, and the number it read before was wrong for every run under way.

Two functions named has_run answer two questions risk-two-functions-of-one-name

The program's has_run and the validator's differ on a value the schema does not list, and a later reader could take one for the other and unify them in the wrong direction.

The program's function says in its documentation which question it answers, that the validator's answers another, and why they differ on an unlisted value; its unit test pins the typo cases, so a unification the wrong way fails it.

Another test file could share a scratch label through a helper risk-another-file-shares-a-label

Most test files name their scratch directories by label and process id alone. A search found no label written into a test that two tests give a scratch root in one file, and found the repeated ones to be subdirectories of one test's scratch, or names the tools crate's counter already separates. Labels a helper passes on from its callers were not traced. The change bears it: no failure but the topology tests' has been seen, and a later one takes this fix.

Follow-ups

The review of pull request 110 left two for later changes: reading a verification's outcome into a type with one case for each kind, so the count, the conformance report, and the run check match on it rather than on strings; and one convention for the scratch directories of every test file, a counter beside the process id as the topology tests and the tools crate now have, in place of the label and process id the other helpers use, which are unique in their binaries today.
