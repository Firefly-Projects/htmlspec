Count only the checks a run ran

What this change established. htmlspec run <runbook> --status <record> counts a requirement as having an outcome only where a verification referencing it records an outcome that says its check ran, which is how the conformance report, run --check, reads a record, so the two reports agree about which requirements every record attests to; a requirement whose only outcome is not-run is still listed with it. runbook-execution's "A run's progress is reported from its record" gains the sentence that says so and two scenarios, a run just started and a requirement recorded twice; its other statements and its seven scenarios are unchanged. The same release gives every scratch directory of the topology tests a name of its own, which the contract does not speak to, and builds the stage help of htmlspec instructions from the workflow table, on which the contract is silent. No command, flag, exit code, or payload field changed, and the release is the patch 1.3.3.

runbook-execution

A run's progress is reported from its record req-a-run-s-progress-is-reported-from-its-record

htmlspec run <runbook> --status SHALL report every file under the runbook's runs/, one line each, in name order, and SHALL say that the order is name order, because a record states no time. For each run it SHALL state the steps done of the total and the steps dropped, and then the steps in progress, or the first step neither done nor dropped where none is in progress, or that the run finished and whether it passed.

Whether a run finished and passed SHALL be decided by the rule runbook-portability's "A prerequisite run is met by a finished, passed record" states, without a lowest release, and by the code the run check applies, so the report and preflight give one answer about every record. A run that did not pass, and a file not read as a run's record, SHALL be named with the first reason that rule gives, in its words.

htmlspec run <runbook> --status <record> SHALL report the run recorded under that name, matched byte for byte against the names the runbook's runs/ holds: every step in order with its state and its heading, each dropped step's reason, each requirement the record carries with an identifier and does not withdraw, with the outcomes recorded for it, the outcome of every other verification the record holds, the runbook release the record's head states, and whether it is finished and passed. An absent or empty outcome SHALL be shown as no outcome, as the rule reads it, and every verification the rule reads SHALL be shown, so a verdict never names an outcome the report leaves out. The count of the requirements that have an outcome SHALL count a requirement only where a verification referencing it records an outcome that says its check ran: one the schema's vocabulary of outcomes lists, other than not-run, which is how "A run's conformance to its runbook's contract is reported and never gated" reads a record, so the two reports agree about which requirements a record attests to. A requirement whose only outcomes say no check ran SHALL still be listed with them.

The report SHALL write nothing, and SHALL exit 0 whatever the runs say. It SHALL exit 2 when the runbook or the record is not there, naming the records the runbook has. With --json it SHALL write the payload run's published schema states. A name or text a record or a directory holds SHALL reach the terminal with each character a terminal would act on written by its code point.

Every run on one line

Given
a runbook backup with a finished, passed run, a run whose fifth step is in progress, and a finished run that recorded failed for a requirement
When
htmlspec run backup --status runs
Then
each run is one line in name order, reading "finished and passed", "step 5 in progress", and "finished, not passed: recorded failed for" the requirement, and the report exits 0

One run in full

Given
a run whose first step was dropped with a reason and whose second is in progress
When
htmlspec run backup --status names that run's record
Then
both steps are listed with their states and headings, the dropped one with its reason, each requirement with the outcome recorded for it, the release the record states, and that the run is not finished and passed, with the rule's reason

The report and preflight agree

Given
a runbook another runbook requires, with records of every kind, a record holding a verification that references no requirement, and a record whose only requirement is withdrawn
When
preflight on the requiring runbook and the report each read them
Then
the records preflight counts are the ones the report calls passed, its open runs are the ones the report calls open, and each record it does not count carries the reason the report gives

An outcome no requirement shows

Given
a finished record whose requirement passed, and which also holds a verification that references no requirement and recorded failed
When
the run is reported
Then
that verification is listed among the other outcomes, and the run is not finished and passed, naming it

An empty outcome

Given
a finished record whose one verification states an empty outcome
When
the run is reported
Then
its requirement is listed with no outcome, and the run is not finished and passed, having recorded no outcome

A file that is not a run's record

Given
an empty file and a file whose markup needs error recovery under the runbook's runs/
When
the runbook's runs are reported
Then
each is named with the reason it is not read, and the report exits 0

A record that is not there

When
htmlspec run backup --status v9 names no record the runbook holds, or names one with its .html, as a path, or in another case
Then
it exits 2, naming the records the runbook has, and writes nothing

A run just started

Given
a run just started of a runbook stating two requirements, whose record holds the not-run outcome the start writes for each
When
htmlspec run backup --status names that run's record
Then
both requirements are listed with not-run, the report says 0 of 2 have an outcome, and htmlspec run backup --check names both as unrecorded

A requirement recorded twice

Given
a record whose first requirement has two verifications, one not-run and one passed, and whose second has one, not-run
When
the run is reported
Then
the first requirement is listed with both outcomes and counted, the second is listed with not-run and not counted, the report says 1 of 2 have an outcome, and --check names the second alone

Evidence

The two reports disagreed about one record at 1.3.2 evidence-the-count-at-1-3-2

On 2026-11-11, with the installed 1.3.2 binary, on this repository's publish runbook: htmlspec run publish --status v1.2.2 read "Requirements: 6 of 6 have an outcome" above two not-run lines, for req-the-tag-names-the-public-merge-commit-and-the-archived-version and req-each-channels-version-is-recorded, and htmlspec run publish --check named those same two as "2 unrecorded requirement(s) across 7 run(s)". The progress report counted any outcome that is not empty, through outcome_of; --check counted through has_run, which excludes not-run and any value the schema does not list. one_run_shows_its_steps_outcomes_release_and_verdict pinned the first reading, expecting "1 of 1 have an outcome" above a not-run line, and the two new assertions and the new test of agreement each failed against the 1.3.2 code: "1 of 1" beside not-run, and "2 of 2" for a run just started.

With the 1.3.3 binary built at a0cb5ba, v1.2.2 reads "4 of 6", its two not-run lines still listed, and --check's payload records the other four. The other six publish records read "6 of 6" under both binaries, and --check records all six for each, v1.0.0's partial outcome among them. No record was changed.

Three topology tests deleted each other's scratch directories evidence-the-scratch-race

The check suite failed on main three times, each a push run of check whose log gh run view --log-failed still shows: on 2 October, run 37021000931, and on 23 October, run 39879572276, every_project_fixture_reports_the_duplication_it_declares panicked at conformance/tests/topology.rs:119 with "the scratch store is created: Os { code: 2, kind: NotFound, … }"; on 27 October, run 40552369480, a_duplication_report_names_every_location_holding_the_bytes reported "the report omits proposal/htmlspec.js: these 2 locations hold identical bytes", where its fixture builds four. Scratch::new named a directory by its label and the process id, removed it before creating it and again on drop, and three tests of one binary, run on threads of one process, built fixtures under the same two labels.

On this 18-core machine, under the shared suite lock, the topology test binary built before the fix and the one built after it each ran 1,000 times one at a time, and none of the 2,000 runs failed. Run 36 at a time, in 50 rounds, so the tests' threads were preempted as they are when the whole suite shares a machine, the binary from before the fix failed 120 of 1,800 runs, each in one or more of the three tests that share a label, and the binary from after it failed none of 1,800. The new test, run against the old naming, found both of its scratches at one path, and on that first run also failed a_duplication_report_names_every_location_holding_the_bytes, whose tree its scratches removed.

Verification

Each outcome is counted only where it says its check ran verify-the-count-for-each-outcome

In crates/htmlspec-cli/tests/progress.rs, through the built binary: one_run_shows_its_steps_outcomes_release_and_verdict reads a run whose first step was dropped with a reason and whose second is in progress, and asserts the whole report, with "Requirements: 0 of 1 have an outcome" above its not-run line, and the whole payload, whose outcomes still hold not-run. every_outcome_is_shown_as_recorded finishes a run once with each outcome and asserts "1 of 1" above passed, failed, blocked, and partial, "0 of 1" above not-run, and "0 of 1" above "no outcome" for a requirement with no verification. Repeat with cargo test -p htmlspec-cli --test progress.

The count agrees with the conformance report about every record verify-the-count-agrees-with-check

the_count_agrees_with_check_about_every_record adds req-second to a runbook's specification and starts eight runs of it: one just started, whose two requirements both read not-run; one with passed and not-run; passed and failed; blocked and partial; the typo notrun and passed; passed with the second requirement's verification removed; the first requirement recorded twice, not-run and passed, and the second not-run; and an empty outcome and passed. Each case names the requirements it attests to. For each, --status <record> reads that many of 2, and the requirements --check's payload records for the record are exactly those, so for the run just started it records neither and its report names both, and for the record twice it records the first alone. The lines keep each outcome as the record states it: notrun, not-run, passed, and "no outcome" for the missing verification. Repeat with cargo test -p htmlspec-cli --test progress.

One function says whether an outcome attests to a check verify-one-reading-of-an-outcome

has_run is defined once, in crates/htmlspec-cli/src/prerequisites.rs, and both recorded_ids, which run --check reads, and the progress report's Owed::attested call it; git grep -n 'fn has_run' crates/htmlspec-cli finds that definition alone. only_an_outcome_the_schema_enumerates_counts_as_recorded, moved with it, reads every outcome the schema lists and asserts that each attests exactly when it is not not-run, the split the requirement states, so a value the schema added later would fail it until someone decided what it means; it also asserts that passed, failed, blocked, and partial attest, and that not-run, an absent outcome, and notrun, not run, NOT-RUN, ran, and the empty string do not. The validator's the_not_run_outcome_is_found_in_the_schema holds its own function to the same split of the listed values. Repeat with cargo test -p htmlspec-cli --lib prerequisites.
