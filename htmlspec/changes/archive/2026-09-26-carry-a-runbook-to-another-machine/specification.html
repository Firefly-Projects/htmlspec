Carry a runbook to another machine

This change let a runbook be carried to a machine where its source project is absent. A runbook states what it needs of a machine as ordinary requirement units carrying a check declaration (Machine requirements are explicit and mechanically checkable, A machine requirement is still an obligation of the run), leaving package pins to the manifest that holds them (Package manifests retain authority over package pins); htmlspec preflight checks those needs (The command surface checks a runbook's machine prerequisites), and starting a run checks them afresh before its record is created (Preflight gates the creation of a run), without the source project's history (A carried runbook does not require its source project's history). It withdrew A runbook carries no version and no changelog of its own: each runbook now carries a release version and a changelog of its own (A runbook carries an independently checked release version), which archival compares against that runbook's last published snapshot (Archival checks the versions of runbooks it publishes) and the release suite checks across the published history (The release suite checks published runbook version history).

runbook-portability

Lets an operator carry a runbook to another machine and establish its prerequisites before starting a run, while keeping dependencies external and the procedure's release identifiable.

Machine requirements are explicit and mechanically checkable req-machine-requirements-are-explicit-and-mechanically-checkable

A runbook SHALL state machine prerequisites as ordinary requirement units in its specification, with stable identifiers, normative statements, scenarios, and an explicit check declaration. Preflight SHALL read these declarations from the existing projected requirement notes. It SHALL NOT infer checks from prose, requirement names, or executable examples. The declaration format SHALL be documented and restricted to built-in checks; arbitrary commands SHALL NOT be accepted.

The supported needs SHALL include a tool at a stated version, a tool supplied by a pinned package-manager environment, an installed agent skill, and a working-directory state. Machine requirements SHALL remain part of the logging contract: passing preflight does not remove their obligation to have an outcome recorded. Ordinary requirements without a check declaration SHALL remain logging obligations without becoming machine checks.

Malformed declarations, unknown check kinds, duplicate declarations on one requirement, and unsupported format versions SHALL be reported against the requirement and SHALL prevent starting a run. A contract with no machine declarations SHALL report zero checks, without claiming to have established unstated prerequisites.

Package manifests retain authority over package pins req-package-manifests-retain-authority-over-package-pins

A requirement for a package-managed toolchain SHALL identify the existing manifest, selected environment, and tools needed from it rather than repeat the manifest's versions in the runbook. Preflight SHALL delegate interpretation of pins to that package manager's supported read-only adapter and check the tools the invocation would actually use against that environment.

The initial supported package-manager adapter SHALL cover a local locked Nix flake's development shell. Preflight SHALL NOT install, build, download, update locks, enter a shell, or alter the working environment. Missing cached dependencies, an unsupported manifest, an unavailable manager, or an inability to establish a tool's provenance SHALL refuse readiness with an explanation. The existence of a manifest or a shell marker alone SHALL NOT count as evidence of readiness.

Preflight gates the creation of a run req-preflight-gates-the-creation-of-a-run

Starting a run SHALL perform preflight against the selected runbook and the invocation's current working directory and environment before creating the record or its directory. A standalone preflight success SHALL NOT be reusable as permission to skip this check. Only a result in which every declared machine requirement passes SHALL permit record creation; failed, unknown, timed-out, and unsupported results SHALL refuse it. There SHALL be no force or skip-preflight option.

Preflight SHALL execute no procedure steps and SHALL not modify the runbook, existing records, skills, or target working tree. Checks SHALL have bounded execution and captured output. An interrupted preflight SHALL stop its probes and publish no record. Each retry SHALL collect fresh observations. Readiness describes observations at the beginning of a run, not a guarantee about the environment throughout the procedure.

A successfully created record SHALL carry the runbook version and a verification of each passed machine requirement, with its observation and method. Other logging requirements SHALL remain unverified until the run records their outcomes. Checking or editing an existing record SHALL NOT become subject to preflight; run conformance remains advisory as established by log-a-runbook-run.

A carried runbook does not require its source project's history req-a-carried-runbook-does-not-require-its-source-project-s-history

A carried runbook SHALL be usable with its specification, procedure, version, changelog, and the referenced shared asset store in a minimal receiving project layout. It SHALL NOT require the source project's archive, project declaration, accepted specifications, or old run records to perform preflight or start a new local run. The receiving layout SHALL preserve one asset store shared by the runbooks and their records; it SHALL NOT introduce a store inside each runbook.

The runbook SHALL require tools and skills from the receiving machine rather than vendor them. Its dependency manifests SHALL be supplied by the target work environment when required. Old run records SHALL remain at their source unless separately copied; their absence at the destination SHALL NOT imply they never existed or prevent a new run. Transport and history synchronization SHALL remain outside the preflight operation.

runbook-authority

A runbook carries no version and no changelog of its own req-a-runbook-carries-no-version-and-no-changelog-of-its-own

A runbook SHALL NOT declare a version, and SHALL NOT carry a changelog. A runbook is changed by a change, that change records the project version it shipped in, and the runbook's history is the set of archived changes that touched it.

This is the arrangement an accepted specification already has, and the reason is the same. An accepted specification holds its purpose and its requirements and nothing else; its version history is recovered from the archive rather than read from a field anybody maintained.

A version no gate compares SHALL NOT be introduced. Accuracy does not confer authority, so a second version axis with nothing comparing it against the project's own is a value that can drift with no signal — which is how this project's own version gate once came to compare against a value no project ever had.

Where a runbook is carried to a machine on which the project is absent, the derivation from the archive is impossible and a version of its own becomes the only way for the runbook to say which release it came from. That case SHALL be settled where the portability of a runbook is settled, together with what compares such a version, rather than here.

Reason: A carried runbook must identify its release without the source archive. The source publication gate now compares versions, giving the declaration an enforcing consumer.

Migration: Give each existing runbook a VERSION and CHANGELOG.md at its first release under the new contract. Record that adoption honestly; do not invent independent versions for earlier project releases. Older run records remain readable without a carried version.

Migration note: the statements and scenarios above are this requirement as last stated in the specification of establish-a-runbook. This change's delta states only its Reason and Migration.

A runbook carries an independently checked release version req-a-runbook-carries-an-independently-checked-release-version

Every runbook SHALL carry a VERSION containing three nonnegative dot-separated integers and a CHANGELOG.md whose headings identify its released versions. A release version SHALL be greater than 0.0.0. The version SHALL identify the runbook's release independently of the project's version; it SHALL NOT be inferred from a directory name or an HTML schema-version declaration.

Version ordering and content changes SHALL be checked at source publication as specified by project-bootstrap. A version SHALL never identify two different released procedures or contracts for the same runbook. Distinctness SHALL be per runbook, so two different runbooks can each be at 0.1.0. Changelog prose SHALL remain the author's, with one heading per runbook release and a reference to the source project release when published through a project archive.

Preflight and new run creation SHALL refuse a missing or malformed version or missing heading for the declared version. They SHALL NOT require access to the source archive to compare versions. A copied version identifies a release; it does not attest that the copy is authentic. Existing records created before this obligation SHALL remain reviewable without being rewritten.

A machine requirement is still an obligation of the run req-a-machine-requirement-is-still-an-obligation-of-the-run

A runbook's specification SHALL state machine prerequisites beside its hazards and logging requirements, using the same requirement units. The check declaration described by runbook-portability SHALL select when and how a machine condition is checked; it SHALL NOT create a new unit kind, a new document kind, or an exemption from recording the requirement's outcome.

Ordinary document validation SHALL continue to validate the document's kind and schema without inspecting the host environment. Machine inspection SHALL occur only through preflight and new run creation. A failed preflight SHALL be a refusal to start; incomplete logging after a run starts SHALL remain an advisory conformance finding.

project-bootstrap

Archival checks the versions of runbooks it publishes req-archival-checks-the-versions-of-runbooks-it-publishes

In addition to checking the project's declared version, archival SHALL compare each runbook's declared version and canonical specification and procedure against its most recent published snapshot. Snapshots SHALL be ordered by recorded project versions, not archive-directory names, and SHALL carry the runbook version and content fingerprints in a form readable without Git.

For a runbook with no prior snapshot, publication SHALL require a version greater than 0.0.0. Changed canonical documents SHALL require a strictly greater runbook version. An unchanged runbook SHALL be allowed to retain its version or advance it with a matching changelog entry. A downgrade, reusing a version for different canonical content, or a missing version or changelog heading SHALL refuse archival. A malformed existing snapshot SHALL be reported, not treated as an absent predecessor. Adding or editing a run record SHALL NOT require a version increment.

Publication SHALL record snapshots in the same archival transaction as the change and project version. A refusal, cancellation, or failed publication SHALL leave the runbook, previous archive, and active change unchanged. Readiness-only archival SHALL apply the same comparison and write nothing. Archival SHALL NOT choose a version increment or write changelog prose for the author.

Runbook identity for this comparison SHALL be its directory name, as already required by runbook-authority. A renamed runbook SHALL begin a new publication lineage; former snapshots SHALL remain under the former name. A deleted runbook SHALL not cause deletion of its snapshots. An absent source archive on a receiving machine SHALL NOT prevent preflight or running a carried release; these operations do not publish a release.

Migration note: the delta stated: “A malformed existing snapshot SHALL be reported, not treated as an absent predecessor.” As built, a snapshot that cannot be parsed is reported, but an archive whose recorded project version will not parse is skipped rather than refused, so the snapshot it holds takes no part in the history and archival does not report it; reporting that version is left to scripts/check-release. The design records the skip as a decision the implementation reached that the design had not stated, and the change kept the delta's words.

Migration note: as built, readiness-only archival first settles an archival interrupted earlier, completing it where its change had moved and rolling it back where it had not, so it can write before it reports. This was deliberate, and it is recorded outside this change's documents: in the help text of archive --check, which names it as the one exception (crates/htmlspec-cli/src/main.rs:165 at 5ea25e7), and in the message of 5ea25e7, the commit that landed this change (“Say that archive --check settles an interrupted archival first”). It is so still at 139b206.

The release suite checks published runbook version history req-the-release-suite-checks-published-runbook-version-history

The repository release suite SHALL check that every published runbook snapshot has a parseable version and fingerprints, that changed canonical content advances its version, and that each published version has a changelog heading in the published snapshot. Repeated snapshots of an unchanged runbook at one version SHALL count as the same release. Distinct releases for that runbook SHALL have increasing versions, and a lower version SHALL be rejected even when content is unchanged.

The suite SHALL also check that each current runbook has a valid version and corresponding changelog heading. It SHALL NOT require unarchived edits to have advanced their version yet. Archives predating adoption of runbook publication snapshots SHALL remain valid without invented history. Once snapshots are introduced, each later archive SHALL explicitly record its runbook inventory, including an empty inventory, so a missing inventory cannot masquerade as old history.

toolchain-packaging

The command surface checks a runbook's machine prerequisites req-the-command-surface-checks-a-runbook-s-machine-prerequisites

The command htmlspec preflight <runbook> SHALL report whether the selected runbook can start in the invocation's working environment. It SHALL support the existing --store and --json selectors. Store selection SHALL locate the runbook and its records, while machine requirements SHALL be evaluated against the invocation's working directory and environment, not the store's directory. Names SHALL follow the existing runbook-name rules.

The report SHALL identify the runbook, carried version, source location, working directory, aggregate readiness, and each checked requirement with its expected condition, observation, outcome, and remedy for a refusal. Results SHALL follow document order. Human output SHALL lead with readiness. JSON output SHALL contain one structured report with no probe output interleaved.

A completed preflight with unmet requirements SHALL exit 1, a successful one SHALL exit 0, an invalid invocation, invalid contract, or operational failure SHALL exit 2, and cancellation SHALL exit 3. Unknown observations such as an unavailable manifest environment or a timed-out probe SHALL be reported as unmet readiness rather than as success. An invalid declaration SHALL remain distinguishable from a valid check whose condition is false.

htmlspec run <runbook> --as <record> SHALL apply the same checks and exit distinctions before creating a run. htmlspec run <runbook> --check SHALL continue to report existing run conformance without checking the present machine. Existing JSON fields on successful run creation SHALL be preserved, with version and preflight information added.
