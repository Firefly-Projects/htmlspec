A publish run finishes without a hand fix: design

The development shell supplies python3 from the flake's pinned nixpkgs, and both runbooks' toolchain declarations name it, so preflight refuses a run whose interpreter is the macOS developer-tools stub instead of letting a step fail on it. The export titles its commit and pull request by the version it publishes and a twelve-character id, and holds that title to the public guard's rules before it exports anything. How the export's push authenticates stays open.

What fails, and where

craneLib.devShell is an impure mkShell. It prepends its packages' bin directories to the search path and keeps the rest, and on Darwin the stdenv's SDK hook sets DEVELOPER_DIR and SDKROOT to the Nix apple-sdk. Before this change the shell's packages were the Rust toolchain, cargo-nextest, and jq, so python3 resolved to /usr/bin/python3. That executable is a stub that runs the interpreter the developer tools at DEVELOPER_DIR hold, and the Nix SDK holds none.

Measured inside nix develop on the machine whose v1.0.0 publish run stopped: command -v python3 printed /usr/bin/python3, and python3 --version printed error: tool 'python3' not found. With pkgs.python3 in the shell, python3 resolved to /nix/store/…-python3-3.13.14/bin/python3 and printed Python 3.13.14. The same measurement found git, /usr/bin/git, gh, nix, brew, shasum, and curl each printing its version inside the shell.

Decisions

1. The shell supplies pkgs.python3, and nothing else new

devShells.default gains pkgs.python3, the package checkSuite already lists in its nativeBuildInputs for the same scripts. Its interpreter comes from the flake's locked nixpkgs, so flake.lock does not change and every machine entering the shell runs the same Python.

The scripts use the standard library only, so any Python 3 would do. The shell supplies one anyway because the failure is not a missing interpreter but an interpreter that resolves and cannot run, and only a program inside the shell is certain to shadow the stub. Adding the programs that run already, the version-control client above all, would put a second copy ahead of a contributor's own, with their credential helpers and signing configured against it, to fix nothing that was measured to fail.

Found while building it: the shell's interpreter writes bytecode beside a module the scripts import, as publish/__pycache__/, and macOS's own interpreter writes it to a cache directory of its own (its sys.pycache_prefix), so a run inside the shell left an untracked directory nothing had met before, and one was nearly committed. .gitignore now names __pycache__/.

2. Both runbooks name python3 in their toolchain declaration

The note on req-the-pinned-toolchain-is-what-runs in each runbook's specification becomes {"kind":"toolchain","manifest":"flake.nix","shell":"default","tools":["cargo","rustc","python3"]}. The requirement's statement names python3 beside cargo and rustc, and each specification gains a scenario: a python3 that resolves outside the shell is reported, with where it resolved, and the run does not start.

The release runbook's specification said python3 was deliberately not declared, because a tool check states an exact version and pinning one would be "a second dependency language beside the flake". That reasoning is about the tool form. The toolchain form states no version: it checks that the named program resolves into a store path the shell's inputs occupy, which is the property that failed. Measured: outside the shell, with the pinned Rust toolchain first on the search path, htmlspec preflight publish now reports python3 resolving to /usr/bin/python3 and refuses. Inside it, it reports ready.

Declaring it is what makes decision 1 hold. Without the declaration, a shell that lost python3 in a later edit would pass preflight and fail at a step again, and nothing would say so before a run.

3. The publish runbook releases 0.2.0 and the release runbook 0.4.0

Each runbook's VERSION moves and its CHANGELOG.md gains a heading, because archival refuses one version for two different canonical documents. Both are minor increments: a machine that passed preflight before can be refused now, which is a change in what the procedure accepts, and no step changes. The project releases 1.0.1, a patch: no command, flag, payload, exit code, or document rule changes, and the shell is not part of the published crates.

The release runbook's own prerequisites list says that python3 is needed and that the shell supplies the toolchain. That list gains that the shell supplies python3 too, and its 0.2.0 changelog's "does not yet say so" is answered by the 0.4.0 heading.

4. The contract gains two scenarios, not a requirement

toolchain-packaging's "The toolchain builds reproducibly from pinned inputs" already requires equivalent results "regardless of what is already installed on the machine". A shell whose scripts run the machine's interpreter breaks that, so archival restates the requirement with one added scenario: the suite and the runbooks' scripts, run inside the development shell, run the shell's interpreter. No new requirement is needed, because the obligation is the existing one. The title gets the same treatment. toolchain-packaging's "The public repository receives only reviewed exports of the private one" says how an export reaches the public repository, and archival restates it with one added scenario: an export of a full commit id opens a pull request whose title names the version and a twelve-character id, and passes the public repository's title rules.

A separate requirement naming python3 would state a property of one package in the contract, where the flake already states it. The scenario states the property the contract cares about: what is already installed does not decide which interpreter the project's scripts run.

5. The export's subject names the version and a short id, and is held to the guard's rules

publishing.export_subject builds the export commit's subject, which is also its pull request's title: Export htmlspec {version} from {sha[:12]}. The version is [workspace.package]'s version in Cargo.toml at the ref, read by release_facts.section_fields, the one reader of that table the release scripts share. The bootstrap commit keeps its fixed subject, publishing.BOOTSTRAP_SUBJECT. Before it exports anything, the export loads scripts/check-pull-request and applies its title_faults to the subject, and refuses with each fault it reports. A ref whose manifest declares no version is refused too, because the subject has nothing to name.

The old subject named the ref as the caller spelled it, so its length was the caller's choice. The runbook spells it as a full commit id, which made 77 characters. With the version and a fixed-length id, a release's title is 39 characters for a version like 1.0.1, and only a version longer than 38 characters could pass the limit. The rules are applied by loading the guard's own script rather than restating its limit, because a copy of the limit would drift from the rule the public repository runs. Checking before the export starts means a refused title costs a few seconds, not a suite run and a public pull request with a failed check.

Measured: the old title for the first run's ref is 77 characters and title_faults refuses it as over 72. The new one, "Export htmlspec 1.0.1 from 7983c4a90031", passes, and matches the title the first run's pull request was given by hand apart from its version.

Revised after the code review. The rules are read at the ref, not from beside the export: the public repository's guard runs the copy inside the exported tree, which is the ref's, and the export reads every other fact from the ref and nothing from the working tree. A ref that holds no scripts/check-pull-request is refused, because nothing could then say whether the guard would take the title. Only an export onto the target's main reads the version and the rules. The bootstrap commit opens no pull request and carries publishing.BOOTSTRAP_SUBJECT, so it needs neither, and a test holds that subject to the rules instead. The loader is publishing.title_faults, which the export and its tests share. release_facts stays the export's own code, as publishing is, because it reads the ref's Cargo.toml and states no rule the public repository applies.

Risks

A program not declared fails inside the shell on another machine

The measurement covers one macOS machine. Another machine can resolve a program the runbooks run outside the shell, such as gh or shasum, to one that does not run inside it, and preflight would not see it, because those programs are not declared.

Accepted. A tool check would pin a version the procedure does not need, and naming a program the shell does not supply in the toolchain form would refuse every run. If a step meets such a failure, the fix is this change's: put the program in the shell and name it in the declaration.

Open question: who supplies the push's GitHub credential

The export pushes its branch to the public repository with plain git push over HTTPS, and it opens the pull request and reads the rulesets with gh. On the machine that made the first run, git had no GitHub HTTPS credential: the helper its configuration names for https://github.com, manager, is not installed. The run pushed by setting credential.https://github.com.helper to gh auth git-credential for that one command, through GIT_CONFIG_COUNT in the command's environment, after an empty entry that clears the helpers configured before it. This change implements neither answer below. It records them so the next change can choose.

  • The export does it. For a GitHub target, the export sets the same two entries in the environment of its own git push and git ls-remote calls, so nothing persists past the command. Every GitHub operation of a delivery then authenticates as the account gh is signed in to, and a delivery already requires gh for the pull request and the ruleset checks, so this adds no dependency. The cost: the push no longer uses a contributor's own helper. If gh is signed in to another account than the one their helper holds, the push goes as gh's account without saying so, unless the export also prints which account gh is, which is one more call. The tests target local bare repositories, so they would not reach this path, and it would need a test that fakes gh.
  • The runbook says it. The push step names the two entries and the command, and the run records that it used them. Nothing in the code changes, and a contributor whose helper works keeps it. The cost: the knowledge lives in prose, and a run meets the missing credential only when the push fails, which is how the first run met it. Preflight cannot check it either, because no declaration form reads a credential.

My recommendation is the export, limited to a GitHub target: the delivery already trusts gh's account for everything else it does on GitHub, and one credential for the whole delivery is easier to reason about than two. The cost that decides it is the silent account switch, and printing gh's account before the push answers that. Until a change settles it, the publish runbook's run record is where a run states the credential it used.
