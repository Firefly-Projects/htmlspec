A publish run finishes without a hand fix

The first publish run needed two fixes by hand. Its procedure could not run python3 inside the shell its preflight requires, and the export titled its public pull request past the public guard's 72 characters. The shell should supply the interpreter and the preflight should check it, and the export should title what it publishes by version, within the guard's rules.

Subject
A publish run finishes without a hand fix

Why

The first run of the publish runbook, the v1.0.0 release, needed two fixes by hand before it reached the public repository. Each is a defect in what this repository ships for that run, and the next run would meet both again.

The procedure could not run inside the shell its preflight requires. Both runbooks declare req-the-pinned-toolchain-is-what-runs, so a run starts inside nix develop. That shell supplies the Rust toolchain, cargo-nextest, and jq, and every other program comes from the machine's own search path. On macOS the python3 there is /usr/bin/python3, a stub that asks the developer tools at DEVELOPER_DIR for the interpreter. The shell points DEVELOPER_DIR at the Nix SDK, which holds none, so the stub resolves and then exits with "error: tool 'python3' not found". publish/export, scripts/set-version, scripts/check-release, scripts/release_facts.py, and the suite's Python stages all run it. The run's preflight reported it ready, and its second step stopped. The release runbook's 0.2.0 changelog already records the same failure for the release check, and says the runbook "does not yet say so".

The export titled its pull request past the public repository's limit. publish/export titled the pull request, and the export commit's subject, Export htmlspec from {ref} at {sha[:12]}. The runbook passes --ref a full commit id, so the title ran to 77 characters, and the public repository's pull-request guard, which allows 72, failed on Firefly-Projects/htmlspec pull request 1. The run went on only after the pull request was retitled by hand to "Export htmlspec 1.0.0 from 7983c4a90031".

What changes

  • The shell supplies python3. flake.nix's default development shell gains pkgs.python3, from the flake's pinned nixpkgs. The suite's own derivation already builds with the same package.
  • Both runbooks declare it. Each runbook's toolchain declaration names python3 beside cargo and rustc, so htmlspec preflight refuses a run whose python3 resolves outside the shell, and names where it resolved. The publish runbook moves to 0.2.0 and the release runbook to 0.4.0, each with a changelog heading.
  • The export names the version, not the ref. The export commit's subject and its pull request's title become Export htmlspec {version} from {sha[:12]}, with the version Cargo.toml declares at the ref. The export holds the subject to scripts/check-pull-request's title rules before it exports anything, so a title the public guard would refuse stops the export instead of failing a public pull request.
  • A patch release, 1.0.1. No command, flag, payload, or document rule changes.

What working looks like: nix develop -c htmlspec preflight publish reports ready, nix develop -c publish/export --ref "$(git rev-parse origin/main)" --dry-run runs to its end, and an export pushed with a full commit id opens a pull request titled like "Export htmlspec 1.0.1 from 7983c4a90031", which the public guard accepts. On macOS, the same preflight run outside the shell reports that python3 resolves to /usr/bin/python3, and refuses.

Alternatives considered

  • Declare python3 with a tool check. A tool check states an exact version, and the scripts need any Python 3 with its standard library. The release runbook's specification rejected that for this reason. The toolchain form names the manifest and pins nothing new, so the objection does not apply to it.
  • Unset DEVELOPER_DIR in the shell. The stub would then find the system interpreter, but the Nix stdenv sets that variable for the compiler's linker, and the interpreter would still be whatever the machine has.
  • Tell the runbooks to run outside the shell, with the toolchain first on the search path. That is how the runs so far worked around it. It gives up the provenance check, which is the reason the runbooks name the shell.
  • Tell the runbook to pass a short ref. The title would fit, but its length would still depend on what a caller types, and a branch name can be any length. A title built from the version and a fixed-length id fits whatever the ref is.

Scope

This change does not put git, gh, nix, brew, or shasum in the shell. Each resolves outside the shell and runs inside it: measured on the machine that met the failure, every one of them printed its version from within nix develop, /usr/bin/git included. The shell gains only the program that was measured to fail, and the design records how a later one would be found.

It does not settle how the export's push authenticates to GitHub. The first run needed git's GitHub credential helper set to gh auth git-credential for one command. The design records that as an open question, with what each answer would cost, and implements neither.

It does not change the v1.0.0 run already under way, whose record copies the procedure it started with, or the public pull request that run retitled.
