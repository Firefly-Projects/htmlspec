Publish releases through their own runbook

A release is prepared inside its change: the release runbook advances the version, regenerates the instruction files, writes the changelog entry, and confirms the release check. From 1.0 on, a release must also reach the public repository and four channels, and those steps can only run after the change is archived, against another repository. This change gives them a runbook of their own, publish, so each release is published by one run of it after archival. The run makes the public tag through GitHub's API on the public merge commit, so no ref ever travels from this repository to the public one. The program does not change. Release 0.34.0.

Subject
Publish releases through their own runbook

Why

The plan for 1.0 put the publishing steps at the end of the release runbook, in commit-the-contract-and-the-command-line. The code review of that plan's pull request, #63, found five problems with that placement. Each one is a reason for this change.

  • The obvious tag command publishes the private history. The private and public release tags would share the name vX.Y.Z. When git tag vX.Y.Z <merge> fails because the private tag exists, the natural next command, git push <public> vX.Y.Z, sends the private tag and every private commit behind it. The pre-push hook and the public ruleset guard only main, so nothing stops it, and the push also runs the release workflow on the private tree. The review reproduced this with the real hook.
  • Nothing in the plan works against the empty public repository. Firefly-Projects/htmlspec exists and holds no commit. The export's first run must bootstrap it, and the active ruleset refuses that first direct push to main. No step said what to do.
  • A release run after archival repeats finished work. htmlspec run release --as v1.0.0 copies the whole procedure, so its record opens with the four steps already done inside the change, and one requirement that can only be met before archival. Following the record would advance the version again.
  • The co-owner step was in no step. The crates' co-owner, the team firefly-developers, can only be added after the first publish, by an owner.
  • The changes disagreed about the accounts. They now exist, and the plan said they would be made later.

runbook-authority's "A project keeps its procedures in a fourth place" keeps a project's procedures as runbooks, each a directory in that place, so a second runbook beside release needs no new rule.

What working looks like

  1. htmlspec list --runbooks lists publish beside release, and htmlspec preflight publish reports it ready inside the development shell.
  2. After a release's change is archived and merged, htmlspec run publish --as vX.Y.Z starts a record that holds only the publishing steps.
  3. The run reviews the exact export privately before anything leaves this machine, and only then pushes it as a pull request on the public repository.
  4. On the first run only, the run bootstraps the empty public repository with ruleset 25362895 off for that one push, and stops unless the ruleset is active again afterwards.
  5. The public tag is created through GitHub's API on the commit that merged the export's pull request. No step pushes any ref from this repository to the public one.
  6. The run watches the release workflow, adds firefly-developers as each crate's co-owner on the first release, and records that each channel installs the version.
  7. This is release 0.34.0, and scripts/check passes.

What changes

A new runbook, htmlspec/runbooks/publish/, with its specification, its tasks, a VERSION of 0.1.0, and a CHANGELOG.md. Its specification states what a publishing run requires, among them the hazards the review found. Its tasks are the steps, in order.

The release runbook is untouched here. ship-through-four-channels takes it to 0.3.0, and it keeps the steps that run inside a change.

The 1.0 change loses its publishing steps. commit-the-contract-and-the-command-line now follows this change and promises only the contract and the command line.

The program does not change.

Alternatives considered

Append the publishing steps to the release runbook. The first plan did this. Rejected, because a run after archival copies the steps already done inside the change, and the review reproduced that record.

Push the public tag from this repository, from the export's fetched copy of the public main. It works when typed exactly. Rejected, because one wrong word sends the private tag. Creating the tag through the API involves no push at all, so a guard can refuse every push from this repository to the public one without an exception.

Leave the first-run bootstrap to the contributor's memory. Rejected. A step done once, in an order that matters, and with a protection switched off, is the kind of step a runbook exists to hold.

Scope

In scope. The publish runbook, its requirements and steps, a rehearsal of what can be rehearsed without the public services, and release 0.34.0.

Not in scope. The export tool, its private review, and the push guard belong to publish-a-public-tree. The release workflow and the crate publisher belong to ship-through-four-channels. Contract 1.0.0 belongs to commit-the-contract-and-the-command-line. The first real run is not a task here: it is the first release after 1.0.0's archival.

Settled by the contributor. The accounts exist: on 2026-10-18 the contributor had Firefly-Projects/htmlspec created, empty, with ruleset 25362895 requiring a pull request into main, and Firefly-Projects/homebrew-tap, empty; stored CARGO_REGISTRY_TOKEN and HOMEBREW_TAP_TOKEN; granted crates.io access to the organization; and named firefly-developers as the crates' co-owner. On 2026-10-19 the contributor turned on GitHub's "Keep my email addresses private", so a merge in the public repository records a noreply address.

Requirements. This change adds, modifies, and removes no accepted requirement. A runbook's requirements are what it requires of a run, as runbook-authority's "A runbook records what its history taught" states, and runbook-execution's "A run leaves a record where the runbook keeps them" already gives each publication its record. The contract is silent on how a release is published, and this change keeps it so: the procedure is the runbook's.

The release. 0.34.0, a minor increment, my choice under project-bootstrap's "Archival requires the project version to advance", which leaves the size to judgment: the project gains a procedure, and the program is unchanged.
