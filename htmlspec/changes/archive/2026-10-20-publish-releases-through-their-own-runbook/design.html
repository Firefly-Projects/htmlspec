Subject
Publish releases through their own runbook: design

What this settles

The code review of #63 found five problems in where the plan put the publishing steps. This design moves those steps into a runbook of their own and fixes each problem in a named step or requirement. It depends on two things publish-a-public-tree builds: the export's private review, and a pre-push guard that refuses any push from this repository to the public one. It also depends on what ship-through-four-channels builds: the release workflow and scripts/publish-crates. The FOLLOWS chain archives both first.

Decisions

1. Two runbooks: release prepares, publish publishes

The release runbook keeps the four steps that run inside a release's change, as its tasks: the version, the instruction files, the changelog entry, and the release check. A new runbook, publish, holds the steps that can only run after that change is archived and merged. Each release is published by one run of it: htmlspec run publish --as vX.Y.Z.

The review reproduced the failure of one runbook for both: a run after archival copies every step, so its record opened with four steps already done and a requirement, raising spec.nix at archival, that cannot be met after archival. runbook-execution's "A record carries the procedure it ran and the obligations it attests to" makes a record copy the whole procedure, so a procedure whose steps happen at two times needs two runbooks.

runbook-authority's "A project keeps its procedures in a fourth place" identifies a runbook by its directory, so publish sits beside release in htmlspec/runbooks/, and "A runbook is two documents of existing kinds" gives it a specification and a tasks document.

2. The publish runbook's nine steps

The steps, in the order the run takes them. SOURCE is the private commit being published, MERGE the public commit that merged it, and vX.Y.Z the release's version.

  1. Start from the archived release. The release's change is archived and merged into this repository's main. Record SOURCE, the output of git rev-parse origin/main, and confirm that its archive's VERSION is the version being published.
  2. Review the exact export privately. publish/export --ref SOURCE, the export's local review, builds the export commit in a scratch repository, keeps it, changes nothing public, and prints TREE, the exported tree's id, with the command that shows exactly what the pull request would show. Read that diff. Where the export refuses files changed since their read, read what it names. Where publish/READINESS.md at SOURCE carries no sign-off, the contributor gives it. Either lands through a pull request into this repository's main, and the run takes step 1 again, because the export reads the readiness record at SOURCE. publish/ never crosses, so that commit leaves TREE as it was. On the first run the public repository is empty, so this review shows the bootstrap commit alone.
  3. First run only: bootstrap the public repository. gh api -X PUT repos/Firefly-Projects/htmlspec/rulesets/25362895 -f enforcement=disabled, then publish/export --ref SOURCE --bootstrap --reviewed TREE with step 2's tree, then gh api -X PUT repos/Firefly-Projects/htmlspec/rulesets/25362895 -f enforcement=active, and gh api repos/Firefly-Projects/htmlspec/rulesets/25362895 --jq .enforcement must print active.
  4. Push the export and merge it. On the first run, review again first: publish/export --ref SOURCE now builds the whole export on the bootstrapped main, so read its diff and take its TREE. On a later run step 2's tree is this one. publish/export --ref SOURCE --push --reviewed TREE opens a pull request on Firefly-Projects/htmlspec. Merge it as a squash, and record MERGE, the commit it made: gh pr view NUMBER --repo Firefly-Projects/htmlspec --json mergeCommit --jq .mergeCommit.oid.
  5. Tag the public merge commit through the API. gh api repos/Firefly-Projects/htmlspec/git/refs -f ref=refs/tags/vX.Y.Z -f sha=MERGE. Then gh run list --repo Firefly-Projects/htmlspec --workflow release.yml must show a run for the tag within a few minutes. No tag is pushed from this repository, and a private tag, where a contributor wants one, is named private/vX.Y.Z.
  6. Watch the release workflow to its end. If the crates job stops partway, run the job again: scripts/publish-crates skips what exists and waits out the rate limit.
  7. First release only: add the co-owner. Signed in to crates.io as smurphy8, run cargo owner --add github:Firefly-Projects:firefly-developers CRATE for each of htmlspec-schema, htmlspec-parse, htmlspec-assets, htmlspec-format, htmlspec-validate, and htmlspec-cli.
  8. Check each channel. nix run github:Firefly-Projects/htmlspec/vX.Y.Z -- --version, brew install Firefly-Projects/tap/htmlspec then htmlspec --version, cargo install --locked htmlspec-cli then htmlspec --version, and a binary from the release page. Each prints htmlspec X.Y.Z.
  9. Land the record. Commit the run's record on a branch of this repository and merge it through a pull request. It crosses to the public repository with the next export.

Steps 3 and 7 run on the first release only, and each says so in its own text, so a later run marks them dropped with that reason. The order is forced: the export can only follow archival, the tag can only follow the merge it names, and the co-owner can only follow the first publish.

Amended on 2026-10-20, during implementation, from task 1.1. The steps first named the export's commands differently from the export as built, in four places, and each is changed above. Step 2 said publish/export --ref SOURCE --dry-run. A dry run reports a tree and keeps nothing to read, and the review the export's revision requires is its default local run, which keeps the scratch repository and prints the command that shows the diff. Steps 3 and 4 said --bootstrap and --push alone, and each refuses without --reviewed TREE. Against an empty target the local review builds the bootstrap commit and nothing else, so on the first run the whole export can be read only after the bootstrap, and step 4 opens with that second review. The export also reads the sign-off and the reads from publish/READINESS.md at SOURCE, not from the working tree, so a sign-off or a read given at step 2 reaches it only through a commit on main, and step 2 now says so. Decision 11 makes the export hold a delivery to that: --push and --bootstrap refuse a commit main does not hold. Step 5 now repeats decision 3's name for a private tag, because the step is where a contributor makes one.

3. The public tag is created through the API, and no ref is pushed from this repository

Step 5 creates refs/tags/vX.Y.Z in Firefly-Projects/htmlspec with gh api, on MERGE, a commit that exists only in the public repository. No step runs git push to the public repository from this clone. This repository needs no release tag of its own: the archive's VERSION records the release. Where a contributor wants one anyway, it is named private/vX.Y.Z, so no name is shared.

The review reproduced the leak this prevents: a shared tag name makes the natural recovery from "tag already exists" a push of the private tag, which carries every private commit. With no push in any step, publish-a-public-tree's pre-push guard can refuse every push from this repository to the public one without an exception, and the export, which pushes from its own scratch repository, is unaffected by that guard.

The tag is expected to start the release workflow as a pushed tag does, and that is not confirmed: GitHub's documentation of the refs endpoint does not say whether a ref it creates starts a push workflow, as evidence/the-live-commands-read-2026-10-20.md records. So step 5 checks that a run started rather than assuming it, and the first risk below, that the tag starts no workflow, says what the run does if none did.

4. The first run bootstraps the public repository with the ruleset off for that push alone

Step 3 switches ruleset 25362895 off, runs the export's bootstrap, switches the ruleset back on, and stops unless GitHub reports it active. The bootstrap's first commit holds README.md and LICENSE only, and everything else arrives through step 4's pull request, so the first public tree is reviewed like every later one.

The public repository is empty, and its ruleset already applies to main, so it refuses the bootstrap's direct push. publish-a-public-tree's export, as built, refuses to bootstrap while a ruleset on main is enabled, refuses to push while one is not, and never changes a ruleset itself. So the switch belongs to a person, recorded in a step, and the check after it makes a ruleset left off a stopped run rather than a silent one.

5. The export is reviewed before it is public

Step 2 builds the exact export privately and has a person read it before step 4 pushes it. The mechanism is publish-a-public-tree's: its revision requires a private review of the exact export before --push, and this step is where a run performs it.

The review found that a pull request opened on the public repository is world-readable before anyone reviews it, and that GitHub keeps a pull request's head after its branch is deleted. Review after the push is too late, so the run reviews first.

6. A run's record stays out of the export until the run ends

The record htmlspec run publish writes is a new file beneath htmlspec/runbooks/publish/runs/, untracked until step 9 commits it. The export reads a committed ref, SOURCE, and publish-a-public-tree's revision defines a dirty tree as one with tracked changes, so the untracked record does not stop it.

The review found that "dirty working tree" had no definition, and that a run's own record could trip it at the export step. The definition is publish-a-public-tree's to make, and this design depends on the one its revision states. If that definition counts untracked files, step 9 moves before step 2: the record is committed first, and SOURCE is taken after it.

Confirmed on 2026-10-20, from task 1.1. The export's usage text defines a dirty tree as one where a tracked file differs from HEAD, staged or not, and says an untracked file does not count. It checks with git status --porcelain --untracked-files=no, and its test test_an_untracked_file_does_not_make_the_tree_dirty holds it there. Step 9 stays last.

7. What the runbook requires of a run

The runbook's specification states six requirements of a run, each with scenarios: a run reaches the public repository only through the export and the API calls its steps name; the public tag names the public merge commit and the version the archive records; the first run leaves the ruleset active; a run publishes only an archived and merged release; each channel's version is recorded; and the toolchain the flake pins is the one the run uses, declared for preflight as the release runbook declares it. gh, git, nix, and brew are inputs stated in prose, as the release runbook states python3.

runbook-authority's "A runbook records what its history taught" asks for the hazards a procedure has met as requirements, and the first three are the review's findings. runbook-portability's "Machine requirements are explicit and mechanically checkable" admits a tool check only at an exact version, which suits none of the four prose inputs, so they stay prose.

8. Release 0.34.0, with the publish runbook at 0.1.0

A minor increment, from 0.33.0, made with scripts/set-version 0.34.0 as the release runbook's 0.3.0 says. Archival publishes the new runbook at 0.1.0. The release runbook is not changed by this change.

project-bootstrap's "Archival checks the versions of runbooks it publishes" requires a version greater than 0.0.0 for a runbook's first publication, and 0.1.0 matches the release runbook's own first.

9. The release workflow's macOS jobs run in the public repository, and elsewhere only on a labelled pull request

Decided by the contributor on 2026-10-20, after this change was planned: I think both these changes sound good, in answer to running the release workflow's macOS jobs only in Firefly-Projects/htmlspec, and on a pull request in this repository only when it carries the label release-check. The macOS jobs are the two macOS builds and the formula job. In this repository a pull request without the label builds the two Linux targets alone. In the public repository a pull request runs the four builds, sums, and formula, and a version tag runs every job.

As built, the verify job decides once, from github.repository and the pull request's labels, and writes the build matrix from python3 scripts/release_facts.py matrix, all four targets or the two musl targets with --without-macos, so the build job has no macOS entry to skip. sums expects as many tarballs as the matrix built. formula runs only where the macOS tarballs were built. release keeps its condition, which holds no status function, so GitHub runs it only when sums, formula, and suite all succeeded, and its first step refuses a SHA256SUMS that lacks any of the four targets. Nothing publishes on a public tag unless all four builds, the formula, and the suite passed. labeled joins the pull request's events, so adding the label runs the macOS jobs at once. A run started by any other label runs what a push runs, in the pull request's one concurrency group.

Amended on 2026-10-20, from the code review, task 5.1. A run started by another label first skipped every job, in a concurrency group of its own, so that it would not cancel the run in progress. The review found what that did instead. A pull request's checks report the newest run of each check by name, so the skipped run's checks replaced an earlier run's, and a verify, sums, or formula that had failed then read as skipped, which a merge gated on the checks reads as passing. Every label now starts the same jobs a push does, and a label other than release-check costs one run of the Linux jobs. The label itself is a write to GitHub, so this change does not create it: task 1.5 is the contributor's.

In a private repository a macOS minute costs as much as ten Linux minutes. Building on macOS proves nothing in this repository that the public repository's runs do not prove before anything publishes, except on a pull request that changes the builds, and that pull request is where a contributor adds the label.

The matrix comes from scripts/release_facts.py rather than from an expression in the workflow. That file already states the four targets once for every script, and the matrix written out in the workflow was the one copy it could not compare. A matrix job cannot test its own entry in a job-level condition, and two build jobs, one per platform, would have repeated every step of the build. This decision changes what ship-through-four-channels built, which this change's proposal placed outside its scope. It is taken here because the contributor decided it while this change was the next to be built.

10. A read names the content it read, so it survives the squash merge that lands it

Each row of publish/READINESS.md's read table names the content the person read, the id git rev-parse COMMIT:PATH prints for it, a tree for a directory and a blob for a file, where it named the commit the read was made at. The export compares that id with the path's content at SOURCE. Where they differ it lists every file added or changed between the two and refuses, naming the content to record once a person has read them. A row that still names a commit is refused with the command that converts it, and a row naming content this repository does not hold is refused naming the content to record. The rows recorded at 99c0fe4 were converted to the content each one covered there, which reads nothing again.

A read recorded on a branch named a commit that the branch's squash merge leaves out of main's history, so the export refused every path. That happened at publish-a-public-tree's merge, #64, and again at ship-through-four-channels', #67. Step 2 lands its reads through a pull request, which is squash-merged too, so with commit ids no run could ever export. Content keeps its id on every branch and through every merge, and a read covers content, not history. The test test_a_read_survives_the_squash_merge_that_lands_it records a read on a branch, squash-merges it, deletes the branch, and removes its commits. The export as it was refused that read with a commit this repository does not hold, and it now passes.

The alternative was a step after each merge that records every read again at the squash commit, with a check that it was done. It costs every release a second pull request, and a person reading nothing new to satisfy a check. This decision changes publish-a-public-tree's export, which this change's proposal placed outside its scope. It is taken here because step 2 cannot work without it.

11. The export names every file it refuses, delivers only what main holds, and the hook knows the public repository under any spelling

Added on 2026-10-20 from the code review, task 5.1, which found three ways past what the publishing tooling claims, and reproduced each one.

  • Every file changed since its read is named. The export's refusal named the first twenty files and then and N more, while the content it said to record covered every one. Recording that content let the files it never named cross unread. It now names each file, one to a line. test_every_file_changed_since_its_read_is_named_however_many adds twenty-six files and looks for each name.
  • A delivery exports only a commit main holds. The export reads the sign-off from publish/READINESS.md at the ref it exports, and any commit can carry a signed record. The review delivered the rehearsal's throwaway commit, which no branch holds and whose record is signed as a rehearsal's, to a local target. --push and --bootstrap now refuse unless refs/remotes/origin/main holds the commit, read as the last git fetch left it, with nothing fetched. A dry run and a local review are unchanged, because they publish nothing. test_a_delivery_exports_only_a_commit_main_holds sees a branch's commit refused for both, then delivered once main holds it, and test_a_delivery_with_no_record_of_main_is_refused sees a clone with no origin/main refused.
  • The hook compares the repository, not the spelling. .githooks/pre-push matched seven exact spellings of the public repository's address, and the review, running the hook on three more, saw it let each through: one with a user in the address, one with the port of ssh.github.com, and one with a slash after the scp form's colon. It now reduces an address to the owner and name it names, lower-cased and percent-decoded, without its scheme, user, host, port, .git, and stray slashes, and refuses firefly-projects/htmlspec on any host. The tests give it seventeen spellings, an ssh Host alias among them, and see this repository's own address, a lookalike name, and two local paths pass.

The export has no exemption for its tests. They meet the delivery's check as a real run does: each commit a test fixture makes on main moves the fixture's refs/remotes/origin/main, as a merged pull request and a fetch do, and a commit on another branch leaves it behind. An exemption keyed to a local target, the alternative the review offered, would have left the refusal itself untested, and a switch in the environment is one a real run can carry by accident.

The hook ignores the host because a host is not where the danger is. An ssh Host alias names github.com by another word, and no host holds a copy of the public repository that this checkout may push to. A local path, and a file:// address, name nothing beyond this machine, and pass.

Risks

A tag made through the API does not start the release workflow

If GitHub does not treat the created ref as a push, no release runs, and the tag sits on the public repository with nothing published.

Held down by step 5, which requires a run for the tag to appear and stops the run otherwise. The stopped run is recorded, and a person decides between deleting and recreating the tag and starting the workflow by hand. The first release is where this is first seen.

The tap token expires

HOMEBREW_TAP_TOKEN expires around 2027-01-16, and a release after that date fails at the tap job after the crates are published.

Accepted. The runbook's inputs name the expiry, and a failed tap job is rerun after the token is renewed, because the formula is rendered from the release that already exists.

The first run is the first time the public steps run

Steps 3 to 8 touch live services, and none of them can run before the first release.

Partly held down. The tasks rehearse steps 1, 2, and 4 against a local target with publish-a-public-tree's tooling, and print the exact commands of steps 3, 5, and 7 for a reading. What stays unproven is the live calls themselves, and the first run watches each one.
