Ship the crates' notices and runbook affordances

What this change established. The binary carries the notices of the Rust crates it is built from, in every channel that ships it, and the suite fails when they fall behind. A runbook is created in one command, a document can be moved onto the store's current assets on request, and the runbooks a project holds are listed with their versions and titles. A preflight declaration can say where to get what a check needs, and every report shows a declaration's text with its hidden characters named. An export reaches GitHub as the account gh is signed in as, and a walk from above a project passes over its evidence.

toolchain-packaging

The program is distributable as a standalone artifact req-the-program-is-distributable-as-a-standalone-artifact

The toolchain SHALL be packageable as an executable artifact that runs without a source checkout and without the packaging tool present at runtime.

Every binary artifact SHALL carry, beside the program, the notices of everything compiled into it: LICENSE for the program itself, THIRD-PARTY-LICENSES for the libraries it embeds, and CRATE-LICENSES for the Rust crates it is built from. CRATE-LICENSES SHALL credit each crate the binary is compiled from for the release targets, procedural macros included, and each crate the workspace's own code generation depends on, and SHALL NOT credit a third-party crate's build or development dependencies. Under OR it SHALL credit the alternative whose least-preferred license comes earliest in the accepted order, MIT, Apache-2.0, BSD-3-Clause, BSD-2-Clause, ISC, Zlib, Unicode-3.0, MIT-0, Unlicense, MPL-2.0, and under AND every part, and a license WITH an exception SHALL be credited as that license. An expression leaving no accepted license SHALL stop the notices. Each text SHALL come from a file the crate ships whose name states its license, or from a reviewed row naming a file the crate ships or a standard text vendored with the program, and never from a path outside either. A crate whose expression names Apache-2.0 SHALL have its NOTICE files reproduced, and an MPL-2.0 crate SHALL say where its source form is.

A release reaches every channel from one tag req-a-release-reaches-every-channel-from-one-tag

Every release SHALL be cut from one tag, vX.Y.Z, whose version equals the version the workspace declares, and the binaries, the crates, and the Homebrew formula the release produces SHALL each name that version. The release SHALL refuse a tag that names another version before it builds anything.

Publication SHALL begin only from a version tag in the public repository, Firefly-Projects/htmlspec, only for a commit that repository's main holds, and only after the check suite has passed on that commit. A tag in any other repository SHALL publish nothing. A release SHALL publish only from a run in which the binary of every target it releases was built and the formula passed its check, though runs elsewhere leave some of those jobs out.

A publication interrupted partway SHALL finish when run again, and SHALL NOT publish any version twice: the crates publish one at a time, a version the registry already holds is skipped, and a rate limit is waited out within a stated budget, after which the run stops and names the crates that remain. Every request the release makes to crates.io SHALL carry a fixed User-Agent that names the project, and no personal information.

Each channel that ships the binary SHALL ship its notices with it: each release tarball holds them beside the program, the Homebrew formula installs them, and the Nix package installs them under share/doc/htmlspec/. The formula SHALL declare exactly the licenses the binary credits. The check suite SHALL fail when CRATE-LICENSES differs from what the lockfile reaches, naming each crate added, removed, or changed, and when the formula's template declares other licenses than the binary credits, so a pull request that changes either meets it, on Linux as well as where the macOS jobs run.

The command surface names its operations as OpenSpec names them req-a-single-command-exposes-validate-format-and-init

The project SHALL provide one command-line program offering, at minimum, a subcommand to validate documents, a subcommand to format documents, a subcommand to bootstrap a project, and a subcommand to create documents. Each subcommand SHALL be usable without configuration in a conforming project.

Where an operation corresponds to one OpenSpec provides, it SHALL carry OpenSpec's name for it. This holds for the subcommand and for the options that select what it acts on. Every plausible adopter arrives from OpenSpec — HTMLSpec is a spinoff and its README says so — and a contributor who has learned one surface SHALL NOT have to learn a second spelling for the same operation. An operation OpenSpec does not provide takes the name this project chooses for it.

The spellings are therefore fixed rather than left to an implementer: validate, archive, init, new, list, status, sync, show, instructions, and store name the operations OpenSpec also provides. format and assets name operations it does not. The selectors --json, --specs, --change, --store, and --diff carry OpenSpec's spellings for the same reason.

Fixing a spelling in the contract is not decoration. A requirement that describes an operation by role alone — an operation that enumerates a project's active changes — is satisfied by a subcommand called changes, or ls, and the instructions written against it would then name a command that does not exist. The workflow instructions this project installs invoke these commands by name, so the name is part of the contract they depend on.

Each operation SHALL also answer to a request-verb spelling, which says what the operation does to the files it acts on. The verb is one of htmx's five request keywords without their hx- prefix, get, post, put, patch, and delete, and it carries the meaning HTTP gives it: get for an operation that never writes, post for one that creates something that was not there, put for one that creates or replaces a whole thing and leaves it as one run did when run again, patch for one that changes something that exists, and delete for one that removes something. The verb is followed by the operation's object. These spellings are fixed as the OpenSpec spellings are: get validity, get list, get status, get sync, get show, get assets, get preflight, get instructions, get registrations, and get survey; post change, post document, post runbook, post registration, post run, and post promotion; put project and put format; patch archive; and delete registration. The verb names the most the operation writes in any invocation, so get spells only an operation that never writes, and an operation that writes only with an option takes the verb of that write. An option keeps its meaning under both spellings: put format --check writes nothing, as format --check does.

Verb Meaning Spellings
get for an operation that never writes get validity, get list, get status, get sync, get show, get assets, get preflight, get instructions, get registrations, and get survey
post for one that creates something that was not there post change, post document, post runbook, post registration, post run, and post promotion
put for one that creates or replaces a whole thing and leaves it as one run did when run again put project and put format
patch for one that changes something that exists patch archive
delete for one that removes something delete registration

A request-verb spelling SHALL be a second spelling of an operation and never its replacement. It SHALL run the operation its OpenSpec spelling runs, with the same arguments and options, and SHALL produce the same output and exit status. The OpenSpec spellings stay the ones this requirement fixes above, and the program's own messages and the workflow instructions it installs SHALL name them, so a contributor who arrives from OpenSpec still has one spelling to learn. A name says what an operation is about, and a verb says whether it can change the tree, which the names do not say and which differs between the two tools for two of them: OpenSpec's sync and archive write the accepted specifications, and this program's sync and archive never do. The verbs are vocabulary only. No operation sends a request, and none needs a server or a network.

The bootstrap subcommand's subject SHALL be a project and it SHALL require no arguments, because the operation a contributor needs first is the one that establishes the project they are standing in. The creation subcommand's subject SHALL be a document or, a change, or a runbook.

These SHALL be distinct subcommands. One subcommand meaning both "establish this project" and "write this file" would leave a contributor unable to ask for either without also specifying which they meant.

Creation SHALL take the artifact kind of the document to create, and SHALL produce a document already shaped for that kind. A proposal SHALL be initialized as a page of prose with no unit scaffolding at all, and a specification SHALL be initialized with the units its kind expects.

The asymmetry is the requirement. A proposal that arrived full of empty requirement scaffolding would push its author toward stating a contract at the stage meant for arguing about one, and the emptiest possible starting point is the correct one for a document whose structure is the author's to choose.

Creation SHALL be able to create a whole change — the directory and its documents — rather than one document at a time, because a change is a directory of kinded documents. A change created in a project SHALL be placed where that project keeps its active changes, and the resolved location SHALL be reported.

Documents SHALL be created referencing the project's asset store rather than establishing one of their own.

The command surface checks a runbook's machine prerequisites req-the-command-surface-checks-a-runbook-s-machine-prerequisites

The command htmlspec preflight <runbook> SHALL report whether the selected runbook can start in the invocation's working environment. It SHALL support the existing --store and --json selectors. Store selection SHALL locate the runbook and its records, while machine requirements SHALL be evaluated against the invocation's working directory and environment, not the store's directory. Names SHALL follow the existing runbook-name rules.

The report SHALL identify the runbook, carried version, source location, working directory, aggregate readiness, and each checked requirement with its expected condition, observation, outcome, and remedy for a refusal. Results SHALL follow document order. Human output SHALL lead with readiness. JSON output SHALL contain one structured report with no probe output interleaved.

Where a check's declaration carries a remedy, the JSON report SHALL carry it as runbookRemedy on that check whatever its outcome, and the human report SHALL show it, labelled as the runbook's words, after the program's own remedy for a check whose outcome is unmet, unavailable, timed-out, or probe-failed, and never for one that passed. A declaration's field name, tool name, and path SHALL reach a report with each character a terminal would not show as itself named by its code point, and the probe SHALL use them as written. The help of preflight and run SHALL point to the operation that lists the project's runbooks.

A completed preflight with unmet requirements SHALL exit 1, a successful one SHALL exit 0, an invalid invocation, invalid contract, or operational failure SHALL exit 2, and cancellation SHALL exit 3. Unknown observations such as an unavailable manifest environment or a timed-out probe SHALL be reported as unmet readiness rather than as success. An invalid declaration SHALL remain distinguishable from a valid check whose condition is false.

htmlspec run <runbook> --as <record> SHALL apply the same checks and exit distinctions before creating a run. htmlspec run <runbook> --check SHALL continue to report existing run conformance without checking the present machine. Existing JSON fields on successful run creation SHALL be preserved, with version and preflight information added.

The public repository receives only reviewed exports of the private one req-the-public-repository-receives-only-reviewed-exports

The project's public repository SHALL receive only trees exported from its private working repository. Each tree SHALL come from a committed ref of the private repository, through the allowlist of paths that may cross, with every rewrite applied at the count it expects, found clean by the scan against the private pattern file, passed by the project's full suite run inside the exported tree, and reviewed by a person as the exact tree that is pushed.

A tree SHALL reach the public repository only from a commit the private repository's main holds, so that the reads of its paths and the contributor's sign-off it is delivered under are ones a reviewed pull request landed. A read SHALL name the content it covers, so that it survives the squash merge that lands it, and every file under an allowlisted path whose content differs from the content its read names, added or changed since, SHALL be refused, each one named.

Each export SHALL arrive in a commit whose only parent is the public repository's own main, or with no parent for the first commit of an empty public repository, made by a GitHub noreply identity as author and committer, and naming its source ref and commit. No commit of the private repository's history SHALL reach the public repository, and the private repository SHALL refuse any push of its own to the public one, tags included, under any spelling of the public repository's address.

An export's commit subject, which is also its pull request's title, SHALL name the version the exported ref declares and the commit's first twelve characters, and SHALL pass the title rules the ref itself states, the ones the public repository's guard runs from the exported tree, before anything is exported. A ref that states no such rules SHALL be refused. The first commit of an empty public repository opens no pull request and carries a fixed subject, so it needs neither.

Every git command the export runs against a GitHub target, a review's included, SHALL reach it over HTTPS with git's credential helper for https://github.com set to gh auth git-credential for that command alone, after any the environment carries, and without prompting for a password. A delivery to a GitHub target SHALL refuse, before it reaches the target, when the addresses git would fetch from or push to, after the machine's rewrites, are not that target on https://github.com, and when gh names no account. It SHALL name the account it pushes as before it reads the target, and SHALL refuse the push when that account has changed since.

The publishing tooling, its allowlist, rewrites, pattern file, and tests, SHALL stay in the private repository and SHALL be absent from every export, because its tables name the material they guard against.

An operation over a directory collects documents and not a change's evidence req-an-operation-over-a-directory-collects-documents-and-not-a-change-s-evidence

When validate or format, in either its writing or its checking mode, is given a directory or no path at all, it SHALL operate on every .html file beneath that directory, except files beneath a change's evidence as artifact-kinds' "A change's evidence is kept in the change and is not one of its documents" places it. Every other operation that collects a project's documents by walking a directory SHALL make the same exclusion from the same definition.

A path the contributor names SHALL be checked as named. A file means that file. A directory that is itself a change's evidence directory, or lies beneath one, means that directory, and validate and format --check SHALL check every .html file beneath it. The exclusion applies to what a walk comes across and never to what a contributor asked for. A contributor who wants to know whether a record still conforms can ask, and the answer is the ordinary one.

Checking is not writing. format in its writing mode SHALL NOT write a file beneath a change's evidence, including one a contributor names, because artifact-kinds states that no operation rewrites one. Given such a path, it SHALL name each record, write nothing at all, and exit with the status for an operation that could not run. It SHALL NOT write the other documents and skip the records. A partial write would report success for a request it half ignored.

Where the walked directory is not within a project, no directory is a change's evidence, and every .html file beneath it SHALL be operated on. A conformance fixture and a loose directory of documents keep the behavior they have.

Which project a directory belongs to SHALL be decided for each directory the walk enters, as resolving from that directory would decide it, and never once from the walk's root. A walk from a directory above a project, or through a link to one, SHALL pass over that project's changes' evidence exactly as a walk from inside it does.

The exclusion SHALL be defined once and reached by every such operation. It SHALL NOT be restated per command. A second definition that drifts from the first would have validate and format disagree about which files are documents. That is the fault this requirement exists to remove, arriving by another route.

document-template

A project can be initialized with a conforming document req-a-project-can-be-initialized-with-a-conforming-document

The project SHALL provide a way to create a new document that already conforms to the element contract, the visual system, and the runtime conventions, without hand-assembly.

It SHALL also provide a way to create a new runbook without hand-assembly: a specification, a tasks document, a VERSION at 0.1.0, and a changelog heading for that version, where the project the working directory belongs to keeps its runbooks. The runbook SHALL validate at once, report ready with no machine checks, and start a run, and its documents SHALL take the subject a contributor gives, or the name where none is given. Its name SHALL be a plain directory name the project's layout leaves free: no path, no .., no character a terminal would not show as itself, no leading dot, and none of the names the layout already uses. A name refused, or a runbook that would not validate, SHALL leave nothing written.

Initialization SHALL write asset references that match the bytes it stores. It SHALL NOT copy a runtime asset that the project already stores, and SHALL NOT produce a document whose references and stored bytes disagree.

Initialization SHALL decide which project a new document belongs to from the location of the document it creates, never from the directory it runs in. A document created beneath a project's own directory, htmlspec/, SHALL reference that project's store, and establish it there if it is absent. deterministic-formatting

Formatting preserves meaning req-formatting-preserves-meaning

Formatting SHALL NOT change a document's semantic content. It SHALL preserve every semantic unit, every identifier, every attribute value, every cross-reference, and the document order of content. It SHALL NOT add, remove, or reorder semantic units.

One kind of attribute value is excepted. Where an asset reference names bytes the project's store does not hold, formatting SHALL fill it with the address of the bytes the toolchain ships. A reference that names bytes the store holds SHALL be left as written, even when the store also holds a newer revision, because the reference records what the document was authored against.

An asset reference SHALL be the value of an attribute through which an element loads an asset. These are the same attributes that document-validation's "An asset reference must match the bytes it names" judges, so the formatter and the validator SHALL NOT disagree about which values are references. A hyperlink is a citation, not something the document loads, and SHALL NOT be filled. Text SHALL NOT be read as an asset reference. Prose that quotes one, whether as characters in a code element or escaped in an example, is content, and formatting SHALL leave it as the author wrote it.

A second exception is made only on a contributor's request. Where the request is made, formatting SHALL add the fallback stylesheet that "A document stays readable when its stylesheet cannot load" describes to a document that lacks one, SHALL replace a fallback whose text differs from the current one, and SHALL change nothing else. It SHALL NOT do so for a document of an archived change or a run's record, which are history, judged by the project the document resolves into wherever formatting is run from, whether reached directly or through a symbolic link. Without the request, formatting SHALL leave a document's fallback present, absent, or stale as written.

A third exception is made only on a contributor's request as well. Where the request is made, formatting SHALL rewrite each asset reference a document carries to the store location of the bytes the toolchain ships for the same asset, SHALL write those bytes into the store where it lacks them, from the copy the toolchain carries, and SHALL make no network request. It SHALL add no reference the document does not already carry. It SHALL leave as written a reference to an asset the toolchain ships no revision of, one whose stored bytes disagree with its address, and one the store holds other bytes for at the current revision's address, and SHALL say how to restore that file. It SHALL NOT rewrite a document of an archived change or a run's record, judged as the second exception judges them. Checking with the request SHALL name each document it would rewrite and write nothing, and SHALL succeed where it would write nothing, blocked references included.

runbook-authority

The canonical procedure carries no completion state req-the-canonical-procedure-carries-no-completion-state

A runbook's tasks document SHALL carry its steps in the state they have before anyone works them, and that state SHALL NOT advance as a consequence of the runbook being run. The states advance in the copy a run makes, exactly as they advance in a change.

Nothing SHALL report a runbook whose steps are all unstarted. That is the correct state of a canonical procedure at every moment, so a report of it would fire on every runbook always, which teaches a reader to ignore the report.

An enumeration of a project's runbooks SHALL NOT present a completion fraction for the canonical procedure. The fraction is derivable and it is the same value forever, and a column that never moves is read once and then not read.

A unit in a runbook's canonical documents SHALL declare that it is unchanged. A change state describes a unit's relationship to a change in progress, and a runbook has none: its procedure exists and the hazards it records were measured before the document was written. This is the same fact as the preceding paragraphs rather than a second rule, arriving at a different attribute.

A unit in the record of a run SHALL declare that it is unchanged for the same reason, and this is that sentence reaching the one other document a runbook holds rather than a new obligation. A run's record carries the requirements it verifies, copied from the runbook, and a verification recording an outcome against a requirement declared added is reported — correctly — as attesting to an obligation that is not there yet. The obligation a run attests to existed before the run started, so the copy declares itself unchanged.

The consequence is what makes it worth stating. A verification that records an outcome against a requirement declared as added is reported, correctly, as attesting to an obligation that is not there yet — so a runbook whose units are declared the way a change's units are declared reports warnings whose cause is one attribute, and nothing states which. The operation that creates a document SHALL NOT be expected to know the difference, because it cannot: whether a document belongs to a change or to a runbook is not a fact about the document being written.

The operation that starts a run is the exception, and it SHALL declare the state correctly. It knows what it is writing — a copy of an existing procedure, attesting to obligations that already exist — so the reason the general document-creating operation cannot know does not apply to it. This narrows the preceding paragraph rather than contradicting it: an author writing a run record by hand still meets the warnings, and so does an author writing a runbook by hand.

The operation that creates a runbook is a second exception, and it SHALL declare the state correctly too. Every unit of the documents it writes SHALL declare that it is unchanged, and every step SHALL be unstarted. It knows what it is writing, a runbook's canonical procedure, as the operation that starts a run knows it is writing a copy of one.

runbook-portability

Machine requirements are explicit and mechanically checkable req-machine-requirements-are-explicit-and-mechanically-checkable

A runbook SHALL state machine prerequisites as ordinary requirement units in its specification, with stable identifiers, normative statements, scenarios, and an explicit check declaration. Preflight SHALL read these declarations from the existing projected requirement notes. It SHALL NOT infer checks from prose, requirement names, or executable examples. The declaration format SHALL be documented and restricted to built-in checks; arbitrary commands SHALL NOT be accepted.

The supported needs SHALL include a tool at a stated version, a tool supplied by a pinned package-manager environment, an installed agent skill, and a working-directory state. Machine requirements SHALL remain part of the logging contract: passing preflight does not remove their obligation to have an outcome recorded. Ordinary requirements without a check declaration SHALL remain logging obligations without becoming machine checks.

Malformed declarations, unknown check kinds, duplicate declarations on one requirement, and unsupported format versions SHALL be reported against the requirement and SHALL prevent starting a run. A contract with no machine declarations SHALL report zero checks, without claiming to have established unstated prerequisites.

A second declaration format, preflight/v2, SHALL read every form preflight/v1 reads and one optional field, remedy: text saying where to get what the check needs. A remedy SHALL be one line of 1 to 200 characters once the spaces around it are trimmed, holding no control character, no whitespace but the plain space, and no invisible character, Unicode's format and default-ignorable characters, beyond the two joiners and one emoji presentation selector directly after the character it is for. A remedy breaking any of these SHALL make the declaration malformed. A remedy is text: preflight SHALL NOT run it, open an address in it, or count it as satisfying the check. preflight/v1 SHALL keep refusing the field, and an unsupported format version SHALL be reported naming the formats the program reads.
