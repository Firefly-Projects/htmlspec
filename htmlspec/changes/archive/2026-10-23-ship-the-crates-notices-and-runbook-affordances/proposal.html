Ship the crates' notices and runbook affordances (1.1.0)

Ship 1.1.0 as one change with four workstreams. Every binary channel carries the notices of the Rust crates the binary is built from. Runbooks get a template, a way onto the current runtime, and a listing that is easy to find, and preflight can show where to get what is missing. The release also adds a lowercase -v alias, and the export pushes with gh's credentials.

Subject
Ship the crates' notices and runbook affordances (1.1.0)

Why

1.0.0 is public, and the first public run exposed four things a minor release can fix. The user decided they ship together, as one version, 1.1.0. project-bootstrap's "Archival requires the project version to advance" allows one archive per version, so they are one change with four workstreams.

  1. The released binary leaves out the notices of the Rust crates linked into it. Each tarball ships LICENSE and THIRD-PARTY-LICENSES, and that file covers only the four JavaScript libraries crates/htmlspec-assets embeds. The static binary is also built from 170 Rust crates on the four release targets: 158 it links, procedural macros included, and 12 whose generated code the workspace's build scripts compile into it. They carry MIT, Apache-2.0, Unicode-3.0, MPL-2.0, BSD-2-Clause, Zlib, MIT-0, and Unlicense terms. Most of those licenses ask that their notice travel with a binary copy. The tarballs, the Homebrew formula, and the Nix package each distribute that binary, and the Nix package ships no license file at all.
  2. Runbooks have the vocabulary specifications have, and nothing helps an author use it. A runbook document already accepts a Mermaid or Vega-Lite figure and MathML: a copy of this repository's publish runbook with both added validates with no diagnostics. What a runbook lacks is a way in. htmlspec new creates a proposal, a design, a tasks document, a specification, or a change, and no runbook, so an author assembles one by hand from two templates that show neither a procedure nor a figure. Its documents also stay on whatever runtime they were written with: this repository's release runbook still references an older stylesheet, one that styles neither a partial outcome nor a change's inserted and deleted words, because nothing moves a document onto the store's current one. And the runbooks are hard to find: htmlspec run with no runbook says only that an argument is missing, and list --runbooks shows names and documents but no version or title.
  3. A refused preflight cannot say where to get what is missing. A colleague carried one of the user's runbooks to another machine, and the run correctly refused to start without its skills and tools. Preflight names the missing skill, but the runbook has no way to say which repository holds it or which command installs it, so the person running it had to ask. runbook-portability's "A carried runbook does not require its source project's history" requires tools and skills from the receiving machine, and that stays. What is missing is the hint.
  4. Two small things the first run and its users hit. A colleague typed htmlspec -v, which is refused: the flag is --version or -V. And publish/export pushes over plain HTTPS git, which on the contributor's machine had no GitHub credentials, so the v1.0.0 run needed a hand-set credential helper. The archived change 2026-10-20-finish-a-publish-run-without-a-hand-fix recorded that as an open question.

What changes

License notices for the linked crates

A committed, generated file names every Rust crate the binary is built from on the four release targets, with the license text the crate ships, or a reviewed substitute where it ships none. Every channel that distributes the binary carries it beside LICENSE and THIRD-PARTY-LICENSES: the tarballs, the formula's install, and the Nix package. The formula declares the licenses the binary credits. A suite stage regenerates it and fails when the lockfile reaches a crate the file does not credit, or a license the project has not accepted.

Runbooks get a way in

htmlspec new runbook <name> creates a runbook that validates immediately: a specification with a requirement and its scenario, a tasks document whose steps sit beside a figure of their order, its VERSION, and a CHANGELOG.md heading. htmlspec format --upgrade-assets rewrites a document's references to the store's current assets, as --fallback adds the current fallback, and leaves archived changes and run records as written. Despite its name it downloads nothing: the bytes come from the copy the binary embeds. This repository's release runbook moves onto the current stylesheet with it, at a new runbook version. htmlspec run with no runbook lists the project's runbooks and how to start one, list --runbooks shows each one's version and title, and run --help and preflight --help point to it.

Install hints in preflight

A machine requirement can carry a remedy: one line of text the runbook's author writes, naming a repository, a command, or an address. Preflight shows it beside its own remedy when the check is refused, in the human report and in --json. It is text and nothing else. Preflight never runs it, and it never satisfies a check.

Two small additions

htmlspec -v prints the version, as -V and --version do. publish/export authenticates its HTTPS push to a GitHub target with gh's credentials, and prints the account gh is signed in as before it pushes.

What working looks like

  1. Someone unpacks htmlspec-1.1.0-aarch64-apple-darwin.tar.gz and finds LICENSE, THIRD-PARTY-LICENSES, and CRATE-LICENSES beside the binary. CRATE-LICENSES names clap, serde, html5ever, and every other linked crate with its license text. brew install and nix profile install put the same files on disk.
  2. A contributor adds a dependency and pushes. The suite fails, naming the crate the notices do not cover, until the regenerated file is committed.
  3. An author runs htmlspec new runbook rotate-the-keys, opens htmlspec/runbooks/rotate-the-keys/tasks.html in a browser, and sees steps beside a flowchart of their order, styled as a specification is. Later a colleague types htmlspec run, and it lists rotate-the-keys 0.1.0 with its title and the command that starts it.
  4. A colleague runs htmlspec preflight onboard on a fresh machine. It refuses, names the missing skill, and adds the author's line: the runbook says: clone github.com/example-corp/skills and run ./install.
  5. htmlspec -v prints htmlspec 1.1.0 (…). The next publish run pushes the export with no credential helper set by hand, and its output names the account it pushed as.

Alternatives considered

  • Four changes at 1.1.0, 1.1.1, 1.1.2, and 1.1.3. The user chose one version. Separate changes would each need their own archive and version.
  • Change the version gate so several changes share a version. That's cleaner over time, but it puts a contract change in front of all the real work. Not now.
  • Vendor a runbook's skills beside it. runbook-portability forbids it, and a copy bundled beside the runbook does not satisfy a home-scope skill check. A hint tells a person where to get the skill without moving it.
  • Leave the notices to cargo install users. crates.io ships source, and each dependency's source carries its own license, so a person building from crates.io makes their own distribution. That covers crates.io and no other channel, because the other three ship a built binary.

Scope

  • Not a license audit. The change credits what the binary links and refuses licenses the project has not accepted. It does not change any dependency.
  • Not crates.io. A published crate is source. The notices file ships in htmlspec-cli's crate as an ordinary file, and crates.io's role is unchanged.
  • No new vocabulary. Runbooks already accept figures and math. This change gives authors a template, a way onto the current runtime, and an easier listing, and adds no unit, field, or attribute to the document contract.
  • Preflight still never installs. A remedy is text to show, and the check it accompanies decides readiness as before.
  • No Windows build. A separate change drafts that.
  • No publish run. Publishing 1.1.0 follows archival, as a run of the publish runbook with the user's go at each public step.
