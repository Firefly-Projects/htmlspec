Ship the crates' notices and runbook affordances (1.1.0): design

One change, four workstreams, built in parallel worktrees between an opening pull request that moves the workspace to 1.1.0 and a closing one that reviews, archives, and records the readiness reads. A script credits the 170 crates the binary is built from, and every binary channel ships that list. Runbooks get a template, an asset upgrade, and an easier listing. preflight/v2 adds a remedy that is shown and never run. The release also adds -v, and the export pushes with gh's credentials.

Four workstreams, one version

The work is one change because the user chose one version, and project-bootstrap's "Archival requires the project version to advance" gives each archive its own. It is built as four workstreams in parallel worktrees, and only the release bookkeeping is shared. Two integration steps bracket them. The first moves the workspace to 1.1.0 before any workstream merges, for the reason decision 15 gives. The last settles the review, archives, and then records the readiness reads.

The contract is silent on the points below, which this design decides. Each is recorded as mine under the decision that settles it:

  • which license text a crate under an OR expression is credited with, and which licenses the project accepts (decision 3);

License notices for the linked crates

1. A script reads cargo metadata and writes the notices, rather than cargo-about

scripts/crate-notices is a Python script that uses only the standard library, like scripts/pack-release and scripts/release_facts.py. It runs cargo metadata --locked --format-version 1 --filter-platform TARGET for each of the four release targets in release_facts.TARGETS, reads each credited crate's license files from the source directory the metadata names, and writes crates/htmlspec-cli/CRATE-LICENSES. With --check it writes to a temporary file, compares, and names every crate added, removed, or changed.

cargo-about identifies license texts by similarity, which is its strength. It can also fetch clarifications from a network service, which would have to be switched off for the suite to run in the Nix sandbox. A script costs less than adding a new tool to the pinned shell and the suite. The deciding fact is that every crate whose text is not plainly named must be reviewed, not matched by a guess. A script whose only matching rule is file names sends each such crate to a reviewed table (decision 3), and leaves no crate behind a heuristic. This is my choice under silence, and it is cheap to reverse: the output file and its suite stage stay the same if cargo-about replaces the script later.

2. The notices credit what the binary is built from on the four release targets

The credited set is the union, over the four release targets, of two closures, without the workspace's own crates:

  • htmlspec-cli's normal-dependency closure, procedural-macro crates and their dependencies included;
  • the closure of every workspace crate's own build dependencies, because a workspace build script generates code that is compiled into the binary. htmlspec-schema's build script turns the schema into Rust types with typify, schemars, and prettyplease.

Build dependencies of third-party crates are left out, and so is every development dependency. Measured on this commit with cargo metadata --filter-platform for the four targets, the set holds 170 crates. 158 of them are in the normal closure. The other 12 are reached only through the workspace's build scripts: prettyplease, regress, schemars, schemars_derive, semver, serde_derive_internals, serde_tokenstream, thiserror, thiserror-impl, typify, typify-impl, and typify-macro.

The user decided on 2026-10-22 that code-generating build dependencies are credited. A build script's dependency is not linked, but the code a workspace build script generates with it is compiled into the binary, as a procedural macro's output is. Third-party build scripts mostly probe the compiler, so their dependencies leave nothing of their own in the binary. Filtering by target matters both ways: a Windows-only crate credited in a macOS tarball is noise, and a target-specific crate that is missed is a notice owed and not given. The Windows and WebAssembly crates the lockfile also resolves, r-efi among them, are not in the set.

Noted after the pull request's review, on 2026-10-22. Eight of those 12 put nothing of their own into the binary, because they serve the generator rather than the generated code: schemars_derive, serde_derive_internals, typify-macro, serde_tokenstream, thiserror, thiserror-impl, regress 0.11.1, and semver. They stay credited, as this decision states the whole closure. A closure is a rule a script can apply without judging which crate's code reaches the output. So the file's header and the changelog describe the set as the crates the binary is compiled from and every crate the workspace's code generation depends on, and do not claim that each one is compiled in.

3. One text per crate, from a fixed preference, and a reviewed table for the rest

The script reads each crate's SPDX expression, treating the legacy / as OR. Under OR it credits the first license in this order: MIT, Apache-2.0, BSD-3-Clause, BSD-2-Clause, ISC, Zlib, Unicode-3.0, MIT-0, Unlicense, MPL-2.0. Under AND it credits every part. A license WITH an exception is credited as that license: an exception only widens what the license permits, so the license's own text is what a copy must carry. The licenses in that order are the accepted list. An expression that leaves no accepted choice, such as a GPL-only crate, fails the stage. In today's set, unicode-ident's (MIT OR Apache-2.0) AND Unicode-3.0 is credited as MIT and Unicode-3.0, and each of the 170 crates resolves to an accepted license.

The text must come from a file whose name states the chosen license. The rule matches file names, ignoring case:

  • LICENSE-X or LICENSE.X, optionally ending in .md or .txt, where X is MIT, APACHE, APACHE2, APACHE-2.0, BSD, ZLIB, or UNICODE for the matching license;
  • UNLICENSE for Unlicense;
  • LICENSE, LICENCE, or COPYING, again optionally ending in .md or .txt, only where the crate's expression names a single license.

An Apache-2.0 crate's NOTICE file is always reproduced, as that license's section 4(d) asks. Under this rule bytecount's LICENSE.MIT and unicode-ident's LICENSE-MIT and LICENSE-UNICODE match.

A crate whose text the rule cannot find needs a row in crates/htmlspec-cli/license-clarifications.tsv. A row gives the crate, its exact version, the chosen license, the text's source, and who reviewed it. The source is either a file in the crate or the SPDX standard text vendored under crates/htmlspec-cli/licenses/. A row names an exact version, so an upgrade asks for the review again. Measured on this commit, fifteen crates need a row. Thirteen ship no license file: fxhash, inquire, jsonschema-regex, jsonschema-value, mac, match_token, newline-converter, selectors, typify, typify-impl, typify-macro, uuid-simd, and vsimd. Two ship one file for a two-license expression, which the rule does not match: num-cmp's LICENSE.txt and siphasher's COPYING.

A vendored standard text needs a copyright line, which the script builds from the crate's authors with every <…> address removed. A crate that names no authors gets Copyright the authors of NAME, as REPOSITORY names them, from its manifest's repository. Among the rows today that applies to typify, typify-impl, typify-macro, uuid-simd, and vsimd. A text copied from a crate's own file is reproduced verbatim, addresses included, because a license text is not ours to edit. strsim's LICENSE carries one, so the readiness read says so (task 6.4).

Under OR a recipient may take any one of the licenses, so crediting one is enough, and a fixed order makes the output stable. The preference and the accepted list are mine. They live only in the order and the table, so extending or reordering them later is an edit in one place.

Decided on 2026-10-22: the user accepted this order of preference and this list of accepted licenses as stated, and they are no longer open.

Settled while building, on 2026-10-22. A row's source may join several sources with +, because siphasher's COPYING states its copyright and the choice of licenses and not a license's text: its row is COPYING + licenses/MIT, and the entry reproduces both. num-cmp's LICENSE.txt turned out to reproduce CC0, the MIT text with its copyright line, and Apache-2.0, so its row names that file. Three standard texts are vendored. licenses/Apache-2.0 is the Rust project's copy of the Apache text, the one the credited crates ship most often. Measured on 2026-10-22, 98 of the 170 credited crates ship an Apache-2.0 file. Of those, 47 match the vendored text byte for byte, and 55 match it when all whitespace is ignored. licenses/MPL-2.0 is cssparser's LICENSE. licenses/MIT is the permission and warranty paragraphs of this repository's own LICENSE, so the copyright line the script writes is the only one. The credited licenses in the file's header are written in the order of preference, joined by AND.

Decided by the user on 2026-10-22: a row is reviewed by the agent that writes it, and again by the review of the pull request that adds or changes it, and both reviews are recorded. That is enough, and no further review by a person is required. The agent's review is recorded in the row's reviewer column, with its date. The pull request's review is recorded on the task that wrote the rows, which for these fifteen is task 2.2, and on the pull request itself. The design said before that a person reviews every row, and decision 1's rationale and the risk that a file is misread now say what was decided.

Settled after the pull request's review, on 2026-10-22. A row may give, in a sixth column, the copyright line its vendored text carries, read from the crate's repository. The script refuses that column on a row whose sources include no vendored text. 4. An MPL-2.0 crate's entry says where its source is

Four crates in the set are MPL-2.0 only: cssparser, cssparser-macros, dtoa-short, and selectors. Each one's entry adds a line naming its source form, at https://crates.io/crates/NAME/VERSION.

MPL-2.0's section 3.2 asks that recipients of an executable be told how to obtain its source form. Of the accepted licenses, that is the only obligation a notice alone does not meet, and a generated line meets it for every such crate the lockfile ever reaches.

5. Every binary channel ships CRATE-LICENSES, and the formula declares what it credits

Each channel that distributes the binary ships the generated file beside LICENSE and THIRD-PARTY-LICENSES, and the crate that builds the binary publishes it too:

  • scripts/pack-release's NOTICES gains it, so each tarball holds htmlspec, LICENSE, THIRD-PARTY-LICENSES, and CRATE-LICENSES.
  • packaging/homebrew/htmlspec.rb.in's prefix.install gains it.
  • The flake's package installs all three files under $out/share/doc/htmlspec/. Today the Nix package ships no license file at all.
  • htmlspec-cli's published crate includes it. That costs nothing, and it keeps the crate and the tarball telling the same story.

The formula's license all_of becomes the union of crates/htmlspec-assets/Cargo.toml's license field and the licenses CRATE-LICENSES credits. Today that union is MIT, Apache-2.0, BSD-3-Clause, ISC, Unlicense, Unicode-3.0, MPL-2.0, Zlib, and MIT-0. scripts/crate-notices writes the credited list into the file's header. scripts/render-formula's existing comparison reads it beside the assets crate's field, and refuses a template that names any other set. htmlspec-cli's own license field stays MIT, because it describes the crate's source, not what the binary links.

THIRD-PARTY-LICENSES keeps its name and its owner, crates/htmlspec-assets, which publishes it. A separate file for the Rust crates keeps the JavaScript notices, curated by hand, apart from the generated ones, so regenerating never touches what a person wrote. The formula's field is what Homebrew reports as the package's license, and today it names only what the JavaScript side carries.

6. A suite stage fails when the notices fall behind the lockfile, and the flake carries what it reads

scripts/check gains a notices stage that runs scripts/crate-notices --check. It fails, naming the crate, when Cargo.lock reaches a crate CRATE-LICENSES does not credit, or a license outside the accepted list. It also fails when the file credits a crate the lockfile no longer reaches, or names a different version. It runs offline: cargo metadata --locked reads sources the build has already fetched, or that crane vendored inside the Nix sandbox. flake.nix needs two edits for the stage to run there:

  • scripts/crate-notices, and its test script if that is a stage of its own, join checkSuite's patchShebangs line;
  • the source filter keeps license-clarifications.tsv, which no kept extension matches, and the extensionless texts under crates/htmlspec-cli/licenses/, as it already keeps LICENSE and THIRD-PARTY-LICENSES.

A notices file that is right on the day it is written goes wrong at the next dependency update, and that is the failure this stage prevents. The lockfile changes in ordinary pull requests, often through a dependency's own update, and the suite is the one gate every pull request passes. toolchain-packaging's "Project checks are runnable as one command" requires that the one command run the same everywhere, so a stage whose inputs the flake filters out would pass locally and fail in the sandbox.

Settled while building, on 2026-10-22. The generator's tests are scripts/check-crate-notices, a stage of its own, notices-self-test, run before notices, as release-fixtures runs before release: a generator that breaks its own rules would make the comparison's failure about the generator, and a failure line that names the stage says which. Both scripts join the patchShebangs line, and the suite has sixteen stages. Adding insta as a dependency of htmlspec-cli without regenerating made notices fail, naming the seven crates it brings in, and restoring the manifest and the lockfile made it pass again.

Runbooks get a way in

A runbook already accepts everything a specification does. Validation runs on a document's kind, and runbook-authority's "A runbook is two documents of existing kinds". A copy of the publish runbook's tasks document with a Mermaid figure and a MathML fraction added validates with no diagnostics. So this workstream adds no vocabulary. Instead it adds a template, a way onto the current stylesheet, and a listing that is easier to find.

7. htmlspec new runbook <name> writes a runbook that validates immediately

It is a new leaf under new, spelled post runbook in the request verbs. It writes htmlspec/runbooks/NAME/ holding specification.html, tasks.html, VERSION at 0.1.0, and CHANGELOG.md with that version's heading.

  • Where it writes: it resolves the project from the working directory, as new change does, and refuses where there is none. It refuses a directory that exists.
  • Which names it accepts: a plain name only. A new checked constructor, ProjectRoot::named_runbook, beside named_change, refuses an empty name, ., .., any name containing /, \, or .., and any control character. run and preflight move onto it too, so no contributor's name reaches ProjectRoot::runbook() unchecked.

The contract fixes three things about what it writes:

  • No completion state. Every unit is unchanged and every task todo, as runbook-authority's "The canonical procedure carries no completion state" requires of a runbook. That requirement exempts only the operation that starts a run, and this change makes the creating operation a second exception (see the contract table). The existing templates write added, and validation does not catch it, so a test does.
  • Example content is reported. The runbook templates use -example identifiers and a placeholder summary, as the other templates do. They live in a second list, RUNBOOK_TEMPLATES in crates/htmlspec-assets/src/lib.rs, not in TEMPLATES, because template_for maps one kind to one template and a runbook's specification is a second specification. example_identifiers() and example_placeholders() scan both lists, so contract-authority's "Generated example content is non-normative and its survival is reported" reaches a runbook straight from the template.
  • It conforms when created. It carries the fallback stylesheet and the current runtime, as every template does.

Within those limits the template shows three things:

  • The specification states the procedure's purpose and one requirement with a scenario. It shows a machine requirement's declaration as a code sample, not as a note, because a live note would be a check, and a template that refused to start on most machines would teach the wrong lesson.
  • The tasks document holds "What this procedure consumes", two steps, and a figure of the steps' order. The figure's Mermaid source sits in its details, so the order stays readable without JavaScript.

Which affordances the template shows is my choice. They are the three an author is least likely to find alone: a scenario, a figure, and a declaration. The operation and decision 8 are independent of each other.

Decided on 2026-10-22: the user chose to keep htmlspec new runbook <name>, spelled post runbook in the request verbs.

Built, and three details this decision did not state were settled in the building. The templates are a second shape, RunbookTemplate, carrying the file name each document takes, rendered by render_runbook through the same substitution render_kind uses, and pinned in vendor.lock.json as template-runbook-specification.html and template-runbook-tasks.html, as the other templates are. A new runbook's name is held to more than a change's: ProjectRoot::new_runbook applies ProjectRoot::is_a_new_runbook_name beside is_a_name, and named_change keeps its own rule, because tightening it is not this change's work. run, run --check, and preflight go through ProjectRoot::named_runbook, which keeps 1.0's rule, so every runbook 1.0 ran still runs. And the operation is a twentieth Operation, NewRunbook, which writes no payload, so the 1.1 surface records it with payload: null.

Settled by PR #80's review. A runbook name is also refused when it is assets, when it is a name the document walk skips (target, node_modules, result, .git, .jj), or when it starts with a dot. The review measured new runbook assets: htmlspec/runbooks/assets/ is taken by the store walk for the store of every runbook beside it, and every runbook in the project stopped validating. And the operation writes all four files or none. It renders and validates both documents against the store before the runbook's directory exists, and removes the directory if a write fails. Before, it wrote each document and then validated it, and a failure on the second left a directory nothing could run or create again. RunbookTemplate is #[non_exhaustive], for the compatibility reason decision 8's note gives.

Settled by PR #80's re-verification. The stricter name rule is new runbook's alone. run, run --check, and preflight refuse exactly what 1.0 refused, the shapes of a path (empty, ., .., a / or a \), because toolchain-packaging's "The command surface is stable within a major version" keeps every runbook 1.0 ran runnable. Measured against the released 1.0.0 binary, it ran runbooks named result, target, .ops, v1..2, and one holding a tab, so refusing any of them in run would have been a compatibility break, and none is refused there. 1.0.1 changed no name check. A new runbook still may not take .., a control character, a leading dot, or a name the layout uses, because no runbook has that name yet. And new runbook refuses anything already at its path, a dangling link included: exists follows a link, so a dangling one read as empty, and the cleanup then removed the contributor's link. It creates the runbook's directory with create_dir, so the cleanup removes only a directory the run made.

8. htmlspec format --upgrade-assets rewrites a document's references to the store's current assets

Each asset reference a document carries is rewritten to the store location of the bytes this binary embeds for the same asset: the stylesheet, the print stylesheet, and the scripts the document loads. Nothing is added that the document does not load. Where the store lacks those bytes, it writes them from the copy the binary embeds, as new document does. The option downloads nothing and makes no network request, and its help says so plainly: it rewrites references to the store's current assets, and never downloads anything.

It is the third exception to deterministic-formatting's "Formatting preserves meaning", which today requires a reference to bytes the store holds to "be left as written, even when the store also holds a newer revision". Like the second exception, --fallback, it is made only on a contributor's request. Without the flag, formatting leaves every such reference as written. It never touches a document of an archived change or a run's record, whether reached directly or through a symbolic link. With --check it reports each document that is behind. Moving a runbook's documents changes its canonical documents, so the runbook's next archival asks for a new runbook version, and the option's help says so, as --fallback's does.

document-template's "Documents share one pinned runtime" requires that "the bytes a document renders with cannot change without changing the document". This option changes the document, so it keeps that rule. It never rewrites a store location, so a document authored against an earlier entry still renders as authored until someone upgrades it. The problem it fixes is measured: this repository's release runbook references the stylesheet at sha256-e4f5de7cecc4f691, which has no styling for a partial outcome, a renamed requirement's heading, or a change's inserted and deleted words. Specifications reference sha256-03627137bcbb81c9, which has all three.

Decided on 2026-10-22: the user chose the name --upgrade-assets over --current-assets, knowing it reads like a download. So the help, the README, and the changelog each say that it rewrites references to the store's current assets, and never downloads anything.

Built, with one departure from "each asset reference a document carries is rewritten", settled here. Two kinds of reference stay as written: one naming a file the binary embeds no revision of, which has nothing to move to, and one whose stored bytes disagree with its address, because moving it would erase the evidence asset/mismatch exists to report. The rewrite is a new function, htmlspec_format::upgrade, with its own result types, rather than a new variant of ReferenceChange: that enum is part of a crate published on crates.io, and a variant added to it would break an exhaustive match downstream within a minor release. --check names each document that is behind with "references an asset behind the store's current revision", beside the canonical-form line, and writes nothing, the store included.

Settled by PR #80's review, in four places:

  • History is judged per document, where it resolves. format resolved one project, from the path it was given, so a directory above a project resolved into none, and format --upgrade-assets given that directory rewrote the project's archived changes. Each document is now placed by the project its own directory resolves into. format --fallback had the same gap before this change, and the same fix closes it.
  • A link is followed, not judged by its place. The walk collects a link to a file, and the history check judged the link's directory, so a link from a living directory to an archived document or a run's record was rewritten through. I chose to resolve each document, to judge, read, and write it where it resolves, and to take its store and prefix from there, over skipping links. A link to a living document is formatted as that document is, and a link into history is left as written and says why.
  • A clean reference is not moved onto replaced bytes. Where the store holds other bytes at the current revision's address, the reference stays as written, and the report says the file was edited or replaced and how to restore it: from version control, or by deleting it and running the option again, which writes this program's own copy there. htmlspec assets does not compare a stored file with its address, so the report does not send a contributor there. UpgradeOutcome carries these as blocked.
  • The published types can grow. UpgradeOutcome and UpgradedReference are #[non_exhaustive], so a field a later 1.x release adds does not break a caller that builds or destructures one. And --check reports a canonical document that is behind as behind, and no longer also as not canonical.

Settled by the pre-archival review, which closes a gap 1.0 shipped. The per-document judgment above fixed what format writes, but the walk that finds documents still resolved its project from its own root alone, so from a directory above a project it resolved none and descended into that project's evidence: validate reported the records, format --check judged them, and format met them and refused the whole run. toolchain-packaging's "An operation over a directory collects documents and not a change's evidence" does not allow that. The walk now takes the project of each directory it enters, as ProjectRoot::resolve would find it from there: a directory holding htmlspec/ is a project's, and one holding .git begins a repository of its own. So validate, format --check, and format from above a project, or through a link to one, pass over its evidence exactly as they do from inside, and --fallback and --upgrade-assets leave its history as written.

Decided by the pre-archival review, with nothing in the contract to say otherwise: format --check --upgrade-assets exits 0 when every reference it could move is blocked by replaced bytes, because it reports what formatting would write, and it would write nothing. The report names each blocked reference and how to restore the file.

18. The runbooks are easy to find from the commands that use them

The user raised that listing runbooks is hard to find. Three additions answer it:

  • htmlspec run with no runbook lists them. It lists the project's runbooks, each with its version and title, and how to start one (htmlspec run <runbook> --as <record>). It then refuses as a usage error and exits 2. That is OperationalFailure, the code an invocation missing its argument already exits with today, through clap, so the exit status does not change. This follows archive, which with no change lists the active changes when it cannot choose. run's runbook argument becomes optional, which the 1.1 surface records. --as or --check without a runbook is refused the same way.
  • list --runbooks shows each runbook's version and title. In --json each entry gains version, present where the runbook has a VERSION file, and title, the tasks document's title, or the specification's where the tasks document has none. The list payload's schema declares both, and the 1.1 surface records them.
  • run --help and preflight --help point to htmlspec list --runbooks.

Built, and the listing's shape is my choice. Both list --runbooks and a bare run print one table, from one function, with four columns: the name, the version or no version, the documents, and the title. The bare run writes the table to standard error with the refusal and nothing to standard output, so --json gets no payload from it, as no refusal writes one.

Settled by PR #80's review and re-verification. A runbook's name and title reach the terminal with every control character and every bidirectional formatting character written as its escape, from the listing and from a bare run. The bidirectional set is the one the install-hints workstream refuses in a remedy, U+061C, U+200E, U+200F, U+202A to U+202E, and U+2066 to U+2069, stated in both places until both have landed. The --json payload carries the text as it is, because JSON escapes it.

Settled by the closing pull request, once both workstreams had landed. One predicate now decides for both: hides_itself, in crates/htmlspec-cli/src/terminal.rs, which the remedy rule refuses by and the listing escapes by. So the listing escapes what the remedy rule refuses: every control character, every whitespace character but the plain space, and every invisible formatting character but the two joiners, the bidirectional set among them. Two renderings remain, because each pins its own form in its tests: a preflight report names a character as <U+001B>, and the listing writes its Rust escape, \u{1b}.

runbook-authority's "The project enumerates the runbooks it holds" already requires each entry to "carry what a selector needs in order to choose between runbooks". A version and a title are what a person chooses by, and that requirement is restated with them. A bare run that names the candidates is not a second listing command, which the same requirement forbids. It is a refusal that says what to type, as archive's is. The listing's format and the help's wording are my choice, and toolchain-packaging's "The command surface is stable within a major version" does not cover the wording of human-readable output.

Install hints in preflight

10. A remedy needs preflight/v2, which is v1 with one optional field

preflight/v2 accepts every form preflight/v1 accepts, with the same fields, plus an optional remedy on each. 1.1 reads both versions. A runbook that declares no remedy keeps writing v1, and nothing about a v1 declaration changes.

v1's parser refuses unknown fields ("unknown fields are refused rather than ignored", in crates/htmlspec-cli/src/preflight.rs). If remedy were an optional field in v1, a 1.0 reader would refuse the declaration with "`remedy` is not a field this form has". That message blames the runbook when the program is what is out of date. Under v2, a 1.0 reader refuses with the message runbook-portability already requires for a version it does not read, which points at the program. Both refuse before a run is created, so neither starts a run that 1.0 cannot check.

Decided on 2026-10-22: the user chose preflight/v2, which is v1 with an optional remedy, over an optional field added to v1.

11. A remedy is one line of printable text that is reported, shown when a check did not pass, and never run

remedy is a string of 1 to 200 characters, with no control characters. A declaration that breaks either limit is malformed, and runbook-portability's existing rules already make a malformed declaration prevent a run. One rule governs where it appears:

  • In --json, every check whose declaration carries a remedy has runbookRemedy, whatever its outcome. The published preflight schema declares it, and so does run's preflightReport definition.
  • In human output, it is shown only for a check that did not pass, that is, one whose outcome is unmet, unavailable, timed-out, or probe-failed. It comes after preflight's own remedy, as the runbook says: TEXT, so a reader can tell the author's words from the program's.

Preflight never runs the text, never opens an address in it, and never treats it as satisfying anything.

Settled while building group 4, under silence, on 2026-10-22, and tightened the same day after the review of its pull request. "No control characters" did not by itself make what a terminal shows all the remedy holds, which is the harm decision 11 guards against, so a remedy refuses every character a terminal would not show as itself:

  • a control character, as decided above;
  • whitespace other than the plain space, so a tab, U+2028 and U+2029, and spaces of other widths are refused, and the one line holds;
  • an invisible character: Unicode's format category, Cf, and its Default_Ignorable_Code_Point set, as of Unicode 16.0. That covers the bidirectional marks, embeddings, overrides, and isolates, the zero-width space and word joiner, the byte-order mark, the soft hyphen, interlinear annotation, and the tag characters, which spell hidden ASCII, and also the variation selectors, the Hangul fillers, the combining grapheme joiner, the Khmer inherent vowels, and the Mongolian free variation selectors. Without them a remedy could show brew install x and carry hidden text in its JSON. The zero-width non-joiner and joiner, U+200C and U+200D, are kept, because Persian, Devanagari, and every emoji sequence need them, and so is a single emoji presentation selector, U+FE0E or U+FE0F, directly after the visible character it chooses a presentation for. The braille pattern blank, U+2800, is refused as well: Unicode gives it neither property, but a terminal draws it as a blank, so a line holding it reads as holding a space it does not. The table is written out in the program, because the standard library exposes no Unicode property and a crate for two properties would be one more the notices credit.

Spaces around a remedy are trimmed rather than refused, because they carry nothing and an author who left one meant the words. A remedy with no visible character, nothing but spaces and the two joiners, is refused as empty. Its length counts characters, Unicode scalar values, after trimming, which is what a JSON Schema maxLength counts too, so the published limit and the parser's agree. A fault names a refused character by its code point rather than echoing it, so a refusal cannot carry what it refuses. The tests state such characters as the JSON escapes a declaration needs, because the markup cannot hold most of them without error recovery.

The same review found a gap that 1.0.1 shipped, which this change closes. The fault for an unknown field echoed the field's name as written, so a preflight/v1 key holding an escape sequence wrote it to the operator's terminal. The name is now shown with each such character written as its code point, <U+001B>. The other faults already named declaration text through Rust's debug formatting, which escapes those characters.

The JSON payload is a structured description of what the runbook declares, so it carries the remedy whether the check passed or not. A person reads the human report to fix what failed, so it shows the remedy only there. Refusing every character a terminal would not show as itself, and naming any such character a declaration's field name, tool name, or path holds by its code point wherever a report echoes it, means a carried runbook cannot write terminal escape sequences into the report. The 200-character limit and the single line are mine under silence: a remedy points somewhere, and the runbook's prose explains. Labelling the line keeps the runbook from speaking in the program's voice.

Two small additions

12. -v is a short alias of --version

The version flag keeps -V and gains the alias v. No operation uses -v today: the 1.0 surface file records exactly two short flags, -h and -V. tests/surface/1.1.json records the alias under program.

A colleague's first command against 1.0.0 was htmlspec -v, which is refused with a usage error. Many tools accept it. Accepting it here takes nothing from anyone, because no flag could ever claim the letter without colliding with the version flag's meaning.

Built by declaring the version flag on the program, with clap's own ArgAction::Version, -V, --version, and the help text Print version, and turning clap's generated flag off. clap offers no way to give its generated flag an alias: reaching it with mut_arg("version", …) panics with "Argument version is undefined", because the flag does not exist until clap builds the command. The declared flag records exactly as the generated one did, plus shortAliases: ["v"], and the alias stays out of the help, as -V's spelling is the one shown. The alias belongs to the program alone: htmlspec validate -v is refused, as htmlspec validate -V is.

The review of the pull request found the declared flag listed before --help, where clap's generated one had come after it. The flag now carries display_order = 1000, so the flags are listed as 1.0.1 lists them. Two description lines differ from 1.0.1's since the runbook workstream merged, and only those: new reads "Create a document, a change, or a runbook that validates immediately", and post names runbook among what it creates. A help text's wording is not part of the stable surface, which records names, flags, exit codes, and payloads.

13. The export authenticates a GitHub push through gh and names the account first

For a target publishing.github_repository recognizes, the export reads the signed-in account with gh api user --jq .login before it pushes. It prints pushing as LOGIN, and refuses if gh is not signed in. Its own git invocations then get credential.https://github.com.helper reset and set to !gh auth git-credential through GIT_CONFIG_COUNT, for those commands only. No configuration file is written. A target that is not on GitHub, as in the tests, is pushed as before.

This answers the open question recorded in the design of 2026-10-20-finish-a-publish-run-without-a-hand-fix, as that design recommended. Delivery already relies on gh for the ruleset and the pull request, so it adds no tool. Printing the account guards against a push from an account nobody meant. The login is a public handle, and the token is never printed. The v1.0.0 run did exactly this by hand.

As built, three details the decision left open. The two entries follow whatever GIT_CONFIG_COUNT entries the environment already carries rather than replacing them, so a contributor's own command-scope settings keep their effect, and a count git cannot read is refused. GIT_TERMINAL_PROMPT is set to 0 for the same commands, because the export runs unattended and a password prompt would wait forever. And the login gh prints is taken only when it reads as a GitHub login, so an error message printed in its place is a refusal rather than an account. The tests reach no network: a GitHub address rewritten to a local bare repository with url.<path>.insteadOf, behind a proxy in the environment that refuses every connection, so an export that dropped the rewrite fails at once. That guard was seen to fire: with the helper written over the environment's entries, the test failed at the refusing proxy.

The review of the pull request changed four things.

  • Only an HTTPS address delivers. publishing.github_repository also recognizes git@github.com:, and a contributor's url.*.insteadOf or url.*.pushInsteadOf can turn the HTTPS default into SSH. Over SSH the push goes out as whichever account the key belongs to, so pushing as LOGIN could name an account the push never used. Before naming the account, the export now names the target as a remote in a throwaway repository and asks git for its fetch and push addresses, which applies both rewrites. It refuses unless each is the same repository on https://github.com/, or a local path, which needs no credentials and is how the tests reach a local repository.
  • The account comes before the network. The address check and the account are now read before git ls-remote reads the target, so a refusal precedes every network action.
  • The account is read again just before the push. The suite runs between the two reads, long enough for a gh auth switch. A different account at the second read is a refusal, before anything is pushed.
  • The count is read as git reads it. An unset or empty GIT_CONFIG_COUNT is no entries. Anything other than ASCII digits is refused, where str.isdigit had taken ١ as 1 and crashed on ².

A stand-in git in the tests now logs every command with the configuration entries it was handed, and asserts that each ls-remote, fetch, and push to the GitHub target ends with the two credential entries, and that no other command carries them. With env=remote_env removed from all six call sites, that test fails, naming the first command that lacked them.

14. The publish runbook's push steps say the export names the account

Steps 3 and 4 gain one sentence: the export prints the account it pushes as, and the run records it. The publish runbook moves from 0.2.0 to 0.2.1, a patch, because the steps and their order are unchanged.

A run's record holds what the run observed, as runbook-execution requires. The account a push went out as is the observation a later reader most needs when asking who published what, and the step is where the runbook tells the person running it to record it.

How the parallel worktrees merge

15. An opening pull request moves to 1.1.0 before any workstream merges

Before the workstreams branch, an opening pull request does four things:

  • it runs scripts/set-version 1.1.0, which moves the workspace version, the five pins, and the lockfile;
  • it adds a ## 1.1.0 heading to CHANGELOG.md, with one subheading per workstream;
  • it writes crates/htmlspec-cli/tests/surface/1.1.json with the surface writer, write_the_current_minors_surface. The file equals 1.0.json except for its version;
  • it regenerates the 45 installed instruction files, whose generatedBy then names 1.1.0.

spec.nix stays at 1.0.1 until archival.

The workstreams add to the surface: the new runbook operation, run's optional argument, the --upgrade-assets flag, the -v alias, and three payload properties. While the version reads 1.0.x, the current minor's file is the released 1.0.json, and the surface tests require it to equal the program's surface exactly. So no surface addition can land until the version names 1.1, and recording an addition into 1.0.json would misstate what 1.0 released. With the version open, each addition is recorded into 1.1.json, which only the writer edits and which refuses losses. A main at Cargo 1.1.0 and spec.nix 1.0.1 cannot be published by accident, because the publish runbook's first step stops unless an archived change records the version.

16. Each workstream merges on its own, after its own review, and generated files are regenerated, never merged by hand

Each workstream is one pull request off main after the opening one, built in its own worktree. It touches its own files, its own subheading in CHANGELOG.md, its own section of README.md, its own section of this design, and the states of its own tasks. It needs no skip-changelog label, because it touches the changelog. Each workstream's pull request takes its own code review before it merges, under the project's merge rule: one review, every finding settled, and every check green on the head that merges.

Three generated files can conflict between workstreams: 1.1.json, the installed instruction files, and CRATE-LICENSES. A workstream that merges second rebases and runs the generator again, and never resolves those by hand. Two source files are touched by two workstreams in different places: crates/htmlspec-cli/src/main.rs, where group 3 adds new runbook, run's optional argument, and the help pointers, and group 5 adds the -v alias, and crates/htmlspec-cli/tests/cli.rs, where both add tests. Those conflicts are resolved by hand, keeping both sides. No workstream touches publish/READINESS.md: the closing pull request records every read once, at the content that will be exported.

17. A closing pull request reviews, archives, then reads and rehearses

Once every workstream has merged, the closing pull request works in this order:

  1. one pass over the README and the changelog for consistency, including the changelog's 1.1.0 entry as a whole;
  2. the code review of the whole 1.1.0 diff, with each finding settled;
  3. archival at spec.nix 1.1.0, with every archive command naming ship-the-crates-notices-and-runbook-affordances;
  4. every publish/READINESS.md read, at the content the archived tree holds;
  5. publish/export --ref HEAD --dry-run against an empty local bare repository.

The closing pull request edits CHANGELOG.md, so it needs no skip-changelog label. Publishing 1.1.0 is then a run of the publish runbook, outside this change.

The reads come after archival because archival moves this change's documents, writes its specification, and merges it into the accepted specifications. A read recorded before that would name content the export no longer holds, and the export would refuse it. The dry run comes last because it checks the reads. Every archive command names the change because main holds a second active change, release-a-windows-build, and htmlspec archive with no change refuses when there are several.

Risks

The notices stage cannot read crate sources inside the Nix sandbox

cargo metadata names each crate's manifest path. In the sandbox those paths are crane's vendored sources. If the license files are not among them, the stage fails there while passing locally.

The notices workstream runs nix flake check before it merges, and its pull request's check job runs the suite in that sandbox. If the vendored sources lack the files, the stage instead compares the committed CRATE-LICENSES with Cargo.lock's names and versions alone, and full regeneration stays a step run locally and at release time.

Settled on 2026-10-22, and it did not happen. nix flake check on the notices branch ran all 16 stages inside the sandbox and passed. notices regenerated the file from crane's vendored sources and reported the same 170 crates, so those sources hold the license files, and the fallback above was not needed.

A license file is credited under the wrong license

A crate can name its file LICENSE and hold two licenses in it, or a license other than the one its manifest declares.

The script matches a crate's LICENSE or COPYING only when the crate has a single license. A crate with several needs a file named for the license, or a reviewed row. The agent that writes a row reviews it, and the pull request's review reads it again, as decision 3 records. The generated file is in the diff of every pull request that changes it.

A runbook with a remedy cannot run under 1.0

A 1.0 reader refuses preflight/v2, so a runbook that adds a remedy stops working for anyone who has not upgraded.

Accepted. The refusal comes before a run, and it names the version it cannot read. The README says remedies need 1.1, and a runbook that must run under 1.0 keeps v1.

A carried runbook's remedy tells someone to run something harmful

A remedy is the runbook author's words, and a runbook can come from anyone.

Preflight never runs it, and it labels it as the runbook's words. A runbook's prose can say the same thing today, so the remedy adds a place for that text to appear but no new authority.

Parallel workstreams conflict on generated files

1.1.json, the installed instruction files, and CRATE-LICENSES change in more than one workstream.

Decision 16 settles it: rebase and regenerate. The surface writer refuses losses, so a regenerated 1.1.json can only add.

Behaviour no contract row names

The pre-archival review listed what this change does that no row of the contract table states. Each is decided here, and the archived specification states each one beside the requirement it belongs to.

  • An unknown field's name is shown by code point. Kept. A declaration's unknown field, tool name, or path reaches a report with each character a terminal would not show as itself written as <U+001B>, and the probe still uses the text as written. 1.0.1 echoed all three raw.
  • An unknown marker's message names both versions. Kept. A note beginning preflight/ with a version this program does not read is reported as naming a format it does not read, and the message lists preflight/v1 and preflight/v2, the two it does.
  • The export's review and dry run reach GitHub as its delivery does. Kept. Every git command the export runs against a GitHub target, a review's fetch included, sets git's credential helper for https://github.com to gh auth git-credential and sets GIT_TERMINAL_PROMPT=0, so no mode prompts for a password. Only --push and --bootstrap require gh to be signed in and name the account, because only they write.
  • new runbook takes --subject. Kept. It is the subject each document takes as its title and heading, and it defaults to the name, as new change's does. The 1.1 surface records it.
  • format --check --upgrade-assets exits 0 when every movable reference is blocked. Kept, as decision 8's note says.
  • Under OR, compound alternatives are compared whole. Kept. Where an alternative is itself a conjunction, the one whose least-preferred license comes earliest in decision 3's order is credited, which for single licenses is simply the first of them in that order.
  • A NOTICE is reproduced whenever Apache-2.0 appears. Kept. A crate whose expression names Apache-2.0 anywhere has its NOTICE files reproduced, even where it is credited under another license: reproducing a notice costs a few lines, and leaving one out where it was owed would be the defect this workstream exists to close.
  • Build-dependency roots are the workspace's own crates. Kept, as decision 2 says. A third-party crate's build or development dependencies are not credited, because nothing of them is compiled into the binary.
  • The notices are offline only where the sources are fetched. Corrected. cargo metadata --locked reads the sources a build has fetched, or the Nix sandbox vendored, and reaches no network then. On a checkout where nothing was ever built, cargo fetches them first. The script's documentation and the suite's comment said it never reaches the network, and both now say this.
