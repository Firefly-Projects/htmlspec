1. Reproduce the refusal before changing the guidance

  • 1.1 Record the transcript as evidence: the request, both refusals, and the agent's own reasoning that an absence of capability is a legitimate need.

    That reasoning is the finding — the instruction overrode a correct inference rather than failing to inform one

  • 1.2 Quote the two sentences that produced it, by file and line: new.md:35 narrowing a need to a problem with three examples that all presuppose an existing system, and new.md:14 stating the naming rule without saying who may satisfy it

  • 1.3 Confirm against the contract that the narrowing is the instruction's own.

    openspec/specs/artifact-kinds/spec.md:36 gives a proposal's intended content as "Value, need, scope, alternatives" — need, not problem. Without this the change is a preference rather than a defect report

  • 1.4 Confirm no test asserts anything about this text, so the absence of a failing build is expected rather than evidence the guidance is fine

2. A need may be an absence

  • 2.1 Amend the proposal section of crates/htmlspec-assets/instructions/new.md to state that a need is either a problem with an existing system or a capability the project does not have

  • 2.2 Give the absence form three concrete questions: who or what wants the capability, what they cannot do without it, and what working looks like the first time you see it.

    A permission with no form is what produces "we need better data handling"

  • 2.3 Keep the problem form and its three examples — a measurement, an error message, a behavior somebody hit.

    They are correct for the case they were written for and this change does not displace them

  • 2.4 Keep the warning against stating a need as a category of concern.

    That warning is the correct part of the current sentence and it must survive, or the change trades a false refusal for accepted vagueness

  • 2.5 Note in the file that "what working looks like" is the input the tasks are broken from and what archival checks requirements against, so a reader knows why it is asked for rather than deleting it as ceremony

    Migration note: nothing this change carries records this note. It is in crates/htmlspec-assets/instructions/new.md at b995808: "It is the input the tasks are broken from, and at archival it is what the requirements are checked against."

3. The agent proposes the name

  • 3.1 State in new.md that where a contributor describes the work without naming it, the agent derives a kebab-case name from the description, states it, and proceeds

  • 3.2 Leave the naming rule itself unchanged.

    It is a good rule and it applies identically to a derived name

  • 3.3 Require the derived name to appear in the report, so a contributor can correct it.

    A derived name they never see is a decision taken on their behalf

  • 3.4 Do not add a confirmation step before creating the change.

    A round trip to approve a name that follows from the description is the same refusal in a politer form

    In the recorded transcript two of the four requested items were already supplied

  • 4.2 Amend ff.md so an absence of capability does not read as an unsettled idea routed to explore.

    ff.md:13 sends unsettled work to explore and that routing is right; new work whose shape is described is not unsettled

  • 4.3 Confirm ff.md:35 needs no repair — it already says "the value, the need, the scope", which is the contract's wording

    Migration note: ff.md:35 is the sentence's line before this change gave ff.md its new paragraph. evidence/amended-guidance-2026-08-21.md and commit b995808's message cite the same sentence as ff.md:41, its line after.

    Its stance is correct and this change does not reach it

  • 4.5 Confirm the guidance still asks, rather than invents, when a request carries no description at all.

    A bare /htmlspec-new is the case the current behavior gets right
