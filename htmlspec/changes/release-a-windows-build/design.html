Release a native Windows build of htmlspec: design

A sketch of what a native Windows build would take, kept for the day the change is scheduled. It maps every place the code and the release assume Unix and proposes eight decisions: an x86_64-pc-windows-msvc target built on a Windows runner and gated like the macOS ones, a reproducible zip, a preflight that finds programs through PATHEXT, one home and configuration lookup for preflight and the store registry, tests that run on Windows in a workflow of their own, a .gitattributes that keeps git from rewriting the asset store, and the release zip and crates.io as the channels.

Status

Not scheduled. Every decision below is proposed, and each is a recommendation for the day the change is scheduled, not a decision taken. Nothing here is implemented.

What assumes Unix today

The program is closer to Windows than its release is. The runtime code gives each of its two Unix-only operations a fallback, the formatter already normalizes line endings, and both dependencies that manage child processes support Windows. What does not yet work there is the search for a program on PATH, the home and configuration directories, the tests, the git checkout of the asset store, and the release pipeline.

Decisions to take

1. Build x86_64-pc-windows-msvc on a Windows runner, with the C runtime linked statically

The fifth target is x86_64-pc-windows-msvc, built on windows-2025 the way each other target builds on its own platform, and run there before it is packed. The C runtime is linked statically, through -C target-feature=+crt-static for that target alone in .cargo/config.toml, so the binary needs no Visual C++ redistributable, as the musl builds need no C library.

Recommended over the -gnu target, which brings a MinGW runtime nobody on Windows expects, and over cross-compiling from Linux, which saves the runner but ships a binary that never ran where it was built. The release workflow runs every binary on its own platform before it packs it, and this keeps that true.

2. Pack the Windows build as a zip, as reproducibly as the tarballs

scripts/pack-release writes htmlspec-X.Y.Z-x86_64-pc-windows-msvc.zip, holding one directory of that name with htmlspec.exe, LICENSE, and THIRD-PARTY-LICENSES. Every entry carries one fixed time and no extra attributes, so packing the same binary twice gives the same digest, as the tarballs do now. SHA256SUMS lists it beside them.

Recommended over a tarball, which Windows 10 can unpack with tar but File Explorer cannot open. The reproducibility rule is the existing one: a digest describes the binary, not the moment it was packed.

3. Add the target to the release facts, and gate it as the macOS targets are gated

scripts/release_facts.py gains the target in TARGETS and its runner in RUNNERS, beside a set of Windows targets that a run builds in the public repository and, in the private one, only with the release-check label. The BuildMatrix tests in scripts/check-publish-crates grow to five entries. scripts/render-formula reads only the Homebrew targets from SHA256SUMS, rather than refusing a file it does not use, and the release job's check that every target has its archive accepts the zip.

One list of targets is the existing rule, because a second copy is how the workflow and the formula drifted before. A Windows minute costs twice a Linux minute in a private repository, so the gate that already holds the macOS minutes down holds these too.

4. Preflight resolves a Windows program the way the Windows shell does

On Windows, which tries each PATH directory in order, and in each one the bare name and then the name with each extension PATHEXT lists, defaulting to .COM;.EXE;.BAT;.CMD. The first match wins, as it does on Unix. A file counts as executable when its extension is one PATHEXT lists, rather than always. The home directory and the configuration directory come from one lookup, shared by preflight's home scope and store.rs's registry_path. On Unix it reads what they read today. On Windows, the home scope is USERPROFILE, where an agent keeps its skills, and the registry is recommended at %APPDATA%\htmlspec\stores.json, the place Windows gives a program's configuration. The alternative, the registry under USERPROFILE\.config, keeps one rule on every platform and puts a dot-folder where Windows users do not look. Open question 7 asks the contributor to choose. The toolchain check, which reads a Nix development shell, refuses on Windows with an explanation that names the platform and WSL, as an unavailable manager already refuses.

runbook-portability's "Package manifests retain authority over package pins" already requires an unavailable manager to "refuse readiness with an explanation", so the refusal is the existing rule with a better reason. The search order matters for the same reason it does on Unix: the answer must be about the program the procedure will run.

5. Guard what is Unix-only in the tests, and give the fake tools a Windows form

The four unguarded uses of std::os::unix in tests/run.rs and tests/archive.rs take #[cfg(unix)], each with a Windows counterpart where the case still means something there. The test helper that writes a fake tool writes a .cmd script on Windows instead of a #!/bin/sh one, so the version-reporting tests run on both. The process-group test stays Unix-only, and a Windows test checks instead that a probe past its deadline stops a child that started its own child.

Guarding a test removes coverage on the platform it skips. Each guard is therefore paired with a Windows case where one exists, and the guards that remain are counted in the evidence, so the gap is stated rather than discovered.

6. Keep git from rewriting stored assets, here and in every project

This repository gains a .gitattributes that turns off line-ending conversion for every asset store, **/assets/sha256-*/**, and keeps documents at LF. htmlspec init writes the same line for a project's store when the project has no rule for it, and leaves an existing .gitattributes otherwise untouched.

A stored asset is named by its digest, so a checkout that converts its line endings breaks validation for every document that references it. Telling contributors to set core.autocrlf would leave the invariant in their memory. The file states it where git reads it. This touches every project, not only those with a Windows contributor, which is open question 3.

7. Run the workspace tests on Windows, in a workflow of their own, as a stated exception

A new .github/workflows/windows.yml, not a job in check.yml, runs cargo test --workspace --locked on windows-2025. Its header states the exception the way publish.yml's header states its own: scripts/check is a bash script around Nix, which does not run on Windows, so this workflow runs the one command a Windows contributor runs, and it checks the program and its tests, the parts that can differ there. It triggers on pull_request with types: [opened, synchronize, reopened, labeled] and on a push to main, and its job runs where github.repository == 'Firefly-Projects/htmlspec' or the pull request's labels contain release-check: the condition release.yml computes for its macOS jobs. The condition reads the pull request's labels rather than the label an event added, so a later label of any other kind runs what the earlier run ran, and its result does not hide the earlier one.

toolchain-packaging's "Project checks are runnable as one command", through its scenario "Continuous integration parity", requires continuous integration to invoke the check command a contributor runs, "rather than a separately maintained list of steps", and check.yml's header says the same. A job in check.yml would be that list. A workflow of its own with the exception stated is recommended over changing the requirement to allow a command per platform, because the exception is one command, the one a Windows contributor would run anyway, and no Windows contributor's suite exists yet to be its definition. check.yml has no labeled trigger, so the gate could not live there without a second change to it.

8. Ship through the release zip and crates.io, and leave winget and Scoop to a follow-up

The zip on the GitHub release and cargo install --locked htmlspec-cli are the Windows channels. Homebrew and Nix do not run natively on Windows. A Scoop bucket would be a small repository like the tap, and winget a manifest submitted to Microsoft's repository for every release. Both wait for a reader who asks.

Each further channel adds a repository, a secret or a review queue, and a step to the publish runbook. Two channels answer the need this proposal can name.

What the contract says

The contract says nothing about release targets. The nearest statements are these:

  • toolchain-packaging's "Project checks are runnable as one command", with its scenario "Continuous integration parity", forbids a separately maintained list of continuous-integration steps. Decision 7 runs the Windows tests in a workflow of its own with that exception stated, as publish.yml states its own, rather than changing the requirement.
  • toolchain-packaging's "A release reaches every channel from one tag" requires publishing "only from a run in which the binary of every target it releases was built". The words already cover a fifth target. Its statement names the Homebrew formula among a release's products, which stays true.
  • toolchain-packaging's "The program is distributable as a standalone artifact" is unchanged, and a statically linked Windows binary meets it.
  • toolchain-packaging's "The command surface checks a runbook's machine prerequisites" gains scenarios for PATHEXT and the home-directory lookup, under decision 4. The store registry's location has no requirement of its own, so the contract is silent on where it lives.
  • runbook-portability's "Package manifests retain authority over package pins" already requires the refusal decision 4 describes.
  • deterministic-formatting's scenario "Cross-platform round trip" already covers CRLF.
  • project-bootstrap's requirements would change if init writes a .gitattributes, under decision 6.

On which targets a release builds, the contract is silent. Open question 6 asks whether it should say.

Risks

A document opened from disk may not load its stylesheet in a Windows browser

Chromium loads a stylesheet or script from a parent folder of a file:// page on macOS, where Safari refuses. Edge and Chrome on Windows are Chromium too, and nobody has opened a document there.

Accepted until a task opens a document in Edge and Chrome on Windows. The inline fallback stylesheet keeps a refused page readable, as it does in Safari.

Windows warns before running an unsigned executable

SmartScreen shows a warning for an unsigned binary downloaded from the internet, and some antivirus software holds new executables for scanning.

Accepted. Signing needs a certificate, a secret in the public repository, and a step in the release, which is open question 2.

Archived paths can exceed Windows' 260-character limit

An archived change's evidence lives several folders deep, and a project inside a deep user folder can pass 260 characters. Git refuses such a checkout unless core.longpaths is set. The program itself reads long paths, because Rust's standard library adds the long-path prefix where it needs one.

Accepted. The README states the git setting for Windows. Shortening archive names would change every reference to them, for a limit only one platform has.

A Windows job adds cost and a new way for checks to fail

A Windows minute costs twice a Linux minute in a private repository, and Windows runners are slower to start and more prone to file-locking failures in tests that delete scratch folders.

Gated by the condition release.yml computes for its macOS jobs, in decision 3 for the release and in decision 7 for the tests, so the private repository pays only when a pull request asks with release-check. The scratch helpers already ignore a failed deletion.

Open questions

  1. Is there a reader who needs this outside WSL? The answer schedules the change or keeps it on file.
  2. Is the executable signed? That means a certificate, a secret, a cost, and a release step.
  3. Does htmlspec init write a .gitattributes for every project? Decision 6 recommends it, and it changes what init writes on Unix too.
  4. Is aarch64-pc-windows-msvc worth a sixth target? It runs on a GitHub runner too, at the same cost.
  5. Scoop or winget first, once a reader asks for a package manager.
  6. Should the contract name the supported targets? The contract says nothing about release targets today. A requirement naming the targets a release builds would make adding or dropping one a change to the contract, rather than to a script.
  7. Where does the store registry live on Windows? Decision 4 recommends %APPDATA%\htmlspec\stores.json. The alternative is USERPROFILE\.config\htmlspec\stores.json, one rule on every platform.

Size

About the size of a release change. The program changes are small: the PATH search, one home and configuration lookup, the toolchain refusal, and the test guards and .cmd fixtures, a few hundred lines in all. The pipeline changes are moderate: a reproducible zip, a gated fifth target, a release build job that runs on Windows, the formula's narrower read, and the BuildMatrix tests. Then a Windows workflow and the README. The unknown is the first run of the tests on Windows, which is why it is the first task: what fails there sets the rest of the work.
