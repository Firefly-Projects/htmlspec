Release a native Windows build of htmlspec

htmlspec 1.0 builds for macOS and Linux, and reaches Windows only through WSL, where the static Linux build runs unchanged. This change would add a native Windows build: a fifth release target, the few places the code assumes Unix made to work on Windows, and Windows install instructions beside the others. It is not scheduled. It was drafted on 2026-10-21 because the contributor asked for the proposal and set the work aside, and it waits until someone needs htmlspec on Windows outside WSL.

Subject
Release a native Windows build of htmlspec

Status: not scheduled

This change is a proposal on file, not planned work. Nothing in it is implemented, and no release is waiting for it. It records what a Windows build would take, so the decision to schedule it can be made on its cost rather than on a guess. Schedule it when a reader needs htmlspec on Windows without WSL, and not before: until then, every target added is a target to keep green.

Why

The documents htmlspec writes are platform-neutral: HTML, a stylesheet, and scripts, read in any browser. The program that writes and checks them is not yet. A release builds four targets, aarch64-apple-darwin, x86_64-apple-darwin, x86_64-unknown-linux-musl, and aarch64-unknown-linux-musl, and the README's install section offers Nix, Homebrew, crates.io, and a binary for macOS or Linux.

A reader on Windows has one route today: WSL, where the Linux musl binary runs as it is, because it is statically linked and needs nothing from the system. That route works, and it was the answer given when the question first came up. It is also a second operating system to install before a first command, and the coding agents htmlspec serves increasingly run on Windows itself, outside WSL. An agent in a Windows terminal cannot run a Linux binary.

The need is not yet measured. One person asked, and WSL answered them. That is the reason this proposal is on file rather than scheduled.

What changes

  • A fifth release target. x86_64-pc-windows-msvc, built on a Windows runner and statically linked against the C runtime, packed as htmlspec-X.Y.Z-x86_64-pc-windows-msvc.zip with the binary, LICENSE, and THIRD-PARTY-LICENSES, and listed in SHA256SUMS beside the four tarballs.
  • The code builds and its tests pass on Windows. The runtime code already gives each of its two Unix-only operations a fallback. The tests do not: four call sites use std::os::unix without a guard, so two test binaries do not compile on Windows, the preflight tests fake a tool with a shell script, and one test makes a move fail with a lock Windows ignores on a directory.
  • Preflight finds a Windows program. Its search of PATH looks for the bare name, so it would miss git.exe, and on Windows it treats every file as executable. It would learn PATHEXT.
  • One home and configuration lookup. Preflight's home scope reads only HOME, and the store registry only XDG_CONFIG_HOME or HOME, so on Windows a skill in the home scope is not found, and htmlspec store and every --store find no registry. Both would read one lookup that knows Windows.
  • Line endings cannot corrupt the asset store. A stored asset is named by the digest of its bytes, and git on Windows converts line endings on checkout by default, which changes those bytes. This repository gains a .gitattributes, and the design decides whether htmlspec init writes one for every project.
  • Windows in the checks. The workspace tests run on a Windows runner, in a workflow of their own, because the check workflow runs only the one suite command a contributor runs and that command does not run on Windows. They run always in the public repository, and in the private one only on a pull request labelled release-check.
  • Install instructions. The README gains the zip, how to check it against SHA256SUMS in PowerShell, and cargo install on Windows, and keeps WSL as the route that needs nothing new.

What working looks like

On a Windows machine with no WSL, a reader downloads the zip from the release, checks it with Get-FileHash against SHA256SUMS, and runs htmlspec.exe --version, which prints htmlspec X.Y.Z (revision). In an empty folder, htmlspec init --tools claude, then htmlspec new change add-dark-mode, then htmlspec validate, reports no errors. The new proposal opens in Edge from disk, styled, with its figures drawn. A runbook whose preflight declares a tool check for git finds git.exe, and htmlspec store add portable <path> registers a store that htmlspec --store portable preflight release then finds. cargo install --locked htmlspec-cli builds the same program from crates.io.

Alternatives considered

  • WSL only, written down. Keep four targets and say in the README that Windows means WSL and the Linux build. This costs nothing and is the right answer until the need is measured, which is why this change is not scheduled.
  • crates.io only. Make the code compile and pass on Windows, and let cargo install be the channel. It needs a Rust toolchain on the reader's machine, which most Windows readers do not have.
  • Cross-compile from Linux. Build the Windows binary on a Linux runner with a cross toolchain. It saves the Windows runner's cost, but the binary is then never run where it was built, and the release workflow runs each binary on its own platform before packing it.

Scope

In scope: the x86_64-pc-windows-msvc target, the zip, the code and test changes that target needs, the gated Windows checks, and the README.

Not in scope:

  • Nix and Homebrew on Windows. Neither runs natively there. The Nix development shell, the toolchain preflight check that reads it, and the Homebrew formula stay Unix channels. On Windows, the toolchain check refuses with an explanation rather than pretending.
  • Windows on ARM (aarch64-pc-windows-msvc), until the x86_64 build has a reader.
  • An installer and code signing. An unsigned executable draws a SmartScreen warning. Signing costs a certificate and a secret, and is an open question in the design.
  • winget and Scoop. Each is a channel of its own, with its own repository and review, and belongs in a follow-up once a reader asks for one.
  • The suite on Windows. scripts/check is a shell script around Nix, and stays the Linux definition of a healthy revision. Windows runs the workspace tests, which is what can differ there.
