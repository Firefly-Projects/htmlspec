## Why

A Pi session load lists fourteen html-spec entries for seven workflows:

```
- htmlspec-apply-change      - htmlspec:apply
- htmlspec-archive-change    - htmlspec:archive
… five more …                … five more …
```

**This is a regression the previous change introduced.** `conform-generated-frontmatter-names`
found `write_commands` writing `tool.invocation(workflow.name)` into `name:` — producing
`/htmlspec:apply`, malformed under a loader's lowercase-digits-hyphens rule — and changed it
to `workflow.directory`. That is the same value `write_skills` writes. The old value was
malformed but **distinct**; the new one is well-formed but **duplicated**.

For every tool receiving both skills and commands, the two files now declare one name:

| Tool | Skills | Commands | Names in common |
| --- | --- | --- | --- |
| Claude Code | `.claude/skills` | `.claude/commands/htmlspec` | all 7 |
| Cursor | `.cursor/skills` | `.cursor/commands` | all 7 |
| Pi | `.pi/skills` | `.pi/prompts` | all 7 |

21 files across three tools, 14 of them checked into this repository. Codex is untouched —
`SkillsOnly`, so there is no second file to collide with.

**The previous change stated the duplication as a requirement**, which is why no test caught
it:

> #### Scenario: One identity per workflow
> - **WHEN** a workflow produces both instructions and a command for one tool
> - **THEN** both declare the same name

That scenario passes. It is also the defect. "One identity per workflow" is the right idea
about a workflow's *meaning* and the wrong rule for a `name:` field, because a loader uses
that field as a registry key and two files claiming one key is a collision. The scenario
described the mechanism instead of the obligation, and got the mechanism wrong.

**A command file does not need the field at all.** The vendored `opsx` sets in this
repository disagree about it, and both load:

```
.claude/commands/opsx/apply.md      name: "OPSX: Apply"
.pi/prompts/opsx-apply.md           (no name: field)
```

All ten `.pi/prompts/opsx-*.md` omit `name:` and work, which is the same evidence the
previous change already relied on from the other direction: the **file path** determines the
invocation. It verified that renaming the field did not change what a contributor types. The
corollary it did not draw is that a field which does not determine the invocation, and which
a working installation omits, is not a field worth risking a collision to populate.

## What Changes

- **A command file stops declaring a skill's name.** `write_commands` no longer writes a
  `name:` that duplicates the skill file's. The invocation stays determined by the file path,
  as it already is and as the previous change proved by loading.

- **The colliding scenario is replaced.** `project-bootstrap`'s "One identity per workflow"
  scenario is withdrawn and replaced by one requiring that no two generated files in a
  tool's namespace declare the same name. This is a withdrawal, not a rewording: the old
  scenario is satisfiable only by the behavior being removed.

- **A test asserting distinctness.** `every_generated_name_is_loadable` checks each name's
  characters and passes today, because both duplicates are well-formed. A second check
  collects every name a single tool receives across both file kinds and fails on a repeat —
  which is the property the character check cannot see.

- **This repository's own 14 files are regenerated**, dropping the duplicate entries from
  the session load that reported this.

## Non-Goals

- **Changing what a contributor types.** `/htmlspec:apply`, `$htmlspec-apply`, and
  `/htmlspec-apply` are unchanged, for the same reason as last time: the file names carry
  them, and `report_next_command` remains the one producer of the spelling.

- **Reverting the previous change.** Its finding was correct and its test stays. The
  invocation does not belong in a `name:` field. This change removes the *second* thing that
  does not belong there either.

- **Renaming skill directories or command files.** The seven directories and their file names
  conform and are what the invocation rests on.

- **The eight `[Skill conflicts]` warnings from `~/.agents/skills`.** Six are `_`-prefixed
  Python package markers whose names sibling imports depend on; two are `example-corp:feature`
  and `example-corp:mockup` from `example-corp-product-team`. None are generated by this program, and
  html-spec's own Pi output was verified clean of that fault. That directory is also a
  read-only duplicate of `~/.claude/skills` — 147 entries, byte-identical, two 6.1M copies —
  and whatever installs it was not found. Repairing another repository's names, or
  de-duplicating a directory this program does not write, is not this change.

- **Auditing whether each loader actually rejects a duplicate name.** The observed symptom is
  a doubled listing, not a refusal. Not declaring a name a command file does not need is the
  cheap direction regardless of which loaders would have coped.
