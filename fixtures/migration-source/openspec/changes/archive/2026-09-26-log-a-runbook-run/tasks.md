## 3. Settle the three decisions the proposal leaves open, with reasoning

- [x] 3.1 Decide where run progress is reported. `the-status-gap-2026-09-17.md` measured the gap, so read it before deciding rather than deciding from the proposal's summary of it. `workflow-reporting` governs
  - **`status` is left alone; run progress is `htmlspec run --check`'s.** The measurement decides it: the predecessor found that `status --change <runbook-path>` *works* and counts correctly, so the reusable part already reaches a runbook and what is wrong is the report's shape — `absent proposal.html` about documents a runbook never has. Teaching it a second shape means branching on what its argument turned out to be, and then `--change` is false for half its inputs.
  - `workflow-reporting`'s *A report answers the contributor in their own terms* is the governing clause, and its scenario is exact: a report whose first claim names a document count does not show the request was understood. A contributor asking about a run asks what it recorded.
  - **The stronger reason is that the two reports are not one report with a branch.** A run's reader wants outcomes, not a fraction — which is a different report built from different units, and it is the conformance rule's output.
  - **Not closed:** `status --change` by *name* pointed at a runbook is still a refusal, which is the form a workflow would use. Recorded in the design's risks on the same terms the predecessor recorded it.
- [x] 3.2 Decide whether a run can be resumed, which decides whether a record is ever edited after it is written
  - **A run can be resumed, so a record is edited after it is written.** The argument is that the alternative contradicts the document's own kind: a `tasks` document's steps carry `in-progress`, and a record written once could never carry it honestly — it would mean "in progress at the instant the file was written and nobody knows what happened next". A model making a state in the vocabulary unreachable is the wrong model.
  - The batch abandoned at step 6 is the case, and **two records would each be wrong about it**: the first says six done and four unstarted, which reads as a run that stopped; the second cannot say `done` for the six it did not do, nor `todo` for six that are finished.
  - **This is what makes the `review/*` severity necessary rather than convenient.** A resumed run legitimately has requirements nothing has recorded, so an error would fail every run at the moment it began. Asserted rather than argued: `a_just_started_run_has_recorded_nothing` drives the real binary and asserts exit 0.
  - **Cost stated:** two runs a week apart are indistinguishable on disk from one run interrupted for a week. No timestamp is recorded, for `project-bootstrap`'s reason about an uncompared version — the filesystem already has `mtime`, and when a run happened is `record-a-runbooks-history`'s question.
- [x] 3.3 Decide whether `run` copies eagerly or lazily, and what it names the record. **Name every rejected candidate and what it broke**, because a naming scheme is exactly where `runbook-authority`'s prohibition on deriving an ordering from a name gets violated quietly
  - **Eagerly, and the name is the contributor's with no default.** `htmlspec run <runbook> --as <record>`.
  - Eager because a lazy copy has no honest content for the steps it has not reached: between steps 2 and 3 the record would state a three-step procedure, and nothing in a list of steps says there are more. The record exists to say which version of the procedure ran, and a partial copy shows a version that never existed.
  - **Two rejected naming schemes, each for a stated reason rather than taste.** A date (`2026-09-18.html`) collides when a procedure runs twice in a day, and it would make the record's name the one place a time is recorded — which 3.2 declines to do. A sequence number (`run-7.html`) requires reading an ordering out of the directory's contents, and `runbook-authority` states that *nothing SHALL derive an ordering, a version, or a history* from a runbook's name; the maintained-list shape is what the contract refuses.
  - `--as` is required rather than defaulted, because an operation that invented a name would choose on the contributor's behalf and `artifact-kinds` requires a derived name to be reported. The failure message says why, so a contributor meets the reasoning rather than a bare usage error.
  - Checked through `ProjectRoot::is_a_name`, which is where the predecessor moved this invariant after re-litigating it at three call sites. Verified that a refused name leaves *nothing* on disk, including no `runs/` directory — a name refused after a directory was created would have left the traversal's effect behind.
- [x] 3.4 Decide whether a run record is a canonical document, since `runbook-authority` already requires `unchanged` in a runbook's canonical documents and that sentence now binds. Decide from the measurement rather than from the word
  - **It is, and the measurement decides it rather than the word "canonical".** A copied requirement declared `added` draws `review/stale-verification` — the record's own verification attesting to an obligation the record says does not exist yet. The obligation existed before the run started, which is the same fact as the runbook's own documents arriving at the same attribute.
  - So the delta states it once for a runbook's documents *including* its records, rather than adding a second clause.
  - **`run` is the operation that knows what it is writing**, which narrows `the-canonical-documents-change-state-2026-09-17.md`'s finding without closing it: an author writing a record by hand still meets the warnings, and so does an author writing a runbook by hand. The delta says so explicitly.
