## 4. The plan, and the gate that checks it covers the survey

- [x] 4.1 Settle the plan's shape as a `tasks` document: one task unit per surveyed entity, carrying the source path, the destination path, the disposition, and the reason where one is owed
  - Each fact is a **note paragraph opening with its name and a colon** — `source:`, `destination:`, `disposition:`, `reason:`, `derives:`. Not attributes, and the reason matters: the projection ignores an unknown `data-*` on a unit, so a gate reading `data-source` would parse the HTML a second way and could disagree with the model about what the document says. `data-field="source"` names no field of a task and is invalid. A note whose opening word is none of the five is ordinary prose, so annotating a plan line breaks nothing.
  - `reason:` is read from the note **or** from the task's own `data-field="reason"`, because a task whose `data-state` is `dropped` already carries one and the validator already requires it. Refusing one spelling would make the plan's shape depend on which of two equivalent markups an agent chose.
  - Proven end to end rather than asserted: `crates/htmlspec-cli/tests/plan.rs` builds the plan with `htmlspec init` and `htmlspec new document tasks`, replaces the template's example units, and puts one document through `validate`, `format`, `format --check`, and `migrate promote` in turn. **The `format --check` after the `format` is the load-bearing step** — it proves the shape is a fixed point rather than something that parsed once, which a shape leaning on attributes would not be.
- [x] 4.2 Add `htmlspec migrate promote`, whose first act is the coverage comparison between the plan and the survey payload
